朋友开了家宠物店，微信上问你：「能不能做个小工具管预约？Excel 实在管不过来了。」你答应周五晚上搭出来。

搁一年前，这个晚上你会花四个小时纠结选什么框架、要不要上微服务、数据库哪个更新更快。现在不了——这 15 篇下来你见过每一种墙的样子，选型从「跟感觉走」变成「按需求查表」。这篇把查表演示一遍，顺便把全系列压缩成能贴在墙上的一页。

## 决策一：框架，选你熟的

宠物店工具的需求清单：用户登录（店员 + 顾客）、预约的增删改查、到店提醒。全是第 2 到 5 篇的范围内问题，没有任何一个需要「强框架」。

决策树其实就三问：

**是不是 Web 应用、全 TypeScript、你一个人维护？** 是——Next.js 一把梭，API Routes 或 Server Actions 起接口，[Next.js 系列](/posts/nextjs/01-getting-started)里的套路直接复用。前后端一个仓库一次部署，宠物店工具的最短路径。

**需要独立的 API 服务（比如要给小程序、第三方调用）？** 轻量选 Hono / Express 这一层（路由 + 中间件，第 4 篇的认证中间件概念在这一层最清晰）；项目大、团队多人、想要强结构就 NestJS（依赖注入、模块划分都是现成的，从 Express 过去的人最适应，[Spring Boot 系列](/posts/springboot/01-why-spring-boot)第一篇讲了这条演进路）。

**想借项目练一门后端语言？** Go 或 Java/Spring Boot，博客里各有完整系列（[Go](/posts/golang/01-getting-started)、[Spring Boot](/posts/springboot/01-why-spring-boot)）。语言换掉，这 15 篇的问题清单一行不变：并发还是并发，幂等还是幂等。

一个反直觉的排序原则：**框架的可替换性很高，熟悉度的价值极高**。宠物店工具用你最熟的东西写，两周后要迁移到别的框架，成本是一两天；反过来，为「学个新的」选了不熟的栈，每个坑都要现踩。选型选的是交付速度，不是技术志向。

## 决策二：数据库，默认不变

第 3 篇的结论在真实项目里几乎不用修正：**Postgres，用托管版**（云厂商的 RDS 系产品，备份、高可用、监控都是套餐内含的）。宠物店工具连例外都算不上。

值得记的例外只有三个。团队已经全在 Supabase 生态（它本质是 Postgres 加了一层实时同步和现成鉴权，小游戏团队的最爱）；客户端重度离线（你又要写 Electron 了，本地 SQLite 照旧）；以及公司已有标准（别跟既有的 DBA 和运维体系较劲）。MongoDB 依旧不在名单上——第 3 篇的理由没有变化。

## 决策三：托管，三档台阶

代码写好了放哪跑，这是新手最容易迷失的一步，其实是个三档台阶，按「你能忍受多少运维」选：

**第一档：托管函数平台（Vercel、Netlify、阿里云函数）**。git push 即部署，零服务器概念。代价是运行模型受约束：请求有超时上限（长任务做不了）、常驻进程没有（第 9 篇的 worker 要改用平台提供的定时触发）、长连接支持有限（第 13 篇的 SSE 可能受阻）。纯 Web 型小项目最合适。

**第二档：容器平台（Fly.io、Railway、国内的轻量容器服务）**。你交一个 Docker 镜像（[Docker 系列](/posts/docker/01-why-docker)教你打），平台负责跑、重启、扩。一个镜像跑 API、另一个镜像跑 worker，互不干扰——第 9 篇的架构原样落地。自由度和运维量都适中，**宠物店工具如果以后要做「到店提醒」这种定时任务，直接选这档**。

**第三档：VPS 自管**。租台云服务器，从 Nginx、HTTPS、进程守护到监控告警全自己搭。最自由、规模化后最便宜，运维量也最大，全套手艺在 [DevOps 系列](/posts/devops2/01-linux-server-setup)里。

给个体感数字：宠物店规模（一天几百次访问），第一档免费额度或每月几十块，第二档每月十美元上下，第三档一台最低配 VPS 每月三四十元人民币加你的时间。按规模选组合的完整方法论，[部署基础设施地图收官篇](/posts/infra-map/10-combination-and-choices)讲得比我细。

## 不需要清单：启动阶段请它们靠边

选型时知道「不用什么」和知道「用什么」同样值钱。启动阶段的不需要清单，每条注明什么时候再请进场：

- **Redis / 独立缓存**：先把索引建对（第 7 篇）。同一查询真的重复到数据库吃紧了，再进（第 8 篇给了判断标准）。
- **消息中间件（RabbitMQ / Kafka）**：数据库表就是队列（第 9 篇）。服务拆了、消费方多了、每秒消息过万了，再换。
- **微服务全家桶**：模块化单体走起（第 15 篇的三条检验标准背下来）。
- **Kubernetes**：单机 Docker Compose 起步；容器数量和机器数量多到手动管不动再说（那是 infra-map 的世界）。
- **独立搜索服务（Elasticsearch）**：Postgres 的全文搜索先顶着，检索真的成为产品核心再专业对口。

这份清单的共同逻辑你在各篇都见过：**每个组件都是为某个具体问题准备的，问题没来，组件别来**。提前装上的组件不产生价值，只产生运维和认知成本。

## 下一步往哪深潜

这张地图管「知道」，不管「精通」。哪个方向被工作或兴趣点名了，博客里对应的深潜系列接得住：Java 企业开发进 [Spring Boot](/posts/springboot/01-why-spring-boot)，一门顺手的后端语言进 [Go](/posts/golang/01-getting-started)，缓存和内存数据库进 [Redis](/posts/redis/01-getting-started)，ORM 进 [Drizzle](/posts/drizzle/01-introduction-drizzle) 或 [Prisma](/posts/prisma/01-why-prisma)，类型安全 API 进 [tRPC](/posts/trpc/01-why-trpc)，部署运维进 [DevOps](/posts/devops2/01-linux-server-setup) 和 [部署基础设施地图](/posts/infra-map/01-from-code-to-online)，Node 运行时底层进 [Node.js 核心](/posts/nodejs-core/01-buffer)。想往 AI 应用方向走，[AI 全栈实战](/posts/ai-fullstack/01-llm-api-streaming) 在前面等你——那边的起点，恰好是这篇收官时你的位置：一个能把产品从前端一路写到数据库的人。

回到周五晚上。宠物店工具的答案现在脱口而出：Next.js 加 Postgres（Supabase 托管版），部署在 Vercel 或 Fly，登录用 OAuth 加 Session，预约表带好归属列和唯一约束（同一时段同一美容师只能约一个，第 6 篇的老朋友），提醒任务用平台的定时触发。不装 Redis，不碰 Kafka，一个人，一个仓库，一个周末。

后端知识真正难的从来不是量——每个主题单拎出来都不深——难的是每一类问题都真的遇到过一次。第 1 篇说的三个根本差异，你现在不仅知道名字，还知道它们会在哪一天、以什么面目出现，以及第一反应该去查哪个词。这 16 篇替你先把墙撞了一遍，剩下的，等你真撞的时候，已经不算第一次了。
