索引治理完一个月，数据库的 CPU 报警又响了。

这次不是慢查询。每一条查询的 EXPLAIN 都干净漂亮，全走索引，全都几毫秒。报警的原因换了个朴素的说法：**同样的查询太多了**。ClipNote 上了一批「精选模板笔记」，全站订阅用户首页都展示它们，每秒几百次请求，每一次都去数据库把同样那几十行查出来。数据库没有做错任何事，它只是在高速重复劳动——像一个人被每秒问三百遍「今天几号」，每次都认真翻一遍台历。

把答案抄在旁边，这就是缓存的全部心智模型：第一次有人问，查数据库，把结果记在内存里；之后的询问直接给内存里那份。内存和磁盘的随机访问速度差着几个数量级，Redis 这类内存数据库单机每秒扛十万次读是常态。每秒三百次的模板笔记，缓存之后数据库的压力直接归零。

不过在动手之前，先过一道安检。

## 先确认轮得到缓存出场

缓存的名声太响，以至于很多「数据库扛不住」其实是索引缺失或 N+1，药到病除的根本轮不到缓存。上缓存前自问三个问题：查询本身优化过了吗（第 7 篇的清单过了一遍吗）？慢是不是因为重复（同样的输入、同样的结果、高频出现）？这批数据允许旧几秒吗？

第三问是缓存的先天缺陷：抄本可能过时。笔记标题改了，缓存里还是旧的，用户看到旧标题几秒。每个要缓存的数据，你都要回答「能容忍多旧」——这是产品决策，不是纯技术决策。交易余额这类数据答案可能是零容忍，那它们就不该进缓存。

## 缓存放哪：应用内存还是 Redis

抄答案抄在哪，两个选择。

抄在应用进程的内存里（一个 Map，或 Node 的 lru-cache），零依赖、零网络，最快。但你的服务有两台实例时麻烦来了：请求被负载均衡分到 A，A 的内存里是旧答案；更新请求落到 B，B 删的是自己那份。两台机器各抄各的，不同步。重启更彻底，全丢。

抄在独立的 Redis 里：两台实例共享同一份缓存，谁更新谁删，全局一致；进程重启缓存还在。代价是多一次网络往返（仍然比查库快一到两个数量级）和多运维一个组件。

默认答案：**共享缓存用 Redis，进程内存只做一层小补充**（比如缓存「模板笔记 id 列表」这种几乎不变又极高频的元数据，本地一份免掉那一次网络往返——这就是所谓多级缓存的全部真相）。Redis 本身怎么用熟，博客里有十八篇的[Redis 系列](/posts/redis/01-getting-started)，这篇只讲模式不讲操作。

## Cache-Aside：读时填充，写时删除

应用层缓存的标准姿势叫 Cache-Aside（旁路缓存），读和写各一条固定流程。

读：

```ts
async function getNote(id: string) {
  const cached = await redis.get(`note:${id}`); // 1. 先看缓存
  if (cached) return JSON.parse(cached);

  const note = await db.notes.findOne({ id }); // 2. 没有再查库
  if (note) {
    await redis.set(`note:${id}`, JSON.stringify(note), "EX", 300); // 3. 抄一份，5 分钟过期
  }
  return note;
}
```

写：

```ts
async function updateNote(id: string, patch: NotePatch) {
  await db.notes.update(id, patch); // 1. 以数据库为准
  await redis.del(`note:${id}`); // 2. 删掉缓存那份
}
```

写的流程里有个值得较真的细节：为什么是**删**缓存，而不是把新值**更新**进缓存？因为「更新数据库」和「更新缓存」是两步，两个并发写请求的执行顺序可能交错：请求甲更新库为 v2，请求乙更新库为 v3，然后乙把缓存写成 v3，甲再把缓存写成 v2——库里是最新的 v3，缓存里永远停在 v2，直到过期。删除则没有这个问题：缓存里没有，下一个读者自己去库里拿最新的。删缓存还有一个顺手的哲学：不用为「将来可能被读」的数据白算一遍，谁读谁触发。

那「更新库」和「删缓存」这两步之间，读者拿到旧值的窗口存在吗？存在，几百毫秒内可能出现「库已新、缓存还旧」。这个窗口用第 6 篇的话说：追求的是收敛一致，不是实时一致。真要抹平它，代价（分布式锁、延迟双删这些补丁）远超收益。缓存的本质就是拿短暂的旧换速度，想清楚数据能旧几秒，比背诵一致性算法有用。

## 三大事故：穿透、击穿、雪崩

Cache-Aside 写好，日常就能平稳运行。缓存体系真正的事故都出在「缓存没接住、请求砸到数据库」的瞬间，按原因分三种，每种有成熟解法。

**穿透**：请求的 key 在缓存和数据库里**都不存在**。比如攻击者拿 `note:idonotexist1`、`note:idonotexist2`……高频打你，缓存永远 miss，每一次都穿透到数据库查一遍空。解法是把「空」也缓存：查库确认不存在后，往缓存写一个短 TTL（比如 60 秒）的空标记，下次同样的 key 直接被缓存挡住。讲究一点的会用布隆过滤器（一句话：一个能回答「这个 key 肯定不存在」的超省内存结构）在入口把绝大多数无效 key 筛掉，ClipNote 这个量级用空标记就够。

**击穿**：某个**热 key 过期的那一瞬间**，几百个并发同时发现 miss，同时冲去查库——模板笔记就是典型的热 key，它过期的一毫秒可能就是数据库的一次心跳骤停。解法思路是「单飞」（singleflight）：同一 key 的并发 miss 只放一个请求去查库回填，其他请求等它回来直接共享结果。Redis 客户端和各语言生态都有现成实现；更省事的办法是热点数据不设 TTL，由写路径负责删除、由后台任务定期刷新。

**雪崩**：**大批 key 在同一时刻集体过期**（比如你上线时手滑给所有缓存写了同一个整 TTL），或者 Redis 本身挂了，所有请求一起落到数据库。前者的解法土而有效：TTL 加随机抖动（`300 + random(60)` 秒），让过期时间错开。后者的解法在缓存之外：Redis 上高可用（主从+哨兵，或云厂商的托管版），应用侧对缓存故障要有降级——Redis 连不上时限流着查库，而不是把全部流量放进去。

三个词共用一个规律：**危险不在缓存失效本身，在于失效瞬间失去缓冲的并发量**。理解这一点，解法不用背也能推出来。

## 结尾

收拢这篇的判断：上缓存前先用第 7 篇的清单排除掉索引和 N+1 的问题，缓存治的是重复，不是所有慢；每个数据先回答「能旧几秒」；模式无脑用 Cache-Aside，读时填充、写时删除，别在并发下更新缓存；穿透缓存空值、击穿单飞、雪崩 TTL 抖动加高可用。最后一句要放在结尾压轴：**缓存是性能补丁，不是架构**——它是你给数据库请的助理，别让业务逻辑迁就缓存的设计（业务正确性永远只依赖数据库，缓存丢了删了炸了，系统都应该照常工作，只是慢一点）。

数据库的读压力安顿好了。下一篇换个方向：不是读得多，是**单件活太重**。「导出全部笔记为 PDF」上线十分钟，所有接口集体变慢——因为你的 API 进程正在请求里吭哧吭哧渲染五百份 PDF。有些活不该当场干，这是后台任务和队列的故事。
