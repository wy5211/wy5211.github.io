ClipNote 的后端在公网上跑了一个月，你出于好奇看了一眼访问日志，看到的是这样的：

```
GET  /wp-admin/setup-config.php      404
GET  /.env                           404
POST /api/login  （同一 IP，每秒 5 次，持续 40 分钟）
GET  /api/notes/1                    401
GET  /api/notes/2                    401
GET  /api/notes/3                    401
```

没有人盯上你。这些是自动化扫描器，全天候扫整个互联网的每个 IP，探测 WordPress 后台、找暴露的 .env 文件、拿字典爆破登录接口、用递增 id 试探接口鉴权。它们不挑目标，每个公网服务都会被扫到，区别只在于你的防线挡住了没有。「我的应用太小没人攻击」在这个事实面前不成立——被攻击的成本低到没有门槛，你的安全成本也得低到能随手做，这就是这篇的写法：不是教科书，是一份单体应用的入口清单。

## 入口一：注入——用户输入永远不是代码

SQL 注入的老例子：登录接口把用户输入直接拼进 SQL：

```ts
// 千万别这样
const sql = `SELECT * FROM users WHERE email = '${email}' AND ...`;
```

攻击者在 email 里输入 `' OR '1'='1`，SQL 的 WHERE 条件恒真，登录绕过；输入更长的 payload 可以拖走整库。**根治手段只有一个：参数化查询**——用户输入永远作为参数传给数据库，永远不参与 SQL 语句的拼接：

```ts
// ORM 的标准写法天然就是参数化的
await db.users.findFirst({ where: { email } });
// 手写 SQL 时用占位符
await pool.query("SELECT * FROM users WHERE email = $1", [email]);
```

用 ORM 的日常 CRUD 基本不用担心注入，真正的危险区有两个：手写拼接 SQL 的地方（尤其是 `ORDER BY ${sortField}` 这种动态列名，参数化占位符管不了列名，要用白名单映射：允许的列名枚举出来，不在表里就拒绝）；以及把用户输入拼进 shell 命令的地方（「用户给个文件名我去 tar 一下」——同样的注入，换成命令执行）。

## 入口二：XSS 与 CSRF——前端人的主场，后端的补全

XSS（跨站脚本）你熟，后端视角补的是**存储型 XSS**：恶意脚本不来自请求参数，来自存进数据库的内容，渲染时执行。剪藏应用是高危场景——用户剪藏的网页 HTML 原样入库、原样渲染，等于把任意脚本的执行权白送出去。防线在后端入库或渲染前做**白名单过滤**（sanitize：只保留允许的标签和属性，script、onerror、javascript: 伪协议一律剥掉；用成熟的库如 DOMPurify，别手写正则），再配一道 CSP 响应头（`Content-Security-Policy: script-src 'self'`，即使有脚本漏网，浏览器也拒绝执行）兜底。

CSRF（跨站请求伪造）在 Session + Cookie 方案下要专门防：用户登录着你的站，同时打开了恶意网页，恶意网页向你的接口发请求，浏览器会自动带上用户的 Cookie。现代防线两道：Cookie 设 `SameSite=Lax`（现代浏览器默认值，跨站请求不再自动带 Cookie，挡掉大半）；对改数据的请求再校验 `Origin` 头或要求自定义头（纯表单和跨站 fetch 很难伪造自定义头）。JWT 放 Authorization 头的方案天然没有这个问题——token 不自动携带，这也是第 4 篇说「两种方案都要想清楚你怕哪种攻击」的具体含义。

## 入口三：越权——最高频，回看第 5 篇

真实漏洞统计里，越权（IDOR）是出镜率冠军，而且专挑「功能都对、就漏一个接口」的系统。第 5 篇给了完整解法（归属条件写进查询、双用户测试、review 固定问一句），这里只重申它的地位：上面两个月日志里那些 `GET /api/notes/1、2、3`，就是在逐个探测你的越权防线。它们今天全是 401，是因为你的每个查询都带着归属条件。哪天新接口忘了带，这个扫描器就是第一个知道的。

## 入口四：爆破与刷量——限流

日志里那条「同一 IP 每秒 5 次登录，持续 40 分钟」是字典爆破。防线是**限流**：超过频率就拒绝（返回 429），让爆破在时间上不可行。限流的实现算法（令牌桶：桶里匀速生成令牌，请求拿到令牌才放行）不用自己写，网关层（Nginx）、应用层（-rate 中间件）、Redis 计数器都有现成的，要花心思的是**维度**：只按 IP 限不够（攻击者换 IP），登录接口要 IP 和账号两个维度各限各的（同一 IP 每分钟最多 20 次尝试，同一账号每分钟最多 5 次）；注册和发验证码接口要防刷号（配合图形验证码）；导出这类重接口要按用户配额（一天 10 次）。限流是少数「配上就完事」的防御，性价比极高。

## 入口五：密钥——泄露的方式永远比想象中蠢

数据库密码、对象存储密钥、支付平台私钥、发邮件的 SMTP 凭证，这些密钥的管理只有三条规矩，但条条有人栽过。

**不进 git。** 密钥放 `.env.local`（已被 .gitignore 忽略），代码里只读环境变量。曾经顺手 commit 过一次 `.env`？它已经在 git 历史里了，删掉文件没用——视为已泄露，全部轮换。

**最小权限。** 应用连数据库的账号，只给这张库的增删改查权限，不给建表删库的权限；对象存储的密钥只给目标 bucket 的读写，不给账号级的。这样单个密钥泄露的伤害被圈死在一个角落。

**不进日志。** 打日志时把 Authorization 头、密码字段、token 脱敏。密钥泄露最隐蔽的路径是「调试时打了个完整请求对象，忘了删」。

## 入口六：依赖——你引入的每个包都是你的安全边界

npm 生态的供应链事故这几年的剧本已经演熟：热门包被劫持发个带后门的版本，或者一个没人维护的小包被恶意接盘。单体应用的务实做法：lockfile 锁死版本，升级是主动行为不是被动发生；装新包前看一眼它的下载量、维护状态、最后更新时间（冷门又长期不更新的包，风险和收益一起掂量）；定期跑 `npm audit`，高危项当天处理。追求更多（签名校验、私有镜像、依赖审查流程）是团队规模到了以后的事。

## 上线前 20 分钟自查清单

把六条入口压成一份可以逐条打勾的清单，下次发版前过一遍：

1. 所有 SQL 参数化，动态列名走白名单（搜一遍代码里的字符串拼接）
2. 用户产生的内容（笔记、剪藏 HTML）入库前过了白名单过滤，响应头带 CSP
3. Cookie 方案配了 SameSite，改数据的接口校验 Origin
4. 每个按 id 操作的接口，查询条件里带归属（第 5 篇的双用户测试跑过）
5. 登录、注册、验证码、导出四类接口挂了限流，维度含 IP 和账号
6. 密钥全在环境变量里，git 历史没进过密钥，日志打印已脱敏
7. lockfile 提交了，npm audit 无高危
8. 数据库账号非 root，只有业务库的权限
9. 错误响应不带堆栈信息（那是给日志的，不是给用户的）
10. 管理后台入口独立、单独鉴权

九和十在前面各篇零散出现过，清单里补齐位。这份清单不保证安全——安全没有完成态——它保证的是把「无意识漏掉」这个最大风险源收掉。攻击者找的是成本最低的入口，你的目标是让每个入口都有个门闩，仅此而已。

## 结尾

安全这条线的取舍原则就一句：**不追求绝对安全，追求攻击成本高于攻击收益**。自动扫描器找的是没锁门的家，你的清单让门都锁上，剩下真正针对性攻击的对手，等业务值得那个攻击成本时再升级防御也不迟。

下一篇回到产品体验：现在设备 A 改了笔记，设备 B 要等下一次轮询才知道。用户要的是「这边一保存，那边立刻出现」。实时推送这个词听着简单（WebSocket 嘛），但连接怎么管理、两台服务器怎么通知到彼此、离线设备回来怎么补课，每个环节都有坑。
