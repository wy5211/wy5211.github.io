接口的形状定下来了，资源是笔记、标签、附件和变更。现在回答下一个问题：这些数据具体放在什么容器里、怎么摆。

ClipNote 本地版用的是 SQLite，单文件，零配置，用起来和写 localStorage 差不多随意。也正是因为这份随意，你在本地干过一些上云之后干不得的事——比如有一版为了图省事，把笔记的标签直接存成了 content 字段里的一个 JSON 数组，还试过直接打开数据库工具手动改表结构。

这篇讲三块：选哪种数据库、表怎么设计才算对、以及「改表」这件事为什么必须换一种做法。

## 选型：先说结论，一个 Postgres 覆盖到你想不到的远

后端新人最容易被这个问题轰炸：MySQL 还是 Postgres？要不要 MongoDB？听说还有时序数据库、图数据库、搜索引擎……选型焦虑的第一解药是知道边界：**你在单体应用里遇到的需求，一个现代关系数据库全能接住**。

以 Postgres 为例，它同时给你：行数据（笔记、用户这些正经表）、JSON 字段（jsonb 类型，能建索引能查询，杂七杂八的元数据不用另找数据库）、全文搜索（中文分词装个扩展就能用，第 7 篇会再遇到它）、还有数不清的扩展。MySQL 在这个用途上也完全够用，两者在这个量级的差别远小于网上论战的激烈程度——选一个，别回头。

MongoDB 这类文档数据库要不要？它的卖点是 schema 灵活：同一集合里的文档可以长得不一样，不用提前定义列。听着很自由，但你想清楚灵活的代价落在谁头上：关系数据库里「email 必须填、必须是唯一的」写成一列约束，数据库替你把门；文档数据库里没有 schema 这层约束，每个写入方（你的代码、你同事的代码、三个月后的你）都得自己记得守规矩，忘了就是脏数据。灵活没有消失，它从数据库层转移到了你的代码层，而且是每次写入都要重新灵活一遍。

什么时候文档数据库真的合适？数据结构天然无结构、字段差异极大、且彼此之间几乎不需要关联（比如埋点日志、爬虫抓的原始页面）。ClipNote 的笔记、标签、用户全是强关联数据，一条笔记属于一个用户、挂着一列标签、可能还有附件，这是关系数据库的主场。

再诚实一点：同步服务挂在云上，但每个客户端本地那份 SQLite 继续用——本地存储和云端数据库各干各的活，这个架构本身没问题，很多产品就是这么做的。

## 建模第一步：每张表先问「这是谁的数据」

多用户系统的表设计，和单机软件只差一个字，但这个字长在每一张表上：**归属**。

notes 表的第一版草稿：

```sql
CREATE TABLE notes (
  id         TEXT PRIMARY KEY,     -- note_7f3k9
  title      TEXT NOT NULL,
  content    TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

单机时代这样没问题，因为数据库里只有一个用户。上云之后问题来了：这张表里会混着所有人的笔记，而「note_7f3k9 属于谁」居然无从得知。第 1 篇说过的越权漏洞，一半的根源就埋在这种表结构里——如果数据模型本身都不记录归属，接口层拿什么去校验？

于是多用户系统的每张业务表，几乎都要长出这一列：

```sql
CREATE TABLE notes (
  id         TEXT PRIMARY KEY,
  user_id    TEXT NOT NULL REFERENCES users(id),
  title      TEXT NOT NULL,
  content    TEXT,
  deleted_at TIMESTAMPTZ,         -- 先占个位，下面讲
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

`user_id` 加上 `REFERENCES users(id)`，就是外键：数据库承诺这一列里的值必然是 users 表里真实存在的用户，插一个野 id 会直接报错。笔记和标签的多对多关系（一条笔记多个标签，一个标签多条笔记）则用第三张表：

```sql
CREATE TABLE note_tags (
  note_id TEXT NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  tag_id  TEXT NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
  PRIMARY KEY (note_id, tag_id)
);
```

`ON DELETE CASCADE` 的意思是：笔记删了，它和标签的关联跟着删。这种「删主带删从」的规则写在表定义里一次就够，写在代码里则是每个删除入口都要记得调一次——迟早有新同事不知道。

这段还有个值得停留的细节：`PRIMARY KEY (note_id, tag_id)` 天然挡住了重复打标签。同一条笔记把同一个标签打两遍？插不进去。你见过不少应用里「标签去重」的 if 判断，数据库早就提供了。

## 把业务规则写进约束，而不是写进祈祷里

上面的写法指向一个通用原则：**凡是能被数据库约束兜住的规则，就别只依赖应用代码**。

应用层的校验（「email 不能为空」「标题最长 200 字」）会被每一个新接口绕过——今天有网页版守规矩，明天写数据导入工具忘了守，脏数据就进来了。而 `NOT NULL`、`UNIQUE`、外键、CHECK 约束长在表上，谁来了都一样。应用层校验仍然要写（它负责给出友好的错误提示），但它是体验层，数据库约束才是最后一道闸。

顺带处理掉开头那个历史包袱：标签存成 content 里的 JSON 数组。上云建模时把它拆成 tags + note_tags 两张正经表。判断标准：一个字段需不需要**单独被查询和关联**（「列出带『工作』标签的所有笔记」）？需要，就值得独立成表；永远是整存整取、从不单独查（比如笔记的排版偏好设置），jsonb 一个字段装下反而是好设计。第 7 篇讲慢查询时你会看到，JSON 里面刨数据，是慢查询的常客。

## 改表这件事：从「打开工具直接改」到迁移文件

本地 SQLite 时代你改表的方式是：打开 DB Browser，右键表，设计，改列名，保存。上云之后这个动作变成事故：40 万条别人的笔记在里面，手动操作没有记录、没有回滚、没有「改错了发现是三小时前」的后悔药。

正规做法叫**迁移（migration）**：每次表结构变更写成一个带序号的文件，里面是「怎么从上一版变成这一版」的 SQL，由工具按顺序执行并记录进度：

```
migrations/
  0001_create_users.sql
  0002_create_notes.sql
  0003_create_tags_and_note_tags.sql
  0004_add_deleted_at_to_notes.sql
  0005_backfill_note_owner.sql     ← 0004 的教训：先加列、再回填、再约束
```

它给你三样东西。可重放：新同事、新环境、 staging 服务器，把迁移从头跑到尾，数据库结构保证和你一致——「我本地是好的」从此有了机制保障。可审查：改表的动作进了 git，code review 能看见有人要 DROP COLUMN。可对齐：生产库落后几个版本，跑一下工具就知道。

Drizzle 和 Prisma 都自带迁移工具，博客里有现成的深入系列（[Drizzle](/posts/drizzle/01-introduction-drizzle)、[Prisma](/posts/prisma/01-why-prisma)），这里不展开。要点只有一个：从云上数据库的第一天起就用迁移，别给自己留「就这一次手动改改」的口子——第 1 篇说过，数据的事故没有 Ctrl+Z。

## 软删除：DELETE 键其实是个「归档」键

notes 表里那列 `deleted_at`，就是软删除：用户点删除，你不执行 `DELETE FROM notes`，而是 `UPDATE notes SET deleted_at = now()`。查询时加一个 `WHERE deleted_at IS NULL`，被删的笔记就从应用里消失了，但物理上还在。

为什么要多此一举？三个很实际的场景。用户反悔：「上周误删的笔记能找回吗」——软删除下能，回收站功能顺手就有了。排障需要：「这个 bug 昨天还在复现，被删的那条数据长什么样」——数据还在，查就是了。还有同步协议需要它：设备 A 删了笔记，设备 B 怎么知道该删本地的？靠变更列表里出现一条「note_8d2m1 已删除」的记录——物理删除的话，这条记录根本无从谈起。第 13 篇讲同步协议时，软删除的记录有个专有名字，叫 tombstone（墓碑）。

代价也要说：所有查询都要记得带 `WHERE deleted_at IS NULL`，忘带就是「回收站里的笔记又出现了」的事故（ORM 一般支持全局过滤，用它）。存储永远只增不减，隔一段时间要做真正的物理清理。这些代价在笔记这种「删除不频繁、反悔很常见」的数据上是划算的；日志、验证码这类用完即弃的数据，老实真删。

## 结尾：一张表就是一句承诺

把这篇收进一句话：表结构是数据库世界里的公共契约，约束是契约的牙齿，迁移是契约的变更流程，归属列是多人世界的地基。

选型上的取舍再压一遍：默认一个 Postgres（或 MySQL，选一个别回头），MongoDB 留给真正无结构且弱关联的数据，本地客户端继续用 SQLite 各干各的。判断字段该进 JSON 还是该拆表，标准就一条：它需不需要被单独查询。

表建好了，users 表也躺在那里了，里面有一列还没填：`password`。下一篇文章从这一列开始——它到底该存什么、为什么答案是「肯定不是密码本身」，以及 Session 和 JWT 这对冤家怎么选。
