凌晨一点半，用户在工单系统留了言：「同步一直失败，转圈」。你睡眼惺忪地登上服务器，敲下看日志的命令，屏幕上是这样的：

```
[nodemon] starting `node dist/index.js`
Server listening on port 3000
```

应用跑了两周的全部记录就这两行。同步失败了吗？不知道。什么时候开始的？不知道。影响了几个用户？不知道。你唯一确定的是问题存在，因为用户说它存在——而你没有任何工具回答接下来的任何一个问题。

本地开发时你有一整套趁手的兵器：console.log 随处插、断点一步步跟、问题必现所以改一行试一次。生产环境把这三样全部没收：日志没有（没人写过）、断点不可能（不能停掉所有用户的服务等你单步）、复现不了（凌晨那个用户的网络环境、数据状态、操作序列都是谜）。这篇讲拿什么兵器换：结构化日志、request id、三个指标。合起来这堆能力有个名字叫**可观测性（observability）**——出了事之后，系统自己能告诉你发生了什么。

## 第一课：日志是结构化数据，不是字符串

绝大多数项目的日志是从 `console.log("同步失败" + err)` 开始的，然后在一个深夜付出代价。字符串日志的问题不在少，在**不能查**：「同步失败」这条日志出现在日志文件的第三万七千行，和它相关的其他线索散落在上下文各处，你既没法按用户过滤，也没法按时间范围筛，更没法统计「今天这个错误出现了几次」。

结构化日志把每条日志写成一行 JSON，机器可解析、可检索、可聚合：

```json
{
  "time": "2026-10-16T01:34:02.114Z",
  "level": "error",
  "msg": "sync failed",
  "requestId": "req_9a4e1f",
  "userId": "usr_2q8v7n",
  "noteId": "note_7f3k9",
  "err": "ETIMEDOUT connect 10.2.1.9:5432"
}
```

这一行在检索时能做的事立刻多了起来：按 `requestId` 过滤出一次请求的全部日志；按 `err` 聚合统计同类错误的发生次数；按 `userId` 查这个用户今晚所有失败的请求。各语言生态都有成熟库（Node 的 pino 是性能标杆），接入成本半小时，收益是从此生产环境不再是黑盒。

顺手把级别分了：error（出错了，需要人看）、warn（可疑但系统自己处理了，比如重试成功）、info（关键业务事件的发生，一行账）、debug（开发期的细节，生产不开）。别把所有东西都打成 error——告警和排查时，「什么都重要」等于什么都不重要。

## 第二课：request id，串起一次请求的一生

第 2 篇设计错误响应时埋了一个 `requestId` 字段，说它是「给未来的你看的」。现在兑现。

机制：一个中间件在请求进来时生成唯一 id（客户端带了就复用客户端的），塞进请求上下文，之后这个请求路径上产生的**每一条日志**都带上它。于是一次请求的一生被串成了一条线：

```
req_9a4e1f  收到请求 GET /sync/changes
req_9a4e1f  查询数据库 notes（12ms）
req_9a4e1f  对象存储 HEAD 附件（401ms ⚠）
req_9a4e1f  重试对象存储（超时）
req_9a4e1f  同步失败，返回 502
```

凌晨那个工单的排查流程从此变成：用户说「同步失败」→ 你问一句「设置页最下面有个错误码，念给我」→ `req_9a4e1f` → 日志系统里一筛 → 四行日志看穿一切：不是数据库，是对象存储那晚抖了，重试也超时。两分钟定位，对比「在两万行字符串里肉眼考古」，是两个职业。

request id 还要会**跨越进程边界**：请求处理到一半入队了一个后台任务（第 9 篇），任务日志要带上触发它的 requestId；调了第三方支付（第 10 篇），把 requestId 发给对方做幂等键或备注。线索断了的地方，就是排查断掉的地方。同理，响应体里也永远带着它（02 篇的错误信封），它是你和用户之间的暗号。

## 第三课：记什么，不记什么

日志不是越多越好，量一大检索变慢、成本变高、真正有用的行被淹没。单体的务实清单：

**每个请求一行**（access log）：方法、路径、状态码、耗时、requestId、userId。这是流量和错误率的原始数据，下一课的指标从这里来。**关键业务事件一行**：`payment.succeeded`、`user.registered`、`export.completed`——业务出争议时（「我明明付了钱」）这是最硬的证据。**错误必带完整堆栈和上下文**：error 级别的日志要能让没见过这个代码的人看懂发生了什么。

不记的更关键：密码、token、Authorization 头，一个字节都不许进日志（第 12 篇的规矩）；完整响应体和请求体（只记关键 id 和大小——用户笔记内容是隐私，日志系统往往是权限最松的地方）；每条 SQL 全文（记表名和耗时就够，慢查询有自己的专项日志）。

## 第四课：三个指标，面向症状告警

日志回答「这件具体的事怎么了」，指标回答「系统整体现在健康吗」。指标是数字的时间序列：每秒请求数、错误数、P99 延迟……入门不需要背一堆，**RED 三件套**覆盖了服务健康的主干：

- **Rate（流量）**：每秒多少请求。它是背景板——任何指标脱离流量都没有意义（错误 10 次/秒，在 50 次/秒的总流量里是灾难，在 5 万次/秒里是噪声）。
- **Errors（错误率）**：5xx 占比。用户正在遭遇失败的比例，最接近「用户体感」的数字。
- **Duration（延迟）**：注意看分位数不是平均值——P99 延迟 8 秒的意思是最慢的 1% 请求要 8 秒，平均值对这个事实几乎无感（lee 那个 8 秒的列表接口，平均值看起来一直很健康）。第 7 篇说的「P99 到 8 秒」，度量的就是它。

工具形态知道长什么样就行：应用暴露指标端点，Prometheus 抓取存储，Grafana 画图告警——这套的部署实操在 [DevOps 系列](/posts/devops2/01-linux-server-setup)里，基础设施视角的监控告警在[部署基础设施地图第 8 篇](/posts/infra-map/08-production-reality)，本篇不重复。哪怕暂时什么都不搭，云厂商自带的 CPU、带宽图也先把错误率和 P99 延迟盯起来。

告警的设计原则只有一条：**面向症状，不面向原因**。告「错误率超 2% 持续 5 分钟」（用户正在受苦，起来修），不告「CPU 超 80%」（CPU 高可能什么都坏，也可能只是忙；原因候选无穷多，症状只有几种）。半夜把你叫醒的应该是「用户在受苦」，不是「某个内部数字越了线」。

## 结尾

可观测性的收拢版：日志用结构化库写 JSON，级别分清；request id 从中间件生发、贯穿 worker 和第三方、回到错误响应里和用户见面；每请求一行、每事件一行、错误带全上下文、敏感信息绝不入日志；指标盯 RED 三件套，告警只面向症状。所有这些的共同目标：出事时能快速回答三个问题——发生了什么、影响谁、从哪开始。

还要补一句这篇没展开但你应该知道的词：**链路追踪**（distributed tracing）。它做的事是把 request id 标准化、自动化——每个请求经过每一站的耗时自动记录成一条瀑布（OpenTelemetry 是事实标准）。单体应用里 request id + 结构化日志够用了；等系统拆成多个服务、一次请求穿过五个进程，链路追踪从奢侈品变成必需品。什么时候会走到那一步？下一篇就聊这个——以及为什么我劝你晚一点再走。
