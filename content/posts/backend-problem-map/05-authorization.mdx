现在每个请求进你的服务，中间件都能给出一个确定的答案：这是 usr_8x9k2m，lee，合法登录，Pro 套餐用户。认证这一关过了。

但只过这一关，第 1 篇那颗雷还埋着。把场景再摆一次：

```
GET /api/notes/8823
Authorization: Bearer eyJ...（lee 的合法 token）
```

token 是真的，登录是真的，请求格式挑不出毛病。可 note_8823 不是 lee 的笔记，是另一个用户的私人日记。你的接口怎么回答？这个问题的答案，就是这一篇的全部内容：授权（authorization）。认证和授权常被连着念成一个词「auth」，但它们是两道独立的关卡——只做认证不做授权的系统，等于大门装了锁、每间屋子却都敞着。

## 越权的两个方向

按「越过了什么线」，越权分两种。

**水平越权**：同级别的用户，动了别的用户的数据。lee 拿自己的 token 读、改、删别人的笔记。这条线是水平的，因为攻击者和受害者在系统眼里是平级的普通用户。它有个更广为人知的名字——IDOR（Insecure Direct Object Reference，不安全的直接对象引用）：接口拿一个 id 直接定位对象，只验了「登录没有」，没验「这个对象归不归你」。

**垂直越权**：低权限用户触发了高权限才能用的功能。普通用户调到了 `/api/admin/users/deleteAll`。实现方式通常有两种：管理接口忘了挂「要求管理员」的中间件；或者界面藏了按钮，但接口还开着——前端把入口藏起来就当做了权限控制，这是把第 1 篇「客户端不可信」又忘了一遍。

ClipNote 作为多用户笔记应用，水平越权是主要威胁：每个人的资产就是自己的笔记，而接口全是按 id 操作的。团队共享功能上线后，垂直越权也会来凑热闹：一个共享空间里有 owner、editor、viewer 三种角色，viewer 能不能调到「修改笔记」的接口？代码里不检查，能。

## 归属检查：写进查询条件，不要写成 if

防水平越权的写法，一版一版看。

第一版，最直觉也最危险：

```ts
const note = await db.notes.findById(noteId); // 只按 id 查
if (note.userId !== currentUser.id) throw new ForbiddenError();
```

这段代码本身是对的，问题是它把安全性寄托在「每个 handler 都记得写这个 if」上。今天二十个接口都记得，三个月后新来的接口忘了，漏洞就开了。而且这个写法还有个隐蔽的信息泄露：id 存在和不存在返回的错误不同（403 和 404），攻击者据此能探测出「这个 id 真的有笔记」。

第二版，把归属写进查询条件：

```ts
const note = await db.notes.findOne({
  id: noteId,
  userId: currentUser.id, // 不是你的，查询结果直接是 null
});
if (!note) throw new NotFoundError();
```

查询条件同时带 id 和 userId，别人的笔记在数据库层面就查不到，返回统一的 404。单条查询天然安全，且忘写 userId 的概率比忘写 if 低——因为同一个 where 结构在 list 接口里反正要写（你的笔记列表当然是 `WHERE user_id = 当前用户`），单条查询照抄就行。

更好的做法是让框架替你统一：ORM 的全局 scope（所有 notes 查询默认带 `userId = 当前用户`，需要跨用户时显式声明）。写法层面的技巧属于第二道防线，第一道永远是数据建模：第 3 篇建表时每张表都长了 `user_id` 归属列，现在的检查就是拿这列做文章。建模时欠的债，到这里要还本付息。

## 每个接口 × 每个动作，过一遍

越权为什么防不住？不是因为哪个技术点难，是因为检查的次数太多。每新增一个接口，就多一次忘记的机会。系统性的做法是拿一张矩阵逐格过：

| 动作 | 单条接口                                  | 列表接口                   |
| ---- | ----------------------------------------- | -------------------------- |
| 读   | note 归他吗                               | 列表条件带他的 id 吗       |
| 改   | note 归他吗（PATCH 的每个字段都该他改吗） | ——                         |
| 删   | note 归他吗                               | 批量删除的每一行都过一遍吗 |
| 创建 | 外键指向的父对象（附件的 note）归他吗     | ——                         |

容易被漏的两格特别点出来。一是「创建」：POST /attachments 挂到 note_8823 下面，挂之前查过这条 note 归他吗？没查的话，攻击者可以往别人笔记里塞附件（顺便耗你的存储费）。二是「批量」：DELETE /notes?ids=a,b,c 一把删过去，每一行都校验了吗，还是只校验了第一行？

团队共享功能上线后，这张矩阵长出第三维：同一个动作，在不同角色下答案不同。owner 能删空间，editor 只能改内容，viewer 只能看。这时候硬编码 if 开始爆炸，通常的解法是把「谁能做什么」变成数据——角色（role）挂在「用户-空间」的成员关系上，检查逻辑统一成一个问题：「当前用户在这个空间里是什么角色，这个动作要求什么角色」。这就是 RBAC（基于角色的访问控制）的全部内核；至于 ABAC（基于属性），是「按属性而非角色判断」的进阶版，ClipNote 这个量级用不上，知道名字就够。

管理后台另有一条铁律：**独立部署、独立鉴权**。后台接口和普通接口不共用一套入口，后台的中间件单独判管理员身份，宁可配置繁琐一点。混在一起的后台，出事只是时间问题——某个忘了挂权限中间件的路由，就是整条防线上的破洞。

## 怎么在写代码时不再依赖记性

三个实际可用的手段。

写测试时用两个用户。哪怕就两个：usr_a 创建一条笔记，usr_b 去读、改、删，断言全是 404。这套测试写一次，每个新接口抄一份骨架，越权在 CI 里就现形。

Code review 固定问一句：「这条查询带归属条件了吗？」不需要 reviewer 懂业务细节，这一句是无差别覆盖。

上线后自己当一次攻击者。拿自己两个测试账号，curl 换 id 打一遍主要接口。五分钟的事，比任何文档都直接——第 12 篇的安全清单里，这一条在首位。

## 结尾

把这篇收拢成一句话：**认证是自动的（中间件统一做），授权是手工的（每个接口都要想）**，所以漏洞总出在授权。防御姿势按优先级排：归属写进查询条件优于事后 if，框架 scope 优于逐处手写，双用户测试兜底。共享协作场景把「归他吗」升级成「他在这个空间里是什么角色」，用数据而不是 if 爆炸来表达权限。

权限这一关守住，接口之间终于是安全的了。但 ClipNote 的共享笔记马上要撞上另一个问题，它跟安全无关，跟时间有关：lee 在公司改那条「团队 OKR」，同事同时在家里改同一条，两人都点保存——服务端先处理谁的写入，后到的那个把先写的覆盖掉。上一篇预告过的丢失更新，下一篇正面迎上，解法是事务和锁。
