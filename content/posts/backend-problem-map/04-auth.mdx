上一篇建表时，users 表里留了一列 `password`。现在第一个用户要注册了：邮箱 `lee@clipnote.dev`，密码 `c0ffee-Lift-42`。这一列存什么？

把密码本身存进去，是最直觉也最不可饶恕的做法。数据库一旦泄露（拖库），几十万用户的密码明晃晃躺在里面。而现实中用户在多个网站用同一个密码，你泄露的不只是 ClipNote 的账号，是用户在所有网站的账号。历史包袱并不遥远：CSDN 2011 年被拖库，600 万明文密码直接成了流传至今的密码字典。

正确答案是存**哈希（hash）**。先把概念掰开，这里的坑比想象中多。

## 哈希不是加密

加密是双向的：有密钥就能还原出明文。密码存储恰恰需要**单向**：进得去，出不来。登录时也不是「解出密码来比对」，而是把你这次输入的密码做同样的哈希，比对两个哈希值是否一致。数据库里自始至终没有存过密码本身。

那用一个 MD5 或 SHA-256 不就行了？不行，这是密码存储的第二个坑：这两个哈希**太快了**。快，对攻击者是好消息。拿到哈希后，攻击者用 GPU 每秒能算几十亿次，你的数据库里几十万个哈希，挨个碰撞一遍就出去喝茶了。就算不暴力碰撞，还有人早就把常见密码的哈希算好建了表（彩虹表），`123456` 的 MD5 值一查就有。

所以密码哈希专门用**故意很慢**的算法：bcrypt、argon2、scrypt。它们慢得恰到好处——单次校验花几百毫秒，用户登录完全无感，攻击者暴力碰撞的成本则乘上了天文数字。它们还自带**盐（salt）**：哈希时掺一段随机数进去并和结果存在一起，同一个密码每次哈希出来的结果都不一样，彩虹表直接作废。

```ts
import bcrypt from "bcrypt";

const hash = await bcrypt.hash(password, 12); // 12 是成本因子，12 ≈ 每次约 300ms
await db.users.insert({ id: "usr_8x9k2m", email, passwordHash: hash });

// 登录时
const ok = await bcrypt.compare(inputPassword, user.passwordHash);
```

成本因子的含义：机器变快了，把这个数字调大一点，攻击成本跟着涨。它不神秘，就是「故意让你慢」的那个旋钮。

## 登录之后：Session 和 JWT 这对冤家

密码验过了，接下来是每个请求都要面对的问题：HTTP 没有记忆，这个请求怎么证明「我是刚登录过的那个 lee」？

**Session 方案**：登录成功后，服务端生成一条记录（session id 12345 → 用户 usr_8x9k2m，有效期到明天 8 点），存进数据库或 Redis；给浏览器的 Cookie 里只放这个 id。之后每个请求带上 Cookie，服务端查一次表就知道你是谁。

它的优点是**可以撤销**：用户点「退出登录」，把那条记录删了，session id 立刻作废；发现盗号，删掉全部 session，所有设备下线。「改密码后强制全端下线」这种安全需求，Session 天然支持。

代价是服务端有状态：每个请求查一次 session 存储。只有一台服务器时这不算事，等你有两台、用户请求被负载均衡随机分过去，A 机器上的 session 在 B 机器上查不到——要么 session 集中存到 Redis，要么让负载均衡把同一用户固定分给同一台机器。这是部署侧的经典问题，[部署基础设施地图第 5 篇](/posts/infra-map/05-cluster-and-ha)里有完整展开。

**JWT 方案**：把「你是谁、什么时候过期」直接写进一个 token，用服务端密钥签个名发出去。之后每个请求带上 token，服务端用密钥验签名，验过就认——全程不查库、不存状态，天然适配多台服务器。

但「不存状态」反过来就是它全部的坑：**发出去的 token 在过期前收不回来**。用户点了注销，他手里的 token 还是有效的，服务端没有任何单一开关能作废它（真要作废，就得维护黑名单，那又回到了有状态）。于是工程上长出各种补丁：把过期时间压短到 15 分钟、再配一个有效期长的 refresh token 换新 token、检测到盗号时轮换签名密钥……每一样都在把「无状态的优雅」一点点还回去。

存放位置也有讲究。放 localStorage 里，遇到 XSS（页面被注入脚本）token 就被偷走；放 `HttpOnly` Cookie 里脚本读不到，但要比对 `SameSite` 设置来防 CSRF。没有满分答案，只有你更怕哪一种攻击。

ClipNote 怎么选？我的判断：**需要频繁踢人下线的产品（有封禁、有盗号申诉、有多设备管理）选 Session；纯 API 服务、多端客户端、想要无状态扩容的选短时 JWT + refresh token**。笔记应用有「退出所有设备」的刚需，Session 略优。两个都是正确答案，真正的错误是选了 JWT 还指望注销立即生效。

## 「用 Google 登录」：密码的事从此归 Google

自己管密码哈希已经是标准动作，但能让用户不设密码更好——「使用 Google 账号继续」点一下就完成注册，转化率肉眼可见地高。这背后是 OAuth 2.0，流程比名字温和：

1. 你的应用把用户跳转到 Google 的授权页（带上你的应用 id 和回调地址）；
2. 用户在 Google 的页面里登录并点「允许」——注意，密码输在 Google 的页面，你的服务器全程碰不到；
3. Google 把用户带回你的回调地址，附一个一次性的授权码；
4. 你的服务端拿授权码向 Google 换取用户信息（id、邮箱、头像）；
5. 按邮箱找你的 users 表：没有就建档，有就登录。

你的数据库里这个用户的 `passwordHash` 是空的，加一列 `google_id` 就够了。你卸下的不是注册流程，是整个密码安全的责任——代价是登录可用性从此依赖 Google，还有第 1 篇那句老话：回调地址的校验、state 参数防 CSRF，这些细节一个都不能省，OAuth 的历史漏洞几乎都出在流程细节上。

## 找回密码：篓子最容易出在这里

邮件验证和找回密码，是用户系统里安全上最脆的一环。核心三条规矩。

找回链接里的 token 必须是一次性、短时效的。生成一个随机 token 发到用户邮箱，15 分钟有效，用过即焚；数据库里存的是 token 的哈希（万一库泄露，攻击者拿到的 token 也都用不了）。绝不能用「用户 id + 时间戳拼一下」这种可预测的东西当 token——攻击者不需要拖库，猜就能猜出来。

验证通过、允许设置新密码的那一刻，必须作废该用户**全部**现有 Session 和 refresh token。否则场景是这样的：攻击者先偷到了你的 session，再触发你的邮箱收到找回邮件（攻击者拿不到邮件，但也无所谓），你的新密码改完，攻击者手里那个旧 session 还活着，改密码白改。

邮件验证同理：验证完成前，账号能做的事要压到最少。别出现「邮箱还没验证，但已经能通过 API 正常使用全部功能」的设计，那验证邮件就成了装饰。

## 结尾

这篇的选型压成一段：密码用 bcrypt 或 argon2 哈希存储，成本因子 12 起步，永远不存明文也不存可逆加密；会话方案按「要不要频繁踢人」在 Session 和短时 JWT + refresh 之间选；能用 OAuth 分流一部分用户就分流，密码少一个是一个；找回流程记住 token 一次性短时效、改密全端下线这两条，它们覆盖了真实事故的大头。

认证做完，每个请求都知道「这是 usr_8x9k2m」了。但第 1 篇埋的那颗雷还没拆：张三拿着自己合法的 token，去请求李四的笔记 `GET /api/notes/8823`，你的接口放不放行？下一篇就拆这颗雷，它的名字叫越权，是真实世界里出镜率最高的漏洞。
