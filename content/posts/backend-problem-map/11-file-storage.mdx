剪藏网页图片的功能上线一周，三个症状一起出现：服务器带宽跑满、API 进程内存吃紧（一个 40MB 的 multipart 请求能占掉几十 MB 缓冲区）、云账单比预算多了一个零。功能本身用户很满意，麻烦全在文件怎么「存」和「传」这两个想当然的决定上：你想当然是存到了自己服务器磁盘，你想当然是经过你的 API 中转。

这篇把文件这件事的三个决定挨个重做：存哪、怎么传、怎么发。

## 决定一：文件不进数据库，也不进应用服务器

第 3 篇建模时给 attachments 表只留了 `storage_key` 一列，当时说「文件不进数据库」，现在把理由说透。

数据库存 BLOB（二进制大对象）的问题是全方位的：备份体积跟着文件一起膨胀，今天几 GB 的库明天就是几百 GB，备份窗口从分钟变成小时；查询性能被拖累，哪怕你只 SELECT 其他列，数据库的 IO 也可能被大对象波及；数据库为了事务一致性设计，而图片恰恰是最不需要事务的东西——笔记正文错了要回滚，图片没有「回滚一半」这种事。

应用服务器磁盘同样不是家。它容量有限、重启可能清空（容器环境一定会）、多实例之间不共享（图片传到 A 实例，下载请求落到 B 实例，404）。存本地唯一说得过去的场景是开发环境。

正确的家是**对象存储（object storage）**：S3（AWS）、OSS（阿里云）、R2（Cloudflare）都是。心智模型一句话讲完：**一个通过 HTTP 访问的超大 key-value 存储**。PUT 一个 key 写入，GET 同一个 key 读出，DELETE 删除，没有目录、没有权限树、没有部分写——就是键值对，只是 value 是文件，key 是你起的一个字符串（比如 `attachments/usr_8x9k2m/2026/10/img_a71f.jpg`，斜杠只是 key 的组成部分，不是真的目录）。

它的性质刚好和文件匹配：容量近乎无限按量付费、持久性按「个九」承诺（11 个 9，意味着一千万文件放一年期望丢失一个）、天生多实例共享、和应用的伸缩完全解耦。

## 决定二：上传走预签名 URL，别经过你

文件的家定了，第二个决定是路径：用户的浏览器怎么把 40MB 送到对象存储。

直觉方案是中转：浏览器把文件 POST 给你的 API，API 收完再转存到对象存储。能跑，但每一层都亏：你的 API 进程要为每个上传占住内存缓冲；服务器入站和出站带宽各付一遍（流量费双倍）；上传时长受 HTTP 超时约束（第 9 篇的老问题）；高峰期几十个并发上传就能把一台小机器打满——上线一周的那三个症状，全是这条路径的直接后果。

正解是**预签名 URL（presigned URL）**：对象存储支持「把某个 key 的写权限临时授给一个 URL」。流程变成：

```
1. 浏览器 → 你的 API：我要传一张图（附文件名、大小）
2. 你的 API 校验登录、校验归属、生成 storage_key，
   用存储密钥签一个 15 分钟有效的 PUT URL，返回
   { uploadUrl, storageKey }
3. 浏览器 → 对象存储：PUT 预签名 URL，直传文件
   （数据完全不经过你的服务器）
4. 浏览器 → 你的 API：传好了，key 是 xxx
   → 写入 attachments 表（或由存储回调确认）
```

你的 API 在整个链路里只干了签 URL 和记账两件轻活，40MB 的流量一次都不碰。预签名 URL 自带过期时间，泄露了也只有十几分钟的窗口，而且 key 是你生成的、归属关系在签名前就校验过（第 5 篇的规矩没破）。

下载是镜像的同一招：bucket 默认私有，读也发短期预签名 GET URL（比如 10 分钟有效），权限始终攥在你手里。用户分享出去的公开图片是另一回事，往下看 CDN。

## 顺手的事：图片处理扔给 worker

用户剪藏的是原始网页图，4MB 一张的相机原片很常见，直接原样存储和分发，存储和流量双倍浪费。处理链路是标准的后台任务：上传完成后入队（第 9 篇的 jobs 表），worker 压缩、转 WebP、生成两三档尺寸（列表缩略图 / 详情中图 / 原图）。这一步「别在 API 请求里同步处理图片」就是第 9 篇教训的原样复用：图片编解码是 CPU 重活，放在请求里就是又一次「一个人的重活惩罚所有人」。

顺带修一个隐形依赖：attachments 表里记下每张图的字节数和 mime 类型，列表接口据此决定加载哪档尺寸，别让客户端猜。

## 决定三：分发开 CDN，账单不降反升是错觉

最后是读的分发。所有用户都从对象存储的某一个区域下载，等于全国用户挤一个柜台。CDN（内容分发网络）做一件事：把你的文件的**副本**预先放到离用户近的几十上百个机房，用户下载时由最近的那个应答。

对图片这种静态内容，CDN 几乎无脑正确：用户端的下载速度显著变快（物理距离近了）；抗住流量尖峰的能力强了（成百个节点分担，而不是一个源站硬扛）；成本通常还更低——CDN 的流量单价普遍低于源站出流量，你付的第一笔「多出来的钱」是 CDN 的，省下的钱是源站带宽和对象存储请求费里的。

控制权在缓存头和 key 设计上。图片内容不变就让 URL 不变、`Cache-Control` 设长（`max-age=31536000`），热门图的绝大部分请求永远到不了源站——流量费大头就是这么省下的。变了怎么办？改 key（文件内容 hash 进 key，`img_a71f_v2.webp`），新内容新地址，旧地址的缓存随它去。附件这种私有内容走 CDN 也行，各大厂都有「CDN + 鉴权 URL」的组合，原理同预签名。

算笔账感受一下量级：存储每 GB 每月几毛钱，流量每 GB 一到三毛。ClipNote 的图片库一年 200GB 存储（上百块），但每天 10 万次图片访问、平均 500KB，一个月流量 1.5TB（两三百块起）——**贵的是流量，省的方向是减少回源**。这也解释了为什么压缩和 WebP 值得做：文件小一半，流量和用户等待时间一起减半。

## 结尾

这篇三个决定收拢：文件住对象存储（key-value 心智模型，永不进数据库和应用服务器）；传走预签名 URL（API 只签名不搬砖，权限校验留在签名那一步）；分发上 CDN（长缓存 + 内容 hash 进 key，私有内容用鉴权 URL）。图片处理永远是后台任务。

到这里，ClipNote 该有的功能都有了，该防的事故都防了一遍。下一篇把散落在 04、05、10 各篇里的安全线索拧成一份上线前能逐条打勾的清单——顺便回答一个你可能一直嘀咕的问题：我这么小的应用，真的会有人来攻击吗？（上线一个月的访问日志会替我回答。）
