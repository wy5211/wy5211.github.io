上一篇说到，ClipNote 的同步需求背后是三个后端特有的问题：数据要活很多年、很多人同时写、客户端不可信。现在动手干活，第一步是把「拉取上次同步以来的变更笔记」做成一个接口。

你大概十分钟就能写出一个能跑的版本：

```
GET /api/getUpdatedNotes?userId=1104&lastSyncTime=2026-10-14T08:00:00Z
```

它没什么错，但按这个路子写下去，三个月后你的 URL 列表会长这样：getUpdatedNotes、getDeletedNotes、updateNoteTitle、deleteNoteForever、searchNotesByTag……每加一个功能造一个新动词，每个动词带自己的一套参数，客户端和服务端各记一份秘籍。这就是所谓的 RPC 风格接口——不是不能用，是规模一大就没法维护。这篇讲怎么把它设计成三个月后你自己还愿意看的样子。

## 先把「东西」找出来：资源建模

API 设计的第一步不是想接口，是想清楚你的系统里有哪些**资源**（resource）：可以拿出来指称的「东西」。ClipNote 里一眼可见的有笔记、标签、附件，同步场景里还有一个不那么明显的：**变更本身**。

把变更也看成资源，整个设计就顺了。客户端要的不是「执行一次同步」，而是「给我某个游标之后发生的变更列表」。列表，就是典型的资源：

```
GET /api/sync/changes?cursor=eyJ0IjoxNzI4ODk0NDAwfQ
```

返回的每一项是一条已经发生的事实：note_7f3k9 在某时刻被创建，note_8d2m1 在某时刻被删除。客户端拿到列表自己消化。这个视角还有个好处：多台设备、多少次拉取，用的都是同一个接口，因为它只是「读一份清单」，不关心谁在读。

判断某个东西是不是资源，一个土办法：它能不能用「一条 / 一列」来数？一条笔记、一列变更、一个设备。能数的，就给它起名词；数不出来的（比如「立即同步」这种命令），后面会讲到怎么处理。

## 动词交给 HTTP：方法语义

资源定了名，操作类型交给 HTTP 方法表达，别再塞进 URL 里：

```
GET    /api/notes          拉笔记列表
POST   /api/notes          创建一条笔记
GET    /api/notes/note_7f3k9    拉某一条
PATCH  /api/notes/note_7f3k9    改某几个字段（title、content）
DELETE /api/notes/note_7f3k9    删除
```

PATCH 和 PUT 的区别值得记一下：PUT 是「整体替换这条资源」，PATCH 是「只改你给的字段」。笔记这种大字段的对象，客户端通常只改标题或内容，PATCH 更省流量，也更不容易把别人刚更新的字段冲掉——这个「冲掉」的隐患，第 6 篇讲并发时会正面撞上。

方法语义还附带一层约定：**GET 不应该有副作用**。同一个 GET 请求发一遍和发十遍，服务器状态不变、返回结果一样。这个性质叫幂等，第 10 篇讲支付的时候会看到它值多少钱。你现在只需要记住：写代码时把「读」和「写」老实分到 GET 和 POST/PATCH/DELETE 里，很多工具会因此免费帮你——浏览器缓存、CDN、重试逻辑，都默认 GET 是安全的。

## 错误怎么返回：统一信封

出错的返回最见设计功力。两种常见的烂法：直接抛 500 让客户端看堆栈；或者所有错误都返回 200，body 里塞个 `{ success: false }`。后者看起来「不会报错」，实际上客户端的状态码监控、重试逻辑、日志告警全部失效——你的接口永远「成功」，只是有时候成功得不带数据。

定一个错误信封，全站只用这一种：

```json
{
  "error": {
    "code": "NOTE_NOT_FOUND",
    "message": "笔记不存在或已被删除",
    "requestId": "req_9a4e1f"
  }
}
```

三个字段各有分工。`code` 是给程序看的稳定标识，客户端靠它决定重试还是弹提示；`message` 是给人看的，可以直接展示给用户；`requestId` 是给未来的你看的——用户投诉「昨天下午同步失败」，你拿这个 id 去日志里一查，那次请求发生了什么一清二楚。这个字段现在只是埋下，第 14 篇讲排障时它会成为主角。

状态码不用背全表，常用的一段一只手数得过来：400 参数不对、401 没登录、403 登录了但没权限（第 5 篇的主角）、404 不存在、409 冲突（第 6 篇的版本冲突会用上）、500 自己的锅。剩下的大多数场景，这七个够用。

## 列表怎么分页：cursor 为什么赢了

变更列表一开始几十条，后来会到几万条，不可能一次全给。分页有两种做法。

Offset 分页是前端最熟的：`?page=3&pageSize=50`，翻译成 SQL 就是 `LIMIT 50 OFFSET 100`。简单，但要命的是它在数据变动时会出错：你翻第 2 页的瞬间，别的设备新写了一条笔记，整列数据往后挪了一位，你翻到的第 2 页会重复展示上一页的最后一条，同时漏掉一条。购物网站翻页时偶尔看到重复商品，就是这么来的。

Cursor 分页换成「从哪之后」：`?cursor=eyJ0IjoxNzI4ODk0NDAwfQ&limit=50`，cursor 里通常编码着「最后一条的位置 + 排序」。它不关心绝对页码，所以数据怎么动都不会重不会漏——代价是没法直接跳到「第 7 页」。

同步接口天然该用 cursor：增量同步本来就是「接着上次的位置继续拉」。 ClipNote 的流程会是：设备存一个本地 cursor，每次 `GET /sync/changes?cursor=...`，返回新一批变更和下一个 cursor，拉到没有下一页为止。对 UI 列表展示，如果产品就是要有页码跳转，用 offset 也没关系，知道它会偶尔重复就行。

## REST、GraphQL、tRPC 选谁

到这你可能想问：这些是不是只有 REST 这一套？前端圈这几年听的更多的明明是 GraphQL 和 tRPC。

三者其实回答的是同一个问题的三种答案：客户端怎么向服务端描述「我要什么」。

**REST** 就是上面讲的这套：资源 + 方法 + 一堆端点。它无聊、土、哪里都能用。任何 HTTP 客户端都能调，缓存语义清晰，团队里不管谁用什么语言都能立刻上手。缺点是经常要拼多次请求才能凑齐一个页面要的数据。

**GraphQL** 让客户端自己声明要哪些字段，一次请求拿全。它解决「接口为不同的页面反复定制」的痛，代价不小：服务端要多写一层 resolver、要处理查询复杂度（不然客户端一个嵌套查询能把数据库打挂，第 7 篇的 N+1 问题在 GraphQL 里换个形式重现）、要自己做缓存策略。适合多端差异大、或对外的公开 API（GitHub、Shopify 的 API 都是 GraphQL，让第三方自由取数）。

**tRPC** 是 TypeScript 全栈的甜点：服务端定义的 procedure 直接生成客户端的类型，调接口像调本地函数，编译期就查参数错误。对「前后端都是 TS、部署在一起」的项目（比如你的 Next.js 全栈应用），开发体验没有更好的了。边界也在这里：客户端一旦不是 TS——移动端原生、第三方接入——它就帮不上忙；接口永远和代码同版本部署，等于放弃了 API 的独立性。

给 ClipNote 这种「自己客户端 + 自己后端」的产品，我的看法是：全 TS 单体就上 tRPC，想吃透后端通用套路就用 REST。GraphQL 留到你要做公开 API 或者多端取数差异真的痛了再碰。选型这事的判断标准从来不是哪个更新，是客户端是谁。

## 鉴权放哪：一个预告

每个接口都要回答「这是谁在调」。这个判断不要写在每个 handler 里，写在统一的中间件层：请求进来先过一道验证，解析出「当前用户」，挂到请求上下文上，后面的代码只管用。哪个接口需要登录、哪个公开，用一条声明解决。

中间件里具体验什么、token 怎么发、密码那一栏到底存什么——这是下一篇的开场，也是 User 表的第一次真实使用。

## 结尾：什么时候可以不讲武德

上面整套是 REST 的正统做法，但别把它当法律。有些操作天然不是对资源的增删改查：「置顶一条笔记」「合并两条笔记」「触发立即同步」。硬凑成 `PATCH /notes/note_7f3k9` 加一个 `isPinned: true` 有时很别扭，直接 `POST /notes/note_7f3k9/pin` 反而诚实——URL 里出现动词，天塌不下来。教条主义的标志是宁可扭曲业务也不违背风格，方向反了。

总结一下这篇的选型：资源建模用「能数出来吗」来判断；读和写严格分进 GET 和其他方法；错误用统一信封带 requestId；列表分页默认 cursor，要页码再 offset；协议上，全 TS 单体选 tRPC，学通用套路选 REST，公开 API 再考虑 GraphQL。
