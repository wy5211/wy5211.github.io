ClipNote 的同步目前是这样的：客户端每 30 秒调一次第 2 篇设计的那个变更接口，问一句「有新东西吗」。功能上没毛病，体验和成本都有话讲：用户在手机上改完笔记，回到电脑前最多要干等 30 秒；全量用户每 30 秒一轮拉取，绝大多数轮次的答案是「没有变更」——你为了等一个可能出现的事件，付出了全天候的空转轮询。

「这边一保存，那边立刻出现」需要的是**服务端推送**：有变更时服务器主动说，没变更时谁也别说话。这篇讲三件事：推送通道怎么选、推送来了之后同步协议怎么设计、以及绕不开的冲突怎么解。

## 通道选型：先问推送是单向还是双向

推送技术的四个台阶，按成本排：

**轮询**：现状，客户端定时拉。实现为零，浪费和延迟都是结构性的。

**长轮询**：客户端发起请求，服务器 hold 住不回，直到有变更（或 30 秒超时）才响应，客户端收到立刻发起下一个。延迟接近实时，实现简单。缺点：每个客户端长期占着一条 HTTP 连接，服务器并发连接数压力大；每次「事件到达」还是借 HTTP 响应的壳，开销不小。

**SSE（Server-Sent Events）**：一条普通 HTTP 连接，服务器沿着它持续写事件流（`data: ...\n\n` 的文本格式）。浏览器原生 `EventSource` 自带断线自动重连，还带 `Last-Event-ID` 机制帮你续传错过的事件。**只能服务器推给客户端，客户端要说话就另外发普通请求。**

**WebSocket**：一条全双工的长连接，双方随时互发。升级自 HTTP 但之后是独立协议，浏览器和服务器都支持成熟。能力最强，自己要管的事也最多。

选型的判断题只有一道：**客户端需要高频向服务器推数据吗？** 笔记同步的答案是不需要——设备的「上传变更」走普通 HTTP 请求完全够（变更本来就低频），需要推送的只有「别的设备改了东西，通知我」这一个信号。单向信号，SSE 正合适。WebSocket 留给客户端也要高频上行的场景：聊天、协同编辑的光标移动、多人游戏。 ClipNote 上 SSE 的账：实现半小时，自动重连白送，流量是纯文本的事件 id，几乎可以忽略。

两个实战细节值一次踩坑的学费：SSE 经过 Nginx 等反向代理时默认会被缓冲（事件攒够一批才转发，实时性归零），要配 `X-Accel-Buffering: no`；连接是长命的，服务端要定期发心跳注释行，好让中间设备别把闲置连接掐了。

## 真正的同步协议：通知归通知，数据归数据

推送通道选好，最容易犯的设计错误是把数据塞进通知里：变更发生时，服务器把整条笔记沿 SSE 推给所有在线设备。听起来直接，坑在后面：哪个设备当时断线了？离线期间错过的事件怎么补？设备本地已经有部分变更了怎么去重？——你等于在 SSE 之上又发明了一套可靠的有序传输协议，而这套问题 HTTP 增量拉取早就解决了。

正确的分工是：**推送只当门铃，同步仍然走第 2 篇那套 cursor 拉取**。

```
设备 A 保存笔记 → POST /notes（普通请求）
服务端：写库，记录变更序号 seq 8841
       → 沿该用户所有在线设备的 SSE 连接发一条：
         event: sync-hint  data: {"seq": 8841}
设备 B 收到门铃 → GET /sync/changes?cursor=本地cursor
       → 拉到 seq 8841 及之前漏掉的所有变更 → 应用 → 推进本地 cursor
```

这个分工下，每条技术都是前面篇章的老朋友，且各自只干自己擅长的事：SSE 只保证「铃响了」（丢了没关系，下一次门铃或下一次轮询兜底会补拉）；cursor 保证「一条不漏、一条不重」（第 2 篇的分页设计在这里价值兑现）；tombstone（第 3 篇的软删除）保证删除也能被同步——设备 B 收到门铃拉到一条「note_8d2m1 已删除」，照做就是。离线设备回来也一样：cursor 还停在三天前，一次拉取把这三天全补上；cursor 太老（服务端变更日志已清理），退化为全量重拉，逻辑不变。

一个容易忽视的协议细节：**同步的排序键用服务端的单调序号，永远不要用客户端时间戳**。设备 A 的时钟快了两分钟，它的「最新」会永远压住别人真正的最新——第 6 篇的丢失更新会换一副面孔回来。

## 两台服务器之后：门铃怎么送到

单体应用躲不开的一课：业务大了上第二台服务器（第 1 篇说过部署细节归部署系列管，这里只讲它给实时推送出的题）。设备 A 连在服务器 1，设备 B 连在服务器 2。A 的保存请求落在服务器 1，变更事件怎么通知到连在服务器 2 的 B？

服务器 1 和服务器 2 互相不认识，需要一个共享的传话人——通常是 Redis 的 pub/sub：保存发生后，往频道 `user:usr_8x9k2m` 发一条「该发门铃了」；两台服务器都订阅着自己用户们的频道，收到后各自沿自己持有的 SSE 连接把门铃敲响。通知仍然只是通知，数据同步仍然各回各家走 cursor 拉取，所以这个 pub/sub **丢了也不出错**，只是那次提醒慢了（等下一次轮询兜底）。能容忍丢失的通知，用最轻的组件就够了——这是「通知与数据分离」送的第二份礼。

（另一种解法是让负载均衡把同一用户固定分到同一台机器，叫粘性会话，第 4 篇讲 Session 时提过。它省掉了传话人，代价是流量分布不均、发版时连接集中断开，实时通道这个场景一般选 pub/sub。）

## 冲突：离线把问题还回来了

最后一道关：实时推送做到位，冲突并没有消失，只是换了出场时机——**离线**。高铁上没网，你在手机上改了那条「旅行清单」的标题和内容；同一时间在家里的电脑上，家人也改了同一条。两台设备都连不上彼此，各自都是「当时的最新」。联网后两份变更同时到达服务端，听谁的？

三档解法，成本递增。

**Last-Write-Wins（后写覆盖）**：按（服务端收到的）先后，后到的整条覆盖先到的。实现就是第 6 篇的乐观锁，一行不多。代价：先到那份修改整体丢失。对「旅行清单」这种各改各的词条的场景，丢的可能是家人加的三个景点。适合：数据价值低、冲突罕见、或字段本来就一体的（比如配置项）。

**字段级合并**：把「整条覆盖」细化成「逐字段比」。标题以设备 A 的为准（B 没改标题），内容字段两份都改了才冲突——冲突字段再 LWW 或者标红让用户手动合。实现成本上一个台阶（每字段记版本），挽救了大部分冲突。ClipNote 的选择停在这档：笔记结构是「标题 + 内容 + 标签」几个独立字段，逐字段合并的收益明显、实现可控。

**OT / CRDT（操作变换 / 无冲突复制数据类型）**：字符或词级别的自动合并，两份编辑都能保留，飞书文档和 Notion 的「多人同时编辑不打架」就是这个层面的技术。代价是真正的研究级复杂度——CRDT 的数据结构和算法自己造等于读博。工程上的正确姿势是：需要协同编辑时，用现成库（Yjs、Automerge），把 CRDT 当黑盒。ClipNote 的产品卖点是「同步」不是「协同」，这一档用不上，知道名字和适用边界就完成了本系列的求知任务。

判断用哪档的问题始终是产品问题：用户对「丢了另一边的修改」的容忍度是多少？容忍度高就 LWW，低就逐字段，零容忍才轮到 CRDT。

## 结尾

收拢这篇：通道选型只问「客户端要不要高频上行」，单向通知 SSE、双向高频才 WebSocket；通知和数据分离——门铃走推送、数据走 cursor 增量拉取，丢失可容忍的用 Redis pub/sub 扇出到多台服务器；排序键用服务端单调序号，别信客户端时钟；冲突按产品容忍度选 LWW、字段级合并、现成 CRDT 库三档。

同步这条线走完，ClipNote 的功能面齐了。但你心里可能一直有个隐隐的不安：现在这一整套东西——API、worker、缓存、SSE、数据库——出问题的时候，你从哪里开始查？下一篇讲可观测性：日志怎么记、request id 怎么串起一次请求的一生、哪三个指标值得你设告警。第 2 篇埋的那个 requestId 字段，到了兑现的时候。
