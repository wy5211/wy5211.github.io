「导出全部笔记为 PDF」是用户投票投出来的功能，你花一个周末写完了：接口收到请求，循环渲染五百篇笔记，打包 zip，返回下载链接。上线十分钟，客服工单来了：导出的人卡在转圈，没导出的人更惨——打开首页要 12 秒。

原因很快定位到：你的 API 进程是 Node 的，一个 CPU 核渲染 PDF 时忙到满格，排在它后面的所有请求全部排队。一个用户触发的重活，惩罚了所有用户。而且这活天生干不长：代理服务器默认 60 秒超时，五百篇的导出在第 61 秒连接断开，前功尽弃，用户只看到失败。

## 分界线：用户在等这个结果吗

判断一件活该不该当场干，就一个问题：**用户的下一步操作依赖这个结果吗？**

登录要等——不拿到 token，之后的请求都发不了。保存笔记要等——用户需要确认「存上了」才敢关窗口。但导出 PDF 不用等，用户完全接受「先去干别的，弄好了通知我」；发验证邮件、清理过期数据、生成缩略图、月底给订阅用户出账单，全都属于此类。这类活的共同点：**用户等的是「承诺」，不是「结果」**。

所以正确的交互是异步的：接口收下请求，回一句「任务已创建，预计 2 分钟」，把活交给别人慢慢干。结构一画就三行：

```
API 进程：收请求 → 写一条任务记录 → 立刻返回任务 id
             ↓（任务躺在表里）
Worker 进程：捞任务 → 干活（渲染 PDF）→ 写回状态和结果地址
客户端：拿任务 id 轮询状态 → done，给下载链接
```

API 进程从此只做轻活，重活全在 worker。worker 挂了不影响 API，API 重启不影响 worker。干活慢也不怕超时——超时的概念只属于 HTTP 请求，worker 自己慢慢跑。

## 队列长什么样：一张表就够了

「队列」这个词听起来像某个要安装的中间件，其实它的最小形态是数据库里的一张表：

```sql
CREATE TABLE jobs (
  id         BIGSERIAL PRIMARY KEY,
  type       TEXT NOT NULL,            -- 'export_pdf'
  payload    JSONB NOT NULL,           -- { "userId": "usr_2q8v7n", "format": "pdf" }
  status     TEXT NOT NULL DEFAULT 'pending',  -- pending/running/done/failed
  run_at     TIMESTAMPTZ NOT NULL DEFAULT now(),  -- 定时任务的入口
  attempts   INT NOT NULL DEFAULT 0,
  locked_by  TEXT,                     -- 哪个 worker 在处理
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

API 写入一条 pending，worker 循环里做 `UPDATE ... SET status='running', locked_by=me WHERE id=(SELECT id FROM jobs WHERE status='pending' AND run_at <= now() ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING *`——`SKIP LOCKED` 保证多个 worker 并发捞任务不会捞到同一条、也不会互相等锁（第 6 篇的锁知识在这里直接复用）。干完写 done，失败写 failed 或者留在 pending 等重试。

这不是我发明的省钱技巧，PostgreSQL 生态里成熟的任务库 pg-boss 内部就是这么干的，Node 生态的 BullMQ 则把队列放在 Redis 里（更快，但任务数据不在数据库里）。**单体阶段用数据库当队列是最优解而不是将就**，理由有三个：不用多运维一个组件；任务记录和业务数据在同一个库里，可以塞进同一个事务（下一篇讲支付时这个性质价值千金）；任务表本身就是运维后台——线上出了什么任务、卡了几条、失败原因，一条 SQL 全看得见。

什么时候这张表不够用？任务量级到每秒几千上万条、或者任务的产生者和消费者是不同服务（事件订阅关系）时。那时再换 RabbitMQ（经典消息代理，路由灵活）或 Kafka（严格说是分布式日志，为超高吞吐和回放设计）。换的动作不难，难的是到时候你已经养成的任务模型（幂等、重试、监控）全部原样带走——所以先用数据库，什么也不亏。

## Worker 的三件工程事

任务系统真正的坑不在「怎么入队出队」，在 worker 这一侧的三个工程问题。

**重试要配退避，执行要设超时。** 任务失败是常态（第三方邮件服务抖一下、用户数据正好在迁移），自动重试是标配。但重试要隔开：立即重试大概率再失败，退避（backoff，第一次 1 分钟后、第二次 5 分钟后、第三次 30 分钟后）给下游恢复的时间。同时每个任务要有执行超时和最大重试次数，超了就进 failed，别让一个死循环任务把 worker 槽位永久占住。重试有個前提条件，接下来说。

**任务必须是幂等的。** 「至少执行一次」是任务系统的默认承诺：worker 干到一半崩了，任务回到 pending，会被**再执行一遍**。这意味着同一个任务跑两次，结果必须和跑一次相同。渲染 PDF 天然幂等（覆盖同一个文件），扣积分就不幂等（加两次）——非幂等的步骤要么做成幂等（先查「这个任务的奖励发过没有」，发过就跳过），要么挪到能保证恰好一次的地方（下一篇的主题）。第 10 篇整篇都在讲这件事，这里先立牌。

**定时任务是队列的一种。** 清理回收站里超过 30 天的笔记、每天的对账，用同一张 jobs 表：`run_at` 写到凌晨三点，worker 到点捞出来执行。要不了 cron。唯一要防的是多实例部署后两个 worker 同时触发同一定时任务——解法是把「定时任务该不该跑」本身做成一条记录（唯一约束兜底，第 6 篇的老朋友），或者用一把简单的锁。

## 结尾

这篇的决策收拢：判断异步的唯一标准是「用户的下一步等不等这个结果」；单体阶段数据库表就是队列，pg-boss 或 BullMQ 拿来即用，RabbitMQ 和 Kafka 等「跨服务、高吞吐、多订阅者」真的出现再说；worker 侧记住重试配退避、执行设超时、任务做幂等——三条全是血的教训换来的行业默认值。

到目前为止，ClipNote 的每类麻烦都安顿了：数据建模、用户、权限、并发、慢查询、缓存、重活。下一篇进入最不能出错的一块：钱。用户点订阅按钮，手抖点了两下；支付平台回调你的接口，网络超时又重发了三次——在「至少执行一次」的现实世界里，怎么保证用户只被扣一次钱？这个性质叫幂等，它值得单独一篇。
