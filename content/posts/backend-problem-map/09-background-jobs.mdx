「导出全部笔记为 PDF」是用户投票投出来的功能，你花一个周末写完了：接口收到请求，循环渲染五百篇笔记，打包 zip，返回下载链接。上线十分钟，客服工单来了：导出的人卡在转圈，没导出的人更惨——打开首页要 12 秒。

原因很快定位到：你的 API 进程是 Node 的，一个 CPU 核渲染 PDF 时忙到满格，排在它后面的所有请求全部排队。一个用户触发的重活，惩罚了所有用户。而且这活天生干不长：代理服务器默认 60 秒超时，五百篇的导出在第 61 秒连接断开，前功尽弃，用户只看到失败。

## 分界线：用户在等这个结果吗

判断一件活该不该当场干，就一个问题：**用户的下一步操作依赖这个结果吗？**

登录要等——不拿到 token，之后的请求都发不了。保存笔记要等——用户需要确认「存上了」才敢关窗口。但导出 PDF 不用等，用户完全接受「先去干别的，弄好了通知我」；发验证邮件、清理过期数据、生成缩略图、月底给订阅用户出账单，全都属于此类。这类活的共同点：**用户等的是「承诺」，不是「结果」**。

所以正确的交互是异步的：接口收下请求，回一句「任务已创建，预计 2 分钟」，把活交给别人慢慢干。这套结构里有三个角色：活本身怎么表示（job）、活在哪排队（队列）、谁来干活（worker）。一个一个说。

## Job：把一件活写成一条数据

「后台任务」这个词听起来像一门新技术，落到底就是数据库里的一行记录。行里写清三件事：干什么、拿什么参数干、干到哪一步了：

```sql
CREATE TABLE jobs (
  id         BIGSERIAL PRIMARY KEY,
  type       TEXT NOT NULL,                   -- 'export_pdf'：干什么
  payload    JSONB NOT NULL,                  -- {"userId": "usr_2q8v"}：拿什么参数
  status     TEXT NOT NULL DEFAULT 'pending', -- pending/running/done/failed：干到哪步
  run_at     TIMESTAMPTZ NOT NULL DEFAULT now(),  -- 最早什么时候可以干（定时任务靠它）
  attempts   INT NOT NULL DEFAULT 0,          -- 已经试了几次
  locked_by  TEXT,                            -- 哪个 worker 正在干
  locked_at  TIMESTAMPTZ,                     -- 什么时候开始干的
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

这样的一行记录就叫一个 job。拿 lee 触发的那次导出，看一个 job 的一生：

```
14:03:01  API 收到请求，INSERT 一条 job：
          type='export_pdf'，payload={userId: 'lee'}，status='pending'
14:03:01  API 返回 { taskId: 42 }，请求结束，耗时 8 毫秒

14:03:05  worker-1 认领：UPDATE status='running', locked_by='worker-1'
14:03:05  worker-1 开始渲染 PDF（慢，要 4 分钟）
14:07:12  渲染完，上传 zip，UPDATE status='done'，把下载地址写进去
14:07:30  lee 轮询发现 done，拿到下载链接
```

四个状态连起来就是全部：pending 排队等领，running 正在干，done 干完了， failed 干砸了。API 只干第一行的事（写入加返回），后面全是 worker 的事。

## 队列：活排队的地方，一张表就是

队列这个名词没有任何神秘成分：**队列就是活排队等待的地方**。API 把活写进表，叫入队；worker 从表里取出活，叫出队；先写入的先被取出，先进先出，跟食堂排队的道理一样。上面那张 jobs 表，就是队列的最小形态，不需要安装任何中间件。

为什么活不能放在 API 进程的内存里排队？进程一重启，内存里的队列整个消失，排队中的活全没了，用户那边永远转圈。放在表里，进程的死活和活无关：API 重启，活还在表里；worker 挂了，活还在表里，换一个 worker 照样能领。

用数据库当队列还有两个红利，后面会兑现。一是任务记录和业务数据在同一个库，可以塞进同一个事务——下一篇讲支付时这个性质价值千金。二是任务表本身就是运维后台：线上积压了多少活、卡在哪一条、失败原因是什么，一条 SQL 全看得见，不用给队列单独搭监控。

这不是我发明的省钱技巧。PostgreSQL 生态的任务库 pg-boss 内部就是这么一张表；Node 生态的 BullMQ 则把队列放在 Redis 里，更快，代价是多运维一个 Redis，任务数据也不在数据库里。单体阶段用数据库当队列是最优解而不是将就，什么时候它不够用，结尾说。

## Worker：另一个进程，死循环领活

worker 不是什么特殊软件，就是你的同一份代码、另一个入口。API 的入口是「监听端口，等请求」；worker 的入口是一个不退出的循环：

```ts
while (true) {
  const job = claimNextJob(); // 从表里认领一条 pending（下节展开）
  if (!job) {
    await sleep(1000);
    continue;
  } // 没活，睡一秒再看
  try {
    await run(job.type, job.payload); // 真正干活：渲染 PDF、发邮件
    await markDone(job);
  } catch (e) {
    await markFailedOrRetry(job); // 失败怎么办，后面单独说
  }
}
```

部署上它们是两个独立进程，可以不在一台机器上：API 两台扛请求，worker 一台专心干活。导出的人多了，加 worker；看笔记的人多了，加 API。两边互不拖累：worker 挂了，API 照常收请求，活堆在表里排队等 worker 恢复；API 重启，正在渲染的 worker 察觉不到。

开头那个 60 秒超时，也在这里消失了。超时是 HTTP 请求的规矩，约束的是「用户等多久」。现在用户只等 8 毫秒的「任务已创建」；worker 自己跑 4 分钟、40 分钟都行，没有连接会断。

## 两台 worker 抢同一个 job：分布式锁

现在到这类系统最经典的一个问题。你部署了两台 worker（一台挂了另一台还在，这是对的），某天它们同一秒去表里领活。如果领活只是普通的一句 SELECT，会发生这个：

```
worker-1：SELECT → 查到 job 42（pending）→ 开始渲染
worker-2：SELECT → 也查到 job 42（还是 pending）→ 也开始渲染
```

同一个导出跑两遍，lee 收到两封「导出完成」的邮件，五百篇的活白干一倍。问题出在「查到」和「标成 running」是两步，两步之间能插进别人。

你可能想用代码里一个变量当锁：「job 42 我占了」。不行——两台 worker 是两台机器上的两个进程，各自的内存互相看不见，worker-1 的变量 worker-2 根本读不到。**锁要生效，必须放在双方都看得见的地方**：数据库，或者 Redis。放在公共地方、给多台机器用的锁，就叫分布式锁。道理和单机锁一样：一个公共的地方，谁先占到谁干；区别只是锁的位置从「进程内存」换成了「所有机器都连得上的存储」。

数据库当队列时，这把锁是免费送的，就藏在认领那句 UPDATE 里：

```sql
UPDATE jobs SET status='running', locked_by='worker-1', locked_at=now()
WHERE id = (
  SELECT id FROM jobs
  WHERE status='pending' AND run_at <= now()
  ORDER BY id
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
RETURNING *;
```

两个词是关键。`FOR UPDATE`：选中的那行先上锁，别人动不了它（第 6 篇的悲观锁原样复用）。`SKIP LOCKED`：已经被别人锁住的行直接跳过，去拿下一条，不傻等。效果像一群人从同一摞单子里抢单：谁先在单子上写下自己的名字，单子归谁；后来的人看到有名字的单子，跳过，拿下一张。两台 worker 同时执行这句话，数据库保证 job 42 只会被其中一台改成功。不需要任何新组件，抢任务的问题一句 SQL 解决。

这套机制还顺手回答了另一个问题：worker 认领之后断电了怎么办？认领的 UPDATE 一提交，行锁就释放了——四分钟的渲染不可能一直抱着数据库锁。之后这个 job 靠 status='running' 挡住别人（认领只挑 pending）。如果 worker 死在半路，job 会卡在 running 没人管。所以表里记了 locked_at：一个 running 超过约定时长（比如 15 分钟）的 job，就认定它的 worker 死了，把它放回 pending 等别人领。这也埋下了一个伏笔：被救回来的 job 会被**再执行一遍**，哪怕上一遍已经干了一半——「至少执行一次」，重试那节接着说。

最后给分布式锁立两根柱子，将来你用 Redis 做锁（`SETNX`：设一个键，设置成功就是拿到锁，第 10 篇会用它防双击）时同样适用。**锁必须能自己过期**：拿到锁的进程可能当场断电，永远没机会释放，所以锁要挂一个几十秒的过期时间，人死了锁也会自动打开。**拿锁干活别超过锁的寿命**：活要干三分钟，锁三十秒就过期，第二台 worker 进来了，又回到两个一起干的局面。这两条是所有分布式锁踩坑记录里的前两名。

## 定时任务：run_at 写到未来的 job

前面的活都是「用户一点，立刻入队」。还有一类活没有用户触发：回收站里超过 30 天的笔记要清理，每天凌晨三点要对账，每月 1 号要出账单。这类活叫定时任务。

传统做法是用操作系统自带的 cron：服务器上的小闹钟，配置文件里写一行「每天 3:00 执行 clean.sh」，到点它就启动这个命令。cron 能用，但有两个先天短板：任务绑在那台机器上，机器挂了任务就静默消失，没人知道；它跟你的任务系统是两套东西——cron 里的失败记录、重试、监控，全要自己另搭一遍。

其实 jobs 表已经把定时任务包含了，靠的就是 run_at 那一列。worker 领活的条件一直是 `run_at <= now()`（上面那句认领 SQL 里就带着）：把清理任务的 run_at 写成今天凌晨三点，三点之前它不满足条件，等于还在排队；三点一过，它就是一条可以被领走的活。到点要跑的活，和用户触发的活，从此是同一套东西：同一张表、同一套重试、同一个运维后台。不要 cron。

只剩一个问题：这条「凌晨三点」的任务是谁插进去的？可以让 API 进程里挂一个每分钟跳一次的小闹钟，到点前插入。但两台 API 机器上的闹钟会在同一分钟各插一条——凌晨三点的清理跑两遍。解法第 6 篇见过：唯一约束。给 jobs 加一列 dedupe_key，清理任务每天填 `cleanup-2026-10-16` 这样的值，在 dedupe_key 上建唯一约束，插入用 `ON CONFLICT DO NOTHING`——第二台机器插同样的 key，被数据库直接忽略。「只此一份」的逻辑交给唯一约束，别用「先查再插」，这是老朋友了。要么就用上一节那把分布式锁：到点谁抢到锁谁插入，结果一样。

## 失败怎么办：重试、超时、幂等

任务系统剩下的坑，集中在「失败」这一个词上，三条规则全是行业默认值。

**失败要重试，重试要隔开。** 任务失败是常态：第三方邮件服务抖一下，用户数据正好在迁移。自动重试是标配，但别立即重试——刚失败马上再来，大概率再失败，还把下游按在地上摩擦。退避（backoff）：第一次失败 1 分钟后再试，第二次 5 分钟，第三次 30 分钟，给下游恢复的时间。attempts 列就是记这个的。重试要有上限，比如 5 次，超了就写 failed 停下来等人看，别让一个死循环任务把 worker 永远占住。

**执行要设超时。** 每个任务定一个时限，比如 10 分钟，到点没干完就算失败走重试。这条防的是卡死的任务，不是慢任务。

**重试的前提是任务幂等。** 任务系统的默认承诺是「至少执行一次」：worker 干到一半崩了，job 被放回 pending，会从头再执行；退避重试更是故意的再执行。这意味着同一个任务跑两次，结果必须和跑一次相同，这个性质叫幂等。渲染 PDF 天然幂等——输出覆盖同一个文件，跑几遍都一样。发邮件不幂等（用户收到两封），扣积分不幂等（加两次）。非幂等的活要么改成幂等（先查「这个任务的奖励发过没有」，发过就跳过），要么挪到能保证恰好执行一次的地方——第 10 篇整篇都在讲这件事，钱的事那里见。

## 什么时候才轮到 RabbitMQ 和 Kafka

到这里队列全在一张表上。两种情况会让它不够用。一是量级：任务每秒几千上万条，这张表从「够用的排队处」变成大家都在挤的热点，写入和认领互相拖累。二是关系：任务的产生者和消费者是不同的服务——订单服务发「订单已创建」，库存、积分、通知三个服务都要订阅，这种一对多的广播用一张共享表表达就很别扭。

到那时再换 RabbitMQ（消息代理，路由灵活）或 Kafka（严格说是分布式日志，为超高吞吐和回放设计）。换的动作不难：入队出队从 SQL 换成调它的客户端，而你养成的任务模型——幂等、重试、退避、监控——全部原样带走。所以先用数据库，什么也不亏。反过来，任务每秒几十条、产生者和消费者都在你这个单体里，就别上消息中间件，纯属给运维加作业。

## 结尾

这篇把五个名词落了地：job 是写成一行数据的活，status 记录它干到哪步；队列是活排队的地方，单体阶段一张数据库表就是它，pg-boss 或 BullMQ 拿来即用；worker 是死循环领活的另一个进程，和 API 分开部署、分开扩容；分布式锁是放在数据库或 Redis 里、所有机器都看得见的锁，认领那句 `FOR UPDATE SKIP LOCKED` 就是它；定时任务是 run_at 写到未来的 job，多实例下用唯一约束或锁防住跑两遍。工程三条：重试配退避、执行设超时、任务做幂等。

到目前为止，ClipNote 的每类麻烦都安顿了：数据建模、用户、权限、并发、慢查询、缓存、重活。下一篇进入最不能出错的一块：钱。用户点订阅按钮，手抖点了两下；支付平台回调你的接口，网络超时又重发了三次——在「至少执行一次」的现实世界里，怎么保证用户只被扣一次钱？这个性质叫幂等，它值得单独一篇。
