你写过一个叫 ClipNote 的剪藏应用。Electron 壳，里面是熟悉的 React，笔记全存在本地一个 SQLite 文件里。两年了，它运行稳定，用户不多但都是真用户。

某天早上你收到一封邮件：

> 你好，我在公司和家里两台电脑上都装了 ClipNote，笔记能不能同步？手动导出导入太痛苦了，我愿意付费。

你回了个「马上」，然后坐下来想了十分钟，意识到这件事比听起来大：同步意味着要有一台自己的服务器、要管用户的账号密码、要处理两台设备同时改一条笔记的情况。这些事你一个都没做过。

奇怪的是，你并不是不会写服务端代码。Express 起个服务、写个接口、查个数据库，这些都干过。但让你从零做一个「真的有人依赖」的后端，你就是心里没底。

这份没底是准的。后端和前端的差异不在语法，你早就会一门够用的语言了。差异在三件更根本的事上。这篇先把它们讲清楚，再给出整个系列要走的地图。

## 差异一：你的数据要活很多年

前端的状态活在内存里，刷新就重置。最大的事故不过是一个用户看到白屏，刷新好了，数据还在 localStorage 里。就算 localStorage 被你写坏了，坏的也只是一个用户，道歉、发版，事情就过去了。

后端没有刷新这个按钮。数据写进数据库，就要做好活五年的准备。你的代码可以重写、下线、换语言，数据不行，它得一直在。

「活五年」听着抽象，拆开是几个很具体的问题：

- 你两个月前给 notes 表加了个字段，今天想改名。本地 SQLite 随手就改了，坏也坏不了几个用户。云上的数据库里有 40 万条别人的笔记，改错一次，伤害全部用户，而且没有 Ctrl+Z。
- 服务器磁盘坏了，用户的笔记要不要跟着没了？备份说着简单，怎么做、多久做一次、怎么验证备份真的能恢复，全是问题。
- 用户删了一条笔记，三天后反悔了。你是真的 DELETE 了，还是留了个标记以后还能捞回来？

这些问题的共同点是：**错误不可逆**。前端的 bug 修了就消失，数据的事故会跟着你很多年。写后端的人那种小心翼翼，就是被这件事训练出来的。

这组问题的解法在[第 3 篇](/posts/backend-problem-map/03-data-modeling)：数据建模、迁移和软删除。

## 差异二：没有「此刻」，所有人同时在写

写前端的时候，你的心智模型是：程序属于当前这一个用户。状态是这个用户的，操作也是，哪怕手速再快，事件也是排队进来的，一个处理完才轮到下一个。JavaScript 单线程替你挡掉了几乎所有并发问题。

后端没有这层保护。同一秒里，可能有 400 个请求在跑你的代码，读同一批表，写同一批数据。你的代码不再属于某一个人。

感受一个场景：ClipNote 上线了共享笔记功能。张三在公司电脑上改那条「晋升述职提纲」，同一时刻同事李四也在改同一条，两人先后点了保存。留下谁的版本？

后到的那个人覆盖先到的。先保存的人再打开笔记，发现自己写的三段话没了。这个事故有个正式名字，叫**丢失更新**（lost update），是后端世界里最经典的一类问题。

更麻烦的是，你顺手就能写出这种 bug。前端最自然的写法是「先查出来，改一改，再存回去」：

```ts
const note = await db.notes.findById(noteId); // 查出来
note.title = "晋升述职提纲 v2"; // 改一改
await db.notes.save(note); // 存回去
```

单用户下这段代码没有任何问题。但两个请求同时跑到第一行，各自拿到旧版本，各自改各自的，后存的覆盖先存的。你甚至很难在测试里复现，因为它要求两个请求恰好「同时」。

事务、锁、隔离级别——解决这类问题的整套工具，在[第 6 篇](/posts/backend-problem-map/06-concurrency-transactions)。

## 差异三：客户端的一切都不可信

这条最反直觉，因为它是世界观级别的转变。

前端世界里，你写的代码就是规则。你校验了邮箱格式，不合法的表单就提交不上去。

后端世界里，你的接口暴露在公网上，每个到达的请求都可能不是你的前端发出的。可能是用户按了 F12 改过参数的请求，也可能是别人用 curl 直接伪造的请求。

所以前端做的所有校验，后端都要再做一遍。前端的校验是体验，让用户早点知道哪里填错了；后端的校验才是安全。而且后端要多校验一件前端从来不用关心的事：**这条数据属于当前这个用户吗？**

一个真实的坑长这样：

```
GET /api/notes/8823
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...（张三的合法 token）
```

张三登录着，token 是真的，请求完全合法。但 8823 这条笔记属于李四，是他的私人日记。如果你的接口只检查了「登录没有」，没检查「这条笔记是不是张三的」，那张三只要把 id 换成 8824、8825，一路递增下去，就能把全站用户的笔记拉一遍。

这个漏洞叫**越权**，在真实世界的漏洞统计里常年排前几名，但教程几乎不讲它。因为它不是一个技术点，是一个要在每个接口里都想一遍的习惯，漏一个接口就全暴露。

认证（你是谁）在[第 4 篇](/posts/backend-problem-map/04-auth)，授权（你能动谁的数据）在[第 5 篇](/posts/backend-problem-map/05-authorization)，一份上线前的安全自查清单在[第 12 篇](/posts/backend-problem-map/12-security-checklist)。

## 一张按「撞墙顺序」排的地图

三个差异展开，就是后端开发会遇到的大部分问题。这个系列按你真正撞墙的顺序来讲，每篇解决一堵墙：

```
阶段一：让同步跑起来
  02  第一个 API 怎么设计（REST / GraphQL / tRPC，错误格式，分页）
  03  数据放哪、表怎么建（为什么默认一个 Postgres 就够）

阶段二：用户来了
  04  注册登录（密码为什么不能明文存，Session 和 JWT 选谁）
  05  谁能动谁的数据（越权，最容易写出来的漏洞）

阶段三：数据和用户都多起来
  06  两个人同时编辑（事务、锁、丢失更新）
  07  列表页越来越慢（索引、N+1、什么时候才要分库分表）
  08  数据库扛不住读（缓存加在哪、怎么失效）

阶段四：功能变重
  09  不用当场干的活（后台任务、队列）
  10  用户点了两次支付（幂等、重试、回调）
  11  图片和附件（对象存储、CDN）
  12  上线前的安全清单

阶段五：体验和判断力
  13  多设备实时同步（WebSocket、SSE、冲突处理）
  14  出事了怎么查（日志、request id、指标）
  15  什么时候才需要微服务（把分布式放回工具箱）

16  收官：下一个项目从 0 到上线怎么选
```

你可能注意到清单里没有 Spring Cloud，没有消息中间件选型，没有 K8s。这是刻意的。这个系列讲的是**单体应用**会遇到的问题：一个人或一个小团队，把一个产品从前端一直写到数据库。绝大多数产品和绝大多数团队，一辈子都在这个范围里。微服务那套东西什么时候才真的需要，[第 15 篇](/posts/backend-problem-map/15-when-microservices)专门回答，答案可能比你想的晚很多。

部署、容器化、监控告警是另一个世界，博客的[部署基础设施地图](/posts/infra-map/01-from-code-to-online)系列已经讲得很完整，本系列走到需要的地方会直接指过去。

## 这个系列怎么用

写这个系列的目的不是让你读完就会，是让你**知道有什么问题、解法叫什么名字**。后端知识点浩如烟海，但常用问题的名字就几十个。知道名字之后，遇到问题时的路径就从「不知道自己不知道什么」变成「查一下这个关键词」。这大概是 AI 辅助编程的时代里性价比最高的一种知识：你负责知道该问什么，AI 负责补齐怎么做。

每篇讲清楚四件事：这个问题发生时是什么感觉（一个真实场景）、成熟的解法家族有哪些、选型时怎么权衡、什么时候它纯属过度设计。代码只作示意，概念不绑定语言，示例用 TypeScript 和 SQL，因为读这个系列的你最熟这两样。

下一篇就开工。同步功能的第一步，是把「拉取上次同步以来的变更笔记」这个接口设计出来。你会看到，光是「一个接口长什么样」这件事，值得想清楚的地方就比想象中多。
