笔记量涨起来之后，性能问题自己找上了门。

lee 是个重度用户，攒了两年，两万条笔记，列表接口一直 80 毫秒上下，体感良好。某个周一，他的接口 P99 到了 8 秒，工单附了张录屏：转圈，白屏，再转圈。你没有改过一行代码——变的是数据量，和数据库面对同样代码时做的完全不同的事。

这篇讲四件事：怎么定位慢在哪、索引为什么是第一嫌疑人、ORM 藏着的 N+1 坑、以及那个所有人都听过的词「分库分表」到底离你多远。

## 先看数据库自己怎么说：EXPLAIN

猜是猜不出慢查询原因的，数据库会亲手告诉你。任何 SQL 前面加个 `EXPLAIN ANALYZE`（真的执行一遍并给实测数据），返回的是**查询计划**：数据库打算怎么找数据、实际怎么找的、每一步扫了多少行、花了多久。

```sql
EXPLAIN ANALYZE
SELECT * FROM notes
WHERE user_id = 'usr_2q8v7n' AND deleted_at IS NULL
ORDER BY updated_at DESC
LIMIT 50;
```

lee 那个慢查询的计划长这样（节选）：

```
Sort  (cost=... rows=41203)  (actual time=7812.4 .. 8104.9)
  ->  Seq Scan on notes  (actual rows=41203 loops=1)
        Filter: (user_id = 'usr_2q8v7n' AND deleted_at IS NULL)
        Rows Removed by Filter: 958417
```

两行信息把案子破了。`Seq Scan`，全表扫描：数据库不知道数据在哪，从第一行开始一百万行挨个看。`Rows Removed by Filter: 958417`：看了一百万行，扔掉九十六万行，留下 lee 的四万条再排序。你的接口 8 秒里 7 秒在干这个。

以后看到 Seq Scan 出现在大表上，基本就可以结案了。解药是索引。

## 索引：给数据库一本目录

没有索引的表是一本没有目录的书，找一个词只能从第一页翻到最后一页。索引就是目录：B-tree 结构把某一列（或几列）的值按序组织好，查找从「逐行翻」变成「沿着树走几步」。一百万行的表，B-tree 三四层就到底，定位成本从「百万」级掉到「个位数」级——这是所有「加了索引快了一百倍」故事的共同来源。

给 lee 的查询建一个覆盖排序键的联合索引：

```sql
CREATE INDEX idx_notes_user_updated
  ON notes (user_id, updated_at DESC)
  WHERE deleted_at IS NULL;   -- 部分索引：只索引未删除的行
```

再跑 EXPLAIN，Seq Scan 变成 `Index Scan`，实际行数从九十六万变几百，耗时从 8104ms 掉到 11ms。这不是魔法，是数据库终于「知道东西在哪」了。

但索引不是建得越多越好，三个判断点。

**列的选择性要够**。索引的意义在于快速缩小范围，`deleted_at IS NULL` 这种「绝大多数行都满足」的条件单独做索引没意义——目录告诉你「在第 1 页到第 999 页」，等于没说。判断某列值不值得进索引，看它的不同取值数量占总行数的比例：邮箱、用户 id 这类近乎唯一的列是上品，状态列这种两三个值的列是下品。

**联合索引讲最左前缀**。`(user_id, updated_at)` 这个索引，能服务「按用户找」，也能服务「按用户找并按时间排」，但服务不了「只按时间找」——目录先按用户分章，跳过用户直接按时间找，目录帮不上忙。把最常用的等值条件放最左边，排序列跟在后面，这是建联合索引的基本功。

**写入要付账**。每个索引在每次 INSERT/UPDATE 上都要维护一次。一张表三五个精心设计的索引是健康态，三十个「以防万一」的索引就是写放大。同理，永远不要在生产库上直接 `CREATE INDEX` 大表（会锁写），用 `CREATE INDEX CONCURRENTLY`，这一条值一次事故的学费。

## N+1：ORM 替你写的慢查询

下一类慢查询不怪数据库，怪 ORM 替你「聪明」的次数太多。列表页每条笔记要展示标签，代码这样写：

```ts
const notes = await db.notes.findMany({ where: { userId }, take: 50 }); // 1 次
for (const note of notes) {
  note.tags = await db.noteTags.findMany({ where: { noteId: note.id } }); // 每条 1 次
}
```

跑起来功能完全正常，但数据库的日志里：第一条查询之后，跟着 50 条一模一样结构的查询。列表 50 条就 51 次往返，列表 200 条就 201 次，每次往返一两毫秒的网程开销，乘起来就是用户肉眼可见的转圈。这叫 **N+1 查询**，ORM 默认「懒加载」关联数据时的标准产物，也是「本地好好的，上了云变慢」的头号疑犯——本地数据库和代码同机，往返近乎免费；上云后每次往返都走真实的网络。

解法是把「逐个问」改成「一次问」：要么 JOIN，要么 `WHERE note_id IN (...)` 批量取回再在内存里组装。Prisma 和 Drizzle 都有关联查询的写法（各自的深入系列里都有：[Prisma 关联加载](/posts/prisma/04-relations-loading)、[Drizzle 关联与 JOIN](/posts/drizzle/04-relations-joins)）。再往前，GraphQL 的 resolver 层是 N+1 的高发区——每个字段一个解析函数，不小心就逐条触查询，那边有 DataLoader 这个专用工具批量合并，原理同样是「攒一批再问」。

发现 N+1 靠两样东西：查询日志（开发环境把 SQL 全打出来，一串结构雷同的查询会刺眼到不可能忽略），和慢查询统计。养成看日志的习惯，N+1 无所遁形。

## 两个小坑：深分页与 count(\*)

第 2 篇讲分页时说过 offset 的毛病，这里补上性能这一面：`LIMIT 50 OFFSET 500000` 的执行方式是「读 50 万零 50 行，扔掉前 50 万行」。翻得越深越慢，而且是线性变慢。Cursor 分页（拿上一页最后一条的位置做查询条件，天然利用索引）没有这个问题——产品形态允许的话，尽量 cursor。

另一个是列表页的总数展示：「共 1,204,311 条」。`SELECT COUNT(*)` 在大表上是一次全表扫描（或至少一次全索引扫描），为了页脚那个数字每次翻页都付一遍。常见做法是缓存总数、隔几分钟刷新，或者干脆用 cursor 分页后不展示总数（「加载更多」的交互本来就不需要它）。用户真的在乎那 1,204,311 吗？多数时候不在乎。

## 分库分表：先算算轮不轮得到你

写到这必须回答一个高频焦虑：单表一百万行了，要不要分库分表？

先给数字锚点：现代关系数据库单表撑到千万行级、单库撑到每秒几千次简单查询，都是正常工作范围，加上这篇的索引治理和下一篇的缓存，绝大多数产品在关停那天也没碰到这个天花板。

分库分表解决的是「一台数据库装不下 / 一台数据库扛不住写」的问题，手段是把数据按某个键（比如用户 id 哈希）拆到多个库多个表。代价是一次性买断：跨分片的查询和 JOIN 变得别扭，跨分片的事务要引入分布式事务（第 15 篇会专门泼冷水），「按订单号查」和「按用户查」要同时支持就得异构两份数据。这是一条单行道，上去就下不来。

正确的性能路径是逐级上锁：先治理查询和索引（本篇），再上缓存扛读（下一篇），再考虑读写分离（读流量分给只读副本），分库分表是最后一块多米诺，而且多半永远轮不到它倒下。面试里背的分库分表答案，工作中大概率只用来回答面试。

## 结尾

这篇的操作清单：慢了先 `EXPLAIN ANALYZE`，别猜；Seq Scan 在大表上等于索引缺失；建索引看选择性、记最左前缀、用 CONCURRENTLY；警惕 ORM 的懒加载，开发环境开着 SQL 日志抓 N+1；深分页换 cursor，大表的 COUNT 缓存或者不展示；分库分表在你单表过千万、且索引和缓存都做过之前，一律视为过早优化。

读的路径治理完，剩下一种数据库压力它治不了：同一份热门数据被高频率反复读——比如那几条被全站订阅的模板笔记，每秒被拉几百次，每一次都命中数据库。索引再快也架不住「同样的查询」本身次数太多。这种重复劳动的解法是把答案抄在旁边，这就是下一篇：缓存。
