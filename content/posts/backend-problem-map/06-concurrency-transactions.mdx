共享笔记功能上线第一天，客服工单来了。

lee 说，他编辑那条「团队 OKR」写了三段目标，保存成功，十分钟后再打开，三段全没了，只剩下同事写的另外几行。数据库里，他的版本确实存在过——在另一个请求把它覆盖掉之前的四十七秒里。

第 1 篇预告过这个事故，名字叫丢失更新。这篇把它拆到机制层面，然后给出两套解法。搞懂这一篇，后端并发问题的大头就通了，因为后端的并发麻烦，十有六七是「读-改-写」撞上「同时」。

## 为什么「先查再改再存」必错

出事的代码就是第 1 篇贴过的那段，这次把两个请求的执行时序摆开看。假设数据库里那条笔记当前版本号是 v5，lee 和同事几乎同时点保存：

```
时刻    lee 的请求                 同事的请求
t1     读出笔记（v5）
t2                                 读出笔记（v5）
t3     基于旧内容写入（v6-lee）
t4                                 基于旧内容写入（v6-同事）← 覆盖了 lee
```

两个请求各自看代码都没错：读、改、写，三步清清楚楚。问题在三步**不是原子的**。在 t2 到 t4 之间，数据库里躺的还是 lee 以为的那个 v5，他从读到的写入，中间世界已经变了。单用户时代不会出事，是因为「同时」不存在；多用户之后，「同时」是常态。

更气人的是它极难复现。你本地起服务，开两个浏览器模仿两个用户，手速再快也很难让两个请求恰好卡进同一个窗口。事故工单里写着「必现」，你复现一晚上一无所获——因为让两个请求在毫秒级窗口里相遇，概率本来就低，架不住每天几万次保存。

## 事务：它救的场景和它不救的场景

很多前端转后端的人第一个想到的武器是事务（transaction），然后困惑地发现：包了事务，丢失更新还在。

事务救的是另一类问题。经典例子是转账：扣你账户 100 元和给对方账户加 100 元，必须都成功或都失败，只成功一半就是钱凭空消失或凭空出现。事务把一组操作捆成一个「要么全做、要么全不做」的单元——中途任何一步失败，已做的全部回滚，像没发生过。笔记场景里也有它的用武之地：「删除笔记」要同时删 notes 行、删 note_tags 关联、往变更列表里写一条 tombstone（第 3 篇埋的词），这三步就该是一个事务，删一半停下来，数据就处于说不清的状态。

但事务不自动解决「两个事务写同一行」。数据库默认的隔离级别下，两个事务各自读旧值、先后写入，后提交的照样覆盖先提交的。**事务保一致性，不自动保并发冲突**——把这两件事混为一谈，是并发理解上最常见的一口锅。真正对付丢失更新，要下面两把锁。

## 悲观锁：先把门锁上

第一把锁的思路直白：改之前先把这行数据锁住，别人等着。

```sql
BEGIN;
SELECT * FROM notes WHERE id = 'note_7f3k9' FOR UPDATE;  -- 锁住这行
-- 应用层：基于刚读到的最新内容做合并或修改
UPDATE notes SET content = $1, version = version + 1 WHERE id = 'note_7f3k9';
COMMIT;  -- 锁释放
```

`FOR UPDATE` 是关键：读的同时声明「我要改它」，数据库给这行上锁。后到的同事事务跑到同一句 SELECT 时被挡住，挂起等待，直到 lee 的事务提交、锁释放，他才读得到 lee 写入后的新内容。丢失更新的窗口被彻底焊死——因为「读」这个动作本身就排队了。

代价也直白：等待。冲突频繁、每个请求都等，吞吐量往下掉；更糟的是两个事务以相反顺序锁两行，互相等对方，谁也走不了（死锁，数据库会检测到并牺牲一个，但你的接口表现为随机报错）。悲观锁适合的场景：冲突率高、临界区短。秒杀扣库存是教科书案例——成千上万人抢同一行库存，冲突必然发生，与其人人重试，不如排队。

## 乐观锁：先办事，提交时对账

第二把锁假设冲突很少见：不锁，放手去做，提交时检查「我读的时候看到的版本，是不是还是现在的版本」。

第 3 篇建表时没写这列，现在补上：notes 加一列 `version INTEGER`，每次更新 +1。写入变成：

```sql
UPDATE notes
SET content = $1, version = version + 1, updated_at = now()
WHERE id = 'note_7f3k9' AND version = 5;   -- 5 是 lee 读到时的版本号
```

数据库返回受影响的行数。等于 1，说明从读到写之间没人动过，成功。等于 0，说明有人抢先写入、版本已经变成 6 了——lee 的更新作废，服务端返回 409 Conflict（第 2 篇错误清单里留的那个状态码，在这里兑现）。接下来怎么办是业务决策：自动重试（重新读、重新应用修改、再提交），或者干脆把冲突抛给前端：「这条笔记刚被别人改过，刷新后合并你们的修改」。

对笔记编辑这个场景，409 抛给前端是对的。两个方向的重写各有道理，自动合并文本几乎必然产出用户看不懂的缝合怪；让用户看一眼两边的改动再决定，反而是最体面的产品行为。顺带一提，现代协作编辑器（飞书文档、Notion）做到了自动合并不冲突，靠的是比乐观锁复杂得多的冲突算法（OT / CRDT），第 13 篇讲多端同步时会再见到它们的名字。

乐观锁适合冲突稀少的场景，绝大多数业务数据其实都是：同一条笔记同时被两个人编辑，本来就是小概率事件，为小概率冲突让所有请求排队（悲观锁）不划算。判断标准一句话：**冲突大概率发生，用悲观锁排队；冲突小概率发生，用乐观锁加对账**。

## 隔离级别：一段话版本

数据库教科书里最劝退的一节，实际有用的浓缩版如下。隔离级别是数据库对「多个事务互相能看见多少」的四个档位。最低档会脏读：读到别人还没提交、可能回滚的数据（等于读到从未存在过的世界）。第二档（PostgreSQL 和 MySQL 的默认档）防住脏读，但同一个事务里两次读同一行可能结果不同（别人提交了修改）。第三档再加防，但挡不住同一查询两次跑出行数不同（别人插入了新行，即幻读）。最高档 Serializable 完全隔离，代价是并发性能明显下降，冲突时还会报错要求重试。

实务建议：留在默认档，用乐观锁的 version 列或 `FOR UPDATE` 显式保护「读-改-写」的关键路径。调隔离级别是全局开关，影响所有查询还看不见；代码里的版本号检查是局部的、可读的、可测试的。数据库自带的全局方案（比如 PostgreSQL 的可序列化快照隔离）在特定场景很优秀，但那是你已经踩过并发坑之后的事。

## 别忘了数据库之外还有一层

还有一种丢失更新不发生在行内，发生在「本该只创建一次的东西」上。ClipNote 的注册流程：用户快速点了两次「创建默认空间」，两个请求同时查「该用户有没有空间」，都查到没有，都创建——两个默认空间。行级锁救不了它，因为两个事务锁的是不同的新行。

解法第 3 篇其实写过：`UNIQUE (user_id)` 约束往 spaces 表上一拍，第二个插入直接被数据库拒绝，应用层捕获唯一冲突，改读已有的那个。**约束是并发下最便宜也最可靠的防线**，能用唯一约束挡住的「只此一份」逻辑，都别用「先查再插」去实现。

## 结尾

这篇的选型收拢：多步写操作用事务包裹，但别指望它自动处理并发；「读-改-写」的关键路径，冲突频繁用 `FOR UPDATE` 排队，冲突稀少用 version 列对账，冲突了返回 409 让业务决定重试还是问用户；「只此一份」的逻辑交给唯一约束；隔离级别保持默认，别碰。

写并发的坑填上了，下一个来找麻烦的是读。lee 的笔记攒到两万条之后，列表接口从 80 毫秒爬到了 8 秒，而代码一行没改过。数据量涨了，查询计划变了——下一篇讲慢查询怎么定位、索引怎么建、以及为什么你听说的「分库分表」多半还轮不到你操心。
