# 后端问题地图：前端转全栈会撞到的墙 系列计划

## 背景

- 为什么写这个主题：作者是前端开发，有 Electron 经验，想往后端扩展能力。目标不是精通某门语言，而是建立「后端会遇到什么问题 → 有哪些成熟解法 → 什么时候需要、什么时候不需要」的路由能力。博客已有的语言深潜系列（springboot、golang、nodejs-core）回答「怎么写」，本系列回答「会遇到什么、该选什么」。
- 核心话题：API 设计、数据建模、认证与权限、并发与事务、慢查询与索引、缓存、后台任务与队列、幂等与可靠性、对象存储、安全、实时同步、可观测、架构边界（单体 vs 微服务）、技术选型
- 文章类型：A（技术类），地图型系列——重问题与选型，轻实现细节，代码只作示意。语言中立：概念不绑定语言，示例用 TypeScript/SQL（读者前端出身，TS 是母语）
- 视角约束：**单体视角**。讲一个人/小团队把一个产品从前端写到数据库会遇到的问题，不讲大流量分布式架构。分布式话题（微服务、分布式事务、MQ 全家桶）只在第 15 篇以「什么时候才需要」收口

## 贯穿案例：ClipNote 的后端化

读者写了一个本地优先的剪藏笔记应用 ClipNote（Electron + SQLite），一直运行良好。用户开始提需求：多设备同步、团队共享、附件图片、订阅付费——本地存储撑不住，需要一个真正的后端。每篇文章对应一次「被迫加后端能力」的时刻：

```
阶段 0：本地应用，数据全在 SQLite（01 回顾）
阶段 1：做多端同步 → 第一个 API + 云端数据库（02-03）
阶段 2：多用户来了 → 注册登录、权限归属（04-05）
阶段 3：协作与数据量 → 并发冲突、慢查询、缓存（06-08）
阶段 4：功能变重 → 后台任务、支付回调、附件、安全加固（09-12）
阶段 5：体验与运维 → 实时同步、排障、架构边界（13-15）
收官：下一个项目从 0 到上线的选型决策（16）
```

## 每篇文章大纲

### 01 后端到底难在哪：和前端的三个根本差异

- 核心问题：「我会写 Node 脚本，为什么写后端还是心里没底？后端的知识到底多在哪？」
- 主线场景：ClipNote 用户发来邮件：换了台电脑笔记没了，能不能同步？你打开本地 SQLite 文件，意识到要开始一段全新的旅程
- 内容要点：三个根本差异——持久状态（页面刷新即重置 vs 数据要活很多年）、并发（单用户 vs 成百上千人同时写）、信任边界（前端代码跑在用户手里，天然不可信）；一张全系列问题地图；每个问题都配「成熟解法家族」的名字，本系列只建立索引不深入实现
- 与前篇关联：系列开篇

### 02 第一个后端服务：API 怎么设计才不返工

- 核心问题：「同步接口怎么设计？为什么有的 API 用起来舒服，有的改三个版本还是别扭？」
- 主线场景：ClipNote 的第一个接口：拉取某设备上次同步后的变更笔记
- 内容要点：资源建模（笔记是资源、同步是资源还是动作）；URL 设计与 HTTP 动词语义；错误响应的统一格式（错误码、可读信息、request id）；分页（offset vs cursor，数据量大了为什么 cursor 赢）；版本化什么时候需要；REST vs GraphQL vs tRPC 怎么选（前端人熟悉的对照：tRPC 全家桶的舒适区在哪、边界在哪）；鉴权放中间件还是每个 handler
- 与前篇关联：01 的「信任边界」落到第一个具体决策

### 03 数据放哪、怎么建模：为什么默认是一个 Postgres

- 核心问题：「MongoDB/MySQL/Postgres 怎么选？表怎么设计才算对？」
- 主线场景：把 ClipNote 的本地 SQLite 表搬到云端，顺便发现本地随便存的 JSON 字段在多用户下会失控
- 内容要点：为什么 90% 的场景一个 Postgres 覆盖（关系、约束、JSON、全文搜索都有）；表设计的核心是关系和归属（谁的数据、能不能删）；外键与约束是把业务规则交给数据库；迁移（migration）为什么不能手动改表；软删除（deletedAt）的取舍；NoSQL 什么时候才真的需要（几乎从不在起步期）；ORM 用不用（Drizzle/Prisma 一句话定位，深入互链）
- 与前篇关联：02 定义的 Note/Tag 资源落到表结构

### 04 用户系统：密码不能明文存

- 核心问题：「注册登录到底涉及什么？JWT 到该不该存 localStorage？」
- 主线场景：ClipNote 要支持多用户了，第一个用户注册
- 内容要点：密码存储——哈希不是加密，bcrypt/argon2 为什么慢反而对；Session vs JWT 的真实差异（可撤销性、存储位置、CSRF 关系）；OAuth2「用 Google 登录」到底发生了什么；邮件验证与密码找回的流程和坑（找回链接一次性、时效）；token 泄露了怎么办
- 与前篇关联：03 的 User 表第一次真实使用

### 05 权限：最容易写出的漏洞是能改别人的数据

- 核心问题：「接口加了登录校验就安全了吗？」
- 主线场景：用户 A 猜到用户 B 的笔记 id，直接 GET /notes/8823 把 B 的私人笔记拉出来了——越权，OWASP 排名靠前但教程最少讲
- 内容要点：认证（你是谁）vs 授权（你能干什么）；水平越权 vs 垂直越权；归属检查（这条数据是不是当前用户的）要写在哪一层；RBAC/ABAC 一句话定位；管理后台的权限隔离；为什么这是「最容易写出的漏洞」——每个接口都要想一遍，漏一个就全暴露
- 与前篇关联：04 解决了「你是谁」，本篇解决「你能干什么」

### 06 两个人同时编辑一条笔记：并发、事务与锁

- 核心问题：「后端最难的问题为什么是并发？两个人同时保存，谁的版本留下？」
- 主线场景：ClipNote 加了团队共享，两个人同时打开同一条笔记编辑保存
- 内容要点：丢失更新问题（后写的覆盖先写的）；事务是什么、保什么不保什么；乐观锁（版本号，冲突了让用户决定）vs 悲观锁（先锁住别人等着）；隔离级别一段话讲透（脏读/不可重复读/幻读，业务上真正要防哪个）；「select 再 update」这个前端最顺手的写法为什么在并发下必错
- 与前篇关联：05 的共享功能直接制造了本篇的冲突场景

### 07 数据涨到一百万条：慢查询、索引与 N+1

- 核心问题：「本地秒开的列表页，上了云为什么转圈十秒？」
- 主线场景：某个重度用户的笔记列表接口 P99 到了 8 秒
- 内容要点：慢的第一原因是没有索引（B-tree 一句话原理：书的目录）；怎么定位慢查询（EXPLAIN，数据库自己告诉你它在扫全表）；索引不是越多越好（写入代价、选择性）；N+1 查询——ORM 里最经典的坑；深分页为什么慢；count(\*) 的大表陷阱；分库分表什么时候才需要（基本不用，先索引、再缓存、再读写分离）
- 与前篇关联：06 讲写并发，本篇讲读性能，同一个数据库的两面

### 08 数据库扛不住读：缓存加在哪、怎么失效

- 核心问题：「都说加缓存，到底加在哪一层、什么时候加？」
- 主线场景：热门模板笔记被频繁拉取，数据库 CPU 报警
- 内容要点：先问「真的需要缓存吗」——多数性能问题索引就能解决；Cache-Aside 模式（读时填充、写时失效）；缓存三大事故——穿透（查不存在的）、击穿（热 key 过期瞬间）、雪崩（同时过期），各自的成熟解法；缓存与数据库一致性的取舍（先更新库还是先删缓存）；本地缓存 vs Redis（深入互链 redis 系列）；「缓存是性能补丁，不是架构」
- 与前篇关联：07 解决不了的读压力，才是缓存的入场券

### 09 不用当场干的活：后台任务与队列

- 核心问题：「导出 500 篇笔记的 PDF，接口要不要等它做完再返回？」
- 主线场景：ClipNote 上线「导出全部笔记为 PDF」，第一个导出请求把 API 服务拖死了
- 内容要点：同步处理 vs 异步任务的分界（用户要立刻看到吗）；任务队列的基本形态（塞进队列 → worker 取出执行 → 记录状态）；轻量方案先行（数据库表当队列、pg-boss/BullMQ）；定时任务（清理、对账）；失败重试与退避；什么时候才需要 RabbitMQ/Kafka（基本不需要——量级到了再换，队列语义没变）；顺带讲清 MQ 的三大用途在单体内怎么替代
- 与前篇关联：07/08 讲请求内的事，本篇讲请求外的事

### 10 用户点了两次订阅：幂等、重试与回调

- 核心问题：「为什么支付平台的文档反复强调幂等？网络超时了到底成没成功？」
- 主线场景：ClipNote 上线 Pro 订阅，用户双击支付按钮被扣了两次款——客服工单来了
- 内容要点：幂等是什么（同一个操作做一次和做多次结果一样）；幂等键（客户端生成唯一 id，服务端去重）；为什么重试是必然的（网络不可靠，超时≠失败）；支付回调 webhook 的正确处理（验签、先落库再处理、按事件 id 去重）；本地消息表（任务和业务数据同库写入，杜绝「扣了钱没发货」）；分布式锁一瞥（同一用户的并发请求只放一个进来）
- 与前篇关联：09 的队列在支付场景遇到重试，引出「至少一次投递 + 幂等消费」这对搭档

### 11 附件与图片：对象存储、预签名 URL 与 CDN

- 核心问题：「用户上传的图片放哪？存数据库行吗？」
- 主线场景：ClipNote 支持剪藏网页图片，第一周存储和流量账单超预期
- 内容要点：为什么文件不进数据库（大小、备份、性能）；对象存储的心智模型（无限大的 key-value，S3/OSS/R2）；预签名 URL——浏览器直传，不占后端带宽；图片处理的常见链路（压缩、多尺寸、懒加载）；CDN 是什么、什么时候值得开；流量成本怎么估（算一次账）；私有读的授权访问
- 与前篇关联：03 埋下的 Attachment 表正式启用

### 12 后端安全清单：攻击者会从哪进来

- 核心问题：「我的小应用会被盯上吗？安全到底要做到什么程度？」
- 主线场景：ClipNote 公网运行一个月后的日志里出现了扫描器痕迹
- 内容要点：会——自动扫描器不看应用大小；注入（SQL/命令，参数化查询一句话根治）；XSS/CSRF（前端人也懂，后端视角补全：CSP、SameSite）；05 的越权回顾（最高频）；限流与防刷（按 ip/用户/接口，算法一句话：令牌桶）；密钥管理（.env 不进 git、轮换、最小权限）；依赖供应链（锁版本、审查新包）；一份「上线前 20 分钟自查清单」
- 与前篇关联：把 04/05 的遗留问题收进一份可执行清单

### 13 多设备实时同步：WebSocket、SSE 与冲突

- 核心问题：「A 设备改了笔记，B 设备要刷新才知道——怎么做实时推送？」
- 主线场景：ClipNote 的同步目前靠轮询，电量子和服务器都受不了
- 内容要点：轮询 vs 长轮询 vs SSE vs WebSocket 的选型（单向推送 SSE 就够，双向才 WebSocket）；连接管理的隐藏成本（断线重连、心跳、在线状态）；水平扩展时连接落在不同机器——粘性会话或消息广播；同步协议设计（增量同步、游标、 tombstone 删除标记）；冲突解决三档——Last-Write-Wins、字段级合并、OT/CRDT 一瞥（是什么、什么时候需要，别在笔记应用里自研 CRDT）
- 与前篇关联：06 的并发冲突在多设备场景重新登场，解法从「锁」升级为「协议」

### 14 出事了怎么查：日志、request id 和指标

- 核心问题：「用户说昨晚报错了，你怎么定位？没有日志的后端是黑盒」
- 主线场景：凌晨收到用户反馈「同步失败」，你打开服务器只有一屏无关的启动日志
- 内容要点：printf 调试在生产失效；结构化日志（JSON 字段而不是拼字符串，能检索）；request id 贯穿一次请求的所有日志（02 埋的伏笔回收）；记什么不记什么（敏感信息脱敏、量）；三个黄金指标——延迟、流量、错误率（RED）；告警该alert什么（面向症状不是面向原因）；入门工具形态（日志聚合、Grafana 一句话；深入互链 infra-map 08 / devops2）
- 与前篇关联：13 的实时连接排障天然需要本篇的 request id

### 15 什么时候才需要微服务：把分布式放回工具箱

- 核心问题：「面试都在问微服务，我的单体是不是落后了？」
- 主线场景：ClipNote 团队扩到 4 个开发，有人说「我们拆微服务吧」，你算了一笔账
- 内容要点：单体优先不是保守，是默认正确（部署简单、事务本地、排障一条链）；拆分的真实代价（网络调用代替函数调用、分布式事务、链路排障、运维翻倍）；什么时候才真需要（独立扩缩、团队物理隔离、技术栈强需求）；模块化单体——用包边界获得微服务的解耦而不付分布式的钱；MQ/分布式事务/服务网格逐个「什么时候才需要」；吸收归档 backend-map 的结论：大多数团队到关门也用不上全家桶，但名词要知道（互链）
- 与前篇关联：前面 14 篇的能力全部在单体内，本篇解释为什么这是刻意的

### 16 收官：下一个项目从 0 到上线怎么选

- 核心问题：「都懂了，下一个真项目第一步怎么迈？」
- 主线场景：朋友找你做一个内部工具，你用一晚上做完选型和上线
- 内容要点：选型决策树——框架（Next.js API / Hono / NestJS / Go，按团队和场景不按流行度）；数据库默认 Postgres 何时例外；托管的三档（Vercel/Netlify 托管函数 → Fly/Railway 容器平台 → VPS 自管，成本与自由度对照，互链 infra-map 收官）；「不需要清单」——消息队列、Redis、K8s、微服务，各自注明什么规模才请进场；把 16 篇的问题地图浓缩成一页决策速查表；下一步往哪深潜（博客深潜系列索引：springboot/golang/redis/docker/devops2）
- 与前篇关联：全系列收口，从「知道有什么问题」到「知道怎么开始」

## 系列节奏规划

- 入门（01-03）：01 建立思维框架，02-03 完成「第一个服务 + 第一个数据库」，主线场景从本地应用走到云端可同步
- 核心（04-08）：五堵经典墙按「用户来了 → 用户多了 → 数据多了」的因果顺序排列，每篇的坑都是上一篇的解决方案带来的
- 进阶（09-12）：功能工程化，主题相对独立，用「功能变重」的叙事串起来
- 高阶（13-15）：体验与架构判断，13 回收 06 的伏笔，15 给整个单体视角做辩护性收口
- 收官（16）：决策树 + 速查表 + 深潜索引，服务「读完之后真的开工」

节奏设计上，相邻篇之间都有因果或回收关系（同步→多用户→冲突→数据量→读压力→异步→支付→附件→安全→实时→排障→边界），避免变成 16 个孤立话题的清单。
