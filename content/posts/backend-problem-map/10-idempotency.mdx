ClipNote 的 Pro 订阅上线第一周，来了一个和以前所有工单质感都不同的工单。

用户说：点订阅按钮的时候手抖，双击了，被扣了两次 39 元。你先去找支付平台，平台的回复无懈可击：你们的服务器提交了两个订单，订单号分别是 pay_20261016_8841 和 pay_20261016_8842，我们如实处理了两笔。问题不在平台，在你自己的代码里——**每次点击都生成一个新订单**，双击就是两个意图，两个意图就是两笔扣款。

钱的事和笔记不一样：笔记覆盖了能找回，钱多扣了要退款、要客服、要用户投诉。这篇讲的后端性质叫**幂等（idempotency）**：同一个操作执行一次和执行多次，结果完全一样。它是所有和钱、和外部副作用打交道的系统的地基。

## 先接受现实：请求就是会来多次

单机软件的世界里，「用户点了一次按钮」是一个清晰的事实。后端的世界里，这个事实不存在，你会遇到同一意图的多次到达：

- 用户双击、狂点、刷新重发；
- 客户端（尤其移动端）请求超时后自动重试；
- 你的接口调支付平台，超时了——**超时不等于失败**，请求可能已经成功，只是响应在回来的路上丢了，你一重试就是第二笔；
- 支付平台的回调（webhook）按「至少送达一次」的承诺投递，同一事件重发三次是正常行为不是故障。

最后一条值得单独强调。分布式系统的第一课就是：**网络上没有「失败」这个确定答案，只有「不知道」**。超时之后你面对的不是「失败了，重试就好」，而是「可能成了可能没成」。所有可靠的机制，都建立在「假设重来」之上。

## 幂等键：给每个意图发身份证

解法的核心动作是反转：不再让服务端猜「这两个请求是不是同一个意图」，而是让客户端**声明**。

客户端在用户点下按钮那一刻，为这次意图生成一个唯一 id（幂等键，通常用 UUID），双击的两次点击复用同一个 id（id 在点击时生成一次，不是每次网络请求都新生成——这里是第一版代码出错的根源）。服务端第一次见到这个 id，正常处理，并把「id → 处理结果」存下来；第二次再见到，不处理，直接把上次的结果还回去。

落地上不需要什么新组件，唯一约束就是全部机制：

```sql
CREATE TABLE idempotency_keys (
  key        TEXT PRIMARY KEY,        -- 客户端生成的幂等键
  user_id    TEXT NOT NULL,
  action     TEXT NOT NULL,           -- 'create_subscription_order'
  result     JSONB,                   -- 处理结果：订单号、状态
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

```ts
async function createOrder(req: Request) {
  const idemKey = req.header("Idempotency-Key")   // clp_9f2e7a1c（点击时生成）

  const existing = await db.idempotencyKeys.findById(idemKey)
  if (existing) return existing.result            // 见过：直接还上次结果

  try {
    const order = await paymentProvider.create({ amount: 3900, ... })
    await db.idempotencyKeys.insert({ key: idemKey, result: { orderId: order.id } })
    return { orderId: order.id }
  } catch (e) {
    if (e.code === "UNIQUE_VIOLATION") {          // 并发双击同时杀到
      return (await db.idempotencyKeys.findById(idemKey)).result
    }
    throw e
  }
}
```

唯一约束兜住了最后一种边角情况：双击快到两个请求**同时**到达，两个都查到「没见过」，都往下走——第二个插入会被数据库拒绝（第 6 篇「唯一约束是并发下最便宜的防线」在这里第三次出场）。注意失败时不要存幂等键：这次真失败了，用户重试应该真的重试，而不是拿到缓存的失败。

## webhook 回调：对方也会重发

你的服务器发起支付是一半，另一半是支付平台主动通知你「支付成功了」——这个主动通知就是 webhook：平台向你预设的 URL 发 POST。第 9 篇说过任务系统「至少执行一次」，回调的投递也是同一个契约：**平台保证送达，不保证只送一次**。你的回调接口必须做好「同一事件到达多次」的准备，规则三条。

**先验签再处理。** 平台用密钥对请求体签名，你先验签名，确认这真是平台发的，不是别人伪造的「支付成功」。验签不过直接 403，一个字都别处理。

**先原样落库，再慢慢处理。** 收到回调的第一动作不是「开通 Pro」，而是把原始事件插进 webhook_events 表（第 3 篇建好的那张，`event_id` 上有唯一约束——平台每个事件都带唯一 id，这就是天然的幂等键）。插入成功说明第一次见，接着处理业务；唯一约束冲突说明处理过了（或正在处理），直接返回成功。这样还有个运维红利：平台文档让你「排查某次回调」时，原始报文就在表里躺着。

**处理结果要可查，异常要可重放。** 处理完成标记 processed_at；处理中途崩了，事件还在表里，第 9 篇的 worker 把它当失败任务重跑。回调接口本身要快：验签、落库、返回 200，重活都扔给后台——平台对回调有超时要求，超时它会重发，你的慢处理会引来更多重发。

## 扣了钱，就一定要开通：本地消息表

还剩最后一道缝：支付成功的事件处理到一半，「已确认收款」写进了库，「开通 Pro」还没来得及执行，进程崩了。用户付了钱没开通，这是最伤口碑的一种事故。

硬看这是个分布式事务问题（支付在平台、开通在你库里），但单体架构下有个非常朴素的解法，叫**本地消息表**：把「开通 Pro」写成本地任务，和「记录支付成功」放进**同一个数据库事务**——要么两笔都进库（任务随后被 worker 执行，第 9 篇的队列直接复用），要么都没进（回调重发，从头再来）。事务保住了「记账」和「待办」的原子性，worker 保住了「待办」最终被执行。没有分布式组件，用的全是前两篇的存货。

顺带一句「分布式锁」：同一用户的并发请求只放一个进来（Redis 的 SETNX 就能做），可以当「防双击」的又一道保险。但要清楚它的边界——锁只防「同时」，防不了「重试」（隔三秒再发一次，锁早释放了）。根本解永远是幂等键，锁只是锦上添花。

## 结尾

这篇收拢：和钱、和外部副作用打交道的接口，幂等是设计时就要想的事，不是补丁。客户端为意图发身份证（幂等键），服务端用唯一约束认脸；回调先验签、先落库、按事件 id 去重、快返回慢处理；跨边界的「要么都做要么都不做」用本地消息表把两边拉回同一个事务。至于真正的分布式事务（TCC、Saga 那一串名词），第 15 篇统一收拾。

到这里，钱的事故防住了。下一篇回到轻快一点的话题：用户剪藏的网页图片存哪、怎么传、为什么上了 CDN 之后账单反而降了。文件这件事的坑全在「想当然」：想当然存数据库、想当然经过自己服务器中转、想当然所有用户都从同一台机器下载。
