前九篇你一直站在三只小鹿（甲方）那边看系统。收官篇换边：你入职了一家软件公司（乙方），第一个项目恰好就是三只小鹿的「全渠道订单中台」——把散落的渠道订单和库存统一管起来的系统。这篇跟着这个项目走完全程，把还没讲完的最后一批黑话收进地图。

先看这个项目是怎么出生的，再看那场让你如坠云雾的评审会。

## 项目诞生记：售前、POC、招投标

**第一个登场的不是程序员，是售前**（Pre-sales）。三只小鹿的 IT 负责人跟几家软件公司接触，每家都派售前来「聊需求」——写方案、做演示、陪吃饭的技术角色。售前承诺的东西，最后都变成开发团队的你来实现，所以乙方程序员对售前的感情很复杂。

聊得不错，甲方说：空口无凭，**做个 POC**（Proof of Concept，概念验证）——用最小的代价做个演示版，证明你们真的能对接我们的天猫和抖音后台。POC 通常免费或收个成本价，是乙方的投标前投资。

然后是**招投标**。三只小鹿年营收过亿，按规矩这类采购要正式招标：甲方发招标文件，几家乙方密封递交标书，评标、中标、签合同。政企项目这一步是法律流程，绕不过。你在新闻里看到的公司「中标某某项目 XX 万元」，就是这一刻。

合同签完，项目才正式开始。然后你参加了入职后的第一个需求评审会——就是第 01 篇开头那个场景，原样重演：

> 「这个 ToB 项目是给甲方做 MES 二开，原厂接口不开放，售前答应的 POC 下周就要演示。需求侧 PRD 还没评审完，甲方信息科说 UAT 环境得等他们把 ERP 的主数据同步打通……」

现在逐句拆。

## 那段话的逐句翻译

**「给甲方做 MES 二开」**——甲方是掏钱的客户（三只小鹿），乙方是你东家。二开（第 03 篇）：在别人家成品系统上做定制。这句话同时交代了：项目性质（定制开发）、甲乙方关系、技术路线（在现有系统上改）。

**「原厂接口不开放」**——MES 原厂商的 API 没覆盖你要的功能，只能想办法绕：直接读写它的数据库（危险且掉头发），或者联系原厂开接口（收钱且排期）。

**「售前答应的 POC 下周就要演示」**——经典剧情：售前为了签单答应了演示时间，没跟开发对过工作量。你下周的通宵有了着落。

**「PRD 还没评审完」**——PRD（Product Requirements Document，产品需求文档）：这个系统要做什么的正式文字描述。评审：相关各方坐一起过一遍这份文档，撕明白歧义。PRD 没定，开发就没法排期——这是会上最大的风险项。

**「UAT 环境得等 ERP 的主数据同步打通」**——UAT（User Acceptance Test，用户验收测试）：上线前甲方亲自测试、签认可的环节；UAT 环境就是为这个环节准备的一套独立部署。主数据（第 03 篇）：物料、客户的统一编码。这句话的意思是：物料编码还没从 ERP 同步过来，测试环境没数据可跑——依赖卡住了。

十个词，全是这十篇讲过的。你已经全部认识了。

## 一个需求的完整流水线

评审会之后，一个需求走到上线的完整路径，也是乙方的项目日历：

```
PRD 撰写 → 需求评审（撕歧义）→ 排期（承诺时间）→ 迭代开发
   → 提测（交给测试）→ 修复回归 → UAT（甲方验收测试）
   → 上线 → 验收签字 → 维保期
```

中间「迭代开发」四个字里藏着敏捷黑话全家桶：**迭代**（Sprint，固定一到两周一个周期，结束时要交出能跑的东西）、**站会**（每天十五分钟，昨天干什么今天干什么被什么卡住）、**Story Point**（用相对规模估工作量，不是小时数）、**燃尽图**（剩余工作量的下降曲线，用于判断「这次能不能按时交」）。

对这套仪式要有清醒认识：**敏捷术语的一半价值是管理对外承诺**——燃尽图与其说是给团队看的，不如说是给「什么时候能上线」这个问题一个随时可查的答案。乙方项目里，这个问题的背后是合同和回款。

再记两个金钱相关的：**验收**——甲方正式签字确认系统合格，通常和回款节点绑定，乙方的命根；**维保期**——上线后一年（或合同约定的时长）内免费修 bug 的时期。维保期结束又是新的收费续约，ToB 生意闭环了。

## 甲方乙方：两种程序员人生

最后拉远一点，说这个系列没明说但贯穿始终的一件事：**乙方程序员和互联网（甲方自研）程序员，过的是两种生活**。

互联网程序员的需求来自产品经理，改需求是白板上的事；乙方程序员的需求来自**合同附件**，改需求要走变更流程、动商务——因为每一条都对应着钱。互联网程序员的用户是海量陌生人；乙方程序员的用户是**坐在会议室对面、会打电话给你老板的那个具体的人**。互联网程序员上线看监控大盘；乙方程序员上线要**驻场**（泡在甲方办公室）陪跑，出差是家常便饭。

没有优劣，是两个真实不同的世界。选哪个，看你喜欢确定性还是喜欢规模感——第 06 篇制造业、本篇的定制项目、第 09 篇的私有化，都是乙方的世界；你在教程里读到的技术栈，多半是甲方的世界。

## 收官：到底要上哪些系统

十篇的最后，回答那个从第 01 篇埋到现在的问题。系统不是公司标配，是被问题逼出来的——按规模给三档参考：

**档一：夫妻店到十几人**（三只小鹿起点）。收银/电商平台后台 + Excel + 微信群，齐了。这个阶段上任何管理系统都是负资产，唯一值得花钱的是把 Excel 用明白。

**档二：几十人到两百人**（三只小鹿现状）。四件套够用：进销存或轻量 ERP（对账开始跨部门时上）、钉钉飞书免费版 OA（审批开始丢单时上）、SaaS 工单（客诉开始无主时上）、BI 用 Excel 透视表顶着（口径开始打架时再上真 BI）。CMS 视生意而定，CRM 五个以上销售再谈。

**档三：集团**。多条业务线、多仓库、自建产线、财务并表——ERP 正式版加 MES/WMS/OMS，数据团队和数仓，这时候「中台」两个字才勉强有讨论价值。

每一档的判断信号都是同一个句式：**痛了再上**。所有系统加起来，都不如「问题驱动」这四个字值钱。

## 系列收官

回到第 01 篇开头的那个周一早上。那段对话现在对你来说只是普通话——你甚至能听出话里的糟点：POC 排期没和开发对齐，PRD 没评审完就答应演示，是个该被项目经理拦下的节奏。

这张地图的用法从头到尾只有一个：**不背，查**。任何时候撞见一个陌生缩写，回来找到它管公司的哪个部位、被什么问题逼出来、一般什么时候才会真的碰到。三只小鹿会继续长大，新的系统会继续被逼出来——但造词的套路、营销的包装、问题的逻辑，翻来覆去就这几招。

听懂黑话不是终点。听懂之后你该问的下一个问题是：这个系统，到底解决了谁的什么问题——这个问题，比所有黑话都值钱。
