三只小鹿五十人了。行政管理制度还停留在微信群：

> 行政：@老板 张三的报销单 3860 元，麻烦批一下
> （三条拼单奶茶的消息刷过去）
> （两天后）
> 张三：@行政 我的报销有消息吗

老板出差那三天，群里积压了四十条「收到，批」。有一条 8600 元的设备采购审批夹在奶茶拼单和周末团建投票之间，五天没人看见——这个真实到扎心的场景，就是 OA 存在的理由。

## OA 的本质：流程找人

OA（Office Automation，办公自动化）这个词大到没边，考勤、公告、网盘都能往里装，但它的心脏只有一个：**把「人拿着单子找领导」变成「流程自动找人」**。

想想纸质时代的请假：填单子 → 走到组长办公室签字 → 组长说这事我得问问部门经理 → 再走一趟 → 最后交给行政存档。单子在你手里，进度全靠腿。OA 做的事情是把这条链搬进系统：你点提交，单子自己流动，该谁审批谁的钉钉就响，全程状态可查，结果自动归档。

## 解剖一条审批流

以三只小鹿的请假为例，一条审批流在系统里长这样：

```
表单：请假类型 / 起止时间 / 事由
  ↓ 提交
节点1：直属组长审批（或签：任一人通过即过）
  ↓ 条件分支
  ├─ 请假 ≤ 3 天 → 节点2：HR 备案 → 归档
  └─ 请假 > 3 天 → 节点2：部门经理审批
                      ↓ 条件分支
                    └─ 事由选「病假」→ 节点3：HR 总监加签 → 归档
```

四个概念各就各位：

**表单**：申请人填什么。字段、类型、必填校验——本质上就是第 02 篇 CMS 里「内容建模」的同款思想，换个场景复用。

**节点**：一站审批。谁审、怎么审（一人通过即过还是都要过）、超时怎么办。

**条件分支**：流程的智能所在。「3 天以下」「病假」这些规则让不同单子走不同路径——**业务规则的复杂度主要堆在这里**，也是需求评审时扯皮最久的地方（和第 04 篇的漏斗口径并列）。

**会签与或签**：多人审批的两种规则——所有人都同意才算过（会签），任一人同意就算过（或签）。金额大的采购要会签，组长代审可以或签。

这条链跑起来，靠的是下面这个更通用的东西。

## 流程引擎：藏在无数系统里的发动机

把上面那条链抽象一下：**节点 + 连线 + 条件 + 状态流转**。这个抽象在软件行业有个专门组件叫**流程引擎**（工作流引擎），Java 世界的事实标准叫 Flowable（前身 Activiti），干这行的开发者多少都碰过。

流程引擎的通用性远超 OA 本身：

- 第 07 篇的工单系统：提交 → 分派 → 处理 → 关闭，是流程
- ERP 的采购审批：申请 → 审核 → 付款，是流程
- 甚至代码世界的 CI/CD 流水线：构建 → 测试 → 部署，思想同宗

所以看到这你就明白：**OA 是产品，流程引擎是引擎，BPM 是理论**。BPM（Business Process Management，业务流程管理）是研究「怎么把公司流程建模、执行、监控、优化」的整套方法论，传统软件公司会把 BPM 平台当产品卖——理念先进，但卖法老旧，然后时代变了。

## 钉钉飞书是怎么赢的

传统 OA 三巨头——泛微、致远、蓝凌——卖法是经典的 ToB 套路：项目制、私有化部署、实施排期、按人头收费。一套系统上百万，用起来像 Windows 98。

然后钉钉和飞书来了：审批功能**免费**，界面和 IM 融为一体，配置流程像搭积木，员工不用培训（反正已经在用钉钉聊天了）。企业微信带着同样的打法入局。这不是同维竞争，是降维打击——**把 OA 从「公司买的大系统」变成「IM 软件的免费附属品」**。

传统三巨头如今的生态位退缩到大客户和体制内：数据必须留在自己机房、流程复杂到钉钉配置不了、需要和二十年前的老系统对接的地方。这个分野本身就是第 09 篇「SaaS 对私有化」的预演。

对开发者还有一层意义：钉钉的审批开放了 API 和连接器，「审批通过后自动触发我们的 ERP 生成采购单」这类集成开发，是 ToB 公司非常常见的活——**你不一定写流程引擎，但大概率要和流程引擎的 API 打交道**。

## 名词卡片

| 名词        | 全称                        | 一句话定义                                   |
| ----------- | --------------------------- | -------------------------------------------- |
| OA          | Office Automation           | 办公自动化，核心是审批流线上化               |
| 流程引擎    | Workflow Engine             | 驱动「节点+条件」流转的通用组件，如 Flowable |
| BPM         | Business Process Management | 流程管理方法论，OA 背后的理论体系            |
| 表单引擎    | Form Engine                 | 拖拽配置表单字段的组件，低代码的雏形         |
| 加签        | —                           | 流转中临时增加一个审批人                     |
| 会签 / 或签 | —                           | 多人审批：全部同意 / 任一人同意              |
| 电子签章    | —                           | 有法律效力的电子签名，合同类流程的终点       |
| 连接器      | Connector                   | 钉钉飞书的集成插件，跨系统传数据             |

## 小结与下篇预告

什么时候需要 OA？信号和上一篇 CRM 类似：**审批开始丢单**。微信群吼得过来的时候，微信群就是最好的 OA；消息被冲走、领导出差就积压、没人说得清单子到哪了——上系统。反过来，十人以下的团队用 IM 群 + 共享表格，效率高于任何正式系统。

内部流程理顺了，三只小鹿做了一个大决定：自建工厂。从代工贴牌转向自产，然后立刻发现新世界的问题和办公室完全是两个物种——淘宝订单打印出来，车间排产靠喊，仓库拣货靠老师傅的记忆，发错货率 3%。下一篇：MES、WMS、OMS，工厂和仓库里的软件，以及为什么制造业程序员和互联网程序员活在两个世界。
