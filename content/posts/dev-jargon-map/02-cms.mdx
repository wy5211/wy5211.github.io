上一篇说过，看到缩写先拆词：CMS，Content Management System，内容管理系统——管「内容」的系统。拆完你大概还是没感觉，因为「内容」这个词太虚了。这篇把它变实。

场景从三只小鹿开始。淘宝店做顺了，夫妻俩决定做品牌：要个官网，还要开个食谱博客（「每日坚果怎么吃」这种内容营销）。他们招了个前端工程师，花两周做了漂亮的官网和博客页。

然后老板娘说：「把上周参加食品展的新闻发一下。」

前端工程师打开编辑器，新建 `news-2026-0901.html`，复制上一个新闻页的代码，改文字、传图片、调样式，重启构建，发布。第二篇，第三篇，第七篇。每次发内容都是一次工程发布，老板娘眼里的「发个新闻」，在他这里是半小时的手工操作，还改错过两次线上。

问题出在哪？**内容长在页面里**——文字、图片、排版全部焊死在 HTML 代码中，改一个错别字都要走代码。而发内容的人不懂代码，懂代码的人不想天天发内容。

## CMS 的全部理由：一句话

**把「内容」从「页面」里拆出来存，需要展示时再灌进模板。**

这句话就是 CMS 的全部。拆开之后：内容存在数据库或文件里，只关心「标题是什么、正文是什么、封面是哪张图」；页面模板只关心「文章页长什么样」。发新闻变成了：老板娘打开后台，填表单，点发布——工程师彻底下场。

用这个标准看，你会发现 CMS 的门槛低得惊人。一个装 markdown 文件的文件夹加一个静态站点生成器，就是一个能用的 CMS——你现在读的这篇博客就是这么跑的：`.mdx` 文件存内容，Next.js 负责渲染。没有数据库，没有后台界面（我直接写 markdown），但「内容与展示分离」这个灵魂是齐的。

不过给非技术人员用，光有灵魂不够。一个完整的 CMS 有三大件。

## 三大件：建模、后台、渲染

**第一件：内容建模。** 系统得知道「一篇食谱」长什么样。以三只小鹿的食谱为例，你会定义一个「食谱」内容类型，字段大概是这样：

```
食谱（Recipe）
├── 标题        文本
├── 封面图      图片
├── 难度        单选：新手 / 进阶 / 硬核
├── 烹饪时长    数字（分钟）
├── 食材清单    列表：食材名 + 用量（可多行）
├── 步骤        列表：文字 + 配图（可多行）
└── 发布状态    草稿 / 已发布
```

这一步本质上是在设计数据结构——像定义一张数据库表，但产出的不只是表，还有配套的录入表单。「文章」「产品」「招聘信息」都是这样被定义成内容类型的。**内容建模做得好不好，直接决定这个 CMS 顺不顺手**：食材清单要是只能塞一个大文本框，「按食材搜食谱」这种功能就没戏了。

**第二件：编辑后台。** 给老板娘用的界面：左侧内容列表，右侧编辑表单，正文用富文本编辑器（WYSIWYG，所见即所得，界面上加粗，发布出来就是加粗）。这一件没什么技术含量，但决定非技术用户敢不敢用。很多自研 CMS 死在这一步——功能都有，编辑器难用到市场部集体要求「还是发 Word 给程序员吧」，一夜回到解放前。

**第三件：发布渲染。** 内容加模板变成最终页面。这里是近十年变化最大的地方，出现了两条路线的分岔——传统 CMS 和 Headless CMS，下面分别讲。

## WordPress：一个生态吃下四成网站

讲 CMS 绕不开 WordPress，因为它可能是世界上份额最大的软件：**全网约四成网站跑在它上面**，从个人博客到《纽约客》官网都是。一个 PHP 项目凭什么？

- **主题机制**：网站长什么样由主题决定，一键换肤。不懂代码的人挑一个主题，改改 logo 和配色，官网就有了。
- **插件生态**：几万个免费插件，要评论装评论、要 SEO 装 SEO、要电商装 WooCommerce（这个插件本身的规模相当于一个独立产品线）。
- **装机成本**：随便一个虚拟主机，五分钟装完。

对开发者的现实意义：2010 年代「会 WordPress 定制」是接外包建站单的硬通货，这个市场今天仍然存在，只是被建站平台（Wix、国内的凡科这类）和下面要讲的 Headless 蚕食了。

WordPress 的软肋也明显：它是为「建整站」设计的，渲染页面这件事焊死在系统里。而三只小鹿 2026 年的需求是——官网一个站、小程序一个端、天猫店铺页面又一个端，**三个前端界面需要同一份内容**。让 WordPress 同时伺候三个端，就得在它身上打洞，越打越别扭。

## Headless：砍掉脑袋，只留内容

于是出现了 Headless CMS。Headless 直译「无头」，头指的就是渲染层（用户看到的那颗「头」）——把它砍掉，CMS 只负责存内容和吐 API：

```json
{
  "title": "三日坚果能量棒",
  "difficulty": "新手",
  "cookMinutes": 25,
  "ingredients": [
    { "name": "混合坚果", "amount": "200g" },
    { "name": "蜂蜜", "amount": "40g" }
  ]
}
```

上面是内容 API 的典型响应。官网的 Next.js 拿它渲染网页，小程序团队拿它渲染小程序，天猫详情页运营手动复制——**内容只存一份，前端随便换**。这就是「内容与展示分离」推到极致的形态。

代表产品：Strapi（开源，可自己部署）、Contentful（SaaS 订阅）、Sanity。国内的博客圈常见组合则是「markdown 文件 + 静态生成器」，思路同宗——我这个博客就是：内容是 mdx 文件，渲染全权交给 Next.js，一个手搓的迷你 Headless CMS。

代价也直白：没有现成的「头」了，每个前端都要自己写；编辑后台的体验参差（Strapi 的后台就够工程师审美的）。**内容只有一个端、团队没有前端资源，用 WordPress 反而是正解**——技术选型看约束，不看先进。

## 什么时候自研

三只小鹿的食谱博客要不要自研一个？判断标准三条：

1. **内容类型特殊**：食谱的食材要结构化存储、要支持「用冰箱里的坚果搜食谱」，WordPress 的默认文章模型扛不住，深度定制不如自己定义数据结构。
2. **团队本来就有前后端**：自研 CMS 对全栈团队不是额外负担，就是一次普通的业务开发。
3. **内容是核心业务**：内容只是官网新闻稿的话，任何花在自研上的时间都是浪费。

如果三条都占，自研合理。而且自研 CMS 恰好是练手的好题目——本博客的 [Spring Boot 系列](/posts/springboot/04-restful-api-design)就是在手把手写一个迷你 CMS：从文章 CRUD 到 RESTful API 到鉴权部署，一个不落。那个系列回答「怎么写」，这篇回答「这是什么、边界在哪」，正好互补。

顺带一个前面挖的坑：CMS 之后有个词叫 **DXP**（Digital Experience Platform，数字体验平台）。对照第 01 篇的「营销包装」定律——DXP 大体就是 CMS 加了个性化推荐、多渠道触达之后的升级改名。名字变了五倍长，内核没有五倍新。

## 小结与下篇预告

CMS 的判断题其实就一道：**你的内容是谁在发、发到几个端**。非技术的人频繁发、只有一个网页端——WordPress 这类传统 CMS；多个端、有前端团队——Headless 或自研；内容一年改两次——静态页面写死，别折腾。

三只小鹿最后选了自研：食谱的结构化需求是真的，前端工程师也是现成的。官网和博客上线后流量稳步涨，天猫店订单翻了一倍——然后，仓库炸了。账面 1200 箱坚果，实际盘点 900 箱，采购一本账、销售一本账、财务一本账，月底对账像三方会谈。下一篇：ERP，公司的大管家，和它那个「上 ERP 找死，不上 ERP 等死」的恶名从哪来。
