三只小鹿一百五十人了，两件「支撑部门」的事故在同一个月爆发。

第一件：HR 算绩效用 Excel，某个月一个公式引用错了列，全公司两百块档位的绩效扣款多扣了一档。有人发现截图发到匿名吐槽群，第二天全员都在核对工资条，HR 道歉三次。

第二件：客户的售后投诉散落在五个微信群（天猫群、抖音群、批发客户群、企业微信、还有个离职员工忘了交接的群），一袋漏气的夏威夷果被踢了两周皮球，最后客户直接投诉到了 12315。

这两件事对应两类系统：管人的 HRM，管事儿的工单系统。

## HRM：四个模块，一部名字通胀史

HRM（Human Resource Management，人力资源管理）按模块拆：

| 模块        | 管什么                | 三只小鹿的痛点                        |
| ----------- | --------------------- | ------------------------------------- |
| 招聘（ATS） | 简历、面试流程、offer | 简历散在 HR 邮箱和 Boss 直聘后台      |
| 考勤        | 打卡、请假、排班      | 打卡机和 Excel 各一套（请假在 OA 里） |
| 薪酬        | 工资、社保、个税      | 公式错误全员围观事故                  |
| 绩效        | 目标、考核、结果      | 每季度发一轮 Excel 收集表             |

其中**招聘模块（ATS，Applicant Tracking System，应聘者跟踪系统）值得单独看一眼**，因为它和第 04 篇的 CRM 严格同构：简历池是公海，跟进中的候选人是私海，面试漏斗和销售漏斗一个形状——「待筛选 → 初面 → 复面 → offer」对「初步接触 → 报价 → 赢单」。软件行业的造物规律在这暴露无遗：**同一个引擎，换个领域就是新产品**。

**薪酬模块是 HRM 里最难啃的**：公式复杂（基本工资 + 绩效浮动 + 加班费 - 五险一金 - 个税，各地政策还不同）、保密性要求极高（谁能看到谁的工资是权限设计的噩梦）、和考勤绩效的联动错一步就是全员事故——三只小鹿的 Excel 事故就是这个模块存在意义的反面教材。

名称上再来一次第 01 篇的「营销包装」定律：行业热词已经从 HRM 涨到 **HCM**（Human Capital Management，人力资本管理）——把人当资本经营，听起来战略高度立刻不同，模块还是那些模块。国际玩家 Workday、SAP SuccessFactors，国产北森、Moka，卖法差异第 09 篇讲 SaaS 时会再次出现。

## 工单系统：ToB 界的 Hello World

处理第二件事故的武器是工单系统（Ticketing System）。为什么说它是 ToB 界的 Hello World？看它的通用形状：

```
提交：客户/员工通过入口（电话、表单、机器人）创建工单
分派：按规则路由到处理人（售后组、按产品线、按技能）
处理：沟通、升级（搞不定转给二线）、计时
关闭：客户确认解决
沉淀：处理过程存档，常见问题整理进知识库
```

就这么五步。**任何「请求 → 处理 → 反馈」的业务都能塞进这个形状**：客服售后、IT 支持、行政报修、法务咨询。所以每家 ToB 公司、每个有点规模的信息化部门，都有一套工单系统——它出现频率之高、形状之稳定，配得上「Hello World」这个玩笑。

拆开看两个高频变体：

**客服工单**。三只小鹿的落地方式：五个渠道的客户消息统一汇入一个收件箱，每条投诉自动建单、编号、开始计时——**SLA**（Service Level Agreement，服务等级协议）规定了「食品类客诉 2 小时内响应、24 小时内解决」，超时自动升级到主管。漏气的夏威夷果从此有处可去，踢皮球在系统里留痕。呼叫中心、在线客服、坐席（接线/接待的客服人员）这些词都围绕这个场景。

**ITSM**（IT Service Management，IT 服务管理）。IT 部门版的工单系统：电脑坏了、VPN 连不上、要开权限——「提个单」是 IT 人最爱说的话。这个细分领域养出了 ServiceNow——一家市值曾超千亿美元的公司，主营业务说白了就是企业内部的报修和流程。同类的还有 Jira Service Management。ITSM 比普通工单多的一层是**知识库**：每个工单的处理过程自动沉淀，重复问题直接推自助答案，「重启试试」的富集度随时间指数上升。

## 工单和流程引擎的关系

眼熟吗？提交 → 分派 → 处理 → 关闭，这就是第 05 篇解剖过的流程，换个皮而已。区别在侧重：OA 审批流的节点是「领导」，靠规则分支驱动；工单流的节点是「办事的人」，靠分派和升级驱动。底层同一套思想：**状态机 + 责任人流转**。你在简历上写「深入理解工作流」时，应该能同时想到这两个场景。

## 名词卡片

| 名词      | 全称                                | 一句话定义                                 |
| --------- | ----------------------------------- | ------------------------------------------ |
| HRM / HCM | Human Resource / Capital Management | 人力资源管理 / 人力资本管理（名字通胀版）  |
| ATS       | Applicant Tracking System           | 招聘管理系统，简历版的 CRM                 |
| 工单      | Ticket                              | 一个待处理的请求单元，有编号、状态、责任人 |
| SLA       | Service Level Agreement             | 服务等级协议，规定响应和解决时限           |
| 升级      | Escalation                          | 超时或搞不定时，自动上升到上级/二线        |
| ITSM      | IT Service Management               | IT 部门的工单与流程管理，代表 ServiceNow   |
| 坐席      | Agent                               | 客服接线/接待人员，呼叫中心的计量单位      |
| 知识库    | Knowledge Base                      | 工单沉淀出的常见问题自助答案库             |

## 小结与下篇预告

什么时候需要这两类系统？HRM 的信号是「Excel 开始出事故」——工资条出错一次的信任成本，远超一套北森的年费；工单的信号是「请求开始无主」——投诉在群里被刷走、IT 问题靠拍肩膀，就该建单了。反过来，五十人以下的团队，HRM 用表格、工单用一个共享邮箱，绰绰有余。

人到齐了，流程顺了，货也管住了。然后老板在年度会议上问了一个所有人都答不上来的问题：「天猫、抖音、线下门店，到底哪个渠道在赚钱？」运营连夜导出七个 Excel，销售额对不上——天猫的含运费，抖音的没扣退款。下一篇：BI 和数据黑话，一场关于「口径」的战争。
