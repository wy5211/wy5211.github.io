大促前一天晚上，你收到一条磁盘使用率 85% 的告警。处理的时候顺手检查了一下备份目录——全量备份每天凌晨三点在跑，文件一个不少。然后你心里冒出一个从没想过的问题：**这些文件，真的能恢复出一个数据库吗？**

你从来没有试过。你不知道恢复要多久、权限对不对、恢复出来的数据是不是完整的。也就是说，如果明天大促数据库出事，你的救命稻草**从未被验证过**。

这一篇讲数据层的两件事：为什么会有多个数据库（分工），和数据怎么才叫安全（复制与备份）。第二件事会回答一个从 03 篇拖到现在的悬念：数据库的集群，和应用集群到底差在哪。

## 为什么一个数据库走不了天下

先盘点 ShopLite 现在有几个「存数据的家伙」：MySQL（订单、用户、商品表）、Redis（Session、商品详情缓存）、RocketMQ（消息暂存）。而如果 ShopLite 继续长大，还会需要 Elasticsearch（商品搜索）、ClickHouse（运营分析）。**为什么不能把所有数据塞进 MySQL？**

因为**数据的访问模式不同，而每种数据库是对一种访问模式的极致特化**：

| 数据         | 访问模式                     | 最合适的存储       | 硬塞进 MySQL 的代价                  |
| ------------ | ---------------------------- | ------------------ | ------------------------------------ |
| 订单、账务   | 精确读写、事务、强一致       | MySQL（关系型）    | ——它就是为此而生的                   |
| 热门商品详情 | 每秒几万次读、容忍秒级旧数据 | Redis（内存 KV）   | 磁盘和连接数先扛不住                 |
| 商品搜索     | 模糊匹配、关键词、排序       | ES（倒排索引）     | LIKE '%手机%' 全表扫描，慢到怀疑人生 |
| 用户行为日志 | 每秒十万条追加、批量分析     | ClickHouse（列存） | 写入先把行存格式的它压垮             |

这不是「数据多了装不下」的问题，是**数据结构和查询模式的匹配问题**。Redis 快不是因为它是更好的 MySQL，而是因为它砍掉了一切（磁盘、事务、复杂查询），只留「内存里的 key-value」这一件事；ES 搜得快是因为为「关键词→文档列表」专门建了倒排索引。**每种数据库都是用通用性换特化性能的偏科生**，多数据库架构就是让每个偏科生只做它最擅长的那道题。

[后端技术地图第 3 篇](/posts/backend-map/03-database-pressure)从「数据库扛不住」的视角讲过缓存和读写分离的引入时机，那篇的结论在这里依然成立：**先用索引和缓存把单库榨干，再谈加数据库**——每个新数据库都是新的运维对象、新的一致性问题（缓存和库谁更新谁？[后端技术地图第 9 篇](/posts/backend-map/09-distributed-transaction)的分布式事务多一半是多数据库逼出来的）。

## 数据库集群：和应用集群差在哪

05 篇留的悬念：为什么应用可以「简单复制两份」，MySQL 不行？

一句话：**应用复制的是计算，数据库复制的是数据**。应用的副本之间不存在「不一致」——它们不持有数据（数据在数据库里），谁处理请求结果都一样。而数据库的每个副本自身就是数据的主人，**两份 MySQL 各自接收写入的那一刻，它们就开始分道扬镳**：用户 A 的订单进了 1 号库，用户 B 的退款进了 2 号库，此后任何一边都看不到完整的世界。

所以数据库的高可用不能靠「复制两份」，要靠一套专门解决「**多副本怎么保持一致**」的机制。最主流的形态叫**主从复制（master-slave replication）**：

```
        写入（下单、支付）
              │
         ┌────▼────┐   binlog 同步（异步！）
         │ 主库 M  │ ───────────────┐
         └─────────┘                ▼
                          ┌─────────┐      ┌─────────┐
        读取（查订单）──→ │ 从库 S1 │      │ 从库 S2 │
                          └─────────┘      └─────────┘
```

**一主多从**：所有写入走主库，主库把变更写进 binlog（变更日志），从库拉取日志回放，于是拥有和主库一致的数据。这个结构一举解决两件事：

- **读扩容**：读请求分给从库——「读写分离」。绝大多数业务读写比是 10:1 甚至 100:1（看 100 次商品才下 1 单），从库能无限加（直到写入成为瓶颈）。
- **高可用**：主库挂了，把某个从库提升（promote）为新主库，写入恢复——**故障转移（failover）**。Redis 世界的 Sentinel（哨兵）、MySQL 集群的自动选主，做的都是「监控主库、挂了自动提拔从库、通知所有客户端换地址」这件事。

但注意图里那行小字：**binlog 同步是异步的**。主库写入成功的瞬间、从库还没回放完的瞬间，主库挂了——最后那几条写入在从库上不存在，提升新主库意味着**它们永远丢了**。这不是实现缺陷，是 CAP 定理的物理约束（[后端技术地图第 9 篇](/posts/backend-map/09-distributed-transaction)讲过：网络分区的世界里，一致性和可用性必须取舍）。可以调成半同步（至少一个从库确认收到才返回成功）来缩小窗口，代价是每次写入变慢。**记住这个权衡的存在比记住参数更重要**：数据复制的每一个选项，都是在「丢数据风险」和「写入延迟」之间选边站。

### 如果写入也扛不住：分片

从库加多少都不解决**写入**都在一个主库上的问题。下一步是**分片（sharding）**：按某个 key 把数据水平拆到多个独立的库——订单表按 userId 取模拆成 16 个库，每个库各自主从。这是[后端技术地图第 3 篇](/posts/backend-map/03-database-pressure)讲过的分库分表，从部署视角补一句它的真实代价：16 个库 = 16 套主从 = 监控、备份、故障转移全部 ×16，而且跨片的查询和事务（用户 A 的订单和用户 B 的商品）失去了单库时代的简单答案。**分片是数据库的最后手段，不是第一选择**——前面还有索引优化、缓存、读写分离、垂直拆分排队等着。

## 备份：数据安全的最后一道墙

复制解决的是**高可用**（服务不停），备份解决的是**另一类完全不同的事故**：误操作。`UPDATE orders SET status='paid'` 忘了 where 条件、删库跑路、勒索病毒加密了数据文件——**主从复制对此无能为力**，因为从库会忠实地把这条错误语句也回放一遍。主从是「防故障」，备份是「防后悔」，两者不可互相替代。

备份的正确姿势是一套组合拳：

- **全量 + 增量**：每天一次全量（完整快照），每小时一次增量（binlog）。「最多丢一小时数据、最多花两小时恢复」这类指标就是从这里算出来的——它们有正式名字：**RPO**（Recovery Point Objective，最多丢多少数据）和 **RTO**（Recovery Time Objective，最多停多久）。这两个数字是和业务谈出来的合同，不是技术自己定的。
- **异地**：备份文件和数据库在**同一个机房**，约等于没备份——机房级事故（05 篇提过的那种）会让两者一起消失。备份要传到另一个地域的对象存储里。
- **加密与最小权限**：备份文件包含全部数据，却常常是权限最松的地方。

然后是最重要的那条，回到开头那个深夜的问题：**没验证过的备份等于没有备份**。恢复是一个完整流程（找文件、起实例、回放 binlog、校验、切流量），任何一个环节没跑通过，你拥有的只是一堆「看起来像备份的文件」。业界的纪律叫**恢复演练**：定期（每季度或每月）在隔离的环境里，用备份文件真的恢复出一个数据库来，掐表计时。**只有演练过的 RTO 才是 RTO，纸面上的只是愿望。**

### 数据分级：不是所有数据都值得同样的对待

给这段收个尾，一个让备份策略不再昂贵的心智模型：**数据是要分级的**。

- **丢了不能活的**（订单、支付流水）：全量+增量+异地+定期演练，顶格伺候
- **丢了很麻烦但能重建的**（用户资料、商品信息）：每日全量+异地
- **丢了无所谓的**（缓存、Session）：根本不用备份，进程重启重建就行——Redis 默认的持久化（RDB 快照）开着更多是为了重启快点，不是当数据库用

分级的思想和 03 篇的有状态/无状态一脉相承：**状态越重的东西，伺候它的成本越高，所以架构师的一生都在把状态变少、变集中、变清晰**。

## 现实预告：这一切大多交给 RDS

这一篇讲的所有东西——主从、故障转移、备份、异地——自己搭建是真实的全职工作（需要一个 DBA 团队）。而现实世界里，绝大多数公司的选择是：**用云厂商的托管数据库（阿里云 RDS、AWS RDS）**。控制台上勾一下：一主一从、自动备份保留 7 天、跨地域冗余、监控告警全带，月费几百起。

这不意味着这篇白学了——恰恰相反：**你勾的那几个选项，每一个就是这一篇的一个小节**。「同城容灾」「备份保留期」「日志备份」这些控制台参数，不懂原理的人看不出它们对应什么风险、值多少钱。09 篇会展开托管与自建的光谱，这里先把结论挂着：**原理决定你能不能看懂报价单，托管决定你不用亲手搭**。

## 什么时候不需要这些

- 单库 + 每日备份 + 备份能恢复（演练过！），对绝大多数中小系统就是全部答案。主从、分片、多活，每一层的入场券都是「下一层的问题真实出现了」——读延迟真实地影响了用户、写入真实地到了单机极限。为简历提前上这些，等于给自行车装涡轮。
- 一个诚实的自检问题送给你：**「如果现在数据库所在机器永久消失，我的业务会丢多少数据、停多久？」**能准确回答这两个数字，你的数据层就是合格的；答不出来，说明还没有数据层——只有一个还没出事的数据库。

## 小结与下篇预告

- **多数据库 = 访问模式的特化分工**：关系型/内存 KV/倒排索引/列存各做各的偏科题；先榨干单库再谈加库
- **应用集群复制计算，数据库集群复制数据**——后者的一切复杂度来自数据一致性：主从复制（读写分离）、故障转移、分片，每个选项都在「丢数据风险 vs 写入延迟」之间取舍
- **主从防故障，备份防后悔**，不可互替；备份的完整公式 = 全量+增量+异地+**演练**
- **RPO/RTO 是和业务的合同**，纸面上的数字不算数，演练过的才算
- 数据要分级：不是所有字节都值得同样的伺候成本
- 现实世界里这些大多交给 RDS——但原理决定你能不能看懂报价单

到这里，六层地图还剩两层。下一篇先讲一个没有任何技术含量、却决定了无数个凌晨三点质量的话题：**上线之后的现实**——证书会过期、磁盘会被日志写满、备份没演练过、依赖里有漏洞，这些没人主动告诉你的隐性清单，以及监控告警怎么兜住它们。
