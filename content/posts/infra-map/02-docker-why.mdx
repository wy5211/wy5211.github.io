上一篇你租好了云服务器，SSH 上去，面对着九步安装清单。今天从清单的第一步开始——然后你会撞上一堵所有开发者都撞过的墙。

ShopLite 的 jar 包在本地是好的。你 `mvn package` 打出来，scp 传到服务器，`java -jar order-service.jar`——起不来。报错是 `NoSuchMethodError`，一个你从没在本地见过的异常。

查了半小时，原因：本地 JDK 17，服务器上 `apt` 装的是 JDK 11，某个依赖库的两个版本里方法签名变了。你把 JDK 换成 17，order 服务起来了；轮到 product 服务，又挂——这次是 Redis 报协议错误，本地 Redis 7，服务器装的是发行源自带的 6.x。等你把 Redis 也升上去，user 服务告诉你连不上 MySQL：服务器的 MySQL 8 默认不开放远程连接，而本地的配置文件里写的是 `127.0.0.1`。

三个服务，三种「本地和生产不一样」。这就是**环境漂移（environment drift）**——同一份代码，因为所在机器的环境（运行时版本、依赖版本、网络配置、系统设置）不同，表现出不同行为。它有个更流行的名字：**works on my machine**。

## 「按文档装」为什么治不了环境漂移

传统解法是写一份详尽的《环境安装手册》，或者更进一步的——把安装过程写成脚本。这条路在 2010 年代之前是主流，但它有三个治不好的病：

**文档会腐烂。** MySQL 官方源今天提供的版本和下个月不一样，手册里那句「执行 apt install mysql-server」半年后装出来的可能就是另一个大版本。文档描述的是写下的那一刻的世界。

**人会漏步骤。** 手册 47 步，新同事执行到第 33 步去倒了杯水，回来漏了一步。三天后一个诡异的 bug，没人想得到根源是那杯水。

**环境之间的差异是无限的。** JDK 版本、MySQL 版本只是最容易被撞见的。时区（本地 CST 服务器 UTC）、文件路径（本地 Mac 服务器 Linux）、字符编码、内核参数、DNS 配置……你永远不知道下一种不一致藏在哪。

根本病因在于：**代码和环境是两个独立分发的东西**。代码你有 git 管，版本精确到秒；环境却是每台机器手工长出来的，没有哪个机制保证你本地的环境和生产的环境是同一个东西。

Docker 的解法就一句话：**别分发了，把代码和环境打包成一个东西发。**

## 镜像、容器、仓库：三个核心概念

Docker 的世界只有三个名词要背，其他一切都是这三个词的展开。

### 镜像：环境和代码的只读快照

**镜像（Image）= 操作系统基础层 + 所有依赖 + 你的代码**，打包成的一个不可修改的文件。

比如 ShopLite 的 order 服务镜像，里面是：一个精简版 Linux（只有运行 Java 需要的部分）+ JDK 17 + 应用依赖的 jar 包。注意**没有**的东西：没有 MySQL、没有 Nginx、没有任何与 order 服务无关的东西。一个镜像只装一个东西该有的环境，这是容器世界的基本礼仪。

镜像解决了环境漂移的原理很朴素：**本地和生产跑的是同一个文件的同一个版本**。「我本地能跑」和「服务器上能跑」从此是同一个命题，不存在漂移的可能。

如果你写过面向对象程序，可以直接套这个类比：**镜像是类，容器是实例**。一个类可以 new 出多个实例，一个镜像可以启动多个容器，它们的行为完全一致。

### 容器：镜像的运行实例

**容器（Container）= 正在运行的镜像**，本质是宿主机上一个被隔离的进程。

「隔离」是关键词：容器里的进程看不到宿主机上的其他进程，有独立的文件系统（就是镜像的内容加一层可写层）、独立的网络空间。order 服务跑在容器里，它以为自己在独占一台 JDK 17 的 Linux——实际上一台服务器上可以同时跑十几个这样「以为自己在独占机器」的容器。

这里藏着 Docker 和虚拟机最本质的区别，值得单独说清楚。

### 和虚拟机到底差在哪

云服务器本身就是虚拟机（一台物理机虚拟出多台），容器也是一种「隔离」，两者的实现层级完全不同：

```
虚拟机路线：物理机 → Hypervisor → [完整 OS ①] [完整 OS ②] [完整 OS ③]
                                            ↑ 每个 VM 都带一整套操作系统，几个 GB 起步

容器路线：  物理机 → 宿主机 OS（Linux）→ [容器①] [容器②] [容器③]
                                        ↑ 容器共享同一个内核，只是进程被隔离，MB 级
```

虚拟机虚拟的是**硬件**，每台 VM 要装完整的操作系统；容器隔离的是**进程**，所有容器共享宿主机的 Linux 内核，只是互相看不见。后果：

- **启动速度**：VM 开机要几十秒到几分钟（要引导操作系统），容器启动是秒级（就是启动一个进程）
- **资源密度**：一台 4G 内存的机器跑 3 个 VM 就很勉强，跑十几个容器很正常
- **体积**：VM 镜像几个 GB，容器镜像可以做到几十 MB

代价是隔离强度：VM 之间连内核都隔离，容器共享内核，隔离性弱一档（所以安全要求极高的场景，比如跑不可信租户的代码，还是会用 VM 或容器+沙箱的组合）。对部署自己的应用来说，这个弱一档无伤大雅。

### 仓库：镜像的中转站

镜像在你开发机上构建出来，怎么到服务器上？**镜像仓库（Registry）**就是镜像的 GitHub：`docker push` 推上去，服务器 `docker pull` 拉下来。公共仓库是 Docker Hub，国内常用阿里云 ACR，公司内部一般自建私有仓库（Harbor 最多）。

到这一步，上一篇安装清单里的「scp 传 jar 包」变成了「服务器执行 docker pull」。别小看这个变化——**分发的单位从 jar（只有代码）升级成了镜像（代码+环境）**，环境漂移在分发这一环被物理消灭了。

## Dockerfile：镜像的菜谱

镜像不是手工拼出来的，是**构建**出来的。构建的依据叫 **Dockerfile**——一个文本文件，描述「这个镜像怎么造」。ShopLite 的 order 服务大概长这样：

```dockerfile
# 基础层：从官方注册表拉一个带 JDK 17 的精简 Linux
FROM eclipse-temurin:17-jre-alpine

# 工作目录：容器内部的 /app
WORKDIR /app

# 把构建好的 jar 复制进镜像（target/ 下的产物）
COPY target/order-service.jar app.jar

# 声明容器对外提供 8080 端口（文档性质）
EXPOSE 8080

# 容器启动时执行：跑这个 jar
ENTRYPOINT ["java", "-jar", "app.jar"]
```

五行，把「一台装好 JDK 17 的机器怎么跑 order 服务」描述成了可重复执行的版本化文件。**Dockerfile 应该进 git**——从此环境不是「每台机器手工长出来的」，而是「从同一个描述文件构建出来的」。手册会腐烂、人会漏步骤，但一个进 git 的构建文件，任何人在任何机器上执行，得到同一个结果。

这里有个值得多看一眼的设计：`FROM` 那行说明**镜像是一层层叠出来的**。你的 order 镜像 = alpine Linux 层 + JDK 层 + 你的 jar 层。分层带来两个实际好处：

1. **复用**：product、user 服务同样 `FROM eclipse-temurin:17-jre-alpine`，三个镜像共享同一组基础层，磁盘和网络传输都只算一份。
2. **构建缓存**：改了一行 Java 代码重新构建，基础层没变直接用缓存，只有 jar 那一层重建——几秒完成。这也是为什么 Dockerfile 里 `COPY` 代码的习惯写法都放在安装依赖之后：把常变的放上层，不变 的放下层，缓存命中率最高。

## ShopLite 现在长什么样

给四个服务各写一个 Dockerfile（内容几乎一样，只差 jar 名），各构建一个镜像，推到仓库。服务器上：

```
服务器上现在有 4 个镜像：
  registry.cn-hangzhou.aliyuncs.com/wy/shoplite-order:1.0.0
  registry.cn-hangzhou.aliyuncs.com/wy/shoplite-product:1.0.0
  registry.cn-hangzhou.aliyuncs.com/wy/shoplite-user:1.0.0
  registry.cn-hangzhou.aliyuncs.com/wy/shoplite-gateway:1.0.0
```

`docker run` 第一个容器，order 服务在服务器上起来了——用的是和你本地一模一样的镜像。那句「我本地能跑啊」的哀嚎，从此失去了意义：**没有「本地」和「服务器」的区别了，只有同一个镜像的不同实例。**

但是——你现在大概已经预感到了——`docker run` 一个容器容易，`docker run` 八个呢？MySQL 容器要先于 order 启动，order 要能连到 MySQL 容器的网络，Redis 的数据要持久化在容器外面……这些「多容器怎么组织」的问题，就是下一篇 Compose 的主场。

## 什么时候不需要 Docker

照例的反面视角。Docker 不是免费的：要学概念（今天这些）、要给每个服务写 Dockerfile、要处理容器网络和权限这些新麻烦。以下情况可以理直气壮地不用：

- **一个静态网站或纯前端项目**——没有运行时环境，扔到对象存储或 CDN 上就完事
- **一个只用标准库的脚本**——`python script.py` 在哪都一样，没有环境漂移可言
- **服务器上只跑一个东西且永远只有一台机器**——比如个人博客，直接裸跑反而省内存

但反过来，「公司只有一台服务器」不是不用 Docker 的理由——**环境一致性问题在一台机器上也存在**（你的开发机和它不一致）。2026 年的实际默认值是：只要服务要部署，就容器化，这个决定的讨论成本已经低于不用它的解释成本。

## 小结与下篇预告

把这一篇压缩成三句话：

- **环境漂移**的根源是代码和环境分开分发，环境靠每台机器手工长出来
- **镜像**把环境+代码打成不可分割的快照，**容器**是它的运行实例，**仓库**负责分发——三件套合起来，把「在我机器上能跑」变成「在哪个机器上都是同一个东西」
- Dockerfile 是镜像的菜谱，进 git、可版本化、任何机器上构建结果一致

下一篇解决你此刻头上冒出的新问题：四个服务四个容器好说，加上 MySQL、Redis、RocketMQ、Nacos 一共八个，启动顺序、网络互通、数据持久化——手动 `docker run` 八次的痛苦，比你想象中来得快。**Docker Compose** 登场，顺带讲清一个贯穿整个系列的核心概念：有状态和无状态。
