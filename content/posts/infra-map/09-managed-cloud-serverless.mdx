你和老板过了一遍前八篇的成果。讲到 K8s 那页时，他问了个问题：「学这个要多久？招个会的人要多少钱？」

你诚实地在纸上写：K8s 上手到能运维生产集群，一个后端工程师要挤出两三个月的精力；招一个靠谱的运维/SRE，年薪不比高级后端低。老板盯着纸看了十秒，问出了这一篇的问题：「**有没有不用自己搭的办法？**」

有。而且这不是妥协方案——**这是大多数公司的真实选择**。云行业过去十几年的主线，就是把 02 到 08 篇讲的每一层，逐个做成可以按月付费购买的产品。这一篇讲这条产品光谱，以及怎么在上面选位置。

## 四档光谱：从全自己来到全托别人

把「谁来运维」作为横轴，部署世界的产品可以排成一条光谱：

```
自建               云托管              PaaS              Serverless
（IaaS 上自己搭）  （买组件）          （买平台）          （连机器都没有）
│                  │                   │                  │
ECS + 自己装       RDS / 托管K8s /      Vercel /           函数计算
MySQL主从          云Redis / OSS / CDN Railway / Render    按调用计费
自己备份           …
│                  │                   │                  │
你管一切 ──────────────────────────────────────────→ 云厂商管一切
灵活性/成本控制高                                  省心/被锁定深
```

从左到右，**你操心的事情递减，交给云厂商的决定权递增**。这不是「先进程度」的排序——每 一档都有大量公司站在上面，选哪档是成本和控制的权衡，不是水平的高低。

## 第一跳：从自建到托管组件

光谱的第一次跳跃不是换平台，是**把最难伺候的零件逐个换成成品**。回忆一下 07 篇那张「数据库的完整公式」：主从复制、故障转移、全量+增量备份、异地、监控告警、安全补丁——自己搭，这是一个 DBA 团队的全职工作。而阿里云 RDS（AWS 对应产品也叫 RDS）的控制台上，这些是**一页勾选项**：

```
规格：4核8G
高可用：一主一从（同城双可用区）        ← 07 篇的主从复制
备份：每日全量 + binlog 增量，保留 7 天  ← 07 篇的备份公式
异地容灾备份：开启（另一个地域）         ← 07 篇的异地
监控告警：CPU/磁盘/连接数，默认模板      ← 08 篇的基础设施监控
```

月费几百块。**你勾的每个选项，就是 07 篇的一节小标题**——这就是为什么原理不能跳过：不懂的人看不出「保留 7 天」意味着最多丢多少数据、「同城双可用区」挡住的是哪一级事故。托管消灭的是体力活，**报价单上的每个参数依然要求你做得出判断**。

同样的逻辑套到其他层：**托管 K8s**（EKS/ACK）把控制面（06 篇那个「大脑」）的运维包了，你只管业务容器；**对象存储**（OSS/S3）把「文件放哪、磁盘够不够、备份怎么做」整个问题变成「一个 HTTP 接口」，还天然带 CDN 加速；**云 Redis** 把哨兵、持久化、升级包了。ShopLite 走到这一步的形态：1 台 ECS 跑应用容器（Compose 都还够用）+ RDS + 云 Redis + OSS，**自建的只剩「跑应用」这一件事**——而它恰好是最简单的一件事。

## 第二跳：PaaS——git push 即部署

再往右一档，连「跑应用」也交出去。**PaaS**（Vercel、Railway、Render，国内有对应物）的产品形态是：连上 git 仓库，之后每次 push 自动构建、部署、绑域名、发证书、挂 CDN——**04 篇那条 CI/CD 流水线，在这里退化成 git push 一个动作**。

对一个 Next.js 博客或轻量 API，PaaS 体验近乎魔法：五分钟从零到 https。代价在三个地方：

- **运行时受控**：语言/框架版本、可用端口、进程模型都是平台说了算。Spring Boot 能跑，但要接受平台的 JVM 内存上限；RocketMQ、Nacos 这种「自己起一堆有状态中间件」的需求，PaaS 上没有位置——得改用平台外的托管服务，架构要适配。
- **规模大了贵**：按实例计费的模式在流量上来后显著贵过 IaaS 自管（你在为省心付溢价）。
- **锁定**：深度使用平台特性（预览环境、边缘函数）后，迁移成本随时间累积。

PaaS 的甜蜜区很明确：**前端应用、内容站、中小 API、验证期的产品**。产品跑通、规模上来后，很多公司从 PaaS 毕业到 IaaS/托管 K8s——这个方向的单程票，反向（从自建搬回 PaaS）少见得多。

## 第三跳：Serverless——连「一直跑着的实例」都没有

光谱最右端干脆取消常驻：**Serverless 函数计算（FaaS）**——代码按函数部署，**没有请求时不运行、不计费；请求来了自动拉起实例处理，还支持从零瞬间扩到几百实例**。

它改变了成本模型：为「流量」付费而不是为「容量」付费。一张对比表看清它的领地：

|                       | 常驻实例（ECS/K8s/PaaS） | Serverless 函数                                                                      |
| --------------------- | ------------------------ | ------------------------------------------------------------------------------------ |
| 计费                  | 按规格×时长，闲时照付    | 按调用次数+执行时长                                                                  |
| 流量从 0 到 1000 并发 | 手动/HPA 扩容，有上限    | 自动，理论上无上限                                                                   |
| 没流量时              | 空转烧钱                 | 零成本                                                                               |
| 代价                  | ——                       | **冷启动**（首次调用多几百毫秒到几秒）；执行时长有上限；不能长连接、不能常驻后台进程 |

所以 Serverless 的天然领地是**事件驱动和流量极端波动**的场景：图片上传后自动压缩（一天几百次，凭什么为它养一台机器）、webhook 接收、每天一次的对账任务、秒杀报名页（三分钟流量洪峰）。反过来，WebSocket 长连接、依赖本地状态的进程、跑不完时间限制的任务，都不属于这里。顺带一个词汇：**BaaS**（Backend as a Service）——把登录、数据库、存储做成现成 API 供函数调用，「函数 + BaaS」的组合就是所谓 Serverless 架构。

## 认知纠偏：托管时代，前八篇白学了吗？

这一篇可能给你一种「前面都白学了、花钱就能解决」的错觉。恰恰相反——**托管产品是前八篇概念的商品化，你买的每个东西的说明书都是用那些概念写的**：

- 用托管 K8s，你依然要懂 Pod/Deployment/Service——YAML 还是你写，只是大脑不用你养
- 用 RDS，备份保留期、容灾等级、只读实例数量，参数背后的取舍就是 07 篇的 RPO/RTO
- 用 PaaS，环境变量注入配置、密钥管理，还是 04 篇那套
- 选型本身——该不该上 K8s、要不要分片、黑白盒监控——前八篇的「什么时候不需要」清单就是为这些决策准备的

区别只在动词：以前是「搭」，现在是「配」。**名词全部保留**。这也解释了为什么招聘 JD 里永远写着这些名词——公司买的可能是托管服务，但要的是看得懂说明书的人。

## ShopLite 的三份账单

把三个方案摆在一起（价格按 2026 年国内云厂商量级估算，重点是相对关系不是绝对数字）：

| 方案 | 组成                                            | 月成本（钱）      | 月成本（人力）               | 上限潜力     |
| ---- | ----------------------------------------------- | ----------------- | ---------------------------- | ------------ |
| 自建 | 2 台 ECS，全部自己装自己管                      | ~600 元           | 高：备份/监控/升级全是你的活 | 无限，全看你 |
| 托管 | 1 台 ECS（应用）+ RDS 高可用版 + 云 Redis + OSS | ~1500 元          | 极低：每周瞄一眼告警         | 换规格即可   |
| PaaS | Railway 中档实例 + 托管 MySQL（平台内购）       | ~$60（约 430 元） | 几乎为零                     | 架构受限     |

三档都「对」，取决于你是谁：**学习期的个人开发者选自建**（人力成本是零，学到的就是 02-08 篇的全部，这些经验租不来）；**跑业务的初创选托管**（钱换人力，创始人的时间应该花在产品上）；**前端为主的项目选 PaaS**（体验最好）。注意自建那栏的「上限潜力：全看你」是双刃剑——它既是灵活性也是责任，大部分团队高估了自己想要的灵活性、低估了自己要付的责任。

## 什么时候反而要往左走

光谱从右往左的真实理由只有三类，值得知道以免被「趋势」带偏：

- **数据主权与合规**：数据不能出境、监管要求物理隔离（金融、政务）——云托管不是选项
- **极端规模**：大厂的单机成本优化到极致后，自建机房比云便宜（阿里云自己就是例子）——要到百万级服务器规模这个账才翻过来
- **特殊需求**：GPU 集群特殊拓扑、超低延迟、自有硬件——云的标准产品覆盖不了

除此以外，「我们不用云」在 2026 年几乎只剩情怀一种解释。

## 小结与下篇预告

- 光谱四档：**自建 → 云托管 → PaaS → Serverless**，横轴是「谁来运维」——每档都站着大量公司，选择是权衡不是水平
- **托管组件**（RDS/托管 K8s/OSS）把最难伺候的零件变成勾选项，但每个参数依然是前八篇的概念——托管消灭体力活，不消灭判断题
- **PaaS** 把部署退化成 git push，甜蜜区是前端/内容站/验证期产品；**Serverless** 按调用计费、自动伸缩到零，领地是事件驱动与流量洪峰，死穴是冷启动和不能常驻
- 托管时代前八篇没有白学：**说明书是用那些概念写的**
- 往左走的真实理由：合规、极端规模、特殊硬件——不是情怀
