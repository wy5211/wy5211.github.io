[后端技术地图](/posts/backend-map/01-the-big-picture)系列的收官篇里，ShopLite 终于长成了完整的样子：网关、订单、商品、用户四个微服务，外加 MySQL、Redis、RocketMQ、Nacos 四个中间件。架构图画在 whiteboard 上很漂亮。

然后你合上笔记本，它就没了。

所有这些东西都跑在你自己的电脑上——IDEA 里八个绿色按钮，开机后要按顺序点。用户访问不了 `localhost:8080`，投资人打不开你的演示，而你隐约知道「上线」这件事隔着很远，但具体隔着什么，说不上来。

这篇就是要把这段距离画成一张地图。和后端技术地图系列一样，我们不急着学任何具体技术，先把「部署世界」的名词各自钉在它该在的位置上——**每个基础设施技术都是被一个具体问题逼出来的**，这系列就是把这些问题按出现顺序讲一遍。

## 先体会一下「手动上线」是什么体验

为了不架空，我们真的走一遍最原始的路线。你租了一台云服务器（2 核 4G，一年几百块），拿到一个 IP 和 SSH 密码，登进去是一台干干净净的 Linux。

要让 ShopLite 跑起来，你的安装清单长这样：

```
1. JDK 17（注意：Ubuntu 自带的 openjdk 版本要核对）
2. MySQL 8.0（改默认密码、建库、导表结构、开放 3306？先别，安全问题后面说）
3. Redis 7（ apt 装的可能是 6.x，要加官方源）
4. RocketMQ 5.x（先装 NameServer 再装 Broker，内存不够要改 JVM 参数）
5. Nacos 2.x（standalone 模式，要建它的数据库）
6. 四个服务的 jar 包（本地 mvn package 打出来，scp 传上去）
7. 写八个启动脚本，按依赖顺序：MySQL → Nacos → Redis → RocketMQ → 服务们
8. 配置开机自启（systemd？crontab @reboot？）
9. 挂了谁管？——你半夜爬起来 ssh 上去重启
```

这清单看着长，其实忍一忍也能搞完。真正的麻烦在三件事上：

**第一，环境和本地不一样。** 你本地 JDK 17 服务器装成了 11，本地 MySQL 8 服务器是 5.7，本地跑得好好的代码上去就报错。「按文档装」治不了这个——文档会过时，人会漏步骤，版本悄悄就不一致了。这是下一篇（Docker）要解决的核心问题。

**第二，东西太多，人脑管不过来。** 八个进程的启动顺序、端口、依赖关系、挂了之后谁先拉起谁——三个以内靠记性，八个开始靠脚本，二十个的时候脚本也救不了你。这是 Compose 和 Kubernetes 要解决的问题。

**第三，一台机器就是单点。** 服务器一重启，整个 ShopLite 全部下线；云厂商通知宿主机维护，你没有第二台机器可以顶上。「加机器」听起来简单，加完之后一堆新问题冒出来：流量怎么分？容器怎么分布在多台机器上？这是集群和 K8s 篇的内容。

部署世界的所有技术，都是围着这三类问题打转的。现在把它们摆上地图。

## 部署世界的六层地图

把「从代码到用户可访问」路上的所有东西按职责分层，整个部署世界可以压缩成六层。**这张图是全系列的目录**，后面每一篇就是放大其中一层：

```
┌─────────────────────────────────────────────────┐
│  托管层    云托管 / PaaS / Serverless             │  ← 09 篇：能不能不自己搭？
├─────────────────────────────────────────────────┤
│  数据层    多数据库分工 / 备份容灾                │  ← 07 篇
├─────────────────────────────────────────────────┤
│  流量层    DNS / 负载均衡 / 网关                  │  ← 05 篇
├─────────────────────────────────────────────────┤
│  交付层    CI/CD / 环境分离 / 密钥管理            │  ← 04 篇
├─────────────────────────────────────────────────┤
│  编排层    Docker Compose（单机）→ K8s（多机）    │  ← 03、06 篇
├─────────────────────────────────────────────────┤
│  运行环境层 服务器 → 虚拟机 → 容器                │  ← 02 篇
└─────────────────────────────────────────────────┘
```

从下往上看，正好是一部演进史：

**运行环境层**回答「程序跑在什么上面」。最底下是物理服务器，云时代你租到的「云服务器」其实是虚拟机。而这一层过去十年的主角是**容器（Docker）**——它解决的就是上面说的第一个问题：环境不一致。第 2 篇讲。

**编排层**回答「一堆容器怎么组织」。单机上十来个容器，用 Compose 描述清楚就能跑；等容器散布在多台机器上、还需要自愈和自动扩缩容，就轮到 Kubernetes。第 3、6 篇讲。这两篇之间隔着第 5 篇，因为你会先遇到「为什么要多台机器」这个更根本的问题。

**交付层**回答「代码怎么变成线上跑着的服务」。手动 scp 上线一次痛一次，CI/CD 流水线让「push 代码」到「用户看到新功能」之间没有人肉环节。这一层还藏着两个容易被忽略的话题：多环境分离，和密钥管理。第 4 篇讲。

**流量层**回答「用户的请求怎么找到你的服务」。用户输入的是域名，不是 IP；流量大了要分给多台机器；几十个微服务要一个统一入口。负载均衡在[后端技术地图第 2 篇](/posts/backend-map/02-cluster-and-session)已经从应用视角讲过（Nginx 分活、Session 怎么办），第 5 篇从基础设施视角补全：DNS、四层/七层负载均衡、单点故障的完整清单。

**数据层**回答「数据放哪、怎么丢不了」。为什么一家公司往往同时有 MySQL、Redis、ES 好几个数据库？数据库的集群和应用的集群有什么本质区别？备份到底怎么做才算数？第 7 篇讲。

**托管层**回答「以上这些能不能不自己搭」。这是最容易被人忽略的一层——你以为学了 02 到 08 篇就要亲手搭全套，实际上**大部分公司用的是云厂商的托管版本**：RDS 替你运维 MySQL，托管 K8s 替你管控制面。第 9 篇讲自建到 Serverless 的完整光谱，以及各自的真实代价。

最后第 10 篇收官，回答一个你可能从第一篇就在琢磨的问题：**这些东西是全都要用，还是挑几个用？**（先剧透：绝大多数项目一辈子只用到底下三四层。）

## 这张地图的使用方式

有三句话想在一开始就说清楚，它们是整个系列的「世界观」：

**第一，这些技术是补丁链，不是购物清单。** Docker 不是因为「先进」才用的，是因为环境不一致痛了；K8s 不是因为「大厂都用」才上的，是容器散到多台机器后管不动了。跳过问题直接上技术，就是过度设计的起点。所以每篇都会先花大力气讲「当时到底遇到了什么麻烦」。

**第二，地图上的东西不是都要用。** 一个个人博客用不到 K8s，一个内部管理系统用不到集群，一个十人的初创公司大概率用不到自建任何东西。第 10 篇会给出按规模的典型组合——**「都要用」是大厂幸存者偏差造成的幻觉**。

**第三，概念比操作保值。** 这系列刻意少放命令和配置（那是 [Docker 系列](/posts/docker/01-why-docker)和 [DevOps 系列](/posts/devops/01-linux-server-setup)的任务），重点放在每个抽象解决什么问题。原因很实际：命令半年一变，概念十年不动；而且就算你以后全用云托管、一条命令都不敲，这些概念依然是你看懂架构图、做技术选型的语言。

## 什么时候连地图都不需要

第一篇照例给反面视角：什么时候这套东西整个都不用学？

如果你的项目是「本地工具」「学校作业」「跑一次就结束的脚本」——不对外提供服务，没有用户，没有数据要保护——那部署世界与你无关，这篇地图看完就可以走了。

还有一个更大的边界：就算要上线，你也可以选择完全不解底层——直接用 [Vercel](https://vercel.com) 或 Railway 这类 PaaS，git push 完事。这是 09 篇的内容。但注意，**「不用自己搭」和「不用懂」是两回事**：选 PaaS 还是自己租机器、Redis 用云的还是自己开个容器、备份策略怎么定——这些决策依然要求你看得懂地图。托管服务消灭的是运维的体力活，不是架构的判断题。

## 小结与下篇预告

这一篇没有讲任何具体技术，只做了一件事：把「从代码到用户可访问」之间的距离切成六层，每个名词钉上位置。

下一站是地图最底下的运行环境层，从一个所有开发者都听过的哀嚎开始：**「我这本地明明能跑啊？」**——jar 包一模一样，本地好好的，服务器上就是起不来。Docker 十年前就是被这句哀嚎逼出来的，我们看看它到底怎么把「环境」这个问题连根拔掉的。
