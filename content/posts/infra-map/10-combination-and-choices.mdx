饭桌上朋友问你：「我那个卖手作耳环的小程序，后端加数据库，要不要上 K8s？他看课程说现在都是 K8s 部署。」

九篇之前，你大概会含糊地说「看情况」。现在你可以说得非常具体：「你的日活撑死两千，一台服务器跑 Docker Compose 就够，数据库用云 RDS 最省事，一年总成本一千出头。K8s 是给几十台机器二十个服务管不过来的场景用的，你现在用它，就像骑自行车装涡轮增压——不是不能装，是你会把命搭在维护涡轮上。」

这就是收官篇要交付的能力：**把九篇的地图收进口袋，遇到具体项目时掏出来做裁剪**。先回答那个从第一天挂到现在的问题。

## 直接回答：用几样？

**「都会用到」是幻觉。** 它来自大厂工程师的幸存者偏差——他们的架构图确实每层都有，但那是被千万级流量逼出来的。真实世界的项目绝大多数停在地图的下半部分。按规模给四档典型组合：

| 档位           | 典型规模        | 用到的层                              | 具体组合                                                             | 月成本量级         |
| -------------- | --------------- | ------------------------------------- | -------------------------------------------------------------------- | ------------------ |
| 个人项目       | 日活 0~1k       | 环境 + 编排 +（托管）                 | 1 台服务器 + Docker Compose；甚至 Vercel/Railway 全托管              | 0~100 元           |
| 小团队（初创） | 日活 1k~10w     | + 交付 + 数据（托管）+ 黑盒监控       | 2~3 台机器 + Compose、云 RDS + 云 Redis、GitHub Actions、UptimeRobot | 500~3000 元        |
| 中型公司       | 日活 10w~百万级 | + 编排（托管 K8s）+ 流量 + 完整可观测 | 托管 K8s、RDS 高可用/分片、全套三支柱监控、灰度发布流程、专职运维    | 数万元             |
| 大厂           | 千万级以上      | 全部 + 超纲项                         | 自建+托管混合、多机房多活、Service Mesh、自研平台                    | 不适用（自有团队） |

对着地图看这个表的规律：**每一档都是前一档加上一两个新层，而不是换一套**。Docker 从第一档用到最后（镜像是最底层的通用语）；Compose 到第二档为止（K8s 接棒，但很多公司的 CI 环境和本地开发依然跑 Compose）；备份监控从第二档开始就再没消失过，只是形态从「cron + UptimeRobot」升级成「跨地域容灾 + on-call 体系」。

还有一个容易被忽略的观察：**第二档覆盖了世界上绝大多数赚钱的生意**。一个日活五万的工具类产品，足够养活一个不错的团队——而它的全部基础设施，就是三台机器加几个托管服务。从第二档往第三档的跨越不是因为「长大了就该上 K8s」，而是被具体的痛逼过去的。什么算具体的痛？这就是下一节。

## 演进触发器：什么信号出现，才引入下一层

九篇里每篇结尾的「什么时候不需要它」，反过来读就是「什么时候需要」。全部收拢成一张表——**左边是真实出现的信号，右边才是你该引入的技术**。信号没出现，右边的东西就是负资产：

| 你遇到的信号（真实成本）                     | 该引入的层         | 对应篇章 |
| -------------------------------------------- | ------------------ | -------- |
| 同一份代码在两台机器行为不一致               | Docker             | 02       |
| 容器超过两三个，手动 run 和记性开始出错      | Compose            | 03       |
| 每周手动上线两次以上，或上线出过人肉事故     | CI/CD + 环境分离   | 04       |
| 一次宕机的业务损失大于一台机器一个月的成本   | 多机 + 负载均衡    | 05       |
| 容器散在 3+ 台机器，发布/迁移/补位靠人肉脚本 | Kubernetes（托管） | 06       |
| 数据丢了赔不起 / 说不清会丢多少              | 备份体系 + RDS     | 07       |
| 出过「系统挂了自己最后知道」的事故           | 三层监控 + 告警    | 08       |
| 运维占用了写业务的时间                       | 托管 / PaaS        | 09       |

用这张表的方式不是「对照打勾」，而是**每次痛了来查**。真实系统的演进从来不是规划出来的，是被一个个具体事故推着走的——ShopLite 十篇走的路，就是这条被推着走的路。

也要诚实地说反向的坑：**信号出现了却忍着不引入**同样有害。磁盘三次写满才想起来配告警、数据库手滑删了表才发现备份从没恢复过——忍的成本最后都变成了事故的账单。表的价值是让「引入时机」从感觉变成可讨论的问题：下次团队争论「要不要上 K8s」，先把「容器在几台机器上、发布出过几次人肉事故」摆在桌面上——数字会替你们吵完。

## 一条诚实的学习路线

最后回答「接下来怎么学」。先说一个容易踩空的路径：**从名词清单开始背**。K8s 的对象背得很熟、Docker 命令能默写，但遇到「磁盘 85% 该怎么办」一片空白——这就是没有走过演进链、直接背结论的样子。这个系列的方法论从头到尾就一条：**每个技术先看它治什么病，再看它的药理**。所以路线也按演进链排：

**第一段：亲手走完单机三部曲（所有人相同，无捷径）。** 拿一个自己的真实项目（不是 demo）：给它写 Dockerfile、配 docker-compose 把数据库一起编排起来、再接一条 GitHub Actions 自动部署到一台云服务器。这段路覆盖 02-04 篇，是**从个人项目到大厂都共用的底座**，也是唯一一段必须亲手做、看文章替代不了的——坑（网络不通、权限不对、镜像死循环）都在手上。

**第二段：把 K8s 当阅读理解，不当必修课。** 用 kind 或 minikube 在本地起一个单机集群，把 06 篇的对象地图亲手敲一遍（一个 Deployment + Service + Ingress 跑起来），体会「声明式对账」的手感。到此为止——**生产级 K8s 的运维经验，等工作里真的接触再补**，脱离规模空学调度和排障，忘得比学得快。

**第三段：把托管产品用出深度。** 日常工作里大概率你面对的是 RDS、托管 K8s、对象存储这些成品。把 07/09 篇的概念对着控制台参数过一遍（备份保留期对应 RPO、多可用区对应哪级故障），「看懂说明书」就是大多数岗位需要的全部深度。

**第四段（可选）：三支柱实操。** 如果方向偏运维/SRE，Prometheus + Grafana + 集中日志（EFK）自己搭一套——[DevOps 系列](/posts/devops/08-monitoring-prometheus-grafana)有完整手册。

面试视角补一句（学生会关心）：这一类知识的高频问法恰好就是本篇的骨架——「为什么用 Docker」「K8s 解决什么问题」「什么时候不该上微服务/K8s」「主从和备份什么区别」。**能答好「什么时候不用」的候选人从来比只会答「怎么用」的少**，而前者才是拉开差距的地方。

## 写在最后

十篇之前的问题是：「Docker、K8s、集群、多个数据库——这些名词我都听过，但不知道它们之间是什么关系、什么时候轮到谁登场。」

现在再看这句话，你已经拥有了一张完整的地图和一条走通的路径：一切从**环境不一致**开始（Docker），到**单机编排**（Compose），到**自动化交付**（CI/CD），到**消灭单点**（集群与负载均衡），到**跨机调度**（K8s），到**数据兜底**（复制与备份），到**生产现实**（监控与隐性清单），到**花钱买省心**（托管光谱）。每一站都是被上一站的痛逼出来的，**没有一个技术是为了简历而存在的**。

ShopLite 也走到了它的终点：托管 K8s 上自动扩缩容的一组 Pod，身后是 RDS 高可用集群和跨地域备份，头顶是三层监控和自动化告警。以这个故事的标准，世界上大部分系统永远到不了这个终点——**而它们照样运转得很好，这正是这套地图最想告诉你的事：技术是用来回答问题的，不是用来堆叠的。问题有多少，技术用多少。**
