# 部署基础设施地图：从一台服务器到集群

## 背景

backend-map 系列回答了"应用怎么拆"——从单体到微服务、服务间怎么通信。但拆出来的东西怎么**跑起来**，是另一个世界：Docker、K8s、集群、多数据库、CI/CD……这些名词的关系同样是一张演进补丁链，而且比应用架构侧更抽象（看不见摸不着，全是基础设施）。

本系列与 backend-map 同为**扫盲/地图型系列**：目标是建立「名词 → 解决什么问题 → 在整体中处于哪一层 → 一般会不会真的用到」的认知地图，不教操作细节。核心叙事延续 backend-map 的方法论：**每个基础设施技术都是被上一个阶段的新问题逼出来的**。

- 文章类型：A（技术类）
- 核心诉求（来自读者原话）：
  1. Docker、K8s、多服务、多数据库、集群这些概念模糊 → 串起来
  2. 明白这些是为了解决什么问题的 → 演进故事线
  3. 没想到的东西也要一并加入 → 主动补盲区（环境分离、密钥管理、备份灾备、无状态/有状态、云托管、单点故障……）
  4. 如何组合使用、一般用几个还是全用 → 收官篇按规模给典型组合，反过度设计

## 贯穿案例：ShopLite 上线之旅

延续 backend-map 的迷你电商 ShopLite（读者已熟悉，零认知成本）。起点是 backend-map 收官时的状态：

```
4 个微服务：gateway / order / product / user（Spring Boot 应用）
4 个中间件：MySQL（订单+用户库） / Redis（缓存+Session） / RocketMQ / Nacos
跑在哪儿：开发者自己的笔记本上，idea 里点绿色按钮启动
```

演进主线（与文章目录一一对应）：

```
阶段 0：笔记本上的 4+4，怎么变成用户能访问的系统？（01）
阶段 1：上服务器 → 环境不一致爆炸 → Docker（02）
阶段 2：8 个容器手动管不动 → Compose（03）
阶段 3：每次上线手动敲命令 → CI/CD + 环境分离 + 配置密钥（04）
阶段 4：单机扛不住/挂了就全挂 → 多机集群 + 负载均衡（05）
阶段 5：几十个容器散在几台机器 → K8s（06）
阶段 6：数据是命 → 多数据库分工 + 备份灾备（07）
阶段 7：上线只是开始 → 监控告警 + 半夜炸的隐性清单（08）
阶段 8：能不能不自己搭 → 云托管 / PaaS / Serverless（09）
收官：按规模选组合——你到底需要几样（10）
```

## 每篇文章大纲

### 01 从代码到用户可访问：一张部署地图

- 学习目标：建立"部署世界"的全景名词地图，知道后续每篇在地图哪个位置
- 核心问题："ShopLite 在笔记本上跑得好好的，怎么变成用户能访问的系统？中间隔着哪些东西？"
- 主线场景：第一次要上线——租了台云服务器，然后发现不知道从哪开始
- 内容要点：
  - 一台服务器手动跑 4 个服务 + 4 个中间件是什么体验（环境安装、启动顺序、SSH 手动重启）
  - 部署世界的分层地图：运行环境层（服务器/容器）→ 编排层（Compose/K8s）→ 交付层（CI/CD）→ 流量层（DNS/LB/网关）→ 数据层（多数据库/备份）→ 托管层（云服务）
  - 名词总览表：每个名词一句话 + 全系列哪篇展开
  - 全系列演进故事线预告（流量/可靠性增长的补丁链）
- 与前篇关联：backend-map 收官篇的"最终架构图"是本篇起点

### 02 "我本地能跑啊"：Docker 与环境一致性

- 学习目标：理解镜像/容器/仓库三概念，Docker 解决的真正问题
- 核心问题："本地 JDK 17 服务器 JDK 8、本地 MySQL 8 服务器 5.7——同一个 jar 两台机器两个行为"
- 主线场景：上线当晚 order 服务起不来，报 NoSuchMethodError，本地一模一样的 jar 却好好的
- 内容要点：
  - 环境漂移（works on my machine）的具体表现；依赖清单式安装（装文档）为什么治不了
  - 镜像 = 环境+代码+依赖的只读快照；容器 = 镜像的运行实例；类比：镜像是类，容器是实例（或：镜像 是安装盘，容器是跑起来的系统）
  - vs 虚拟机：为什么不用 VM（启动秒级 vs 分钟级、密度、体积）
  - Dockerfile 是"造镜像的菜谱"；镜像分层与缓存
  - 镜像仓库（Docker Hub / 阿里云 / 私有 Harbor）：镜像怎么从开发机到服务器
  - ShopLite：4 个服务各打一个镜像
- 与前篇关联：01 的"运行环境层"展开

### 03 一台机器跑全部：Compose 多服务编排

- 学习目标：掌握单机多容器编排的概念模型，理解无状态/有状态
- 核心问题："8 个容器手动 docker run，启动顺序、网络互通、端口管理全是坑"
- 主线场景：每次重启电脑要按顺序手动起 8 个容器，漏一个就全崩
- 内容要点：
  - Compose：一个 YAML 描述全部容器、依赖顺序、网络
  - 容器网络（bridge）：容器间用服务名互访（内置 DNS）——呼应 backend-map 的"IP 写死"问题
  - Volume：容器删了数据不能没——数据在容器外的宿主机上
  - **关键概念：有状态（MySQL/Redis）vs 无状态（应用服务）**——为什么应用容器可以随便删随便建，数据库不行；这是 K8s 篇的地基
  - 宠物 vs 牛（pets vs cattle）：容器是临时的，随时可替换
  - restart 策略：挂了自动拉起（单机版的"自愈"）
  - ShopLite：一个 docker-compose.yml 跑起 4+4
- 与前篇关联：02 的镜像有了，怎么组织它们

### 04 从手动到自动：CI/CD 与环境分离

- 学习目标：理解代码→线上服务的自动化流水线，环境与配置分离
- 核心问题："改一行代码，要走 scp 上传、重启容器、手动验证——一天上线三次就是灾难"
- 主线场景：周五晚上手动上线，敲错一个命令，回滚用了两小时
- 内容要点：
  - CI/CD 流水线：push → 自动测试 → 构建镜像 → 推仓库 → 部署；GitHub Actions / Jenkins / GitLab CI 一句话定位
  - 流水线里的"制品"：jar 时代 vs 镜像时代（为什么容器化让 CD 变简单——环境随镜像走）
  - 环境分离：dev / staging / prod——为什么要三个环境、各自干什么
  - 配置与代码分离：同一份镜像跑三个环境，靠环境变量/配置注入
  - **盲区补课：密钥管理**——数据库密码不能进 git（Secret / 环境变量 / .env 不提交）；提交了怎么办（轮换）
  - ShopLite：第一次 push 触发自动上线
- 与前篇关联：02 的镜像仓库是流水线的枢纽

### 05 单机到多机：集群与单点故障

- 学习目标：理解集群的本质、负载均衡全景、高可用含义
- 核心问题："服务器一重启，整个 ShopLite 全挂——所有东西都在一台机器上"
- 主线场景：云厂商通知服务器宿主机维护要重启，你意识到没有任何冗余
- 内容要点：
  - 单点故障（SPOF）：逐个数当前架构里的单点（应用一台、MySQL 一个、Nginx 一个、机房一个）
  - 集群的本质：一堆对等的机器 + 一个调度/分发者
  - 负载均衡全景（引用 backend-map 02 不重讲 Nginx 配置）：DNS 轮询 → 四层 LB（云 LB）→ 七层（Nginx/网关）；健康检查摘除
  - 高可用（HA）的真正含义：每个环节 ≥2，但这只是应用层——**数据库不能简单复制两份**（数据一致性），留到 07
  - 无状态应用随便复制的回报：03 篇的概念第一次兑现
  - 多机的现实问题：8 个容器怎么分布在 3 台机器上？哪台挂了容器怎么迁移？→ 引出 06
- 与前篇关联：03埋的"无状态"在这里兑现；引出 K8s 的必要性

### 06 几十个容器怎么管：K8s 对象地图

- 学习目标：建立 K8s 核心对象地图，理解声明式与自愈
- 核心问题："3 台机器 20 个容器，谁放哪台？挂了谁拉起？发布怎么不停机？"
- 主线场景：扩到 3 台机器后，你写了个"容器分布脚本"，维护两周后放弃了
- 内容要点：
  - Compose 为什么不够：单机边界、无自愈、无跨机调度、扩缩容手动
  - K8s 是什么：集群操作系统——把 N 台机器抽象成一台大机器
  - 核心对象地图（重头戏，配架构图）：
    - Node（机器）→ Pod（最小调度单元，1~N 容器）→ Deployment（声明几个副本+滚动发布）
    - Service（稳定访问入口 + 内置 LB + DNS）→ Ingress（七层入口/路由）
    - ConfigMap / Secret（配置与密钥注入，呼应 04）
  - 声明式 vs 命令式："我要 4 个副本" vs "你去起一个"——控制循环持续对账
  - 自愈：Pod 挂了自动重建、节点挂了容器漂移；健康检查（liveness/readiness）简述
  - HPA：按 CPU 自动扩缩容
  - **重要回响：K8s Service 接管了注册中心的职能**（呼应 backend-map 05 的预告；Nacos 只留配置中心职责）
  - 有状态的数据库怎么办：StatefulSet 一瞥 + 更常见的做法是"数据库不放 K8s"（留 07/09）
- 与前篇关联：05 提出的跨机调度问题在此解决

### 07 为什么有好几个数据库：分工与备份

- 学习目标：理解多数据库分工逻辑、数据库集群与应用集群的差异、备份灾备
- 核心问题："MySQL、Redis、ES……为什么不能一个数据库走天下？数据安全靠什么兜底？"
- 主线场景：大促前夜磁盘报警，你突然发现从来没测过"从备份恢复"
- 内容要点：
  - 多数据库的分工：MySQL（交易数据，强一致）+ Redis（缓存/Session，快但易失）+ ES（搜索）——每个解决一类访问模式（引用 backend-map 03）
  - 数据库集群 ≠ 应用集群：应用复制是无状态的随便复制；数据库复制要解决**数据一致性**——主从复制、读写分离、哨兵/自动故障转移、分片
  - **盲区补课：备份与恢复**——全量+增量、异地备份、RTO/RPO 两个指标；"没验证过的备份等于没有备份"
  - 缓存数据丢了怎么办：Redis 数据丢了到底多严重（可重建 vs 不可丢）——数据分级
  - 现实常见做法：数据库用云托管（RDS）而不是自己运维——留 09 展开
  - ShopLite：MySQL 主从 + 每日备份 + Redis 持久化策略选择
- 与前篇关联：06 的 StatefulSet 遗留问题；backend-map 03/09 的一致性话题在基础设施侧的呼应

### 08 上线之后的现实：监控与半夜炸的事

- 学习目标：建立"生产化隐性清单"，理解监控告警的兜底逻辑
- 核心问题："部署完不是结束——证书过期、磁盘写满、日志把磁盘撑爆，这些没人提前告诉你"
- 主线场景：凌晨三点用户打电话说网站打不开——HTTPS 证书过期了，而你根本不知道证书有有效期
- 内容要点：
  - 生产环境隐性事故清单（读者大概率没想到的）：
    - HTTPS 证书过期（Let's Encrypt 90 天 / 自动续期）
    - 磁盘被日志写满（日志轮转 logrotate / 容器日志限制）
    - 备份一直在跑但从没恢复验证过（呼应 07）
    - 依赖的安全漏洞没人升级（镜像扫描、基础镜像更新）
    - 时区/时间漂移这种小事引发的诡异 bug
  - 监控告警兜底：基础设施层监控（节点存活、CPU/内存/磁盘）+ 应用层（引用 backend-map 10 的三支柱，不重讲）；四黄金指标回顾
  - K8s 的自愈边界：能拉起崩溃的进程，拉不回写满的磁盘
  - 告警哲学简述：面向症状告警（引用 backend-map 10）
  - ShopLite：一次完整的"磁盘写满→服务假死→告警→处理"复盘
- 与前篇关联：07 的备份验证；backend-map 10 的可观测性在基础设施侧落地

### 09 不用自己搭：云托管、PaaS 与 Serverless

- 学习目标：理解自建/托管/Serverless 的光谱，成本与控制力的权衡
- 核心问题："02-08 讲的都要自己搞？中小企业和个人到底怎么干？"
- 主线场景：老板看了 K8s 学习成本和招聘成本，问"有没有更省的办法"
- 内容要点：
  - 云托管光谱：自建（ECS 上全部自己装）→ 托管组件（RDS/云 Redis/托管 K8s/对象存储/CDN）→ PaaS（Vercel/Railway/Render，git push 即部署）→ Serverless（函数计算，按调用计费，无常驻实例）
  - RDS 为例：自己运维 MySQL 要做什么（高可用、备份、升级、监控、安全补丁）vs RDS 一键得到；代价：贵、被锁定、参数受限
  - 托管 K8s（EKS/ACK）：控制面云厂商管，你只管业务容器
  - Serverless 的适用边界：流量波动大、事件驱动（无访问不计费）；冷启动；不常驻=不适合长连接/后台任务
  - **认知纠偏：大部分公司用的是托管服务，不是自建**——02-08 学的概念在托管模式下依然适用（你依然要懂镜像、网络、备份策略，只是不用亲手搭）
  - ShopLite 的三种部署方案报价对比（自建 / 托管 / PaaS）
- 与前篇关联：07 埋的"数据库用 RDS"；04 的 CI/CD 在 PaaS 上退化为 git push

### 10 收官：组合与选型，你到底需要几样

- 学习目标：按项目规模选择基础设施组合，建立反过度设计的判断力
- 核心问题："这些东西是都用上，还是挑几个？大多数实际项目长什么样？"
- 主线场景：朋友看了系列问你"我的 XX 项目该用什么"，你发现自己能给出干脆的答案了
- 内容要点：
  - **核心答案：按规模的典型组合表**（回答"一般用几个还是都用"）：
    - 个人项目/博客（0-1k 用户）：1 台服务器 + Docker Compose，甚至 Vercel——用到 02/03，跳过 05-07
    - 小团队初创（1k-10w 用户）：2-3 台机器 + Compose/轻量编排 + 云 RDS + GitHub Actions + 基础监控——用到 03/04/07/09
    - 中型公司（10w-百万级）：托管 K8s + 全套数据托管 + CI/CD + 完整可观测性——用到 06/08
    - 大厂（千万级+）：多机房、自建混合、Service Mesh、多活——全用到还要加
  - 演进触发器：什么信号出现才引入下一层（"单机 CPU 持续 70%+"→加机器；"挂一次损失大于一周工资"→高可用；"手动上线每月超过 N 次"→CI/CD）
  - 每层引入的代价：不只是钱，还有认知/人力的税
  - 名词总复习表（全系列 60+ 名词分类速查）
  - 诚实学习路线：个人项目从 Compose 起步亲手踩坑 > 背 K8s 概念；面试视角的高频串讲
- 与前篇关联：全系列的收敛与出口

1. 准确说出 Docker/Compose/K8s/集群/LB/多数据库/CI/CD 各自解决什么问题、处于哪一层
2. 看懂任何一家公司的技术架构图里的基础设施部分
3. 对一个具体项目做出"该用几层"的选型判断，不会被"大厂都用 K8s"绑架
4. 知道生产环境的隐性风险清单（证书/磁盘/备份/密钥）
5. 分清自建/托管/Serverless 的边界，理解"大部分公司用托管"
6. 知道下一步深入学什么（互链 docker / devops 专项系列）
