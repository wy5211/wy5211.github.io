上一篇结尾你留下了一份「容器分布脚本」，四周后的现在，它是全公司最神秘的文件——只有你看得懂，而你也开始看不懂了。

三台机器的真实使用体验可以浓缩成三句话。**发布麻烦**：order 服务在 A、B 两台机器上各有容器，每次发布要在两台机器各执行一遍 pull + 重建，还得按顺序来，两台同时重建等于服务中断。**摆放靠人脑**：A 机器磁盘快满了，C 的 CPU 还闲着，挪容器靠手动，挪完还要人肉更新登记表。**最要命的是搬家不存在**：B 机器宿主机维护重启，它上面的容器就跟着消失了——`restart: unless-stopped` 只管本机进程崩了拉起，**机器本身没了，没有任何机制把它的容器在别的机器上重新拉起来**。

这三句话指向同一个缺口：需要一个**俯瞰所有机器的调度者**。这一篇讲它——Kubernetes（K8s）。名词密度预警：这一篇的名词是全系列最多的，但每个名词都对应你已经遇到过的一个麻烦，我们按麻烦讲。

## K8s 是什么：把 N 台机器变成一台大机器

一句话定义：**Kubernetes 是集群的操作系统**。单机的操作系统管理 CPU、内存、磁盘，把进程调度到资源上；K8s 管理一个机器集群，把容器调度到机器上。对你的应用来说，效果是——**三台机器（或三十台）在逻辑上是一台大机器**，你不再关心容器放在哪台物理机上，就像写 Java 时不需要关心对象分配在内存哪个地址。

它的结构分两半：

```
控制面（Control Plane）—— 大脑
├── API Server：唯一入口，你所有的操作都是跟它打交道
├── Scheduler：决定新容器放哪台机器（资源够不够、分散不分散）
└── Controller Manager：持续对账（马上讲，K8s 的灵魂）

工作节点（Node）—— 手脚，就是那三台机器
└── kubelet：每台机器上的代理人，负责"在本机把容器按大脑说的跑起来"
```

大脑自己也要跑在机器上（通常 3 台保证大脑自身高可用）。中小团队几乎不会自建这套大脑——云厂商的托管版（EKS/ACK，09 篇）把控制面包了，你只管用。**记住唯一入口是 API Server 就够了**：你写 YAML、提交给它，其余的一切都是它协调的。

## 声明式：K8s 的灵魂，一句话的革命

使用 K8s 的方式和你以往的一切操作习惯有一个根本区别。对比一下「把 order 服务从 2 个副本扩到 4 个」：

```
命令式（Compose 时代）：到每台机器上 docker run 两个新容器，自己保证别重别漏
声明式（K8s）：提交一份 YAML，说「order 应该跑 4 个副本」——完
```

你**不执行任何动作**，只描述期望状态（desired state）。K8s 里的控制器（Controller）持续运行一个循环：**对账（reconcile）**——「期望 4 个，实际只有 2 个？起 2 个。实际有 5 个？杀掉 1 个。某个 Pod 所在的机器挂了，实际数量跌了？在别的机器补一个」。

这个控制循环（control loop）是 K8s 一切魔法的来源，值得单独拎出来体会：

- **自愈不需要专门的故障处理逻辑**——机器挂了导致副本数低于期望，对账循环顺便就把这事修了。挂机器和日常运维走的是同一条代码路径。
- **声明永远生效**——不是「执行完就结束」的脚本，而是一直立在那里的意图。有人手滑杀掉一个容器？几十秒内对账循环发现实际状态偏离声明，自动补回。**系统会持续向声明收敛**。
- 它是 04 篇「不可变基础设施」的彻底版：改配置不是登录机器修改，而是提交新声明，让系统整体替换。

好，抽象讲完了。剩下的全是名词——但它们组织得意外整齐：**六个核心对象，两两一组，正好三对**。

## 对象地图之一：Node 与 Pod——机器和最小部署单元

**Node** 就是集群里的一台机器（物理机、虚拟机都行）。没什么好说的，地基。

**Pod** 是 K8s 的最小调度单元——**不是容器**。一个 Pod 里放 1 个到 N 个容器，它们共享网络（同一个 IP，互相用 localhost 通信）和存储卷，被一起调度、一起生死。

为什么最小单元不是容器？看一个真实场景就懂：order 服务经常需要一个「伴生」能力——把日志按特定格式转发出去。你可以把这个功能塞进 order 的 Java 进程里（耦合），也可以做成独立小容器放进**同一个 Pod**，共享网络和文件，各干各的、独立升级。这种伴生容器有个专属名字叫 **Sidecar**（边车），是 K8s 世界最经典的设计模式之一。

实践中的常态是**一个 Pod 一个容器**——Pod 这个包装层大多数时候是透明的，但你得知道它存在，因为 K8s 的一切其他对象操作的都是 Pod，不是容器。

## 对象地图之二：Deployment——副本数与发布

Pod 会被调度、会死、会换 IP、名字里带随机后缀——**你永远不直接管理 Pod**。管理它的是 **Deployment**，回答两个问题：这个服务跑几个副本？发布新版本怎么换？

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 4 # 期望状态：4 个副本
  selector:
    matchLabels: { app: order }
  template: # Pod 的模板
    metadata:
      labels: { app: order }
    spec:
      containers:
        - name: order
          image: registry.../order-service:a1b2c3d # 04 篇的制品 tag
          ports: [{ containerPort: 8080 }]
```

`replicas: 4` 就是上一节那个对账循环的输入：机器挂了导致实际副本跌到 3，控制器自动在健康节点上补 1 个——**上一篇「容器不会搬家」的问题，在这行 YAML 里被顺手解决了**。

发布新版本=改 `image` 的 tag、重新提交。K8s 的做法叫**滚动发布（rolling update）**：不是停掉全部旧 Pod 再起新的，而是按批次——起 1 个新 Pod → 健康检查通过 → 杀 1 个旧 Pod → 再起 1 个新的……全程始终有副本在服务，**发布不再需要「挑流量低峰」，因为它不再意味着中断**。回滚也一样：`kubectl rollout undo`，因为旧镜像还躺在仓库里（04 篇的制品三性质在这里兑现——不可变、可追溯、可回滚）。

## 对象地图之三：Service——稳定入口与被收编的注册中心

Pod 会死会重建、IP 会变——**谁来给 Pod 一个稳定的访问地址？** **Service** 对象。它做三件事：

1. **稳定名字**：`order-service.default.svc.cluster.local`，集群内任何地方用这个名字访问（通常直接写短名 `order-service`）
2. **内置负载均衡**：名字背后是所有健康的 order Pod，流量自动分摊
3. **健康过滤**：某个 Pod 不健康就把它摘出分发名单——上一篇云 LB 的健康检查，在集群内部再来一遍

对照一下你在学的东西：Service 的名字解析+负载均衡+健康摘除，是不是很眼熟？**这就是注册中心干的事**。[后端技术地图第 5 篇](/posts/backend-map/05-spring-cloud-map)埋过一个预告：跑在 K8s 上的系统，注册中心的职能被基础设施接管。现在你能看清接管的姿势了：Pod 启动时自动贴上标签（label），Service 靠标签圈定自己的后端名单——**没有「注册」这个动作，Pod 的生与死本身就是在增删名单**。Nacos 在 K8s 世界里只剩一个职责：配置中心（配置下发、动态刷新），服务发现那一半可以下班了。

Service 之上还有一个 **Ingress** 对象管七层入口：HTTP 路由（`/api/order` 给谁）、TLS 证书在哪卸载——相当于把 04 篇谱系里「七层」那一格也做成了声明式对象。加上云厂商的四层 LB（K8s 里叫 LoadBalancer 类型的 Service），上一篇那张流量谱系图在 K8s 里全部落地。

## 补完拼图：ConfigMap 与 Secret

最后一对对象解决「同一个镜像、不同环境」——04 篇讲过的原则「一次构建、处处运行」，K8s 的实现就是 **ConfigMap**（普通配置）和 **Secret**（密码密钥）：把配置作为集群里的对象存着，启动 Pod 时注入成环境变量或文件。镜像里不含任何环境相关的信息，环境差异全部存在于集群侧的声明里。

顺带说一句 Secret 的真相：它默认只是 base64 编码而不是加密，**真正的防护是 RBAC 权限（谁有权限读）和 etcd 的静态加密**——生产上一般还会对接外部的密钥管理服务。这个细节的意义不在技术，在观念：**安全从来不是某个组件的单打独斗，而是体系**。

## 三个没讲但重要的词

篇幅原因，三个名词只做指路牌：

**健康检查的两层**：liveness（进程活着吗？不活就重启它）和 readiness（能接流量吗？不能就先别分给它）。后者解决的是「活着但假死」——Java 进程还在，Full GC 卡了 30 秒，readiness 探测失败，Pod 被摘出名单，恢复后再加回来。滚动发布的「新 Pod 健康检查通过才继续」用的就是它。

**HPA（自动扩缩容）**：副本数不再写死，声明「CPU 超 60% 就加副本，最高 10 个」——大促自动扩容、闲时自动缩回的工作从此消失。上一篇「大促前手动扩容」的场景，到这里自动化闭环。

**request/limit**：每个容器声明自己需要多少 CPU/内存，调度器据此决定放哪台机器。不声明的后果是资源被吃光、节点雪崩——这是 K8s 实践里最常见的翻车点之一。

## 数据库去哪了：StatefulSet 与「不放进 K8s」

细心的你可能发现对象地图里少了一类东西：MySQL、Redis 这些**有状态**的服务在哪？

K8s 确实为它们准备了一个对象（**StatefulSet**：稳定名字、稳定的存储绑定、按序启动——为数据库这种「每个实例不平等」的东西设计）。但实践中更常见的选择是：**有状态服务干脆不放 K8s 里**。原因正是 03 篇那张对比表：数据库的复制要解决数据一致性（主从、故障转移），这套复杂度叠上 K8s 的复杂度，运维成本翻倍；而云厂商的托管数据库（RDS 之类）把整套高可用做成了产品。所以典型架构是：**K8s 管无状态的应用 Pod，数据库在集群外面**（云托管或独立机器），Pod 通过 Service/外部地址连过去。「计算用编排、数据用托管」这个分工，09 篇展开。

## 什么时候不需要 K8s

照例的反面视角，而且这次要说得格外用力，因为 K8s 是被过度使用重灾区：

- **机器少于 3 台、服务少于 10 个、没有专职运维**——K8s 是负资产。它的学习曲线（今天这 2000 字只是目录）和自身运维成本（证书、升级、排障）是真实存在的税，而它换来的收益（跨机调度、自愈、自动扩缩）在你这个规模下用 Compose + 云 LB + 两台机器也能覆盖八成。
- 判断信号不是「公司有多少人」，而是：**容器是不是已经散在多台机器上、且人肉管理开始出错**。ShopLite 现在就该上 K8s 吗？——三台机器二十个容器，处在灰色地带；真实世界里这个规模的团队大多选择托管 K8s（把控制面的运维外包给云厂商，09 篇）来摊薄税负。
- 一个中间态值得知道：Swarm、Nomad 这类轻量编排工具，功能子集、心智负担小——虽然生态上已经边缘化，但它们的存在本身说明「编排不等于必须 K8s」。

## 小结与下篇预告

- **K8s = 集群操作系统**，把 N 台机器抽象成一台大机器；唯一入口是 API Server，用法是提交声明
- **声明式 + 控制循环**是灵魂：你描述期望状态（4 个副本），系统持续对账向它收敛——自愈、容灾、扩容全是同一条代码路径
- **对象地图三对六**：Node/Pod（机器与最小单元）→ Deployment（副本与滚动发布）→ Service/Ingress（稳定入口与流量）；ConfigMap/Secret 兑现「一次构建处处运行」
- **Service 收编注册中心**：后端技术地图的预告兑现——Pod 的生死本身就是服务名单的增删，Nacos 只剩配置中心职责
- 数据库通常**不放 K8s**：有状态的复杂度交给托管或独立部署——「计算用编排、数据用托管」
- 反面视角：K8s 解决的是规模问题，规模没到，它是税不是资产

到这里，**计算这一层**的故事讲完了：从环境一致（镜像）到单机编排（Compose）到集群调度（K8s），应用可以无限复制、自愈、滚动发布。但有个东西从 03 篇拖到现在一直没正面处理——**数据**。MySQL 依然只有一份，它依然是那个最硬的单点；备份只在做而没验证过；Redis 和 MySQL 和 ES 为什么会同时存在也还没说透。下一篇讲数据层：多数据库的分工、数据库与应用完全不同的集群逻辑、以及「没验证过的备份等于没有备份」。
