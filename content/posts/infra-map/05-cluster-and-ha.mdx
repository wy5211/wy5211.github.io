周四下午两点，服务器内存耗尽，内核 OOM 杀掉了 MySQL 容器，连带几个 Java 服务一起崩了。从告警到手动恢复，ShopLite 全站下线 40 分钟。复盘的时候你在白板上画了画当前架构，然后意识到一个冰冷的事实：

```
一台服务器
├── 4 个应用容器     ← 全在这台机器上
├── 4 个中间件容器   ← 全在这台机器上
└── 这台机器本身     ← 它挂了，上面所有东西一起陪葬
```

不是哪个环节脆弱的问题——**你的整条链路就是一个环节**。这个词有个正式名字：**单点故障（Single Point of Failure，SPOF）**。这一篇就从这个盘点开始，讲清三件事：单点怎么数、机器加到多台之后流量怎么分、「高可用」这三个字真正的含义。

先把上一篇结尾的伏笔收了：之所以能讨论「加机器」，是因为 03 篇你已经把状态从应用里抽干净了——Session 在 Redis、文件在卷里、应用容器是无状态的牛。**无状态是水平扩展的入场券**，现在兑现它。

## 数一数你的单点

把「挂了会导致服务不可用」的组件全列出来，这张清单就是高可用的作业范围：

| 单点               | 挂掉的方式               | 影响范围                    |
| ------------------ | ------------------------ | --------------------------- |
| 应用服务器（1 台） | 宿主机维护、OOM、磁盘满  | 全站                        |
| MySQL 容器         | OOM 被杀、磁盘满、进程崩 | 全站（数据还在）            |
| Redis 容器         | 同上                     | 登录态失效、缓存穿透打穿 DB |
| gateway 容器       | 进程崩                   | 全站                        |
| 这台物理机/机架    | 断电、网络、云厂商故障   | 全站                        |

逐个消灭它们的总思路只有一个：**让每个组件的存在数量大于等于 2，且任何一个消失时流量能自动切走**。前半句靠加机器，后半句靠一个新角色——负载均衡器。

## 集群的本质：一群对等的机器 + 一个分发者

**集群（cluster）** 这个词在前几篇出现过好几次，现在给它一个准确定义：**一组对等的机器，做同样的工作，对外表现为一个整体**。关键词是「对等」——任何一台都能干任何一台的活（无状态才做得到），挂掉任何一台，剩下的接着干。

从一台到三台，你的架构变成：

```
                         ┌→ 服务器 A：order ×2, product, gateway
用户 → 分发者（LB）─┼→ 服务器 B：order ×2, user, redis?
                         └→ 服务器 C：MySQL, RocketMQ, Nacos
```

注意那个「分发者」——三台机器各自有 IP，但用户只会访问 `shoplite.com`。**谁来把一个请求交给三台机器中的一台？** 这就是负载均衡器，[后端技术地图第 2 篇](/posts/backend-map/02-cluster-and-session)从应用视角讲过它（Nginx 怎么分活、Session 为什么会丢），这里从基础设施视角补全整个谱系。

## 负载均衡的三层谱系

### 第一层：DNS 轮询——最原始的分发

域名解析的时候返回多个 IP：

```
shoplite.com  →  A 记录：1.2.3.4, 1.2.3.5, 1.2.3.6
```

用户访问时拿到其中一个。零成本，但缺陷致命：DNS 有缓存（TTL 没到，摘不掉死机器）、不知道机器死活（没有健康检查）、分发粒度粗。**DNS 轮询今天几乎只作为最外层的第一道**（或者干脆只解析到负载均衡器的一个 IP），不能单独承担分发。

### 第二层：四层负载均衡——云厂商的入门款

工作在 TCP/IP 层（OSI 第四层，所以叫四层）：只看 IP 和端口，把网络包转发给后端某台机器。你租的每朵云都有这产品（阿里云 SLB/CLB、AWS NLB），按月付费，自带两个关键能力：

- **健康检查**：定期探测后端机器的端口，不通就自动把这台从分发名单里摘掉——**这就是「自动故障转移」**，机器 A 挂了，流量在几秒内全部落向 B 和 C，用户只觉得刚才那个请求慢了一点。
- **自身是高可用的**：云 LB 背后本身就是集群，你不用操心它自己成为单点（这个保证值回票价）。

### 第三层：七层负载均衡——看得懂 HTTP 的分发者

工作在 HTTP 层（第七层），能看懂路径、Header、Cookie，于是能做更聪明的事：`/api/order` 转给订单集群、`/admin` 只允许公司 IP 访问、TLS 证书在这里统一卸载。Nginx 和 [后端技术地图第 7 篇](/posts/backend-map/07-api-gateway)的 API 网关都属于这一层。

真实系统里三层是叠着用的，顺序正好倒过来读：

```
用户 → DNS（把域名变成 LB 的 IP）
     → 四层 LB（云负载均衡：把包分给几台前置机，健康检查摘除）
     → 七层（Nginx/网关：按路径路由、鉴权、限流）
     → 应用机器
```

ShopLite 规模小，用两层就够：云 LB 直接指向跑 gateway 的机器。但这个谱系值得记——以后看任何架构图，先找流量从哪进来、经过几层分发，这条线读懂了，架构就懂了一半。

## 加机器之后，麻烦换了一批

三台机器跑起来，周四那种「一台挂全站挂」的恐惧确实消失了。但一周之内你收获了新麻烦：

**发布变麻烦了。** 以前 `docker compose up -d` 一次搞定，现在 order 服务跑在 A、B 两台机器上——发布要在两台机器各执行一遍 pull+重建，还要挑流量低峰、按顺序来（两台同时重建=服务中断）。

**容器分布靠人脑。** 20 个容器怎么摆到 3 台机器上？A 机器磁盘快满了、C 机器 CPU 闲着——挪哪个？手动挪完，登记表格更新了吗？你在第 2 周写了个「容器分布脚本」，第 4 周这个脚本本身成了最需要文档的东西。

**机器挂了，容器不会自己搬家。** 03 篇的 `restart: unless-stopped` 只管「本机进程崩了拉起来」。整台机器挂的时候，它上面的容器不会自动跑到别的机器上——**Compose 的世界以机器为边界，机器没了，它管的一切就没了**。

这三条麻烦指向同一个缺口：**跨机器的统一调度者**——有一个角色俯瞰所有机器，决定容器放哪、挂了搬家、发布时逐台替换。这个东西叫 Kubernetes，是下一篇的全部内容。这里先把它的必要性踩实：不是「大厂都用所以要用」，而是**机器数量乘以容器数量超过人脑管理能力**这个具体问题逼出来的。

## 高可用的完整含义

现在可以给「高可用（High Availability，HA）」一个负责任的定义了。它不是「加了一台机器」，而是一个对架构的持续追问：**任何一个组件消失，服务是否不中断（或秒级恢复）？**

按这个标准重新审 ShopLite 的三台机器架构，会发现只做了一半：

- 应用层 ✓：多副本 + LB 健康检查，挂一台自动摘除
- **MySQL ✗：还是只有一个**。而且它是不能用「再复制一台」解决的——两份 MySQL 各自接收写入，数据立刻分裂成两个版本，谁的为准？（复制数据库要解决数据一致性，07 篇的主从复制、故障转移整套机制都是为这个）
- 机房 ✗：三台机器在同一个机房（云上叫同一个可用区）。机房级故障（断电、光缆被挖断）发生时，三台一起消失。

对最后这条，云厂商的答案是把「至少两个机房」做成产品能力：**可用区（Availability Zone，AZ）**是同城物理隔离的机房，跨 AZ 部署在云上就是选一下参数的事。再往上的**地域（Region）**是异地容灾的维度——整个城市灾难级故障才需要考虑，ShopLite 这个阶段不用想，但你的高可用词汇表里应该有它们的位置。

一个务实的记法：**高可用是买保险，保费是复杂度和成本**。每一层冗余（应用双副本 → 数据库主从 → 跨 AZ → 跨地域）对应一个概率越来越低、代价越来越高的事故场景。买几层，取决于「那次事故发生时你损失多少」对「保费」的比较——这个账到 10 篇选型时一起算。

## 什么时候不需要集群

照例的反面视角，而且这次的反面特别常见：**绝大多数项目，单机 + 快速恢复就够**。

判断标准是恢复时间目标和数据损失容忍度（07 篇会正式介绍 RTO/RPO 这两个词）：如果你的用户能接受「半年挂一次、每次停 30 分钟、数据不丢」，那么一台配置好点的服务器 + 一套经过演练的恢复流程（镜像在仓库、数据有备份、Compose 文件在 git——前四篇攒下的家底），恢复速度可能比一套维护不善的「高可用」架构还快。后者不是玩笑：**冗余架构自身的复杂度就是新的事故来源**，三台机器的集群配置漂移、脑裂、版本不一致，都是单机世界不存在的问题。

真正需要跨过单机门槛的信号：宕机造成了可计算的金钱损失（电商每分钟订单额）、或单机性能真的顶不住了（CPU 持续 70% 以上且垂直升级不划算）。在那之前，把「单机但可快速重建」做扎实，是比「三台机器的伪高可用」更专业的选择。

## 小结与下篇预告

- **单点故障**盘点是高可用的作业范围：逐个组件问「它挂了会怎样」
- **集群** = 一群对等的机器 + 一个分发者；无状态是机器对等的前提（03 篇的概念在此兑现）
- **负载均衡谱系**：DNS 轮询（原始）→ 四层云 LB（包转发+健康检查）→ 七层 Nginx/网关（懂 HTTP 的分发）——真实系统层层叠加
- 加机器后涌现的新问题（跨机发布、容器分布、故障搬家）指向**跨机器的统一调度者**
- **高可用**是逐层买保险：应用副本 → 数据库主从（07 篇）→ 跨可用区 → 跨地域；保费是复杂度，买几层看事故损失
- 数据库不能简单复制——数据一致性是它的独特难题，留给 07 篇

下一篇的主角是 Kubernetes。它就是那个「俯瞰所有机器的调度者」，也是整个部署世界名词密度最高的地方——但拆开看，它不过是在回答三台机器出现后你遇到的那些具体麻烦。我们会用一张对象地图（Node/Pod/Deployment/Service/Ingress）把它讲清楚，还会兑现一个承诺：K8s 是如何把 Nacos 注册中心的职能收编的。
