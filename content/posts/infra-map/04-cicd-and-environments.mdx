周五晚上九点，你给 order 服务加了个小功能，走上线流程：本地构建镜像、打 tag `1.4.2`、推仓库、SSH 到服务器、pull、`docker compose up -d order-service`。然后你在服务器上多敲了一个字符——重建的是 `mysql` 而不是 `order-service`。

三秒钟后你反应过来的时候，MySQL 容器已经带着 Volume 之外的一切消失了。重新拉起、等初始化、确认数据还在、重新走 order 的上线流程——**这次事故里，回滚和恢复花了两小时，而那个功能本身只改了十行代码**。

这个故事的教训不是「下次小心点」。人肉流程的出错概率是恒定的，上线次数越多，事故只是迟早。教训是：**只要一段流程被精确描述过一次，就应该让机器重复它，而不是让人**。这一篇讲怎么做到，以及它顺带逼出来的两个新问题。

## 流水线：把上线流程写成一个文件

CI/CD 的核心抽象就叫**流水线（pipeline）**：代码 push 之后自动触发的一串步骤。ShopLite 用 GitHub Actions 写，大概长这样：

```yaml
# .github/workflows/deploy.yml —— push 到 main 分支时自动执行
name: deploy
on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4 # 拉代码

      - run: ./gradlew test # 跑单元测试（挂了就停，不会部署）

      - run:
          docker build -t registry.../order-service:${{ github.sha }} .
          # 构建镜像，用 commit 哈希做 tag

      - run:
          docker push registry.../order-service:${{ github.sha }}
          # 推到镜像仓库

      - run:
          ./scripts/deploy.sh ${{ github.sha }}
          # SSH 到服务器：pull 新镜像 → up -d
```

从你 `git push` 到用户看到新功能，中间没有任何人肉环节。测试挂了流程就停在第二步，坏代码根本到不了服务器——**这就是 CI（持续集成）的含义：每次提交都被自动验证和构建**。后半段 CD（持续交付/部署）：构建出的制品被自动送到线上。

这里有个值得展开的认知：**容器化让 CD 变得意外地顺**。jar 时代的自动部署要处理目标机器的环境差异（哪台机器 JDK 版本不对就翻车）；镜像时代，部署的定义退化成三步——拉新镜像、换容器、完。回滚也一样：把 tag 切回上一个版本重新 `up -d` 就行，**因为旧版本镜像还在仓库里，随时可以拉回来**。上一篇说「容器是可以随时替换的牛」，这个替换之所以敢自动化，前提正是替换的动作足够廉价、足够无脑。

### 制品：流水线最重要的输出

流水线构建出来的东西叫**制品（artifact）**——对 ShopLite 就是那个带 commit 哈希 tag 的镜像。它有三个性质，后面几篇会反复用到：

1. **不可变**：`order-service:a1b2c3d` 这个镜像的内容永远不变。要改？构建一个新 tag。「改线上配置文件」这种操作从此没有借口——改了就不是那个制品了。
2. **可追溯**：镜像 tag 对应 commit 哈希，线上跑的每个容器都能回答「你是哪次提交构建的」。
3. **可回滚**：旧制品永远躺在仓库里。

「线上跑的东西必须来自制品、且制品不可变」——这条原则叫不可变基础设施（immutable infrastructure），它是后面 K8s 声明式世界的地基。现在先记住味道：**线上不接受手工修改，只接受整体替换**。

## 三套环境：为什么本地和生产的差距要用机器填

流水线搭起来后，你很快撞到一个新问题：**测试应该打到哪？**

你的第一版方案是流水线直接部署到生产服务器。第二个周五，新版本有个 bug，用户先发现。你意识到问题：**自动化的上线流程 + 没有验证环节 = 自动化的出事故流程**。

正确答案是行业早就踩出来的：**环境分离（environment separation）**。同一个系统，跑三套独立实例：

| 环境    | 谁用         | 数据             | 什么时候动它               |
| ------- | ------------ | ---------------- | -------------------------- |
| dev     | 开发者       | 假数据           | 随便搞，每天 N 次          |
| staging | 上线前的验证 | 脱敏的类生产数据 | 每次发布前，走一遍验证清单 |
| prod    | 用户         | 真数据           | 只通过流水线动，无手工操作 |

dev 随便造（可以删库、可以改崩）；staging 是**彩排间**——配置像生产、数据像生产，但没有真实用户，出了事没人知道；prod 只有流水线能碰（你上周五的事故就是「手工碰生产」的代价）。

于是 ShopLite 的流水线变成两段：push 到 main → 部署到 staging → 在 staging 自动跑冒烟测试（下单、查单、支付回调各来一遍）→ 通过后手动点一下「发布」→ 部署到 prod。**「部署到 prod」这个按钮是流水线里唯一保留的人工环节**——它是你留给自己的刹车，等到 06 篇滚动发布和 10 篇规模上来之后，这个刹车也可以拆掉（每次 push 直接到 prod，出了问题靠秒级回滚）。

### 关键原则：一个镜像，跑三个环境

三套环境立刻引出一个技术问题：order 服务连的数据库，dev 是 `dev-mysql`，prod 是 `prod-mysql`——**同一个镜像怎么在不同环境表现出不同行为？**

错误做法：给每个环境构建一个镜像（镜像里写死各自的数据库地址）。这重新制造了 02 篇的环境漂移——三个镜像就是三个可能不一致的东西。

正确做法只有一条路：**镜像只构建一次，环境差异全部通过「运行时注入配置」解决**。镜像是死的，容器是活的——启动容器时注入环境变量：

```yaml
# dev 环境
environment:
  SPRING_DATASOURCE_URL: jdbc:mysql://dev-mysql:3306/shoplite

# prod 环境（同一个镜像，不同的注入）
environment:
  SPRING_DATASOURCE_URL: jdbc:mysql://prod-mysql:3306/shoplite
```

Spring Boot 的 profile 机制（`application-dev.yml` / `application-prod.yml`）干的就是同一件事。这条「一次构建、处处运行」原则的价值在 09 篇会再次兑现：托管平台和 K8s 的整个配置体系（ConfigMap/Secret）都是围绕它设计的。

## 密钥管理：那一排不能进 git 的字符

配置注入还剩最后一块，也是最容易被轻视的一块：**数据库密码、API 密钥这类东西放哪？**

你现在的做法可能和大多数人一样：写一个 `.env` 文件（`DB_PASS=x7#p9...`），`docker compose` 会自动读它。注意上面 GitHub Actions 的 YAML 里，`MYSQL_ROOT_PASSWORD: ${DB_PASS}` 引用的就是这个文件。问题来了：**`.env` 进不进 git？**

进 git 意味着：有仓库读权限的每个人（包括离职员工、包括未来开源的可能）都能看到生产数据库密码；GitHub 上有连续扫描公开仓库的爬虫，**真实事故的时间线通常是以小时计的**——推上去几小时内，密钥被扫到，云账号被开出一串挖矿虚拟机，账单五位数起。

不进 git，新同事 clone 下来跑不起来，又得靠「找老王要一份 .env」这种原始方式传递。

业界的答案是分两层：

1. **代码仓库里只放模板**：提交 `.env.example`（`DB_PASS=` 后面留空并注释一句「找管理员要」），真身 `.env` 进 `.gitignore`。
2. **真身放在专门的秘密存储里**：CI 里用 GitHub Actions 的 Encrypted Secrets（仓库设置里配置，YAML 里用 `${{ secrets.DB_PASS }}` 引用，日志里自动打码）；K8s 里有 Secret 对象（06 篇）；云厂商有专门的密钥管理服务（KMS）。本地开发则靠「找老王要」的人肉通道——规模小的时候这就是正确答案，别过度设计。

还有一条配套纪律值得刻在脑门上：**密钥泄漏的响应不是「删掉那个文件」**。git 历史是append-only 的，commit 过的东西永远翻得到——正确动作是**轮换（rotation）**：让旧密码立即失效（改掉它），泄漏的字符串就变成废纸。所以密钥设计得「容易换」也是能力：所有密钥集中在配置里（而不是散在代码各处），轮换才能是一次配置变更而不是一次代码重构。

## 部署不等于发布

最后补一个多数人直到第一次出事故才理解的概念区分：**部署（deploy）和发布（release）是两件事**。

部署 = 新版本代码跑起来了；发布 = 用户开始用它了。ShopLite 现在两件事是同时发生的（staging 验证完一键到 prod，全量用户立刻看到新版）。但成熟的系统会把它们拆开：新版本部署到生产、但不接流量（或只接 1% 的流量），观察指标没问题再逐步放开——灰度发布、金丝雀发布这些名词指的都是这类策略，[后端技术地图第 10 篇](/posts/backend-map/10-observability-and-ops)从运维视角讲过一嘴。这一篇只需要建立意识：**流水线把部署变得便宜之后，「小步试探着放流量」才有操作空间**——部署越贵，人越倾向于一把梭；部署越便宜，谨慎才付得起成本。

## 什么时候不需要 CI/CD

照例的反面视角。个人项目、每周上线不到一次、且只有你一个人碰服务器——一个 20 行的 shell 脚本（build → push → ssh deploy）就能覆盖 90% 的价值，完整流水线属于提前付费。判断的分水岭是**上线频率和参与人数**：每天上线一次以上、或有两个以上的人会碰生产，流水线的成本就开始回本。另外 GitHub Actions 对私有仓库有免费额度，小团队的「不用」很多时候只是「没花一小时搭过」。

## 小结与下篇预告

- **流水线**把「push 代码到用户看到新功能」之间的所有人肉环节交给机器；容器化让部署退化成「拉镜像换容器」，这是自动化敢放开手脚的前提
- **制品**不可变、可追溯、可回滚；线上只接受整体替换、不接受手工修改——K8s 声明式世界的地基
- **三套环境**（dev/staging/prod）各司其职；**一个镜像跑所有环境**，差异靠运行时配置注入——一次构建、处处运行
- **密钥不进 git**，真身放秘密存储；泄漏的响应是轮换，不是删除
- 部署 ≠ 发布：部署便宜了，灰度试探才付得起成本
