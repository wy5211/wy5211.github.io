上一篇结尾，ShopLite 的四个服务都有了自己的镜像，`docker run` 一下，order 服务就在服务器上跑起来了。

然后你开始跑剩下的七个。跑到第三个的时候你意识到不对劲：这八条 `docker run` 命令，每条都带着一长串参数——端口映射、环境变量、网络指定、重启策略——而你靠记性和 shell 历史在管理它们。周五重启了一次服务器，周一发现问题：你忘了 MySQL 要先于 Nacos 启动（Nacos 起来时建库失败，默默退出了），而 order 服务连不上 MySQL 也不报错，就是接口全部超时。

更糟的在后头。同事说「数据好像不对，能把昨晚的数据导给我看看吗」，你查了半天文档才发现一个此前完全没意识到的设定：**上周重建 MySQL 容器的时候，里面攒的数据跟着容器一起没了。**

这一篇解决三件事：容器怎么组织（Compose）、容器之间怎么找到彼此（容器网络）、数据怎么不跟着容器陪葬（Volume）。第三件事会引出一个贯穿整个系列的概念——有状态与无状态。

## Compose：把八条命令变成一个文件

**Docker Compose** 的思路朴素：既然容器的启动参数都写在命令行里、人脑和 shell 历史管不动，那就写进一个 YAML 文件，让工具照着执行。

ShopLite 的 `docker-compose.yml`，取中间几段看结构：

```yaml
services:
  # ── 有状态的中间件 ──────────────────────────────
  mysql:
    image: mysql:8.0 # 用官方镜像，不用自己造
    volumes:
      - mysql-data:/var/lib/mysql # 数据放容器外面（马上讲为什么）
    environment:
      MYSQL_ROOT_PASSWORD: ${DB_PASS} # 从 .env 文件读，密码不进 git（04 篇展开）

  # ── 无状态的应用服务 ────────────────────────────
  order-service:
    build: ./order-service # 从本地 Dockerfile 构建
    depends_on:
      - mysql # 声明依赖：mysql 先起
    environment:
      SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/shoplite
      #                                ↑↑↑↑ 注意主机名就是服务名，马上讲

volumes:
  mysql-data: # 声明一个具名数据卷
```

一个 `docker compose up -d`，八个容器按依赖顺序全部拉起；`docker compose down`，全部停掉。**这个 YAML 文件本身就是 ShopLite 的部署架构文档**——有哪些组件、谁依赖谁、谁暴露端口，一眼看全。它进 git，和代码一起版本化：上个月的服务器长什么样，翻 git 历史就知道。

## 容器之间怎么找到彼此：服务名即地址

上面那段 YAML 里有个值得停一秒的细节：order 服务连 MySQL 的地址写的是 `jdbc:mysql://mysql:3306/...`——主机名就是一个单词 `mysql`。不写 IP，不写 `127.0.0.1`。

这是 Compose 自动建的东西：**容器网络（bridge 网络）**。同一网络里的容器，可以用服务名互相访问——网络里内置了一个小 DNS，`mysql` 这个名字解析到 MySQL 容器的当前 IP。

回忆一下[后端技术地图第 6 篇](/posts/backend-map/06-service-communication)讲过的问题：微服务之间调用，IP 写死就完蛋——机器重启 IP 变了、加一台机器代码不知道。当时的解法是注册中心（Nacos）。而你现在看到的是同一问题的**最小形态解法**：在单机 Compose 的世界里，服务发现就是「同一网络里，名字就是地址」。记住这个伏笔——到 K8s 篇你会发现这套机制被基础设施完整接管，连 Nacos 的注册职能都被收编了。

容器网络还有一层隔离语义：默认情况下，外部机器访问不到 bridge 网络里的容器，除非你声明 `ports` 把端口映射到宿主机上。ShopLite 里只有 gateway 对外开了端口，服务之间走内部网络——**这本身就是一层安全设计**：MySQL 不映射端口到公网，扫描器就摸不到它。

## Volume：容器会死，数据不能陪葬

现在说那个数据丢失的事故。默认情况下，容器有一层自己的可写文件系统，MySQL 写的数据就存在这层里——**容器一删，这层跟着没了**。`docker compose down` 加个 `-v` 参数，连数据卷一起清掉，是很多人亲手消灭过自己数据库的方式。

解法是 **Volume（数据卷）**：在 YAML 里声明一块**宿主机上的存储空间**，挂载进容器的某个路径。MySQL 容器写 `/var/lib/mysql`，实际写到宿主机的卷里；容器删了重建，重新挂上同一个卷，数据原地不动。

用「集装箱」类比最直观：容器是集装箱，可以被吊走、销毁、换新的；Volume 是码头仓库，不管集装箱怎么换，货放在仓库里。集装箱天生是临时的，**所以重要 的货不该放集装箱里，该放仓库**。

到这里，一个概念已经呼之欲出了——为什么 MySQL 的数据要放外面，而 order 服务的 jar 放镜像里面就行？

## 有状态 vs 无状态：整个系列最重要的概念

把 ShopLite 的八个容器分成两栏：

|                   | order / product / user / gateway  | MySQL / Redis / RocketMQ / Nacos            |
| ----------------- | --------------------------------- | ------------------------------------------- |
| 数据在哪          | 不在自己身上（在 MySQL/Redis 里） | 在自己管理的文件里                          |
| 删掉重建          | 无所谓，起来就能干活              | 数据没了，事故                              |
| 能否随便复制 5 份 | 可以，谁来了都干一样的活          | 不行，5 份 MySQL 各存一部分数据，谁的为准？ |
| 升级方式          | 换新镜像重新跑                    | 要考虑数据迁移                              |

左列叫**无状态（stateless）**：进程自己不持有需要存活的数据，随时可以杀死、重建、复制。右列叫**有状态（stateful）**：数据就是它的命。

这个区分为什么值得单独一节？因为它**决定了每种东西在部署世界的待遇**：

- **无状态应用**可以随意扩缩容（流量大了加副本，流量小了减）、随意替换（发布新版=换掉旧容器）、随意调度（放哪台机器都行）。K8s 的 Deployment、滚动发布、自动扩缩容（HPA），全部只对无状态应用开箱即用。
- **有状态服务**的复制要解决数据一致性问题（两份 MySQL 各写各的就会数据分裂），它的高可用要靠主从复制、故障转移这套复杂机制（07 篇），它的升级要考虑数据兼容——所以生产环境常见的选择是**干脆不把数据库放进容器编排里**，用云托管或独立部署（09 篇）。

[后端技术地图第 2 篇](/posts/backend-map/02-cluster-and-session)讲集群化时说过：「集群化的本质是把应用变成无状态的可复制单元」，当时把 Session 挪进了 Redis。现在你能从部署视角看到同一件事的另一面：**工程师做的大量架构努力，本质上都是在把状态从应用里抽出去**——Session 进了 Redis，上传文件进了对象存储，日志进了集中式日志系统——抽干净之后，剩下的应用就成了可以随便复制的东西。

## 宠物与牛：一场运维观念的换代

讲 restart 策略之前，先讲行业里一个流传很广的比喻。

传统运维时代，服务器是**宠物（pets）**：每台有名字（db-master01），你记得它的脾气（内核参数改过、磁盘换过一块），它病了你要登上去抢救，救不回来是事故。容器时代的应用实例是**牛（cattle）**：只有编号（order-7f9c2、order-3a1b8），没有名字没有脾气，生病了不治——直接杀掉，从镜像重新拉起一只健康的。

这个比喻不是冷笑话，它是**自愈（self-healing）**的思路来源：与其花人力诊断「这个容器为什么不工作了」，不如默认它随时会坏，坏了就换。Compose 层面你已经能用一行配置尝到味道：

```yaml
services:
  order-service:
    restart: unless-stopped # 容器退出（崩溃）后自动重新拉起
```

进程崩了，Docker 自动重启它，不用你半夜爬起来。当然这只是单机版的雏形——它救不了宕机的整台服务器，也判断不了「进程活着但已经不响应请求」的假死（那需要健康检查，06 篇 K8s 里展开）。但「坏掉就换、不手工修」这个观念，从这条配置开始就要建立起来。

## ShopLite 现在长什么样

```
一台 2 核 4G 的云服务器
└── docker compose up -d
    ├── mysql（数据在 Volume 里）
    ├── redis / rocketmq / nacos
    ├── order / product / user
    └── gateway（唯一对外开端口 :8080）
```

环境一致（02 篇的镜像）、单机编排（本篇的 Compose）、崩溃自拉起（restart 策略）。ShopLite 在单机上的形态，**已经是很多真实小项目的生产形态了**——这句话在 10 篇选型时还会再说一遍。

但还有一件事完全依赖人肉：上线流程。改一行代码的完整路径是——本地构建镜像、推仓库、SSH 到服务器、pull 新镜像、`docker compose up -d` 重建容器、手动点一遍核心功能验证。一次 20 分钟，一天上线三次就是灾难，而且人肉步骤越多，敲错命令的机会越多。下一篇把这条路径交给机器：CI/CD，以及两个你大概率还没想过的问题——为什么需要三套环境，和数据库密码到底该放哪。

## 什么时候不需要 Compose

照例的反面视角，这次的答案很短：**只有一两个容器、且不打算增加时**，直接 `docker run` 足够。但实践中的共识是哪怕只有两个容器也写 Compose 文件——因为 YAML 的成本是十分钟，而它换来的东西（依赖顺序、网络、可版本化的架构描述）从第二个容器开始就在产生价值。

## 小结与下篇预告

- Compose 把「容器的组织方式」从命令行和记性里搬进一个进 git 的 YAML：依赖顺序、网络、卷、重启策略，一处声明
- 容器网络里**服务名就是地址**——服务发现的最小形态，K8s 篇的伏笔
- **Volume 把数据和容器的生死解耦**；由此引出无状态/有状态的分野：无状态的可复制可替换，是后面一切编排便利的前提；有状态的要单独伺候（07 篇）
- restart 策略是「宠物变牛」的第一步：坏掉就换，不手工修
