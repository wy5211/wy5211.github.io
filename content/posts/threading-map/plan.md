# 线程与并发地图：一个前端的单线程与多线程疑问

## 背景

来自一段真实对话，两个原始问题：

1. 「Node 是单线程的，Java、Go 是多线程的，这对服务能力到底有什么影响？我平时开发 Electron，很难有体感。」
2. 「拿 Java 来说，怎么避免多个线程处理同一个事情、避免争抢？是不是要用分布式锁？」

第二个问题里藏着一个典型的混淆：把进程内的线程争抢和跨机器的争抢当成了同一件事，一上来就想到分布式锁。这正说明读者缺的不是某个知识点，是三块地基：

- 线程作为「可调度资源」的模型——前端有「主线程卡死 = 页面冻结」的强体感，但没有「线程是干活的人、人有几个」的模型
- 等 IO 和算 CPU 的分水岭——单线程服务能力的全部秘密在这一刀
- 锁的管辖范围——JVM 锁管一间屋，分布式锁管一栋楼，边界在哪

本系列是小型问题地图（8 篇），和其他地图系列不同：主线不是技术演进史，是**一个人的疑问顺序**。读者画像：写 Electron / 前端的开发者，第一次认真碰后端并发概念。

- 文章类型：A（技术类）
- 系列定位：概念地图，不教语法不教 API。所有「怎么写」互链已有教程系列（java / golang / nodejs-core / redis / springboot）

## 贯穿案例：墨记的云同步之旅

第一人称「你」：写了几年 Electron 笔记应用「墨记」——多窗口、带图片、本地有全文索引。公司决定做云同步，你被拉去写后端。整个系列你会碰到两个服务：

- **同步服务（Node）**：你亲手写的，从「单线程行吗」的自我怀疑开始
- **计费服务（Java）**：公司已有的（免费用户每月 1GB 同步流量），用户量上来后你参与维护，第一次掉进多线程的坑

## 每篇文章大纲

### 01 卡死的那三秒：线程到底是什么

- 学习目标：建立「线程是干活的人、卡 = 人在忙别的」的模型，分清进程和线程
- 核心问题：「渲染进程页面冻结、主进程一卡所有窗口冻结，这两个『卡』背后是什么？」
- 主线场景：墨记打开一篇带大附件的笔记，`JSON.parse` 卡住渲染主线程 3 秒，用户狂点无反应；后来把重活挪到主进程，结果所有窗口一起冻结
- 内容要点：
  - 进程 vs 线程：Electron 天生多进程（每窗口一个渲染进程 + 一个主进程），所以一个窗口卡不影响别的窗口；但每个进程里面有线程，渲染进程里跑 JS 和画界面的是同一根——主线程
  - 「卡」的准确定义：不是程序慢，是这根线程在忙别的，没空理你的点击
  - 一根线程同一时刻只执行一段代码；CPU 多核的意思是多根线程可以真的同时跑
  - 「Node 单线程、Java 多线程」说的就是你的代码跑在几根线程上——把这句话从此讲准
  - 为什么前端难有体感：浏览器给了你进程隔离 + 单线程没有插队，两个保护罩在服务端世界都不一定有
  - 名词卡片：进程 / 线程 / 主线程 / 阻塞
- 与其他篇关联：全系列地基；结尾抛出疑问「服务只有一根线程，能扛住多少用户？」引出 02

### 02 一家店和连锁店：单线程多线程差在哪

- 学习目标：拿到全系列的地图和结论框架——影响不在吞吐数字上，在「某个请求把线程占住时谁受牵连」
- 核心问题：「Node 单线程、Java 多线程，对服务能力到底有什么影响？」
- 主线场景：你接活用 Node 写墨记的同步服务，Java 同事说「单线程扛不住的」，你说不清他错在哪
- 内容要点：
  - 一个请求的生命周期：接客 → 干活 → 回话；活分两种——等（数据库、网络、磁盘）和算（压缩、加密、解析），这是全系列那把刀
  - 比方定调（全系列复用）：Node = 一家店一个店员；Java = 一家店一群店员；部署两台机器 = 开连锁店
  - 差别什么时候显现：店员闲着的时候（等 IO）没差别，某个客人把店员拖住时见分晓——单线程全店停摆，多线程只是那一桌慢
  - 纠正一个常见误解：「Node 单线程」指你的 JS 代码只在一根线程上跑，进程里其实还有文件读写的线程池和 GC 线程，只是你不直接碰
  - 并发 vs 并行一句话分清：交替处理多件事叫并发，同一时刻真同时跑叫并行
  - 全系列地图预告：等 IO 的答案在 03，算 CPU 的答案在 04-05，多线程的坑在 06-07，多机的坑在 08
  - 名词卡片：并发 / 并行 / 吞吐量 / 延迟
- 与其他篇关联：仿 infra-map 01 的地图篇写法；01 的线程模型在此铺开成全景

### 03 服务员的秘密：等 IO 不占线程

- 学习目标：理解事件循环为什么让一根线程扛住上千并发；分清「挂着」和「卡住」
- 核心问题：「一根线程怎么同时伺候一千个正在等数据库的请求？」
- 主线场景：同步服务上线，一千个客户端同时拉增量，监控里 Node 进程 CPU 才 5%，你怀疑监控坏了
- 内容要点：
  - 后端大部分时间在等：给一个典型同步接口画时间构成（等数据库 40ms、等对象存储 30ms、自己算 2ms），「等」占了九成
  - `await` 的本质：登记「结果回来叫我」，撒手，线程去接下一个；结果回来排队继续——服务员点完单把单子递后厨，转身下一桌，不杵在厨房门口
  - 所以一根线程能「挂着」成千上万个等待中的请求；「挂着」不等于「卡住」
  - 内存账：Java 老写法每请求一根线程，1000 并发就是 1000 根线程，光每根的栈就不小；Go 的协程和 Java 21 的虚拟线程都是往轻里做（一句话定位，不展开）
  - 本篇成立的前提只有一个字：等。一旦要算，模型崩塌——结尾留钩子
  - 互链：事件循环的机制细节（六个阶段、微任务宏任务）在 [nodejs-core 03](/posts/nodejs-core/03-event-loop)，本篇只讲为什么行得通
  - 名词卡片：事件循环 / IO 密集 / 回调
- 与其他篇关联：02 的「等 vs 算」兑现前一半；04 接着兑现后一半

### 04 分水岭：算 CPU 的活冻住全场

- 学习目标：会用「等 IO / 算 CPU」判断一类活能不能进单线程；理解为什么一个请求能冻住整个 Node 服务
- 核心问题：「图片批量生成缩略图的功能上线十分钟，全站接口集体超时，回滚立刻恢复——为什么？」
- 主线场景：墨记的同步服务加了缩略图生成（sharp 压缩），一个用户批量上传 500 张图，期间所有用户的同步请求排队超时，连健康检查都失败
- 内容要点：
  - 等 vs 算的本质：等可以撒手（操作系统帮你盯着），算必须 CPU 一步步跑，撒不了手——200ms 一张 × 500 张 = 100 秒的主线程长任务
  - 长任务期间事件循环停转：不是慢，是整根线程被占用，所有人排队——正是 01 里渲染主线程卡死的服务器版，但这次所有用户共用这一个「窗口」
  - 同样的活丢给 Java 服务：一个请求占一根线程，其他线程照常接客，只有那个用户慢——「谁受牵连」的差别在事故里现形
  - 常见算 CPU 活清单（压缩、加密 / 密码哈希、大对象序列化、模板渲染）和等 IO 活清单（CRUD、调接口、读写库）
  - 判断框架：拿到一个需求先问「这活在等还是在算？」——等 IO 单线程放心写，算 CPU 要么挪走（05）要么换工具
  - 名词卡片：CPU 密集 / 长任务 / 主线程
- 与其他篇关联：03 的边界在此爆雷；场景刻意与 backend-problem-map 09 的「导出 PDF」错开（那篇讲 job 系统怎么搭，本篇讲线程原理），互链互补

### 05 单线程的自救：把重活挪出去

- 学习目标：知道 worker_threads 和 cluster 各自解决什么、不解决什么；建立「什么时候别硬撑」的判断
- 核心问题：「Node 一定要算的活怎么办？」
- 主线场景：把 sharp 压缩挪进 worker 线程池：主线程只收图、派活、收结果；缩略图功能重新上线，全站不再卡
- 内容要点：
  - worker_threads：开几根专门的线程去算，算完把结果传回来；主线程回归「接客 + 派活」的本职——店还是那个店，雇了几个后厨
  - 代价也要说：worker 之间传数据靠拷贝（大文件要想 transferable 或传路径）、并发数要自己管、代码复杂度上来了
  - cluster / 多进程一句话：多开几个 Node 进程各占一核，前面挂负载均衡——为 08 的多机世界埋伏笔
  - 判断框架：偶发的重活 → worker 挪出去；常态的重活 → 这个服务可能就不该用 Node，别跟语言较劲
  - 墨记的结局：缩略图这类常态计算活，最后并进了后端组的 Java 服务（它有线程池现成的一套），你顺势开始参与维护——引出 06
  - 互链：worker_threads / 子进程的 API 和用法在 [nodejs-core 08](/posts/nodejs-core/08-concurrency)，本篇只讲取舍
  - 名词卡片：worker_threads / cluster / 线程池
- 与其他篇关联：04 的死穴在此打补丁；叙事上从「我的 Node 服务」过渡到「公司的 Java 服务」

### 06 多线程的坑（上）：一起改一份数据

- 学习目标：理解竞态条件为什么丢数据；面对「改共享数据」会按轻重选原子变量和锁
- 核心问题：「流量计数器每天少记几十万次，代码 review 谁都看不出错，为什么？」
- 主线场景：计费服务里 `counter++` 统计免费用户的同步流量，压测一开就丢更新；你第一次意识到多根线程会互相插队
- 内容要点：
  - `counter++` 不是一步：读、加、写回三步，两根线程的时间线交错着画一遍，丢一次更新的全过程
  - 病根命名：竞态条件；发作三条件——多线程 + 共享一份数据 + 读改写，对上就中招
  - 药按轻重排：AtomicLong（CPU 指令保证一次做完，最轻）→ synchronized / Lock（给一段代码上门锁，一次进一个）→ 并发容器一句带过
  - 锁的代价：门口排队（吞吐掉）、忘了放钥匙（死锁，一句话 + 一个互相等对方的最小例子）
  - 前端为什么没体感：浏览器 JS 单线程，根本没人能插你的队——不是你小心，是没有对手；这就是前端难以想象这类 bug 的原因
  - 分层声明：两人同时改数据库里的同一行是同一类病的数据库版（事务、乐观锁悲观锁），在 [backend-problem-map 06](/posts/backend-problem-map/06-concurrency-transactions)，本篇只讲内存层
  - 名词卡片：竞态条件 / 原子操作 / synchronized / 死锁
- 与其他篇关联：01 的「一根线程一次干一件事」反过来用——多根线程就会插队；语法和 API 用法互链 [java 18](/posts/java/18-concurrency-safety)，本篇讲问题分类和选药逻辑

### 07 多线程的坑（下）：一起干同一件活

- 学习目标：分清「抢数据」和「抢活」两类病；会用分发代替争抢
- 核心问题：「配额用到 80% 发提醒邮件，一个用户收到五封，为什么加锁不是最佳解法？」
- 主线场景：计费服务里 `if (used == threshold) sendEmail()`，一千个并发请求里五根线程同时通过判断，各发了一封
- 内容要点：
  - 两类病对照表：抢数据 = 一份数据被改坏（06），抢活 = 一件事被干多遍（本篇）——病不同，药不同
  - 药一：锁，把「判断 + 发送」圈进一次进门——行，但每个请求都要过这道门，重
  - 药二：队列 + 线程池，把「发提醒」变成队列里的一条消息，谁闲谁取，取走即消失——Java 线程池内部本来就这么转（叫号机：没人抢业务，都是取号等叫号）
  - 判断框架：要保护「一份数据」用锁；要保证「一件事只做一次」优先想分发；多数抢活场景根本不用锁
  - 为什么这是 08 的地基：把队列从「进程内」放大到「跨机器」就是消息队列，把锁从「进程内」放大到「跨机器」就是分布式锁——两样东西 08 都要出场
  - 互链：Spring 里 @Async / @Scheduled 的用法在 [springboot 12](/posts/springboot/12-async-tasks)
  - 名词卡片：线程池 / 任务队列 / 生产者消费者
- 与其他篇关联：06 的药箱里补上第二种药；结尾把视角从「一家店」抬到「两家店」，直接引出 08

### 08 从一家店到连锁店：锁为什么管不住多台机器

- 学习目标：理解进程内锁的管辖边界；知道分布式锁和消息队列各自的定位；带走全系列选型顺序表
- 核心问题：「计费服务部署了两台，月初账单任务跑了两遍、配额也扣错了——synchronized 明明加了，为什么不管用？是不是就该用分布式锁了？」
- 主线场景：用户量上来，计费服务上了两台实例做负载均衡。月初复盘：两台机器各自跑了一遍出账单任务；两台机器同时扣同一用户配额，出了错账
- 内容要点：
  - 根因：JVM 锁是进程内存里的便签，A 进程贴的 B 进程看不见——一家店的店内规则，管不住连锁店；这也是原始问题「是不是分布式锁」的准确回答：先看你是不是连锁店
  - 分布式锁：把锁放到所有机器都看得到的地方（Redis `SET NX` 讲概念）；代价——每次加解锁走网络、锁要设过期时间、释放要防误删别人的锁（点到为止）
  - 定时任务只跑一份的几种解法：分布式锁抢执行权 / 只让一台跑调度 / 交给专门的调度系统
  - 分工的另一半：消息队列——一条消息只投给一台机器，抢活的多数场景它比分布式锁更常用；消费失败的兜底一句话引出幂等，互链 [backend-problem-map 10](/posts/backend-problem-map/10-idempotency)
  - 收官：全系列选型顺序表——能排队（单机队列）不上锁；单机锁够用不上分布式锁；多机抢活优先消息队列；分布式锁留给「必须跨机器看同一份状态」的少数场景
  - 全系列一根线复习：卡（01）→ 等 / 算（02-05）→ 抢数据（06）→ 抢活（07）→ 跨机器（08）
  - 互链：Redis 锁的实现细节与 Redlock 在 [redis 13](/posts/redis/13-cache-distributed-lock)；job / 队列 / worker 系统怎么搭在 [backend-problem-map 09](/posts/backend-problem-map/09-background-jobs)
  - 名词卡片：分布式锁 / 消息队列 / 幂等
- 与其他篇关联：06 的锁和 07 的队列在此各放大一号；系列收官，回答了开篇两个原始问题的全部
