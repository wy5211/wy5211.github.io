[上一篇](/posts/threading-map/06-race-on-data)的病是改坏一份数据，计数器凭空丢数。这类的病更安静：数据一个字节都没坏，但同一件事被干了好几遍。

计费服务有个贴心功能：免费用户的月流量用到八成，发一封邮件提醒该升级了。代码大意是：

```java
if (used >= quota * 0.8 && !reminded) {
    sendEmail(userId);
    reminded = true;
}
```

上线后用户小陈反馈：收到了五封一模一样的提醒。每封内容都对，措辞也真诚，问题是他不该收到五封。

## 五封邮件是怎么发出去的

复盘压测日志：小陈的客户端在批量同步，一千个请求短时间内涌进来，被分给了好几根线程。其中五根线程几乎同时跑到这段判断，它们各自读到的都是「用量到了八成、还没提醒过」，于是各自发了一封，再把标志位置上。

又是插队，和 06 同一个病根：判断和动手是两步，两步之间可以被人插进来。但这次破坏的东西不一样了。计数器丢数，坏的是数据的值；五封邮件，数据没坏（标志位最后好端端置上了），坏的是事的次数。一类是改坏一份数据，一类是干多一遍活，病相不同，药方也该分家。

出问题时先问一句「坏的是什么」：数字错了、内容被覆盖了，是抢数据；事情多了、重复了，是抢活。

## 药一：锁，能治，但贵

最直接的反应是把这三行圈进一把锁，一次只放一根线程进来判断加发信。有效，五封立刻变一封。

但看看代价：所有同步请求都要经过这段判断，哪怕 99.9% 的时候离八成远得很。加了锁，每根线程都得在门口排一遍队，就为了防一个每月才发生一次的瞬间。为了五封邮件的病，给全店客流加了一道安检门。

锁是给「必须护住一份数据」的场景准备的。这里要护的其实是一件事的次数，用锁杀鸡，牛刀也疼。

## 药二：让事情排队，而不是让人排队

换一个思路，不从「不许同时做」下手，从「只排一个人做」下手。

把「查一下该不该给谁发提醒」整个变成一条活，丢进一个队列，由单独一根线程慢慢消费。全服务只有这一根线程有权力判断和发信，判断的时候旁边永远没有别人，五封邮件的土壤就没了。

这就是银行的做法。没人抢窗口，所有人取号，叫到谁谁上。柜员的逻辑里不存在「两个人同时办同一笔业务」这个场景，因为入口就收窄成了一条。

Java 里落地很轻：一个单线程的线程池（executor），把发提醒的任务 submit 进去就完事。往外再多走一步，把消息丢进消息队列、由独立的消费者处理，是这个思路放大一号的样子，08 马上用到。Spring 里的 @Async 和 @Scheduled 就是这类活落地的现成工具，用法在 [Spring Boot 的异步任务篇](/posts/springboot/12-async-tasks)。

两味药的分别在这：锁是让人排队，所有人过一道门，门里的人独占；队列是让事排队，事情排队等处理者，谁闲谁取，取走即消失。抢数据的病，必须大家看同一份数据，躲不开门；抢活的病，多数时候根本不需要大家同时在场，把入口收窄成一条，病就没了。

| 名词         | 英文              | 一句话                                          |
| ------------ | ----------------- | ----------------------------------------------- |
| 任务队列     | task queue        | 活排队的地方，处理者从这取，取走一条少一条      |
| 生产者消费者 | producer-consumer | 一边往队列里放活，一边从队列里取活干，各干各的  |
| 消息队列     | message queue     | 任务队列放大到跨进程跨机器的版本，08 的主角之一 |

## 什么时候不用管它

用户量一天几百的内部服务，五封邮件的概率本身就是零头，加队列属于自找复杂度。这套东西值钱，是请求数和线程数都多起来、判断和动手之间真的会插进人的时候。

还有一件事值得你现在记住：这篇的队列和上一篇的锁，都是一家店内部的东西。便签贴在店内墙上，叫号机摆在店内大堂。下个月，计费服务要部署第二台机器，你会发现店内这两样东西，管不住另一家店。
