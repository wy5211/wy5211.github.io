[上一篇](/posts/threading-map/03-event-loop-waiting)拆完魔术：等 IO 不占线程，一根线程挂一千个等待没问题。但结尾说了，魔法有一个前提：大家都在等。

墨记很快撞破了这个前提。新版本给笔记加了图片，产品要求服务端给每张上传的图生成缩略图。你选了 sharp，Node 生态里做图片压缩的标准答案，快，好用。周三晚上上线，十分钟后告警群炸了：全站接口超时。

你回滚了缩略图这一个功能，超时立刻消失。凶手锁定，但你想不通：压缩图片而已，怎么把整个服务弄瘫了。

## 事故复盘

看数据。一个用户批量上传了五百张照片，sharp 压缩一张平均 200 毫秒，五百张串下来是 100 秒。

这 100 秒里，那根唯一的线程在哪？在 sharp 的 C++ 代码里，一步一步算像素。上一篇说过等的情形：活本来是别人的，你的线程登记一句「好了叫我」就走。算的情形完全相反：这个活没有「别人」，CPU 必须亲自跑完每一毫秒，撒不了手。

线程被按住的这 100 秒，事件循环停转。转圈的人不能动了，那么：

- 一千个客户端的同步请求，全部超时
- 数据库早就返回的那几百个查询，登记着「回来叫我」，没人理
- 健康检查没有响应，负载均衡开始把这台机器摘除
- 新请求还在进门，队伍越排越长

这个场面你太熟了：渲染主线程的长任务。一样的病，服务器版。区别只有一个：Electron 里冻住的窗口，用户关掉重开就是；这次冻住的是所有用户共用的那一个「窗口」。

## 病根：等和算，从来是两种活

现在可以把上一篇那把刀磨利了。

等，本质是活有主人。查数据是数据库的线程在查，读磁盘是磁盘控制器在读，调第三方是对方的机器在跑。你的线程只是一个等通知的旁观者，所以能走开。

算，本质是活没有别人。压缩、加密、密码哈希（bcrypt 那种故意设计得慢的）、解析 40MB 的 JSON、给一万条记录排序，每一步都得你这片 CPU 亲自执行。「撒手」这个动作物理上不存在。

单线程世界的规则因此可以一句话讲完：等的活随便接，算的活看分量。分量小（权限校验那 1 毫秒）无所谓，夹在缝里就跑了；分量大（200 毫秒一张 × 500 张），就是事故。

## 同一场事故，隔壁 Java 店

那五百张图如果丢给老周的服务处理？来一个请求派一个店员，那个店员陪这单压缩 100 秒，其他店员照常接客。挨骂的只有这一个用户（他的上传进度条转了很久），别人的同步一点没受影响。

上一篇那句「全场停摆，还是只慢一桌」，在这次事故里现了形。这是多线程最实在的收益：隔离故障的能力，店员之间互不拖累。

给老周公平起见也要说：Java 店不是不会瘫。店员总数有限（线程池就那么大），要是同时来一百单压缩，一百个店员全被拖住，后面的请求照样排队超时，场面跟墨记这次差不多。多线程买到的是「一桌慢」的隔离，买不到「活本身太重」的豁免。太重的活怎么救，是下一篇的话题。

## 拿到需求，先问一句

从这次事故你能带走一个便宜的习惯：接到一个后端需求，先问这活在等还是在算。

等 IO 的清单：数据库增删改查、调第三方接口、读写文件、发邮件（等 SMTP 服务器）、消息队列收发。这些进单线程服务，放心。

算 CPU 的清单：图片视频处理、加密解密、密码哈希、大文本大 JSON 解析、给大数组排序去重、服务端渲染长页面、生成 PDF 和 Excel。这些进单线程服务之前，先估一下单次多少毫秒、会不会叠加。

真实需求常是混合的。拆开看占比就行：墨记的同步接口是九成等，安全；缩略图是十成算，危险。上一篇挂一万个等待的账，和这一篇被一个人按住全场的账，是同一根线程的两本账。

| 名词     | 英文         | 一句话                                                     |
| -------- | ------------ | ---------------------------------------------------------- |
| CPU 密集 | CPU-bound    | 活的大头在算，CPU 必须一步步亲自跑                         |
| 长任务   | long task    | 把线程占住很久的一段同步计算，前端后端共同的敌人           |
| 健康检查 | health check | 别人定时来问「你还活着吗」的接口，事件循环停转时它最先失联 |

## 收尾

需求本身没有错，错的是让算的活和一千个等的客人挤同一根线程。修法大方向只有一个：挪出去。

挪有两个层次。轻的是在本进程里雇几个专门算的帮工（worker_threads），重的是把这类活整体交给别的进程、别的服务，甚至变成一条任务记录慢慢消化（那套后台任务的玩法在 [后端问题地图的后台任务篇](/posts/backend-problem-map/09-background-jobs) 讲过，本系列不重复）。下一篇讲墨记实际的做法：给这家一个店员的店，开后厨。
