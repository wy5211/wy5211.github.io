[上一篇](/posts/threading-map/07-race-on-work)结尾说，计费服务要部署第二台机器了。用户量涨上来，一台扛不住，也怕它宕机全停，标准的做法：两台机器，前面加负载均衡，请求随机分过去。

两周后月底对账，两个事故一起爆出来。

月初的出账单任务，跑了两遍。每个用户都收到了两条扣费记录，金额一模一样。代码里明明加了 synchronized。

小陈当天的配额扣减出了错账。两台机器同时处理他的同步请求，各自读到旧配额、各自扣减、各自写回，一笔流量扣成了半笔。又是 06 那个读改写插队的病，可这次是两台机器插的队。

## 便签管不住连锁店

两件事一个根因：synchronized 这把锁，是 JVM 内存里的一张便签。

A 机器加锁，是往 A 自己进程的墙上贴了张条子。B 机器的进程有自己独立的内存、自己的墙，那张条子它物理上看不见。于是两台机器各自的「一次只进一根线程」都好好的，但两台机器之间，谁也不拦谁。上一篇的叫号机同理：两台机器各摆了一台，各自叫各自的号，账单任务在两边各排了一次队。

02 挂的号在这里兑现了：一家店的店内规矩，开了连锁店就作废。不是锁坏了，是锁的管辖范围到店门口为止。

## 分布式锁：把锁放到公告板上

要让两台机器互斥，锁必须放在一个双方都看得见的地方。常用的地方是 Redis，所有机器都连它。这套锁叫分布式锁。

概念上就一句话：两台机器都去 Redis 抢着设置同一个 key（用 SET 命令的 NX 参数：不存在才许设置），谁设置成功谁拿到锁，干完活删掉 key，另一台设置失败，就知道有人在做，这次跳过。出账单任务加这么一段，两台机器里只有一台真跑，另一台安静退出。

但跨机器的锁，账单比店内锁厚一沓：

每次加锁解锁都要走网络，毫秒起算，比进程内的锁慢出几个量级，所以它只配用在大粒度的场合，比如「今晚谁跑账单」，不配用在每个请求上。

锁必须带过期时间。拿锁的机器跑一半崩了，没来得及删 key，没有过期时间的话这把锁就永远占着，任务永远没人跑。过期时间设多长又是个手艺活，活没干完锁先过期，第二台机器进来了，又是两遍。

删锁还得只删自己的。你的锁过期被别人拿了，你收尾时随手一删，删掉的是别人的锁。所以值里要带上自己的机器标识，删之前先比对。

这套实现的细节和争议（Redis 单点、Redlock 算法）在 [Redis 系列的分布式锁篇](/posts/redis/13-cache-distributed-lock)，本系列点到为止。你要带走的是定位：分布式锁是跨机器互斥的最后手段，不是第一反应。

## 抢活的多数场景，更好的答案是分发

回到出账单这个事，它要的其实是「全公司只做一次」。除了两台机器抢锁，还有两条路，而且通常更好。

一是干脆只让一方有资格做：定时任务不放业务机器上，独立部署一个调度服务，或者用数据库任务表，谁抢到那条任务记录谁执行。没有第二个候选人，就不需要锁。

二是用 07 的叫号机放大一号：把出账单变成一条消息丢进消息队列（RabbitMQ、Kafka 这类），两台机器都是消费者，但一条消息只会投递给其中一台。事情从源头就只发了一份，后面无人可抢。这套系统怎么搭（任务表、worker、重试）在 [后端问题地图的后台任务篇](/posts/backend-problem-map/09-background-jobs)有完整的讲法。

至于小陈的错账，那不是锁的病，是 06 的读改写插队跨了机器，共享的那份数据在数据库里，正解在数据库层：事务、乐观锁，[后端问题地图的并发篇](/posts/backend-problem-map/06-concurrency-transactions)管那层。这个例子顺便说明：多机问题不都靠分布式锁，先看清共享的到底是什么、在哪一层。

无论哪条路，都记住一件事：队列也可能重复投递（网络断了重发一次），所以最后一步兜底是把事情本身做成重复执行也无害的，行话叫幂等，思路在 [后端问题地图的幂等篇](/posts/backend-problem-map/10-idempotency)。

## 收官：一张选型顺序表

八篇走完，把遇到「争抢」时的选型顺序压成一张表，从轻到重：

1. 能排队就不上锁。抢活的场景，先想单机队列（07 的叫号机），入口收窄成一条，多数病就没了。
2. 单机锁够用，不上分布式锁。只要服务还是一台机器，synchronized 和 AtomicLong 管到底。
3. 多机抢活，优先消息队列或任务表。让事情从源头只发一份，比让机器互斗便宜。
4. 分布式锁留给最后：多台机器必须互斥地动同一份状态的场景，比如定时任务抢执行权、秒杀扣库存。

对应的另一条线，选型之前先问的那句：这服务是等得多还是算得多（02 的刀），算的活挪没挪出去（05），这决定你单线程的店能不能开下去。

## 一根线复习

最后把八篇串成一根线。线程是干活的人，卡就是人被占住（01）。单线程和多线程的差别不在平时，在某个请求把线程占住时谁受牵连（02）。等不占线程，所以一根线挂一千个等待（03）；算撒不了手，所以一个长任务冻全场（04），解法是挪出去（05）。店员多了会抢：抢数据用锁和原子变量（06），抢活用队列（07）。开了连锁店，店内的便签和叫号机全部失效，换公告板和总店发号（08）。

什么时候这八篇全都不用管：你的项目跑在一台机器上、并发不过几百，那 02 的刀给你信心，其余的坑根本不存在。这套地图是留给长大之后用的。

至于最初选型会上老周那句「扛不住吧」，现在你有完整的答案了，而且知道他那里要操的心你也都看得懂。这大概就是一个地图系列最好的结局：两边的店，你都进得去。

| 名词     | 英文             | 一句话                                         |
| -------- | ---------------- | ---------------------------------------------- |
| 分布式锁 | distributed lock | 放在所有机器都看得见的地方（通常是 Redis）的锁 |
| 消息队列 | message queue    | 跨机器的叫号机，一条消息只投给一台机器         |
| 幂等     | idempotent       | 同一件事重复执行也无害，重复投递的兜底         |
| 负载均衡 | load balancing   | 站在多台机器前面分客人的角色，连锁店的总台     |
