[上一篇](/posts/threading-map/01-what-is-thread)把线程讲成了干活的人：卡，就是这个人被占住了。这篇让人多起来。

先摆场景。墨记云同步的活你接了，选型会上你报了 Node。后端组的老周，Java 写了十年，来一句：「Node 单线程的，扛不住吧。」你没吵赢他。不是因为他一定对，是你发现自己说不清单线程到底差在哪、差不差。这篇就把这笔账从头算一遍。

## 一个请求进来，服务在干嘛

把墨记的一个同步请求拆开看，比如客户端来拉今天的笔记增量：

1. 收请求
2. 查用户的登录态，等数据库回话
3. 校验权限，CPU 算一下，不到 1 毫秒
4. 查增量数据，又等数据库
5. 拼成 JSON 发回去，CPU 算 1 毫秒

拆出来就两种活。

等：事情交给别人干，你的线程等结果。别人是数据库、是另一台服务器、是磁盘。数据库查一次几十毫秒很正常，这几十毫秒里，理论上你的线程什么都不用干。

算：CPU 一步一步亲自跑。加密、压缩、解析大文本，每一步都得它来，撒不了手。

等和算，就是全系列那把刀。现在把墨记同步接口的时间账加一下：等占 70 毫秒，算占 2 毫秒。这个 9:1 不是墨记独有的形状，大多数 Web 接口都是这个形状。记住它，下一篇全靠它。

## 一家店，和一个店的一群店员

比方在这里立起来，后面七篇都用它，不再换。

Node 服务：一家店，一个店员。所有客人进门都是他接。

Java 服务（传统玩法）：一家店，一群店员。来一个客人，店里派一个店员从头跟到尾。

Go 服务：也是一群店员，但每个店员便宜得多，术语叫协程，为什么便宜是 03 的事，这里记住结论就行。

部署到两台机器：连锁店。这是 08 的正题，先挂号。

## 那到底差在哪

老周那句「扛不住」，潜台词是店员少就接客慢。可回看上一节的时间账：店员九成多的时间在等菜。等菜的时候，一个店员和十个店员的产出差别不大。

真正的分水岭，在某个客人把店员拖住的那一刻。分两种情况。

第一种，客人点的菜后厨要做三十秒（等 IO）。单店员可以趁等菜去招呼别桌，菜好了再回来上。一个店员同时招呼一整条街，靠的就是这个。这是 03 的内容，也是单线程敢开店的底气。

第二种，客人搬来一台老收音机要店员当场修（算 CPU）。修的每一步都得店员亲自动手，撒不了手。单店员被拖住三十秒，全店停摆：后面排队的、催单的、问洗手间的，全得等他。多店员的店呢？一个店员陪修，其他人照常接客，慢的只有那一桌。

所以对老周的回答可以是这句话：单线程的影响，不在平时能接多少客，在某个请求把线程占住的那一刻，是全场停摆，还是只慢一桌。

顺手把两个常混的词分开。并发是一段时间里处理多件事，一个店员轮流招呼五桌，就是并发。并行是同一时刻真的一起干，五个店员各管一桌才是并行。你的 Node 服务可以做到很高的并发（03 验货），但你的 JS 代码永远不并行，四核 CPU 它最多吃一个核（05 讲怎么破这个限制）。

## 单线程，到底单在哪

把上一篇结尾那句话掰开：单的是你的代码。

Node 进程里其实住着不止一根线程。你调异步的 `fs.readFile`，真正去读盘的是它内部线程池里的线程；垃圾回收也另有线程。这些线程只是不归你指挥。所以说 Node 单线程，说的是你的业务逻辑全部排队过同一根线程，像一家店后台可以有帮工，但前台收银只有一个口，所有客人从这一个口走。

Java 那边反过来：你的代码本身就散在很多根线程上跑。一个请求一根线程是老传统，你甚至能自己开线程，不过现在没人手动开了，都用线程池，那是 07 的内容。

## 这系列的地图

到这里，老周的问题已经拆成了几个能各个击破的小问题：

- 一个店员怎么趁等菜招呼一百桌？03，单线程扛高并发的全部秘密。
- 修收音机这种要算的活进了单线程怎么办？04，全系列唯一的大事故现场。
- 事故之后怎么补救？05，把重活挪出去。
- 店员多了，同时改一本账会怎样？06，抢数据。
- 店员多了，抢着干同一件活会怎样？07，抢活。
- 开了连锁店，店里的规矩为什么不管用了？08，分布式锁和消息队列。

| 名词   | 英文        | 一句话                                     |
| ------ | ----------- | ------------------------------------------ |
| 并发   | concurrency | 一段时间里处理多件事，轮流的那种           |
| 并行   | parallelism | 同一时刻真的同时干多件事                   |
| 吞吐量 | throughput  | 一段时间处理完的请求总数，店一分钟出多少单 |
| 延迟   | latency     | 一个请求从进门到回话花的时间，客人等了多久 |

## 拿什么回老周

现在你能给老周一个完整的回答了：等 IO 的服务，我不怕你，03 会证明；真要算的重活，我会挪出去，05 讲怎么做；至于你那边多线程要操的心，抢数据、抢活，我单线程天生没有，代价是我吃不到多核的饭。

至于「扛不住」三个字，判断标准你现在有了：看这服务是等得多还是算得多。墨记同步是 9:1 的等，Node 没问题。

但一个店员同时招呼一百桌这件事，直觉上还是像魔术。下一篇就拆这个魔术，你会发现它用的道具你天天在用：`await`。
