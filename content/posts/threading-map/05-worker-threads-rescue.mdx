[上一篇](/posts/threading-map/04-cpu-bound-blocks-all)的事故判得很清楚：五百张照片的一百秒，病根是算的活和一千个等的客人挤同一根线程。修法只有一个方向，挪。

墨记的修复当天就定了方案：主线程从此不碰压缩，雇专门的后厨。

## 后厨：worker_threads

Node 内置的 worker_threads 干的就是这件事：在你的进程里再开几根真正的线程，它们不接客，专门算。主线程回归本职，收图、派活、收结果。

```js
// 主线程，示意代码
const pool = new Pool(require("os").cpus().length); // 四核机器，四个后厨

async function makeThumbnail(buf) {
  return pool.run("compress", buf); // 派活给后厨，等结果
}
```

注意 `pool.run` 这一等，是上一篇讲的那种等：活已经交给了别人（后厨线程），主线程登记一句「好了叫我」就去接下一个请求。修完之后的墨记：五百张照片照样占一台机器一百秒的 CPU，但占的是四根后厨线程，主线程随时候着，全站照常。

这是真的并行。你 JS 写的压缩逻辑跑在四根线程上，把四个核吃满，01 里说单线程吃不到多核的饭，这就是补票的地方。worker_threads 的完整用法（怎么建、怎么传消息、怎么写 worker 文件）在 [nodejs-core 的并发篇](/posts/nodejs-core/08-concurrency)有教学，本篇只聊取舍。

## 后厨不是免费的

雇后厨的账单要摊开看。

数据要靠拷贝传递。主线程和 worker 不共享内存，传图片要把数据复制一份过去，结果再复制一份回来。小图无所谓，传几百 MB 的视频就要换思路：只传文件路径，让 worker 自己读盘。

后厨人数要自己定。少了排队，多了白占内存，一般按 CPU 核数来。

出错要自己兜。worker 崩了、超时了、泄漏了，没有框架替你管，要么自己写，要么用 piscina 这类现成的池子库。

还有一点最隐蔽：你的代码从一个世界变成了两个世界。接客的代码和干活的代码分开写、分开跑、靠消息通信，调试的复杂度上一个台阶。

这些代价都值不值，取决于那个算的活有多重、多频繁。墨记判断下来值得：压缩一张 200 毫秒，是实打实的事故级重量。

## 更粗的挪法：多开几个店

如果嫌雇后厨细碎，还有一个粗办法：cluster。一口气起四个 Node 进程，每个进程一根主线程、各吃一个核，前面用负载均衡把请求分给四个进程。

这相当于把一家店开成同街四家分店，客人被随机领进其中一家。它解决「总量」，不解决「单件」：每一家里面还是那个结构，进来一个五百张照片的客人，那家分店照旧冻住，只是波及范围从全站缩到四分之一的客人。

把进程从一变四，和把机器从一变多，是同一个思路的两个尺寸。后者是 08 的正题，到时候你会发现连锁店的麻烦也正是从这里长出来的。

## 什么时候别硬撑

后厨和分店都是补丁。有一种情况不值得打补丁：算的活是这个服务的常态主业。

假设墨记未来主打功能变成「批量视频转码」，那么转码不该是 Node 服务里小心翼翼供着的后厨任务，它该有自己的服务，语言就该选吃多核更痛快的。判断标准很朴素：打开这个服务的接口清单，算的活占几成？占一成，Node 加后厨，挺好；占七成，选型那天就不该选 Node，中途换掉也不丢人，跟语言较劲不划算。

墨记的结局在两者之间：缩略图先用 worker 后厨稳住了，半年后图片量上来，这部分计算整体并进了后端组的 Java 服务，那边的线程池是现成的。你也因为这次迁移，开始正经读 Java 服务的代码，然后参与维护它。

单线程的世界到此走完：卡是什么、等和算的分水岭、怎么自救。你带着这套地图走进多线程世界，第一个礼拜就见到了一个 review 谁都看不出错的 bug。
