[上一篇](/posts/threading-map/05-worker-threads-rescue)结尾你进了后端组，参与维护墨记的计费服务，Java 写的。单线程世界攒下的直觉，从这篇起要挨个接受挑战。

第一个挑战来自一行代码。

计费服务的规则：免费用户每月 1GB 同步流量。每次客户端同步，服务里有个计数器累加这次流量。QA 压测报告：一小时百万次同步，计数器总和比实际少了三十多万次。代码贴出来：

```java
void onSync(long bytes) {
    used += bytes; // 累计本月流量
}
```

组里三个人轮流 review，谁都没看出错。你的第一反应是压测工具少发了请求，换了工具再压，还是丢。代码没有错，错的是我们看代码的方式：我们默认它一口气跑完，而多线程世界里，它随时会被插队。

## counter 加一，其实是三步

`used += bytes` 在 CPU 眼里是三个动作：把 used 从内存读进寄存器，加上 bytes，写回内存。三步之间，随时可以换人。

假设 used 此刻是 1000，两根线程几乎同时来记流量，各要加 40 和 60：

```
时间 →
线程 A：读 used（1000）
线程 B：                    读 used（1000）
线程 A：算出 1040，写回
线程 B：                    算出 1060，写回   ← 覆盖了 A 的结果
```

两次同步，只记下了一次，凭空丢了 40。压测里每秒几千次同刻累加，丢三十万次毫不费力。而且它丢得毫无痕迹：不报错、不崩溃、日志里每笔都在，就是总数对不上。这类 bug 最恶心的地方在这，现场干净得像没发生过。

## 病名，和它为什么找不上前端

这个病叫竞态条件：结果取决于谁先谁后，而谁先谁后是碰运气的。发作要凑齐三件事：多根线程，共享同一份数据，对它做读改写。三件全中，就等着丢数据。

现在你能说清为什么写前端这些年从没遇上它了。01 里说过浏览器给你罩了两层保护，第一层就是单线程：你的 JS 跑的时候，全世界没有第二根线程能碰你的变量，插队这个动作物理上不存在。所以不是你代码写得好，是对手一直没上场。上了服务端，尤其 Java 这种一根请求一根线程的服务，对手成千上万。

## 药按轻重抓

好消息是这病有成熟药方，按病情轻重排。

最轻的药，原子变量。`AtomicLong` 的 incrementAndGet，把读、加、写回压成不可分割的一步，CPU 指令层面保证一次做完，别的线程插不进来。计数器这种单一变量的累加，用它，一行换一行：

```java
private final AtomicLong used = new AtomicLong(0);

void onSync(long bytes) {
    used.addAndGet(bytes); // 一次做完，插不了队
}
```

重一档的药，锁。synchronized 或 Lock，给一段代码上门锁，同一时刻只放一根线程进去，其他在门口等。它治的是原子变量治不了的病：好几步必须连着做完的逻辑。比如「查余额、判断够不够、扣款」这三步，任何一步之间被人插队都会出错，这时候要把三步整体圈进一间屋，用原子变量就不够了。

再配一点常备药：ConcurrentHashMap 这类并发容器，把常用的数据结构提前做成了线程安全的，直接用。

## 锁的账单

药有效，但不免费，用之前看清账单。

第一笔，排队。门锁一次进一个，门外的人干等，吞吐量往下掉。锁的粒度圈得越大（锁整段业务），排队越狠。

第二笔，死锁。两根线程各持一把锁，又都在等对方手里那把：A 锁了订单表等用户表，B 锁了用户表等订单表，两根线程永远卡死。防法有一句口诀：所有代码按同一个顺序拿锁，就不会互相等。但项目大了，口诀会被人忘，这是 Java 服务半夜重启的经典原因之一。

所以用药的总原则是：能不用锁就不用。计数器用原子变量，能用并发容器就用，真要上锁就把圈画到最小。有些场景连药都不用，因为病根本不该在这治，下一篇讲这个。

## 同一个病的别的楼层

插队改共享数据这个病，不止长在内存里。两个人同时编辑同一条笔记，A 读旧内容、B 读旧内容、A 存、B 存，B 覆盖 A，和计数器丢数是同一个病，只是这次共享数据在数据库的一行里，药也换成了事务和乐观锁。那一层在 [后端问题地图的并发篇](/posts/backend-problem-map/06-concurrency-transactions)讲，本系列管内存这一层。

顺带一提，竞态、synchronized、原子类的语法和用法，[Java 系列](/posts/java/18-concurrency-safety)有完整教学，那篇的切入点也是计数器，这类问题它确实是最短路径。本系列要你带走的是选药逻辑：单变量读改写用原子变量，多步连招上锁，锁画小圈。

| 名词         | 英文             | 一句话                                      |
| ------------ | ---------------- | ------------------------------------------- |
| 竞态条件     | race condition   | 结果看谁先谁后，而先后全凭运气              |
| 原子操作     | atomic operation | 不可分割、做完才许别人上手的一步            |
| synchronized | synchronized     | Java 的锁关键字，圈住的代码一次只进一根线程 |
| 死锁         | deadlock         | 两根线程各持一把锁互等对方，永远卡住        |

## 收尾

这类的病有个共同点：所有人都在改一份数据，把数据改坏了。

下一类的病长得不一样：数据一点没坏，一件事却被干了好几遍。计费服务的提醒邮件，同一个用户一天收到了五封，每封内容都对，就是不该有五封。抢数据和抢活，是两类病，药方也分家。
