ShopLite 三岁了。数据层的三板斧都上了：缓存命中率 92%，一主三从，订单表按 user_id 分了四片。但今年双十一的故障报告里，最疼的两次事故和数据层一点关系都没有：

第一次：商品团队修复一个库存计算的 bug，改了一行代码，发布。发布 = 全站重新部署，秒杀活动中断了 11 分钟，订单团队在群里发了三个愤怒的表情。

第二次：新写的店铺报表模块有一个内存泄漏，OOM，JVM 崩了。它把用户、商品、订单、支付全部拖下水——**整站宕机**，因为它们跑在同一个进程里。

数据扛住了，代码本身扛不住了。这是拆微服务的时刻。

## 单体的三宗罪——以及它为什么无罪

把三次故障抽象一下，单体的结构性问题就三条：

**部署耦合。** 30 万行代码是一个部署单元，改任何一行都要全量发布。商品团队发版，需要订单团队"陪跑"确认自己的功能没被影响；回滚一次，所有模块一起回。发布从一件小事变成一场需要全员戒备的仪式。

**故障不隔离。** 所有模块共享一个 JVM：一个模块内存泄漏，全班陪葬；一个模块把线程池占满，其他模块的请求也排不上队。木桶效应写进了进程模型里。

**协作瓶颈。** 几个团队改同一个代码仓库，合并冲突常态化；任何一个团队想升级依赖版本，要全站回归测试；新人面对 30 万行代码，三个月不敢动。

听起来单体罪该万死？先打住。**以上三条只有在"模块之间变更节奏差异大、团队多到互相阻塞"时才成为真问题。** 三个人维护的系统，30 万行代码也可以治理得很好——模块化、分层清晰的单体（有个正式名字叫**模块化单体，Modular Monolith**）直到今天依然是很多成功产品的形态。GitHub 早年、Shopify 的核心、大量国内中型业务，长期都是单体或"数量个位数的服务"。

拆分的信号是具体的，不是感觉：

- 某个模块的发布频率远高于其他（商品一天发三次，其他一周一次）
- 某个模块的负载特征独立（秒杀模块峰值 QPS 是整站其他部分的 50 倍）
- 团队按业务划分且人数到了互相拖累的规模（通常 30 人以上）
- 不同模块需要不同技术选型（报表要跑 Python 生态的分析库）

ShopLite 四条全中。拆。

## 怎么拆：按业务领域，不按技术层

拆分方向上有一个经典错误：按技术层拆——Controller 一个服务、Service 一个服务、Repository 一个服务。这种拆法把三层架构的**进程内调用换成了跨网络调用**，每次改功能还是要动三个服务，复杂度翻了十倍，收益为零。**白挨了分布式的打，没拿到分布式的红利。**

正确方向是**按业务领域（business domain）拆**：一个服务拥有某块业务的完整垂直切片——它的接口、逻辑、数据，端到端：

```
拆分前：单体 ShopLite                    拆分后：四个独立服务
┌────────────────────────┐
│ UserController          │              ┌─────────────┐   ┌─────────────┐
│ ProductController       │              │ 商品服务     │   │ 订单服务     │
│ OrderController   ──────┼──── 拆成 ───▶ │ (Spring Boot│   │ (Spring Boot│
│ ...                     │              │  + 独立商品库)│   │  + 独立订单库)│
│ UserService             │              └─────────────┘   └─────────────┘
│ ProductService          │              ┌─────────────┐   ┌─────────────┐
│ OrderService            │              │ 用户服务     │   │ 支付服务     │
│ ...                     │              └─────────────┘   └─────────────┘
│ 单个 MySQL              │              每个服务：独立部署、独立数据库、独立技术选型
└────────────────────────┘
```

判断拆得好不好，有个朴素的标准：**一个业务需求提出来， ideally 只需要改一个服务**。"给商品加个预售功能"只动商品服务——这就拆对了；如果每个需求都要改三个服务，那是拆错了，或者说是把耦合换了个地方。

## 最关键的事实：每个微服务还是一个 Spring Boot 应用

前面所有铺垫，都为了说清这句话：

> **微服务不是替代 Spring Boot 的新框架。商品服务就是一个只管商品的 Spring Boot 应用，你学的所有东西原封可用。**

看商品服务的项目结构，你会发现眼熟到亲切：

```
product-service/
├── pom.xml                 # 还是一个普通的 Spring Boot 工程
└── src/main/java/com/shoplite/product/
    ├── ProductController.java   # @RestController 接 HTTP
    ├── ProductService.java      # @Service 业务逻辑
    ├── ProductRepository.java   # @Repository 访问数据库
    └── ProductApplication.java  # @SpringBootApplication 启动类
```

三个层、一个启动类、一个独立的 MySQL。第 1 篇里造的那个"零件"，在这里原样复用——变的只是组织方式：**从一个大应用，变成一组各管一摊的小应用**。

真正变化的是服务之间的关系，变化只有一个字，但分量是 everything：** formerly 进程内的方法调用，变成了跨机器的网络调用**。订单服务要扣库存，以前是 `productService.deduct(...)` 直接调方法（编译期保证存在、纳秒级返回、同生共死的事务），现在是订单服务的机器发一个 HTTP/RPC 请求到商品服务的机器——**网络可能超时、对方可能挂、参数可能丢**。调用从"语言特性"降级成了"基础设施问题"。

顺带把一个历史名词归位：这套"把大系统拆成可独立部署的服务"的思想，早一代叫 **SOA**（面向服务架构），重在企业内系统集成，总线（ESB）笨重；微服务是它的轻量化再发明——去中心化、HTTP/轻量协议、独立数据库。面试遇到"SOA 和微服务的区别"，答这个差异就够了。

还有一个拆分时容易被忽略但极其重要的动作：**数据库必须跟着拆**。每个服务独占自己的库，商品库只有商品服务能连。如果四个服务还共享一个数据库，那只是"分布式单体"——部署解耦了，数据还锁死在一起，任何一次改表结构照样惊动全家。

## 康威定律：为什么拆服务往往是在拆组织

聊微服务绕不开**康威定律（Conway's Law）**：系统架构会映射设计该系统的组织结构。直白版：三个团队写代码，最终一定得到三个模块，不管架构图当初画了几块。

它反过来也成立，而且这才是很多公司拆微服务的真实驱动：**想按业务组建小团队（商品团队、订单团队各自为战），就要先按业务拆架构**——让团队边界和服务边界重合，一个团队端到端拥有一个服务：开发、测试、部署、值班，不打扰任何人。微服务的技术复杂度，买的是组织效率。

所以"该不该拆微服务"翻译成组织语言就是："你的团队规模和业务边界，需不需要用架构来固化？"三个人的团队硬拆六个服务，是把大厂的药当饭吃。

## 拆完的账单：一张新的问题清单

第 1 篇那张表，现在可以逐行兑现了。拆分当天，这些问题全部到账，一个都躲不掉：

| 拆完的第一天就撞上                                                           | 去哪解决   | 本系列   |
| ---------------------------------------------------------------------------- | ---------- | -------- |
| 订单服务调商品服务，地址写 `http://10.0.0.11:8080`？扩容换 IP 咋办，挂了咋办 | 注册中心   | 第 5 篇  |
| 四个服务四个配置，改一个数据库地址要登四台机器                               | 配置中心   | 第 5 篇  |
| 跨机器调用用什么写？自己 new HttpClient？                                    | 声明式调用 | 第 6 篇  |
| 客户端和外部流量怎么进来的，鉴权在哪做                                       | 网关       | 第 7 篇  |
| 下单跨订单/商品/用户三个服务三个库，事务怎么保证                             | 分布式事务 | 第 9 篇  |
| 一个请求穿五个服务，挂了去哪查                                               | 链路追踪   | 第 10 篇 |

这就是为什么说**微服务是"买一送 N"的架构**：买的是独立部署和故障隔离，送的是一整排分布式新问题。这些问题各自的解法拼起来，就是那个大名鼎鼎的名词——Spring Cloud。

## 什么时候不需要

这篇的反面视角比前几篇更重要，因为**过度拆分是这个行业最常见的过度设计**，没有之一：

- **团队小于 10 人**：沟通成本远没到需要架构来解耦的程度，模块化单体足够
- **模块变更节奏相近**：大家本来就在一个节奏里迭代，拆开只会凭空多出跨服务协调
- **没有独立扩容需求**：秒杀那种"单模块负载是其他模块几十倍"的场景才真需要独立扩缩容
- **没有专职运维能力**：四个服务意味着四倍的部署、监控、排障工作量，没有平台支撑会拖死开发团队

还有一个专门的反模式值得记住名字：**分布式单体**。特征是拆了一堆服务，但每次发版必须按固定顺序一起发、改一个需求动五个服务、共享数据库。它集两家之短：单体的耦合 + 分布式的复杂度。见到这种架构，问题不在技术，在当初就不该拆。

对 ShopLite 来说，四服务 + 四数据库是它当前规模下合理的一刀。下一刀什么时候切？等"订单服务内部"再出现明确的负载差和团队边界时再说——拆分应该是演化的结果，不是一次性的革命。

## 名词卡片

| 名词                  | 一句话定义                                         |
| --------------------- | -------------------------------------------------- |
| 单体 / 模块化单体     | 所有功能一个进程 / 单体但内部边界清晰的良好形态    |
| 微服务                | 按业务领域拆分、独立部署、独占数据库的一组小应用   |
| 服务拆分粒度          | 拆多细——按团队和业务边界，不按代码行数             |
| 康威定律              | 系统架构映射组织结构；拆服务常常是在配合组织调整   |
| SOA / ESB             | 微服务的前身，面向服务集成，依赖笨重的企业服务总线 |
| 分布式单体            | 反模式：拆了服务但耦合未减，集两家之短             |
| 进程内调用 → 网络调用 | 微服务本质变化：方法调用变远程调用，引入超时/故障  |
| 数据库拆分            | 每个服务独占数据库，共享库 = 变相单体              |

## 回顾与预告

四篇走完，ShopLite 完成了从单机单体到多服务架构的跳跃。从这篇开始，故事的主角从"怎么扛流量"切换到"怎么让一堆服务协同工作"——下一篇登场的是那个出现频率最高、也最容易被误解的名词：Spring Cloud。它不是框架，是问题清单的解决方案超市；而它的第一件商品（注册中心 + 配置中心 Nacos），解决的是"订单服务怎么找到商品服务"这个最基础的问题。
