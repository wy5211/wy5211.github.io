你能用 Spring Boot 写出一个完整的 REST API 了：Controller 接请求，Service 写逻辑，Repository 存 MySQL，JWT 做登录，Redis 做缓存。感觉良好。

然后你打开一个招聘 JD：「熟悉微服务架构，理解分布式事务原理，有 Spring Cloud / RocketMQ / Nacos 实战经验，了解 K8s 部署」。

每个字都认识。但这些词之间是什么关系？它们和你正在学的 Spring Boot 是什么关系？为什么面试官默认你"到了某个阶段自然就该懂这些"？

这篇文章就回答这个问题。先说结论：**这些名词不是并列的知识点，而是一条因果链——每个技术都是为了解决上一个阶段的新问题。** 你不需要"挨个学习"它们，你只需要看懂这条链，每个名词就会自动归位。

## 先摆一个具体的东西：ShopLite

从头开始。假设你要做一个最小化的电商，叫 ShopLite。三张表：

```sql
user:    id, username, password_hash, balance      -- 用户和余额
product: id, name, price, stock                    -- 商品和库存
"order": id, user_id, product_id, quantity, amount, status  -- 订单
```

一个 Spring Boot 应用装下所有代码，一个 MySQL 装下所有数据：

```
用户 App / 浏览器
      │ HTTP
      ▼
┌──────────────────────┐     ┌──────────┐
│  ShopLite 单体应用    │ ──▶ │  MySQL   │
│  (Spring Boot)      │     │  单实例   │
│  用户+商品+订单模块   │     └──────────┘
└──────────────────────┘
```

上线了。日活 500，一切正常。**这个阶段你什么都不缺**——上面那些名词一个都用不到，用到了反而是过度设计。

问题从哪来？从用户规模和代码规模来。下面是 ShopLite 接下来几年的完整病历。

## 演进链：每一次都是业务先出问题

### 第一阶段：一台服务器扛不住

日活涨到 5 万，晚上高峰期单台服务器 CPU 飙到 90%，接口响应从 50ms 涨到 2s。最直接的解法：**再加一台服务器，两台一起干活**——这就是**集群**。但两台服务器得有人分活，前面加一台 **Nginx 做负载均衡**，把请求轮流分给两台。

新问题立刻出现：用户在 A 机器上登录，Session 存在 A 的内存里，下一个请求被 Nginx 分到 B，B 说"你没登录"。这个"登录态丢失"问题逼出了两条路：**Session 共享**（把 Session 集中存到 **Redis**）或者干脆**无状态的 JWT**。

你看，Redis 这个"名词"第一次登场，不是因为它流行，而是因为集群化后 Session 无处安放。

### 第二阶段：数据库扛不住

应用服务器可以随便加（它不存数据），但所有请求最终都砸向同一个 MySQL。日活 20 万的某个晚上，MySQL CPU 100%，全站瘫痪——这次加机器救不了它。

解法按代价从小到大排：**缓存**（热门数据放 Redis，MySQL 只接缓存没有的请求）→ **读写分离**（一主多从，写进主库、读走从库）→ **分库分表**（数据本身太大，切成 N 份分到 N 个数据库）。

这一阶段还会顺带逼出一堆名词：缓存穿透/击穿/雪崩、主从延迟、分片键、分布式 ID。下一篇展开。

### 第三阶段：代码扛不住

数据的问题解决了，新的痛苦来自人。三年过去，ShopLite 代码 30 万行，商品团队改一行库存逻辑，全站重新部署，订单团队正在跑的活动全被打断；任何一个模块的 bug 都可能拖垮整个进程；新人入职三个月不敢改代码。

于是把单体拆开：商品服务、订单服务、用户服务、支付服务，各自独立部署、各自一个数据库。这就是**微服务**。

这里有个最关键、最少有人明说的事实：**拆出来的每个微服务，本质上还是一个 Spring Boot 应用。** 商品服务就是一个只管商品的 Spring Boot + 它自己的 MySQL。你已经会的东西没有作废——微服务不是替代 Spring Boot 的新框架，而是"很多个小单体"的组织方式。

### 第四阶段：拆完之后的连锁反应

拆的时候觉得很爽，拆完发现引入了一堆新问题，每个问题对应一个（或几个）你听过的名词：

| 拆完之后的新问题                                                 | 解决方案           | 名词                             |
| ---------------------------------------------------------------- | ------------------ | -------------------------------- |
| 订单服务要调商品服务，IP 写死吗？挂一台呢？                      | 服务注册与发现     | **Nacos**、Eureka                |
| 几十个服务，客户端要记几十个地址？                               | 统一入口           | **网关**（Spring Cloud Gateway） |
| 几十个服务的配置文件各自改一遍？                                 | 配置中心           | **Nacos**、Apollo                |
| 服务间怎么发起调用？                                             | 声明式远程调用     | **OpenFeign**、gRPC、Dubbo       |
| 商品服务挂了，连带的订单服务线程池被拖垮，全链路雪崩？           | 熔断、降级、限流   | **Sentinel**、Resilience4j       |
| 下单要同时扣库存、扣余额，跨了三个服务和三个库，本地事务管不了？ | 分布式事务         | **Seata**、TCC、Saga、本地消息表 |
| 下单成功还要加积分、发短信、通知物流，同步串行调用又慢又脆？     | 消息队列           | **RocketMQ**、Kafka、RabbitMQ    |
| 一个请求经过 5 个服务，出了 bug 去哪查？                         | 链路追踪、集中日志 | **SkyWalking**、ELK              |
| 几十个服务，手动部署到怀疑人生？                                 | 容器化与编排       | **Docker**、**Kubernetes**       |

盯着这张表看十秒。你会发现**微服务不是"一个技术"，而是一张问题清单**——那些让你迷茫的名词，全都是这张清单上某一行的答案。

## 那 Spring Cloud 到底是什么

现在可以给出准确定义了：**Spring Cloud 不是一个新的框架，而是第四阶段那张问题清单的"解决方案全家桶"**——它把注册中心、网关、远程调用、熔断、配置中心这些组件整合进 Spring Boot 生态，让你用统一的 starter 和注解接入。

有个历史背景值得知道：早期主流是 Spring Cloud Netflix（Eureka + Ribbon + Hystrix + Zuul），但 Netflix 的组件陆续停止维护（"Netflix 停更"事件），国内逐渐转向 **Spring Cloud Alibaba**：Nacos（注册+配置中心）+ Sentinel（熔断限流）+ Seata（分布式事务）+ RocketMQ/Dubbo。今天你在 JD 里看到的组合，大概率是后者。

所以 Spring Boot 和 Spring Cloud 的关系一句话说清：

> **Spring Boot 负责"造好每一个零件"，Spring Cloud 负责"把零件组装成能协同的工厂"。**

你先学 Spring Boot 完全正确——零件都造不好，谈什么组装。

## 总地图

把整条链收进一张图。这就是本系列的目录，也是你以后看到任何后端名词时的归位表：

```
阶段 0  单体 Spring Boot + MySQL
        │  用户多了，一台机器扛不住
        ▼
阶段 1  集群 + Nginx 负载均衡 ──▶ Session 共享 / JWT（Redis 登场）        → 第 2 篇
        │  数据库成为唯一瓶颈
        ▼
阶段 2  缓存 / 读写分离 / 分库分表（Redis 深度使用）                      → 第 3 篇
        │  代码膨胀，团队协作困难
        ▼
阶段 3  拆分微服务（每个微服务 = 一个 Spring Boot 应用）                  → 第 4 篇
        │  拆完出现一整排新问题
        ▼
阶段 4  Spring Cloud 全家桶：
        ├─ 注册与配置中心 Nacos          → 第 5 篇
        ├─ 服务间调用 Feign / gRPC       → 第 6 篇
        ├─ 网关 Gateway                  → 第 7 篇
        ├─ 消息队列 RocketMQ             → 第 8 篇
        └─ 分布式事务 Seata              → 第 9 篇
        │  几十个服务的运维问题
        ▼
阶段 5  链路追踪 / 集中日志 / K8s                                        → 第 10 篇
```

| 名词         | 一句话定义                                              | 归属阶段 |
| ------------ | ------------------------------------------------------- | -------- |
| 单体         | 所有功能装在一个应用进程里                              | 阶段 0   |
| 集群         | 同一个应用部署多份分摊流量                              | 阶段 1   |
| 负载均衡     | 把请求分发给多台机器的调度器（Nginx 是主流实现）        | 阶段 1   |
| 分布式       | 多台机器协同工作对外表现为一个整体（集群是它的特例）    | 阶段 1+  |
| 中间件       | 独立部署、供应用依赖的基础软件（Redis、MQ、Nacos 都是） | 贯穿     |
| 微服务       | 按业务领域拆分的、独立部署的一组小应用                  | 阶段 3   |
| Spring Cloud | 微服务阶段各类问题的组件全家桶（规范 + 集成）           | 阶段 4   |
| RPC          | 服务间远程过程调用（Feign/gRPC/Dubbo 是实现）           | 阶段 4   |

## 最容易被忽略的一课：什么时候不需要这些

扫盲系列最容易犯的错，是让你觉得"这些技术 = 先进 = 必须会"。说三件真事：

**第一，大量公司在阶段 1-2 就停住了。** 一个单体 + Redis 缓存 + 读写分离的架构，服务日活几十万绰绰有余。国内的很多中型业务、绝大多数出海独立应用，就是这个架构——没有微服务，没有 MQ，没有分布式事务，活得很好。

**第二，拆微服务有真实代价。** 服务间通信的延迟和故障、分布式事务的复杂度、运维成本翻倍，这些都是拆完立刻兑现的账单。业界有句被验证过无数次的话：**绝大多数团队高估了自己需要的微服务数量，低估了维护它们的成本。** 判断标准不是"技术先进"，而是：模块变更频率差异大不大、团队是不是多到互相阻塞、单模块负载是不是真的需要独立扩容。

**第三，面试和干活是两回事。** 面试问分布式事务是因为它能区分"写过 CRUD"和"理解系统"，但工作中你会先花大量时间在索引优化、缓存设计、接口设计上——这些"不够时髦"的功夫才是日常。

所以这个系列每篇都会固定回答一个问题：**什么时候不需要它**。知道一个技术什么时候该被拒绝，比知道怎么用它更能说明你理解了它。

## 这一系列怎么讲

从下一篇开始，每一篇对应地图上的一个阶段：用一个具体的故障场景开头（ShopLite 又出事了），讲清那个阶段的核心问题、主流方案怎么选、在 Spring Boot 里长什么样、以及什么时候属于过度设计。

篇幅上做减法：每篇只放关键代码片段，目标是建立判断力，不是替代官方文档。涉及 Redis、Docker、DevOps 的部分，我会链接到这个博客里已有的深入系列——这个系列是地图，深度交给专门的山。
