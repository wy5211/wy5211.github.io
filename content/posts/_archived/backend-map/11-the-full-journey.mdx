十篇之前，ShopLite 是一个跑在单台服务器上的 Spring Boot 应用，配一个 MySQL。现在它长这样：

```
外网用户
   │
   ▼
Nginx（TLS 终止、静态资源、第一层转发）····················· 第 2 篇
   │
   ▼
Spring Cloud Gateway ×2（路由 / JWT 鉴权 / 限流）·········· 第 7 篇
   │
   ▼
订单服务 ×4 ──┐         ┌── Nacos（注册 + 配置中心）········ 第 5 篇
商品服务 ×3 ──┼─ OpenFeign 互调（超时 / 重试 / 幂等）······· 第 6 篇
用户服务 ×2 ──┘
支付服务 ×2
   │                    │
   │                    ▼
   │              RocketMQ（削峰 / 解耦 / 事务消息）········ 第 8 篇
   ▼
MySQL 集群：订单库 ×4 分片（读写分离）、商品库、用户库····· 第 3 篇
Redis 集群：缓存 / Session / 分布式锁 / 限流计数··········· 第 2、3 篇
SkyWalking：全链路追踪 · Prometheus + Grafana：监控告警···· 第 10 篇
K8s：承载以上所有，自动扩缩容、滚动发布··················· 第 10 篇
```

每一个组件都是被一个具体问题逼出来的——这句话是整个系列的题眼。现在验证它：跟踪一个下单请求，看它怎么穿过这张图。

## 一个下单请求的完整旅程

**T+0ms** 用户在 App 点下「立即购买」。

**T+5ms** 请求经 DNS 到达 Nginx，TLS 解密，转发给网关集群中的一台。Nginx 不知道后面有多少服务，它只认识网关。（第 2 篇：负载均衡与反向代理）

**T+8ms** 网关的过滤器链开始工作。`JwtAuthFilter` 校验 token——签名有效、未过期，解析出 `userId=1001`，写进 `X-User-Id` 请求头。接着路由断言命中 `/api/order/**`，目标解析为服务名 `order-service`。顺手查了一下限流计数：这个用户最近一秒第 3 次请求，令牌桶还有余量，放行。（第 7 篇：网关三件套、认证与授权的分工）

**T+15ms** 网关从本地缓存的服务列表里选中 `order-service` 的 2 号实例——这份列表来自 Nacos 的订阅推送，五分钟前 5 号实例因心跳超时被摘除，网关无感更新。（第 5 篇：注册发现）

**T+20ms** 订单服务收到请求。SkyWalking 的 TraceAgent 早已在入口打上了本次请求的 `traceId`，此后它跨服务、跨 MQ 传播，贯穿整条链路的日志。（第 10 篇：链路追踪）

**T+25ms** 业务开始。订单服务需要商品信息——通过 OpenFeign 调用 `productClient.getProduct(1001)`。动态代理拦下这次调用：从 Nacos 缓存选一台商品服务，HTTP 请求 30ms 后返回。缓存热数据时这一步更快——商品详情在 Redis 里，命中率 92%。（第 6 篇：声明式调用；第 3 篇：Cache-Aside）

**T+60ms** 订单服务开启本地事务：写订单表（订单库 user_id 分片，路由到 db1），**同一个事务里**写本地消息表一条 PENDING 记录。提交——订单和"待发消息"原子落地。（第 9 篇：本地消息表）

**T+65ms** 接口返回。App 显示「下单成功」——到此用户侧结束，**总耗时 65ms**。但旅程还有一半。

**T+70ms** 后台任务扫到 PENDING 消息，发往 RocketMQ 的 `order-topic:created`。（第 8 篇：消息必达）

**T+200ms** 库存服务的消费组收到消息。消费逻辑先做幂等检查（积分流水表唯一键），然后扣库存——商品库的本地事务。同一时刻，积分服务、短信服务、物流服务在各自的消费组里并行处理同一条消息，互不等待、互不认识订单服务。（第 8 篇：异步解耦）

**T+5min** 对账任务启动：扫描最近一小时订单，比对订单状态与库存流水，发现一笔不一致（某次消费重试中的并发窗口），自动修复并记录。（第 9 篇：对账兜底）

**T+30min** 这笔订单还是「待支付」。30 分钟前创建时发的那条延迟消息此刻到达：消费逻辑查订单状态——未支付，取消订单、回滚库存。（第 8 篇：延迟消息）

一条请求，穿过 10 篇文章。如果中途任何一环出错，SkyWalking 的 traceId 能把五段服务的日志串成一条线，Prometheus 的告警先于用户投诉到达值班群。（第 10 篇）

## 然后：你的下一步

回到第 1 篇开头那个让你迷茫的 JD：「熟悉微服务架构，理解分布式事务原理，有 Spring Cloud / RocketMQ / Nacos 实战经验，了解 K8s 部署」——现在这串名词在你脑子里应该是一张有因果关系的地图，而不是一堆并列的黑话。

地图有了，但地图不等于行军能力。最后给一条诚实的学习路线，按投入产出比排序：

**第一优先级：把单体的深度补足（占日常工作的 80%）。** Spring Boot 的熟练度（事务、AOP、排查内存问题）、MySQL 的索引与执行计划、Redis 的数据结构与缓存设计、并发编程。这些是所有后续技术的地基，也是面试和工作中被检验频率最高的部分——而且它们在单体和微服务里完全通用。这个博客已有的 [Spring Boot 系列](/posts/springboot/01-why-spring-boot)、[Redis 系列](/posts/redis/01-getting-started)就是为这一层准备的。

**第二优先级：部署与协作能力。** Linux 基础、Docker、CI/CD、把一个项目从开发带到线上运行的完整经验。参照 [DevOps 系列](/posts/devops/01-linux-server-setup)。这一层把你和"只会在本地跑 demo"区分开。

**第三优先级：微服务组件的动手经验。** 本系列给了判断力，但搭过和没搭过是两回事。建议做一个刻意练习：**把一个练手项目拆成两三个服务**，亲手配一遍 Nacos + Feign + Gateway，加一条 MQ 异步链路，用 Docker Compose 把整套跑起来。两天时间，胜过看十篇教程——重点是体验"拆完之后冒出来的那些问题"，而不是组件本身。

**关于微服务的深度（源码、调优、Service Mesh）**：等工作中真的被分配到相关任务再深入。带着真实问题学，效率是完全不同的量级；提前学的东西没有抓手，留存率接近零。

最后一个建议，也是这个系列想刻进你脑子里的唯一元认知：**每遇到一个新技术，先问三个问题——它解决什么问题？不用它的人怎么办？我现在的规模需要它吗？** 能稳定回答这三个问题的人，做技术选型时不会错得离谱——这比会用任何一个框架都值钱。

ShopLite 的故事讲完了。你的，刚开始。
