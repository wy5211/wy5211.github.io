周一早上十点，客服工单涌进来：部分用户下单失败。你登进订单服务的机器 `tail -f` 日志——一切正常。问题可能在商品服务（Feign 超时？）、网关（限流误伤？）、Redis（缓存击穿？）、MQ（消息积压？）。

四个服务 × 几个实例 × 每台机器一个日志文件。用户那次失败的请求，它的痕迹散落在几十个文件的几百万行日志里，而**你甚至不知道它经过了哪几台机器**。

单体时代排障的套路——「登服务器看日志」——在微服务架构下彻底破产。这篇讲它的替代品：**可观测性（Observability）**，外加几十个服务的部署问题（K8s）。前者让你"看得见"，后者让你"管得住"。

## 可观测性三支柱

行业的标准答案由三部分组成，各回答一类问题：

| 支柱                | 回答的问题                 | 主流工具链           |
| ------------------- | -------------------------- | -------------------- |
| 日志（Logging）     | 那一刻发生了什么（细节）   | ELK / EFK            |
| 指标（Metrics）     | 系统现在整体健康吗（趋势） | Prometheus + Grafana |
| 链路追踪（Tracing） | 一次请求经历了什么（路径） | SkyWalking / Zipkin  |

三者的关系用一次排障串起来最直观：**指标**发现问题（告警：订单接口 P99 延迟涨了 3 倍）→ **链路**定位环节（trace 显示耗时涨在商品服务那一跳）→ **日志**查明原因（那台实例的日志里 Redis 连接超时）。三步走完，周一早上那单故障从"无从下手"变成十分钟定位。

### 日志：从几十个文件到一个搜索框

ELK 是最经典的组合（EFK 是同类替换）：**Filebeat** 部署在每台机器上，像搬运工一样把新增日志行收集起来，运往 **Elasticsearch**（全文检索引擎）建索引；**Kibana** 提供网页界面，你在一个搜索框里输入关键词，秒级搜遍全部服务的全部实例。

但集中只是治标，治本要靠一个约定：**日志里打上 traceId**——马上讲它为什么是微服务日志的身份证。

### 链路追踪：traceId 串起一次请求

链路追踪的核心机制朴素到惊人：请求进入系统的第一站，生成一个全局唯一 ID（**TraceId**）；此后这个 ID 随着请求跨越每一个服务——塞进 HTTP header（如 `sw8`）传给下一跳，跨 MQ 时塞进消息属性；每个服务把收到的 TraceId 打进自己的日志行。于是：

```
网关日志:        [traceId=a1b2] 收到 POST /api/order, userId=1001
订单服务日志:     [traceId=a1b2] 订单 88231 创建成功
订单服务日志:     [traceId=a1b2] 调用 product-service... 耗时 3021ms ⚠
商品服务日志:     [traceId=a1b2] 查询商品 1001 ... Redis 超时, 降级查库
积分服务日志:     [traceId=a1b2] 消费消息 order:created 加积分完成
```

在 Kibana 里搜 `traceId=a1b2`，这次请求的全部行为按序铺开——**几十台机器的日志被一个 ID 缝合成一个故事**。周一早上那个工单，第一次能这么查。

TraceId 之下还有 **Span** 的概念：一次请求是一个 Trace，其中每一段工作（一次 HTTP 调用、一次 DB 查询）是一个 Span，记录起止时间和耗时。Span 按父子关系组织，在 SkyWalking 界面上渲染成**瀑布图**——哪一跳最慢、慢在哪一段，一眼可见。Spring Boot 侧的接入通常是 **SkyWalking Java Agent**：启动时挂一个探针参数，无需改一行代码，框架的 HTTP 客户端、数据源、MQ 调用全自动埋点。这种"无侵入"是它相对手写埋点方案（Micrometer Tracing）的主要卖点。

```bash
# "无侵入"的意思：启动命令加一个参数，代码零改动
java -javaagent:/agents/skywalking-agent.jar \
     -Dskywalking.agent.service_name=order-service \
     -Dskywalking.collector.backend_service=10.0.0.9:11800 \
     -jar order-service.jar
```

### 指标：数字说话的体检报告

日志回答个案，指标回答整体。**Prometheus** 定期拉取每个服务暴露的 `/actuator/prometheus` 端点（Spring Boot Actuator 自带），把 QPS、延迟分布、JVM 内存、线程池水位存成时序数据；**Grafana** 把这些数据画成仪表盘；**Alertmanager** 在指标越线时打电话——比如「订单接口错误率 5 分钟均值超过 1%」。

指标世界有个值得记住的最小集，叫**四黄金指标**（Google SRE 提出）：延迟（多快）、流量（多少）、错误率（错多少）、饱和度（还剩多少余量）。任何服务把这四个指标做准，健康判断就有了骨架。

告警设计有一条血泪原则：**面向症状告警，不要面向原因告警**。告「用户下单失败率超 1%」（症状，用户真实感受到的），不要告「CPU 超 80%」（原因，可能根本不影响用户）。原因类的信息放仪表盘里供排查，症状类的才值得半夜叫醒人。

## 几十个服务怎么部署：K8s 登场

看得见了，还要管得住。四个服务几十个实例，发布一次的含义是：构建四套镜像、按依赖顺序滚动更新、健康检查、挂了自动拉起、大促前手动扩容、大促后手动缩回来——用脚本+人肉做到某个规模后就撑不住了。

第 2 篇说应用无状态可以随意复制——**Kubernetes 把这句话变成基础设施级的自动执行**。你用声明式配置描述期望状态（「订单服务跑 4 个副本」），K8s 持续对账：实例挂了自动重建（**自愈**）；发布时逐个替换旧副本，全程不中断（**滚动发布**）；按 CPU 自动增减副本数（**HPA 自动扩缩容**——大促前手动扩容的工作消失了）。

对前面的篇章有一个重要的回响：K8s 的 **Service** 抽象自带服务发现——内置 DNS、自动负载均衡、健康实例过滤。所以第 5 篇说过的那句话在这里兑现：**跑在 K8s 上的系统，注册中心的职能被基础设施接管了**（配置中心仍需要，Nacos 照用）。这是"下沉"趋势的一部分，往下看。

```yaml
# 声明式配置的体感：说清"要什么"，不说"怎么做到"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
spec:
  replicas: 4 # 我要 4 个副本——挂了一个，K8s 自动补
  template:
    spec:
      containers:
        - name: order-service
          image: registry.shoplite.com/order-service:1.42.0
          resources:
            limits: { cpu: "2", memory: 2Gi }
          readinessProbe: # 就绪探针：没 ready 的实例不接流量
            httpGet: { path: /actuator/health/readiness, port: 8080 }
```

这块的深度（Docker、Compose、K8s 生产化）不是本篇能装下的——这个博客的 [Docker 系列](/posts/docker/01-why-docker)和 [DevOps 系列](/posts/devops/01-linux-server-setup)从动手层面完整讲过，可按需取用。

## 顺带一瞥：Service Mesh，治理逻辑的下一站下沉

留意本系列的一条暗线：**治理逻辑不断从业务代码里搬出去**。熔断重试最初要手写（Hystrix 时代）→ 变成注解和配置（Sentinel/Feign）→ 正在被搬进基础设施（K8s 接管服务发现）。这条线的下一站叫 **Service Mesh（服务网格）**，代表是 Istio：给每个服务旁边部署一个代理（**Sidecar**），服务间所有流量都经过它——重试、熔断、加密、灰度分流，全部由 Sidecar 统一执行，**业务代码里一行治理逻辑都不留**。

目前的主流判断：Service Mesh 运维门槛高，是几百服务以上规模的选项，多数团队仍在 Spring Cloud 体系里。但你现在已经能把它放进地图了：它是"下沉"趋势的现在进行时，不是全新的物种。

## 什么时候不需要

可观测性的投入应该和系统规模严格成正比：

- **单体、流量小**：结构化日志写好（带 userId、orderId），一个文件，一个简单的 uptime 监控——够了。上 ELK 是杀鸡用牛刀
- **三五个服务**：一台中央 rsyslog 聚合日志 + Prometheus 监控 + 链路追踪可以缓一缓——先把日志规范化（统一 JSON 格式、关键 ID 入日志）做了，链路追踪等排查痛点真实出现再上
- **判断标准**：每次事故你能在多久内定位？如果答案总是"超过半天"，三支柱按 链路 → 指标 → 日志集中 的顺序补齐——链路追踪对微服务排障的边际收益最大

K8s 同理：四五个服务用 Docker Compose 部署在两台机器上，运维成本远低于维护一套 K8s。**K8s 解决的是"几十个服务"的编排问题，服务没到那个量，它就是新的问题本身**。
