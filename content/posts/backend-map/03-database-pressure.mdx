晚上 8 点，ShopLite 大促开抢。运维盯着监控：两台应用服务器 CPU 稳定在 40%，很轻松。但 MySQL 的 CPU 冲上了 100%——慢查询堆积，连接池耗尽，所有请求排队超时，全站 504。

加机器？再开十台应用服务器也没用，因为瓶颈根本不在应用层：**所有请求最终都收敛到同一个 MySQL**。上一篇解决的是"应用层怎么横向扩"，这一篇的问题是：应用可以随便复制，数据库为什么不行？

答案是一个贯穿整个后端架构的核心概念：**状态**。

## 应用无状态，数据库有状态

应用服务器之所以能随便加，是因为它不保存数据——请求进来，算完就忘，机器炸了再开一台完全等价。这叫**无状态（stateless）**。

MySQL 里有你的全部数据：订单、余额、库存。你不能"再开一台一模一样的 MySQL"——数据在实时变化，两台机器怎么保持一致？这就是**有状态（stateful）**，有状态的东西不能简单复制，扩容难一个数量级。

所以数据库扛压的整条路线，本质都是围绕这个约束做文章：**让 MySQL 少干活（缓存）、把读分摊出去（读写分离）、把数据切开（分库分表）**。按侵入性从小到大排，逐一上。

## 第一板斧：缓存，让 MySQL 只接"缓存里没有"的请求

大促时 3000 QPS 的商品详情请求，其实 90% 在反复查同一段数据：那款热销的耳机详情页，一万个人看到的是同一条记录。每次都打穿到 MySQL 磁盘上的 B+ 树，纯属浪费——把查过的结果放内存里，下次直接返回。

Redis 就是干这个的：数据放内存，读写亚毫秒级，比走磁盘的 MySQL 快一到两个数量级。最常用的模式叫 **Cache-Aside（旁路缓存）**：读的时候先查缓存，查不到再查数据库并回填；写的时候先更新数据库，再删掉缓存。

在 Spring Boot 里，一个注解就能接入：

```java
@Service
public class ProductService {

    // 每次进入方法前，先按 key = "product:1001" 查 Redis：
    // 命中 → 直接返回缓存值，方法体根本不执行
    // 未命中 → 执行方法查 MySQL，把返回值写入 Redis，TTL 30 分钟
    @Cacheable(value = "product", key = "#id", unless = "#result == null")
    public Product getProduct(Long id) {
        // 能走到这里，说明缓存没有，才会打穿到数据库
        return productRepository.findById(id)
                .orElseThrow(() -> new ProductNotFoundException(id));
    }

    // 更新时只删缓存、不更新缓存：下次读取自然会加载最新值
    // （避免"更新缓存"和"更新数据库"两步不一致的问题）
    @CacheEvict(value = "product", key = "#id")
    public void updatePrice(Long id, BigDecimal newPrice) {
        productRepository.updatePrice(id, newPrice);
    }
}
```

两个细节值得注意：`unless = "#result == null"` 把"查不到"的结果排除在缓存之外（为什么重要，马上讲）；写操作选择**删缓存**而不是改缓存，因为改缓存要算新值，和数据库的更新之间容易打架，删掉让下次读触发回填，逻辑最简单。

缓存上完，MySQL 的 QPS 从 3000 降到 300。但缓存在挡流量的同时也引入了三个新故障模式——就是面试必问的"缓存三兄弟"。

### 缓存三兄弟：穿透、击穿、雪崩

**穿透**：恶意请求专门查"一定不存在的数据"（`product?id=-1`），缓存永远不可能命中（因为数据库里也没有，无值可缓存），每个请求都打穿到 MySQL。上面 `unless` 的写法只解决了"偶尔查不到"，防不住恶意扫描。解法：把"空结果"也缓存一小段时间（key 存在、值为 null），或者上**布隆过滤器**——一个能用极小内存判断"某元素一定不存在"的结构，不存在就直接拒绝。

**击穿**：某个**热点 key** 在过期的一瞬间，恰好一万并发同时到达，全部未命中，全部打向数据库——热门商品详情页 TTL 到期的瞬间，MySQL 直接被这一波打死。解法：热点数据不过期由后台异步刷新，或未命中时用**互斥锁**保证只有一个请求去查库回填，其他请求等一下。

**雪崩**：大量 key 设置了相同的 TTL，同一时刻集体过期；或者 Redis 本身挂了。缓存整体失效，全部流量灌进数据库。解法：TTL 加随机值打散过期时间、Redis 部署成集群模式、应用侧对数据库做限流兜底。

三个词经常被混着背，区分的关键就一个：**穿透是"查不存在的数据"，击穿是"一个热点过期"，雪崩是"大面积失效"**。对应的防御也分别落在：入口、单点、整体。

## 第二板斧：读写分离——把读流量分摊到多台机器

缓存挡住了"读热门数据"的流量，但有两类请求它管不了：写请求（下单、扣库存必须进数据库），以及缓存没有的长尾读。数据量涨到一定阶段，单实例 MySQL 连接数和磁盘 IO 都到顶了。

方案是**主从复制 + 读写分离**：给 MySQL 配几个从库（slave），主库（master）负责写，从库负责读。

```
              写请求（下单/扣库存）
                    │
                    ▼
              ┌──────────┐   binlog 异步复制
              │ 主库 M   │ ─────────────┐
              └──────────┘              ▼
                                   ┌──────────┐
              读请求（查详情/列表） │ 从库 S1  │
                    │             └──────────┘
                    │             ┌──────────┐
                    └───────────▶ │ 从库 S2  │
                                  └──────────┘
```

原理一句话：主库把每次数据变更写进 **binlog**（变更日志），从库拉取 binlog 回放，数据就同步了。注意是**异步**的——这四个字后面有坑。

在 Spring Boot 里通常配成两个数据源，按操作路由：

```yaml
# ShardingSphere-JDBC 的读写分离配置（也可以用 dynamic-datasource）
rules:
  readwrite-splitting:
    data-sources:
      readwrite_ds:
        write-data-source-name: write_ds # 主库：承载 INSERT/UPDATE/DELETE
        read-data-source-names: read_ds_0,read_ds_1 # 从库：承载 SELECT，自动轮询
```

四个从库读、一个主库写，读吞吐翻了四倍。但异步复制带来了一个用户真真切切能感知的 bug：

**用户下完单，跳转"我的订单"列表——空的。** 因为下单写进了主库，binlog 还没同步到从库（**主从延迟**，正常毫秒级，高峰期可能秒级），紧接着的列表查询被路由到了从库，读到的是旧数据。用户以为自己没下单成功，再下一次——重复订单。

解法按场景选：对"自己刚写入又要立刻读"的关键路径强制走主库（框架一般支持Hint 强制路由）；或者前端接受短暂延迟（下单后提示"订单处理中"，过一秒再查）。**读写分离不是纯技术配置，它改变了你应用层对一致性的假设**——这是很多团队上线后才补的一课。

## 第三板斧：分库分表——把数据本身切开

读写分离扩容了"读写流量"，但挡不住数据量本身：订单表 2 亿行，任何索引都救不了多条件分页查询，单库磁盘和备份时间也到了极限。这时候只能把数据切开——**分库分表（sharding）**。

切法两种维度。**垂直切**按业务或字段拆：订单库和用户库分开（垂直分库），大字段拆到附表（垂直分表）。**水平切**才是硬仗：订单表按某个字段（**分片键**）的哈希值拆到 N 个库，每库再拆 M 张表：

```
"order" 表，分片键 user_id，按 hash(user_id) % 4 路由：

user_id = 1001 → hash % 4 = 0 → db0.order_0
user_id = 1002 → hash % 4 = 3 → db3.order_1
user_id = 1003 → hash % 4 = 1 → db1.order_0
```

路由这件事由**ShardingSphere** 这类中间件完成，对应用基本透明——你在 Spring Boot 里照常写 SQL，它解析 SQL、算路由、改写表名、聚合结果。

分片键的选择决定了这个系统以后所有查询的形状：按 `user_id` 分，买家查自己的订单只落一个分片，快；但商家查"我店铺的所有订单"没有 user_id，只能**广播到全部分片再聚合**，慢且费。没有全维度都快的分片键，只有"为最重要的查询路径牺牲次要路径"。

而且分库分表一旦做了，三个代价立刻兑现：

1. **自增主键废了**——四个库各自从 1 自增会撞号，需要**分布式 ID**（主流方案是雪花算法 Snowflake：时间戳 + 机器号 + 序列号拼出全局唯一的 long）。
2. **跨分片的 JOIN 和分页几乎不可用**——订单在 db0、用户在 db3，一句 SQL join 不了，要么冗余字段要么应用层聚合。
3. **本地事务失效了**——一次下单扣库存、扣余额、建订单，数据落在三个库，`@Transactional` 管不到——这就是**分布式事务**问题，第 9 篇专门讲。分库分表往往是很多团队第一次被迫面对分布式事务的原因。

再往后一步是 **NewSQL**（代表 TiDB）：兼容 MySQL 协议、数据自动分片、水平扩容对应用透明——相当于把分库分表的活下沉到数据库层。代价是运维复杂、资源要求高，一般是真的到了海量数据规模才考虑。

## 什么时候不需要：优化顺序铁律

数据库慢了就上分库分表，和"发烧了就上化疗"是一个思路。真实的优化顺序是：

1. **先看索引和 SQL**——绝大多数"数据库扛不住"是慢查询没建对索引，`EXPLAIN` 一看全表扫描，加个索引 QPS 立刻翻十倍。成本最低，收益最大。
2. **再上缓存**——读多写少的场景，一层 Redis 解决 90% 的压力。
3. **然后读写分离**——写多、或者长尾读多，加从库。
4. **分库分表是最后手段**——只有单表数据量真到亿级、前面全做过还扛不住，才切。它带来的分布式 ID、跨分片查询、分布式事务问题，复杂度都会转嫁到应用层。

一个参考量级：单表 2000 万行以内、配合好索引，MySQL 通常表现良好；日活几十万的应用，"索引 + 缓存 + 一主两从"基本就到顶了，碰不到分库分表。

| 方案     | 解决什么           | 代价                             | ShopLite 什么时候需要 |
| -------- | ------------------ | -------------------------------- | --------------------- |
| 索引优化 | 慢查询             | 几乎没有                         | 一开始就该做对        |
| 缓存     | 热点读             | 穿透/击穿/雪崩三个坑             | 日活过万              |
| 读写分离 | 读吞吐、连接数     | 主从延迟                         | 日活十万级            |
| 分库分表 | 单表数据量         | JOIN 消失、分布式 ID、分布式事务 | 单表过亿行            |
| NewSQL   | 同上，且不想自己干 | 运维复杂                         | 极大规模              |

## 名词卡片

| 名词            | 一句话定义                                                 |
| --------------- | ---------------------------------------------------------- |
| 无状态 / 有状态 | 不保存数据可随意复制 / 保存数据扩容困难                    |
| Cache-Aside     | 读：先缓存后库并回填；写：先库后删缓存                     |
| 缓存穿透        | 查不存在的数据，缓存永远不命中（防：空值缓存、布隆过滤器） |
| 缓存击穿        | 单个热点 key 过期瞬间并发打库（防：互斥锁、逻辑过期）      |
| 缓存雪崩        | 大量 key 同时失效或 Redis 整体故障（防：随机 TTL、集群）   |
| 布隆过滤器      | 用极小内存判断元素"一定不存在"的结构                       |
| 主从复制        | 主库写 binlog、从库回放同步数据，异步                      |
| 主从延迟        | 写主库后数据尚未同步到从库的时间差                         |
| 读写分离        | 写走主库、读走从库，读能力水平扩展                         |
| 分片键          | 决定一行数据落到哪个分片的字段                             |
| ShardingSphere  | 国内主流的分库分表中间件，也支持读写分离                   |
| 分布式 ID       | 分片后自增主键失效，需全局唯一 ID（雪花算法）              |
| NewSQL          | 兼容 SQL 语法、自动分片、可水平扩容的数据库（TiDB）        |

## 回顾与预告

这一篇解决的是**数据层**的规模问题：ShopLite 的 MySQL 活了下来，缓存、从库、分片各就各位。但注意一个变化——从这一篇开始，ShopLite 的部署里出现了 Redis 集群、多个 MySQL 实例这类**独立的基础软件**，它们有个统称叫**中间件**，是后面每一阶段的主角。

数据库的问题告一段落，下一个扛不住的是**代码本身**：三年后 ShopLite 30 万行代码，商品团队和订单团队开始互相拖累。怎么拆、拆完的世界长什么样——下一篇进入微服务。
