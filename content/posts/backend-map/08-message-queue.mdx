ShopLite 的下单链路长成了这样：创建订单 → Feign 调商品服务扣库存 → Feign 调用户服务加积分 → Feign 调通知服务发短信 → Feign 调物流服务预约取件。五步串行，每步都是远程调用。

产品经理看数据：「下单成功率 99.2%，平均耗时 1.8 秒。」然后某天短信服务的供应商出故障，超时——下单接口直接 500。用户没收到短信不打紧，但**因为发不出短信而下不了单**，这就荒唐了：一个最不重要的环节，卡死了最核心的流程。

这个场景有明确的病理特征：**下游环节多、部分环节不重要的、串在一起互相拖累**。药方是一类中间件——**消息队列（MQ，Message Queue）**。

## MQ 的三个经典价值

把上面的同步链路改成：订单服务创建完订单，往队列里发一条「订单已创建」消息，就立刻返回。扣库存、加积分、发短信、通知物流，各自作为消费者订阅这条消息，各自处理：

```
同步串行（改造前）：                       异步（改造后）：

创建订单 ─ 扣库存 ─ 加积分 ─ 发短信 ─ 物流   创建订单 ──▶ 发消息 ──▶ 返回用户（200ms）
   200ms    300ms    200ms    3s!   1s                │
                                                   ┌───┴──────────────┐
                                                   ▼                  ▼
总耗时 = 之和；任何一环挂，全链路失败      库存服务◆ ◆积分服务     ◆ 短信服务（挂了也不影响下单）
                                          各自消费，互不等待      消息留在队列，恢复后接着消费
```

这一张图同时展示了 MQ 被反复引用的三个价值，它们其实是同一件事的三个侧面：

**异步**：主流程只发消息不等待，耗时从"五步之和"变成"一步"。用户 200ms 拿到下单结果，剩下的环节在后台各自消化。

**解耦**：订单服务从此**不需要知道下游有谁**。以后要加"下单后送优惠券"？优惠券服务自己去订阅「订单已创建」消息，订单服务一行代码不改。对比同步链路：每加一个下游，下单代码改一次——发版、回归、重新部署。

**削峰**：秒杀开始，10 万 QPS 灌进下单接口。如果同步处理，数据库和所有下游当场过载。改异步后：请求快速落单、发消息进队列，消费端按自己能承受的速率（比如 2000/s）从队列匀速取出处理。流量洪峰被队列这个"蓄水池"削平了，超出的部分排队等待——用户看到的可能是"排队中，请稍后查订单状态"，而不是 502。

## 选型：RocketMQ、Kafka、RabbitMQ

三家是面试和选型都绕不开的名字，定位差异比想象中大：

| 维度 | Kafka                        | RocketMQ                         | RabbitMQ               |
| ---- | ---------------------------- | -------------------------------- | ---------------------- |
| 出身 | LinkedIn，大数据日志流       | 阿里，电商交易场景               | 老牌通用消息系统       |
| 吞吐 | 百万级/s，三家最高           | 十万级/s                         | 万级/s                 |
| 功能 | 流处理为核心，功能极简       | 事务消息、延迟消息、消息轨迹齐全 | 路由灵活（交换机模型） |
| 适合 | 日志采集、大数据管道、事件流 | 电商交易、订单、业务消息         | 中小规模、复杂路由需求 |

一个实用的记忆锚点：**Kafka 为"日志"而生，RocketMQ 为"交易"而生，RabbitMQ 为"灵活"而生**。ShopLite 的下单链路是典型的交易消息场景——而且马上要讲的事务消息、延迟消息都是 RocketMQ 的强项——所以选它。如果场景是"把用户行为日志灌给大数据团队分析"，那是 Kafka 的主场。

## 在 Spring Boot 里用起来

发消息和消费消息，各一个注解的量级：

```java
// 订单服务：创建订单后发消息
@Service
public class OrderService {

    private final RocketMQTemplate rocketMQTemplate;

    public void createOrder(CreateOrderCmd cmd) {
        Order order = orderRepository.save(buildOrder(cmd));      // ① 落库

        // ② 发消息：topic 像"频道"，tag 像"子分类"
        //   消息体只放关键标识——下游要详情自己查库，避免消息体膨胀和时效问题
        rocketMQTemplate.convertAndSend(
                "order-topic:created",
                String.valueOf(order.getId()));
        // ③ 立刻返回，不等任何下游
    }
}
```

```java
// 积分服务：自己订阅，订单服务根本不知道它存在
@Component
@RocketMQMessageListener(
        topic = "order-topic",
        consumerGroup = "points-consumer-group",   // 消费组：同组内竞争消费，不同组各自都收到一份
        selectorExpression = "created")            // 只订阅 tag = created 的消息
public class PointsMessageListener implements RocketMQListener<String> {

    @Override
    public void onMessage(String orderId) {
        pointsService.addPointsForOrder(Long.valueOf(orderId));   // 加积分逻辑
        // 方法正常返回 = 消费成功；抛异常 = 消费失败，Broker 会重投这条消息
    }
}
```

代码极其简单，但**生产的复杂度全藏在"消息丢了、重了、乱了怎么办"这三个问题里**——也是面试官真正想考的部分。

## 可靠性三板斧：不丢、不重、有序

### 消息不丢：三段接力，每段都可能掉

一条消息的生命周期分三段，**每一段都有丢失的可能，各自有对策**：

```
生产者 ──①发送──▶ Broker（MQ 服务器）──②存储──▶ 磁盘 ──③投递──▶ 消费者
```

①**发送丢失**：网络抖动，消息根本没到 Broker。对策：**发送确认机制**——Broker 收到后回 ACK，没收到 ACK 生产者就重发（RocketMQ 同步发送默认有确认）。

②**存储丢失**：消息到了 Broker、还在内存里，机器断电。对策：**同步刷盘**（收到消息立即写磁盘再确认，牺牲吞吐换可靠；异步刷盘则先确认后落盘，宕机可能丢几百毫秒的消息）+ 主从复制。

③**消费丢失**：消费者拿到消息、还没处理完就崩了，或者更糟——代码先 ACK 后处理，处理失败消息也回不来了。对策：**手动 ACK**，处理逻辑完成才确认；处理失败消息会被**重投**。

三段都加固后，"丢失"基本消灭。但注意重投这个动作——它直接制造了第二个问题。

### 消息不重：至少一次 + 幂等

MQ 的投递保证叫**至少一次（at-least-once）**：消息保证送到，但可能送到不止一次。上面的每一段"防丢重试"（发送重发、消费重投）都是重复的来源——**不丢和不重在工程上不可兼得，业界的共识是保不丢，然后用幂等消化重复**。

落到积分服务的场景：加积分消息被重投一次，用户积分加了两遍。幂等的设计套路是给每个消费动作一个"去重凭据"：

```java
public void addPointsForOrder(Long orderId) {
    // 数据库唯一约束是最后一道防线：同一 orderId 只能插入一条积分流水
    // 消息重复到达时，第二次 insert 违反唯一键约束，捕获后直接 return
    try {
        pointsFlowRepository.insert(new PointsFlow(orderId, POINTS_PER_ORDER));
    } catch (DuplicateKeyException e) {
        return;   // 已经加过积分了——这条是重复消息，安全吞掉
    }
}
```

唯一键方案之外，常见替代是 Redis `SETNX` 打标记（性能更好，但 Redis 和数据库的一致性要自己兜底）。**核心思想只有一个：让"处理这条消息"这个操作本身幂等，重复到达时天然无害**——和上一篇重试的幂等要求是同一个原理。

### 消息有序

订单的消息有一条隐形的时间线：`created` → `paid` → `shipped`。如果消费端先收到 `shipped` 再收到 `created`，状态机直接错乱。乱序的来源是**并行**：Broker 内部多个队列、消费端多线程。

实用的一致性标准是**局部有序**：不需要全局所有消息有序，只需要**同一个 orderId 的消息严格有序**。RocketMQ 的做法是按 key 哈希路由——同一个订单的消息永远进同一个队列，队列内先进先出，顺序天然保住；不同订单之间乱序无所谓。

## 两个高频实战特性：延迟消息与死信队列

**延迟消息**：发出后不立即可消费，等指定时长。经典应用就是电商的"30 分钟未支付自动取消"：创建待支付订单时发一条 30 分钟的延迟消息，30 分钟后消费逻辑检查订单状态——还是未支付就取消、回滚库存；已支付就忽略。对比定时任务轮询方案（每分钟扫全表），延迟消息精确到秒且不扫库。

**死信队列（DLQ）**：一条消息重试 16 次仍消费失败，Broker 把它挪进一个特殊的"死信" topic，避免毒消息（永远处理失败的消息）堵住正常消费。死信队列需要监控告警 + 人工介入处理——它是 MQ 系统里"最后的安全网"，也是排障时第一个要看的地方。

## 什么时候不需要

- **调用方必须立刻拿到结果的场景**：扣库存如果必须在下单响应里告诉用户"抢到了"，就不能简单异步化（秒杀的真实做法是异步落库 + 轮询/推送结果，复杂度转移而非消失）
- **就一两个轻量异步需求**：Spring 的 `@Async` + 线程池（第 12 篇之前的老朋友）就够了，MQ 是为跨服务、要可靠性保证的异步准备的
- **不能接受最终一致的地方**：引入 MQ 意味着接受"下游晚几秒完成"。给用户看余额、看库存的强实时场景，老老实实同步调用

还有一个组织层面的成本常被低估：**排障变难了**。同步调用出错，异常栈直接指向对方服务；MQ 排障要追"消息发了吗、Broker 收到了吗、消费组积压了吗、为什么消费失败"——多了两个环节和一套全新的监控指标（**消息积压**是 MQ 运维的头号指标）。上 MQ 之前确认团队有精力运维它。

## 名词卡片

| 名词                | 一句话定义                                           |
| ------------------- | ---------------------------------------------------- |
| MQ / Broker         | 消息队列中间件 / 消息队列服务器本体                  |
| 生产者 / 消费者     | 发消息方 / 收消息方                                  |
| Topic / Tag         | 消息的频道 / 频道内子分类                            |
| 消费组              | 同组竞争分摊消息，不同组各自收到全量                 |
| 异步 / 解耦 / 削峰  | 主流程不等下游 / 上游不知道下游 / 队列蓄洪平稳消费   |
| 至少一次投递        | 保证送到但可能重复，需消费端幂等兜底                 |
| 幂等                | 同一消息处理一次和 N 次结果相同（唯一键/Redis 标记） |
| 发送确认 / 手动 ACK | Broker 确认收到 / 消费者处理完才确认                 |
| 同步刷盘            | 先落盘再确认，防 Broker 宕机丢消息                   |
| 局部有序            | 同一业务 key 的消息有序，全局不保证                  |
| 延迟消息            | 定时投递的消息（30 分钟取消订单的标准解法）          |
| 死信队列            | 重试耗尽的毒消息的安置区，需监控人工处理             |
| 消息积压            | 消费速率跟不上生产速率——MQ 运维头号指标              |

## 回顾与预告

下单链路瘦身完成：主流程 200ms 返回，下游各自消化消息。但细心的你应该发现了一个悬而未决的问题：扣库存改成异步后，**订单创建成功和库存扣减之间出现了一个"中间态"**——订单存在，库存还没扣。如果消费失败、消息丢失、或者干脆就是同步的那部分调用失败了，数据就不一致了。这个"跨服务、跨数据库的数据一致性"问题，就是本系列压轴的技术硬骨头：分布式事务——下一篇，把 2PC、TCC、Saga、本地消息表这些名词一次讲透。
