上篇结尾留了一个中间态：订单已创建、库存还没扣。现在把这个洞挖到最深，看看分布式事务问题的完整形态。

ShopLite 用余额支付的下单流程，横跨三个服务三个库：

```
订单服务（订单库）        商品服务（商品库）        用户服务（用户库）
创建订单记录              扣减库存                  扣减用户余额
```

理想结果：三件事要么全成功，要么全失败。用你熟悉的 Spring 写法试试：

```java
@Transactional   // ← 这个注解此刻是"假"的：它只能保证订单库这一个库的事务
public void placeOrder(OrderCmd cmd) {
    orderRepository.insert(buildOrder(cmd));              // 订单库 ✓ 在事务内
    productClient.deductStock(cmd.productId(), cmd.qty()); // 商品库 ✗ 远程调用，另一个世界
    userClient.deductBalance(cmd.userId(), cmd.amount());  // 用户库 ✗ 又一个世界
    // 事务提交时，只有 insert 被回滚保护；后面两步失败，订单记录照样提交
}
```

`@Transactional` 的魔法边界是**一个数据库连接**。第 5 篇拆分时把数据库也拆了，于是同一个业务操作的数据落在了三个物理库里、三个连接上、两次还隔着网络——**单机事务的技术前提（一个进程、一个连接）被拆分动作本身摧毁了**。这就是分布式事务的定义：跨多个资源（库/服务）的操作，需要整体保持原子性。

更糟的是故障模式：库存扣成功后网络闪断，订单服务只看到"超时"——库存到底扣没扣？不知道。**超时不等于失败**，这是分布式事务所有方案必须直面的根本不确定性。先看理论层怎么框定这个问题。

## CAP 与 BASE：先把期望值调对

**CAP 定理**（第 5 篇提过）：网络分区（P）不可避免时，一致性（C）和可用性（A）二选一。

**BASE 理论**是 CAP 的工程化回应：既然强一致（C）代价太高，那就接受 **基本可用（Basically Available）+ 软状态（Soft state）+ 最终一致（Eventually consistent）**——允许数据存在中间态（订单创建但库存未扣），只要保证经过一段时间后收敛到一致。

这两条理论划出了整个方案谱系的坐标轴：**一端是强一致的 2PC/XA，另一端是最终一致的消息类方案**，中间是各有取舍的 TCC 和 Saga。互联网业务（下单、支付）几乎全在最终一致这一端选型——用户可以接受"库存晚半秒扣"，不能接受"系统不可用"。

## 方案谱系：从强一致到最终一致

### 2PC / XA：教科书答案，互联网弃子

两阶段提交（Two-Phase Commit）：选一个**协调者**（TM），第一阶段问所有参与者（RM）"能提交吗"，全部点头后第二阶段统一下令"提交"。

问题三个：**同步阻塞**（第一阶段到第二阶段之间，所有参与者锁着资源等指令，并发能力归零）；**协调者单点**（协调者在第二阶段前宕机，参与者卡死在锁定状态）；**网络分区下数据不一致**（部分收到"提交"部分没收到）。数据库的 XA 协议就是 2PC 的实现，能开（MySQL 支持），但性能损耗常达数倍到数十倍——**银行核心系统这类强一致刚需在用，互联网交易系统基本不用**。

### TCC：手写三个方法，换性能与实时一致

TCC（Try-Confirm-Cancel）把事务的控制权交给业务代码，每个参与方实现三个方法：

```
Try     —— 资源预留：冻结 100 元余额（不是真扣）、预占 1 件库存
Confirm —— 确认执行：把冻结的 100 元真正扣掉、预占转实扣
Cancel  —— 取消释放：解冻 100 元、释放预占的库存
```

下单 TCC 化后：Try 阶段三个服务各自预留资源（全部成功才进 Confirm，任一失败全部 Cancel）。没有长时间锁（预留是业务字段的冻结标记，不是数据库锁），性能好，一致性的达成是实时同步的。

代价直白：**每个参与方为每个操作手写三个方法**，业务侵入极大，而且要自己处理三个经典坑：**空回滚**（Try 没到达，Cancel 先来了——得能识别"没有 Try 过"直接成功）、**悬挂**（Cancel 之后迟到的 Try 才到达——得拒绝执行）、**幂等**（Confirm/Cancel 重试时不能重复执行）。金融级场景（支付、转账）愿意付这个成本，因为它的收益（不锁数据库的准实时一致）正好是这类场景要的。

### Saga：长流程的补偿链

Saga 把分布式事务拆成**一串本地事务** T1 → T2 → T3，每步配一个补偿动作 C1、C2、C3。T3 失败，就反向执行 C2、C1 把已做的撤销。对比 TCC：没有预留阶段，直接做，失败就补偿——侵入小（每步只需多写一个"反操作"），适合**流程长、参与方多**的业务（订机票+订酒店+租车）。

注意补偿的语义弱点：**做了再撤，不是没做过**。撤销一笔"已发送的短信"是不可能的，Saga 适用于"业务上可补偿"的操作。

### 本地消息表：工程派的最终一致主流

前面都是"事务框架"思路。本地消息表换了一个角度：**不追求"同时成功"，只保证"消息一定发出去"，用上一章的 MQ 把最终一致铺完**。它是中小团队最常用、也最容易理解的方案，值得看代码：

```java
@Transactional   // 这个注解又是"真"的了——因为这两步在同一个库！
public void placeOrder(OrderCmd cmd) {
    orderRepository.insert(buildOrder(cmd));          // 业务操作：写订单表
    // 关键动作：把"要发的消息"作为一条数据，和业务写入同一个本地事务
    localMessageRepository.insert(LocalMessage.builder()
            .topic("order-topic").tag("created")
            .payload(String.valueOf(orderId))
            .status(PENDING)                          // 待发送
            .retryCount(0)
            .build());
    // 本地事务保证：订单存在 ⟺ 消息记录存在，两者原子
}
```

```java
// 后台任务（每秒扫一次）：把 PENDING 的消息真正发出去
@Scheduled(fixedDelay = 1000)
public void dispatchMessages() {
    for (LocalMessage msg : localMessageRepository.findPending(50)) {
        try {
            rocketMQTemplate.convertAndSend(msg.topic() + ":" + msg.tag(), msg.payload());
            localMessageRepository.markSent(msg.id());       // 发送成功 → 已发送
        } catch (Exception e) {
            localMessageRepository.incrementRetry(msg.id()); // 失败 → 重试计数 +1
            // 超过阈值 → 告警人工介入；配合消费端幂等，重发是安全的
        }
    }
}
```

一致性链条：订单和消息记录同库同事务（原子）→ 后台任务保证消息必达 MQ（重试）→ 消费端幂等消化重复（第 8 篇）→ 库存服务消费扣减（最终一致）。**没有全局协调者，没有锁，用"本地事务 + 重试 + 幂等"三个朴素元件拼出最终一致**——这就是它的别名"事务消息的穷人版"的由来。RocketMQ 把这套模式产品化成了**事务消息**（半消息 + 回查机制，发送和落库的原子性由 Broker 代管），省掉自建消息表，思想完全相同。

### Seata AT：把补偿自动化

**Seata** 是阿里开源的分布式事务框架，目标是"把上面这些模式的 scaffolding 全包了"。最常用的是 **AT 模式**（Auto Transaction）：

```java
@GlobalTransactional    // 只加这一个注解，对比 TCC 的三个方法
public void placeOrder(OrderCmd cmd) {
    orderRepository.insert(buildOrder(cmd));
    productClient.deductStock(cmd.productId(), cmd.qty());
    userClient.deductBalance(cmd.userId(), cmd.amount());
}
```

写法回到了单机事务的体感，背后 Seata 做了三件事：**代理数据源**拦截每条 SQL，把修改前后的数据镜像存进每库的 `undo_log` 表；全局协调者（TC）跟踪整个全局事务；某参与方失败，TC 指挥各参与方用 undo_log **自动生成反向 SQL 补偿**（insert 的反向是 delete，update 的反向是还原旧值）。

AT 的聪明之处是把 TCC 的 Confirm/Cancel 从"手写"变成"框架按数据镜像自动生成"；代价是全局锁机制带来的吞吐上限，以及"自动反向补偿"只适用于**简单 SQL 语义**（复杂业务约束仍需人工确认）。Seata 同时也支持 TCC、Saga、XA 模式——它更像一个分布式事务的工具箱。

## 谱系总表

| 方案                | 一致性   | 性能       | 侵入性              | 典型场景                   |
| ------------------- | -------- | ---------- | ------------------- | -------------------------- |
| 2PC/XA              | 强一致   | 差（阻塞） | 低（数据库层）      | 银行核心、传统企业         |
| TCC                 | 准实时   | 好         | 极高（三方法三坑）  | 支付、转账                 |
| Saga                | 最终一致 | 好         | 中（写补偿）        | 长流程编排                 |
| 本地消息表/事务消息 | 最终一致 | 好         | 中（消息表/半消息） | 绝大多数业务               |
| Seata AT            | 最终一致 | 中         | 极低（一个注解）    | 想省事的团队，SQL 简单场景 |

## 全系列最重要的工程智慧：能不用就不用

这篇开头我说"挖到最深"，现在说透：**分布式事务的最好解法是让问题不发生**。按优先级：

**第一选择：业务规避。** 把强关联的数据放进**同一个库同一个服务**——把"扣余额"设计成用户服务内部操作，下单只跨订单/库存两个库而不是三个。第 4 篇说拆分按业务领域切，反过来：**领域内强一致的数据不该被拆开**。拆分决策直接决定分布式事务的数量。

**第二选择：接受中间态 + 对账。** 很多"不一致"的窗口期是业务可容忍的（秒级、分钟级），与其上重型方案，不如让中间态可见（订单状态机多一个"处理中"）、配上**定时对账任务**兜底扫描不一致并修复。电商交易的最终防线几乎都是对账，不是事务框架。

**第三选择：本地消息表/事务消息。** 确实需要跨服务最终一致时，首选这类方案——简单、可靠、可观测（消息表就是天然的审计日志）。

**最后才考虑：Seata/TCC。** 团队有专人维护、场景复杂度确实超出消息方案的表达力时。引入一个分布式事务框架是长期运维承诺，不是加一个依赖。

一个真实的比例感：一个成熟的电商系统里，90% 以上的跨服务操作用"本地消息表 + 幂等 + 对账"解决，TCC/Seata 集中用在支付核心的少数几个链路上。**分布式事务不是日常工具，是精确制导武器**——面试时能把"怎么避免用它"讲清楚，比背出五种模式的原理更能加分。

| 名词            | 一句话定义                                             |

## 回顾与预告
