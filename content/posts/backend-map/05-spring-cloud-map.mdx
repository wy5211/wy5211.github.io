ShopLite 拆分后的第一周，故障报告翻了一页：

订单服务要调商品服务扣库存，代码里写的地址是 `http://10.0.0.11:8080`。周三晚上商品服务所在的机器硬件故障，整体迁移到新机器，IP 变成 `10.0.0.30`。运维改完商品服务的部署，满意地下班了——然后订单服务全线报错，因为它还在傻傻地请求旧 IP。

同一天还有一件小事：数据库换了密码，运维需要登上四台服务器、改四个服务的配置文件、重启四个服务。「我们不是拆成微服务了吗，怎么改个密码比重构前还麻烦？」

这是拆分之后的第一课：**服务实例的地址是动态的**（扩容、迁移、宕机、重启，IP 和端口随时变），靠写死地址的调用方式活不过第一次迁移。解决它的组件叫**注册中心**——但把它讲清楚之前，得先回答一个更根本的问题：Spring Cloud 到底是个什么东西。

## Spring Cloud 不是框架，是解决方案超市

第 4 篇末尾那张"拆完的账单"你还记得：找不到服务、配置分散、调用难写、没有统一入口、事务失控、排查困难。这些问题不是某家公司独有的，是**所有**做微服务的团队都会撞上的共性问题——所以每一排都有人做了轮子。

Spring Cloud 做的事情是：**把这一排问题的主流解法统一收集、统一规范、统一集成进 Spring Boot 生态**。它自己几乎不实现功能，更像一个"超市货架"：每一类问题一个货架，货架上摆着实现各异的组件，全都包装成 Spring Boot starter——加依赖、写配置、用注解，开箱即用。

所以准确的理解是三层：

```
Spring Boot     → 造零件（每个微服务的底座）
Spring Cloud    → 定规范 + 做集成（货架：服务注册/配置/调用/熔断的统一抽象）
具体组件        → 干活的产品（Nacos、Sentinel、Seata、Gateway……）
```

这也解释了为什么"学 Spring Cloud"感觉学的不是一门技术，而是一堆名词——因为**它本来就是一堆名词的组织者**。

### 一段必须知道的历史：Netflix 停更

货架上的商品换过一轮血。早期全家桶叫 **Spring Cloud Netflix**：Eureka（注册中心）、Ribbon（负载均衡）、Hystrix（熔断）、Zuul（网关），2015 年前后是国内绝对主流——老项目和老教程里全是这套名字。

2018 年起，Netflix 的这些组件陆续进入维护模式（Eureka 2.x 开发中止、Hystrix 停更、Zuul 1 阻塞模型被放弃）。Spring 官方转向自研替代（LoadBalancer、Resilience4j、Gateway），国内则拥抱了阿里巴巴开源的一套——**Spring Cloud Alibaba**，并且它后来成了 Spring Cloud 官方认可的子项目。

对照着看，新旧两代是按"货架"平移的：

| 问题（货架）   | Netflix 时代（旧） | 现在（国内主流）                 |
| -------------- | ------------------ | -------------------------------- |
| 服务注册与发现 | Eureka             | **Nacos** / Consul / Zookeeper   |
| 配置中心       | Config Server      | **Nacos** / Apollo               |
| 服务间调用     | Feign + Ribbon     | OpenFeign + LoadBalancer / Dubbo |
| 熔断限流       | Hystrix            | **Sentinel** / Resilience4j      |
| 网关           | Zuul               | Spring Cloud **Gateway**         |
| 分布式事务     | ——                 | **Seata**                        |
| 链路追踪       | Sleuth + Zipkin    | SkyWalking / Micrometer Tracing  |

看懂这张表，招聘 JD 里"熟悉 Spring Cloud 生态"就翻译成了可执行的学习清单。ShopLite 选国内主流组合：Nacos + OpenFeign + Gateway + Sentinel + Seata + RocketMQ。这篇先上第一件：Nacos。

## 注册中心：给服务一本"活的电话簿"

回到开头那个故障。它暴露的需求拆开是三个：**商品服务得主动告诉别人"我在哪"**（注册）；**订单服务得随时查到商品服务当前活着的实例列表**（发现）；**有实例挂了，列表得自动更新**（健康检查）。

这三件事就是注册中心的全部。Nacos 作为独立中间件部署（一个 Java 服务，自带控制台），所有微服务都和它保持联系：

```
                    ┌────────────────────┐
     ① 启动时注册    │      Nacos         │        ③ 心跳续约（每 5s）
  ┌───────────────▶ │  服务名 → 实例列表   │ ◀────────────────┐
  │                 │                    │                   │
  │                 │  product-service:  │                   │
  │                 │   10.0.0.30:8081 ✓ │ ◀── 心跳停了?      │
  │                 │   10.0.0.31:8081 ✓ │     ④ 摘除该实例    │
  │                 └────────────────────┘                   │
  │                          │                               │
┌─┴──────────┐               │ ② 订阅/拉取服务列表            ┌┴──────────┐
│ 商品服务    │               │                               │ 商品服务   │
│ 10.0.0.30  │               ▼                               │ 10.0.0.31 │
└────────────┘      ┌──────────────┐                        └───────────┘
                    │   订单服务    │  拿到列表后自己选一台调用（负载均衡）
                    └──────────────┘
```

时序上：商品服务每个实例启动时向 Nacos **注册**自己的名字和地址，并持续发**心跳**；订单服务**订阅**商品服务，本地缓存一份实例列表，Nacos 推送变更；某个实例心跳超时，Nacos 把它标记不健康并通知订阅者。迁移、扩容、宕机，电话簿始终是新鲜的——**调用方只需要知道服务名，永远不需要知道 IP**。

在 Spring Boot 里的接入成本，依旧是 starter 三件套：

```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
</dependency>
```

```yaml
# 商品服务和订单服务的 application.yml 各加这几行
spring:
  application:
    name: product-service # 服务名——注册与调用都用它，是微服务的"身份证"
  cloud:
    nacos:
      discovery:
        server-addr: 10.0.0.2:8848 # Nacos 的地址（唯一需要写死的地址，通常配域名）
```

启动，打开 Nacos 控制台，能看到 `product-service` 下挂着的实例列表和健康状态。订单服务这边以后调用商品服务，目标地址从 `http://10.0.0.11:8080` 变成了 `http://product-service`——名字代替了地址（怎么把名字变成真实请求，是下一篇 OpenFeign 的事）。

## 配置中心：四台服务器改四遍的终结

开头第二个抱怨——改个数据库密码要登四台服务器改四个文件重启四次——的解法就在 Nacos 身上：它同时是个**配置中心**。

思路和注册中心同构：把散落在各机器上的配置文件**抽出来集中管理**，服务启动时从 Nacos 拉取配置，且**配置改了能热更新到运行中的服务**——不用重启。

```yaml
# 把 application.yml 里"会变的部分"搬进 Nacos 控制台：
#   product-service-dev.yaml → 数据源、Redis 地址、开关参数……
# 本地只留一份指引：
spring:
  config:
    import: nacos:product-service-dev.yaml # 启动时从 Nacos 拉配置
  cloud:
    nacos:
      config:
        server-addr: 10.0.0.2:8848
        refresh-enabled: true # 控制台改配置 → 自动推送到服务
```

```java
@RestController
@RefreshScope        // 标了这个注解的 Bean，配置变更时自动重建，字段拿到新值
public class StockController {

    @Value("${stock.warn-threshold:100}")    // 在 Nacos 控制台改成 50，接口立刻生效
    private int warnThreshold;
}
```

配置中心带来的管理收益比看起来大：多环境（dev/test/prod）的配置在控制台分 namespace 隔离；改配置留审计记录；出事故时"谁在什么时候改了什么"一查便知——这是四个散落的 yaml 文件永远给不了的可观测性。国内另一个主流选择是携程开源的 **Apollo**，功能相当，Nacos 胜在注册配置二合一、少维护一个中间件。

## 顺手聊一个面试点：CAP 与注册中心的选型

注册中心选型（Nacos/Eureka/Zookeeper/Consul）是面试高频题，背后其实就一个考点：**CAP 定理**——分布式系统在一致性（C）、可用性（A）、分区容忍性（P）三票里最多投两票。网络分区（P）在真实世界无法放弃，所以实际是 C 与 A 二选一。

对注册中心来说：**短暂地返回一份稍旧的实例列表（保 A），好过为了强一致而拒绝查询（保 C）**——列表晚半秒更新通常无害，但整个系统调不了服务是灾难。所以 Eureka 是 AP，Nacos 默认 AP（可切 CP），而老派强一致系统 Zookeeper 是 CP——这也是它淡出注册中心市场的原因。这个判断同样适用于你以后选任何分布式协调组件：先问自己要 C 还是要 A。

## 什么时候不需要

这篇的反面清单很长，因为 Spring Cloud 全家桶是"规模产品"：

- **服务数 3 个以内、部署稳定**：几个固定地址 + 一个 Nginx upstream 手动维护，比引入 Nacos 全套更省心
- **上了 Kubernetes**：K8s 自带 **Service** 抽象（内置 DNS 服务名 + 自动负载均衡 + 健康摘除），注册中心的三大职能原生覆盖。很多云原生团队是 K8s Service + 少量补充组件，不装 Nacos——第 10 篇会回到这个话题
- **配置少且稳定**：环境变量 + 一份 yaml 足够，配置中心的价值随服务数量和环境数量增长

一个实用的判据：当你维护服务列表的成本（谁的 IP 是什么、挂了通知谁改）开始超过维护 Nacos 的成本（部署、监控、升级一个 Java 中间件），就到切换点了。ShopLite 四个服务、多环境部署，刚好过了这条线。

## 名词卡片

| 名词                 | 一句话定义                                                       |
| -------------------- | ---------------------------------------------------------------- |
| Spring Cloud         | 微服务共性问题解决方案的规范与集成层（不是具体框架）             |
| Spring Cloud Alibaba | 国内主流的 Spring Cloud 实现组合（Nacos/Sentinel/Seata 等）      |
| Netflix 停更         | 早期 Netflix 系组件（Eureka/Hystrix/Zuul）陆续停止演进的历史事件 |
| 注册中心             | 存活服务实例的动态电话簿：注册、发现、健康检查                   |
| Nacos                | 阿里开源，注册中心 + 配置中心二合一                              |
| 服务名               | 微服务的逻辑标识（如 product-service），调用时用它代替 IP        |
| 心跳续约             | 服务实例周期性向注册中心证明自己活着                             |
| 配置中心             | 集中管理配置、支持热更新和多环境隔离                             |
| @RefreshScope        | 配置变更时自动重建 Bean 以加载新值的注解                         |
| CAP 定理             | 一致性/可用性/分区容忍三者最多取其二；注册中心通常选 AP          |
| Apollo               | 携程开源的配置中心，Nacos 的同类竞品                             |

## 回顾与预告

现在订单服务"知道"该调谁了——它手里有一份新鲜的实例列表，`product-service` 这个名字随时可查。但知道归知道，**怎么发出这个调用**还没解决：自己拼 HTTP 请求？负载均衡谁来做？调用的超时、重试、降级写在哪？下一篇讲微服务世界的"远程调用"：从 RestTemplate 的原始时代，到 OpenFeign 的声明式优雅，再到 gRPC 和 Dubbo 的另一种思路。
