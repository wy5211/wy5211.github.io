上一篇结尾，ShopLite 的单台服务器在晚上高峰期 CPU 飙到了 90%，接口响应从 50ms 涨到 2 秒。你做了一个最符合直觉的决定：再加一台服务器，两台一起干活。

一小时后，客服炸了。用户投诉集中在一句话上：「我登录成功了，翻到第二页就变成未登录了。」

加机器是对的，但你只完成了集群化的一半。这篇讲另一半：流量怎么分，以及为什么分完之后登录态会丢。

## 集群化的第一步：谁来分活

两台服务器干一样的活，但用户只会访问 `shoplite.com` 这一个域名。需要一个调度员站在入口，把请求分给两台机器——这就是**负载均衡器（Load Balancer）**，绝大多数团队的第一站是 **Nginx**：

```nginx
# nginx.conf — 核心就是这段 upstream 配置
upstream shoplite {
    server 10.0.0.11:8080 weight=2;  # 应用服务器 1，权重 2（性能好，多分点）
    server 10.0.0.12:8080 weight=1;  # 应用服务器 2，权重 1
}

server {
    listen 80;
    location / {
        proxy_pass http://shoplite;   # 把请求转发给上面这组机器
    }
}
```

请求进来，Nginx 按权重把大约 2/3 分给机器 1、1/3 分给机器 2。机器 1 宕机，Nginx 探测到后自动摘除它，流量全落机器 2——**故障转移**顺手就有了。

顺带澄清一对高频名词：**正向代理**代理的是客户端（翻墙软件，服务器不知道真实用户是谁）；**反向代理**代理的是服务端（Nginx，用户不知道后面有几台机器）。负载均衡是反向代理最常见的一种用法。

分发策略除了权重轮询，常见的还有：最少连接（谁手上活少给谁，适合请求耗时差异大的场景）、ip_hash（同一用户的 IP 永远分到同一台机器——记住这个策略，它是下面登录态问题的第一个候选解法）。

流量分摊的问题解决了。现在处理那个客服工单。

## 登录态为什么丢了

先看 Spring Boot 里最普通的登录是怎么实现的：用户提交账号密码，服务端验证通过后创建一个 **Session**（会话对象）存在**应用服务器的内存**里，同时返回给浏览器一个 `JSESSIONID` Cookie。之后浏览器的每个请求都带上这个 Cookie，服务端拿 ID 找到内存里的 Session，确认"这是登录过的张三"。

问题就出在「存在应用服务器的内存里」：

```
第 1 个请求 → Nginx → 机器 A：登录成功，Session 存进 A 的内存
第 2 个请求 → Nginx → 机器 B：带着 JSESSIONID 来找 Session
                       → B 的内存里根本没有（它在 A 里）
                       → "你谁啊？" → 踢回登录页
```

单机时代天经地义的设计，集群化后直接破产。**Session 是状态，而集群化的本质是把应用变成无状态的可复制单元**——这两件事天然冲突。三条出路，一代比一代彻底。

### 方案一：让同一用户永远落在同一台机器

Nginx 的 `ip_hash` 策略：按用户 IP 哈希，固定路由到同一台机器。Session 还存在各自机器里，但用户永远回到存着他 Session 的那台。

改动最小，但硬伤明显：机器 A 宕机，它上面的所有 Session 全部丢失（用户全部被踢下线）；流量按 IP 分布往往不均（一个公司出口就一个 IP，几万人可能全压到一台机器上）。**只适合当临时补丁**。

### 方案二：Session 集中存储——Redis 登场

既然 Session 放哪台机器都不对，那就从所有机器里拿出来，放到一个大家都够得着的独立存储里——**Redis**。所有应用服务器读写同一个 Redis，Session 在谁的空间里就无所谓了。

Spring Boot 里的接入成本低到离谱，Spring Session 项目把脏活全干了：

```xml
<!-- pom.xml：两个 starter，没有任何配置类要写 -->
<dependency>
    <groupId>org.springframework.session</groupId>
    <artifactId>spring-session-data-redis</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```

```properties
# application.properties：就这两行
spring.session.store-type=redis
spring.session.timeout=30m
```

加完这两段，重启。代码里 `session.setAttribute("userId", ...)` 一行都不用改——Spring Session 用一个过滤器把 `HttpSession` 的实现偷偷换成了 Redis 版本，对开发者完全透明。

这是 Redis 在 ShopLite 里的第一次登场，也是它在中国后端圈的经典角色之一：**把状态从应用里抽出来，应用才配得上"无状态"三个字，才能随意扩缩容**。以后每个阶段它都会以不同身份回来（缓存、分布式锁、MQ 之外的兜底队列……）。

### 方案三：JWT——干脆不要 Session

第三条路最激进：能不能让服务端什么都不存？**JWT（JSON Web Token）**的思路是登录成功后，服务端把"用户 ID + 角色 + 过期时间"这些信息直接编码进一个字符串，用自己的密钥**签名**后发给客户端。之后客户端每个请求都带这个 token，服务端只需要用密钥验证签名——**验证是纯计算，不需要查任何存储**。

```
JWT 的样子（三段用 . 分隔）：
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjEwMDEsImV4cCI6MTc5NTYwMDAwMH0.4fKx...

第一段：算法声明（header）
第二段：载荷——userId=1001、过期时间戳（payload，只是编码，别放密码）
第三段：签名——服务端密钥对前两段的 HMAC，改一个字符签名就对不上
```

服务端无状态到极致：加 100 台机器，不需要任何共享存储，任何一台都能独立验证 token。集群扩容和登录态彻底解耦。

但 JWT 有一个让所有用过的团队都头疼的问题：**它签发之后就管不住了**。Session 方案里踢人下线只需要删掉服务端的 Session 记录；JWT 在过期前始终有效，服务端"开除"一个用户，他手里的 token 还能用半小时。用户改了密码、账号被盗、员工离职——都绕不开这个问题。

所以真实的工程实践大多是**混合方案**：JWT 做无状态验证（省掉每次查库），再加一层 Redis 做精细控制——登出/踢人时把该用户的 token 写进 Redis 黑名单，验证 JWT 通过后再查一眼黑名单。无状态的纯粹性打了折，换回了管理能力。

| 方案                 | 服务端存不存状态 | 踢人下线         | 适用                      |
| -------------------- | ---------------- | ---------------- | ------------------------- |
| ip_hash 粘性         | 每台机器存自己的 | 重启就全丢       | 临时过渡                  |
| Session 集中存 Redis | 存（Redis）      | 容易（删 key）   | 传统 Web 应用             |
| JWT                  | 不存             | 难（需配黑名单） | 前后端分离、App、开放 API |

## 什么时候不需要

这一篇的所有方案都建立在一个前提上：**单机真的扛不住了**。判断标准很具体：CPU 持续高于 70%、响应时间明显上涨、单机可用性不满足要求（宕机一次业务就无法接受）。日活几千到几万的应用，一台配置好点的机器 + 优化过的 SQL，大概率绰绰有余——先确认瓶颈真在"机器不够"，而不是"代码太烂"，后者加一百台机器也救不了。

另外一个容易被忽略的事实：**集群化解决的是可用性问题，不只是性能问题**。哪怕流量单机完全扛得住，两台机器 + Nginx 也意味着单台宕机时业务不断——很多团队做集群，首要动机是这个。

到这一步，ShopLite 的架构是：Nginx + 两台无状态应用 + Redis（存 Session）+ 一个 MySQL。这个结构能陪它走到日活几十万。然后，正如上一篇预告的：下一个倒下的不是应用，是 MySQL。

## 名词卡片

| 名词             | 一句话定义                                             |
| ---------------- | ------------------------------------------------------ |
| 集群             | 同一应用部署多份、共同分摊流量                         |
| 负载均衡         | 入口处把请求分发给多台机器的调度器                     |
| Nginx            | 最常用的反向代理与负载均衡软件                         |
| 正向 / 反向代理  | 代理客户端（用户视角）/ 代理服务端（服务器视角）       |
| 故障转移         | 某台机器宕机后流量自动切到存活机器                     |
| Session          | 服务端保存的会话状态，默认在应用内存里                 |
| 粘性会话 ip_hash | 同一 IP 永远路由到同一台机器                           |
| Spring Session   | 把 HttpSession 的存储透明替换为 Redis 等外部存储的框架 |
| JWT              | 自包含用户信息、带签名的 token，服务端验证无需存储     |
| 无状态           | 服务不保存会话数据，任何实例可互换——扩容的前提         |

## 回顾与预告

两篇走完，ShopLite 完成了从单机到集群的第一跳：Nginx 分活、Session 进 Redis。注意一个已经开始显形的模式——**每解决一个问题，架构里就多一个独立部件**（先是 Nginx，然后 Redis）。这个模式会贯穿整个系列，部件多到最后需要一个专门的名字和专门的团队。
