上个月的事给你提了个醒。

新来的后端小赵在代码评审里问：「咱们的工单附件为什么存数据库里啊，看起来好别扭。」你想说「因为历史原因」，又觉得这答案太混。去翻当时的讨论记录——在两年前某个已被刷走的群聊里；问老员工——三个人的说法三个版本，其中两个版本互相矛盾。

那天的搜索决策（[第 5 篇](/posts/architect-path/05-tradeoff-analysis)）你也是靠翻自己电脑上的备忘录才拼出全貌的。你意识到一件事：**TeaDesk 的每一个技术决策，都在以每个月一条的速度变成谜语。**人会把推理忘掉，聊天记录会沉底，只有决策本身留在代码里，光秃秃的，像没人认领的纪念碑。

当天下午你建了一个目录：`docs/adr/`。

## ADR 是什么：一段，不是一本书

ADR，Architecture Decision Record，架构决策记录。名字听起来像一种重量级文档，实际正好相反——它的全部要点是**轻**。

一条 ADR 就是一个决策的记录，两百到五百字，一个 Markdown 文件，写完就归档，不需要维护更新。业内通行的模板五要素，直接看实例——你写下的第一条，就是那个搜索决策：

```markdown
# ADR-001：工单搜索采用 Postgres 全文检索起步

日期：2026-12-03　状态：已接受　负责人：你

## 背景

皓齿医疗 120 家门店上线后，搜索接口 P99 达 8 秒，客诉升级。
候选方案：Postgres 全文检索 / Elasticsearch / 人工分类目录。

## 决策

采用 Postgres 全文检索：zhparser 中文分词 + GIN 索引，两周上线。

## 理由

客诉在烧，上线速度与搜索质量为最高权重（详见取舍矩阵，附后）。
三年工单量预测为当前 5 倍（销售确认），Postgres 可承接。

## 放弃的方案

- Elasticsearch：搜索上限更高，但新增集群运维，六周起步。
  放弃代价：拼音纠错类高级功能做不了；量超预测需回头补（估两个月）。
- 人工分类目录：常见查询准确，长尾查不到，且需客服团队持续维护。

## 后果

重评触发条件：日搜索量过 5 万，或工单总量过 800 万。
```

注意五要素的分工：**背景**是当时的处境（不知道处境的人看不懂任何决策）；**决策**一句话；**理由**写推理链；**放弃的方案**把落选者和落选原因留在这里——这一节是被引用最多的；**后果**写这个决策带来的债和退出条件。

写一条的耗时：决策做完后十五分钟。你后来算过一笔账，十五分钟换来的东西，在半年内就回本了三次，后面讲。

## 上下文比结论值钱

ADR 用久了，你会遇到一个反直觉的事实：**最先过时的是结论，最保值的是上下文。**

ADR-001 的结论「用 Postgres」有效期大概两三年——工单量到线，ES 重启，结论作废。但那段上下文不会过时：为什么当时上线速度权重最高（客诉在烧）、为什么敢赌 5 倍预测（问过销售）、ES 被放弃的真实代价是什么。三年后重开这个决策的人，无论当时的技术风景变成什么样，他需要知道的正是这些。

所以写 ADR 时最值得花笔墨的不是结论，是当时的约束。一个测试：把结论遮住，只读背景和理由，读者能不能自己推出同一个结论？能，这条 ADR 就写成了——五年后的人拿着新结论来对照，也能看清哪些约束变了、哪些没变。

这也是为什么 ADR 的「负责人」一栏要写真名。不是为了追责，是为了三年后有人想追问细节时，知道去问谁。文档会过时，人的记忆里存着文档写不下的细节。

## 被推翻不丢人：状态机而不是墓地

ADR 的生命周期有个业内惯例：proposed（提议中）→ accepted（已接受），以及一个特殊的第三态——**superseded（已被取代）**。

关键规矩：**决策被推翻时，旧 ADR 不删不改，加一行「被 ADR-009 取代」，新 ADR 里链接回旧的。**两个原因。

一是新决策需要旧决策当参照物。半年后你写「重开搜索选型」的 ADR 时，开头就要引用 ADR-001：「当时的触发条件已达到，且当时放弃 ES 的两大代价中，运维成本一项已因团队扩招消除。」没有旧 ADR，这段推理无从写起。

二是团队文化。会推翻以前决策的团队是健康的——说明约束变了有人响应。把被推翻的决策删掉，等于每次翻案都销毁证据，慢慢地没人敢留痕，ADR 就变成了只许成功的表演。保留 superseded 的记录，等于明示所有人：在这里，改主意是被鼓励的，前提是写清楚为什么。

## 放哪：跟代码一起活

存放位置的答案几乎没有悬念：**git 仓库的 `docs/adr/` 目录，和代码同一个仓库。**

对比一下 wiki：链接会烂（改版、迁移、权限调整），搜索体验随平台兴衰波动，最致命的是它不在工程师的日常动线上。而 git 仓库在每个人每天打开的编辑器里，ADR 跟代码一起被 clone，一起被搜索，PR 改代码时顺手就能引用「本次改动源于 ADR-004」。你甚至可以在代码目录里留指针：工单搜索模块的 README 第一行写着「选型见 ADR-001」。

编号用递增流水号（ADR-001、ADR-002……），文件名 `001-search-with-postgres.md`。别用日期编号——翻案时按编号引用比按日期引用顺口得多。

## 推行的阻力

你建目录后推行的头一个月，团队的反应可以预料：「没时间写。」

你的应对是降低标准到地板：决策谁做的，谁来写两百字，模板就贴在目录 README 里；不追求文采，五个小节填完就行；写完你帮改。第一个月只攒下三条，但第三条是陈舟自己写的——[第 6 篇](/posts/architect-path/06-technology-selection)那次选型评估结束后，他把结论整理成 ADR-003，因为评估过程里他自己的思路被算账过程理顺了，写下来反而顺畅。

第二个月起量。真正的转折是小赵那次提问的后传：他再问「为什么附件存数据库」时，你指给他 `docs/adr/`，他自己翻到了两年前那条（你补写的），看完没再问。后来他问问题的方式变成了：「我看到 ADR-007 说暂不做多租户，现在还成立吗？」——**提问质量的跳升，是文档开始产生复利的样子。**

## 收尾：什么不值得写

ADR 也有边界。它记录的是**有取舍的决策**：方案不唯一、代价真实存在、两年后有人可能翻案的，才值得两百字。不值得写的：跟随业界默认的选择（[第 2 篇](/posts/architect-path/02-decisions-not-diagrams)说过，默认决策不需要留痕，除非偏离）、纯实现层面的选择（用哪个 lint 配置）、还没定的想法（那是 RFC 的事，别把 proposed 堆成半永久状态）。

一个粗糙的判据：如果你预期两年后没人会问「为什么当时这么选」，就不用写。

单条决策的记录到位了，但 TeaDesk 接下来这个决策大得多：多租户权限改造，动三个模块、跨两个小组，一次要过很多人的脑子。两百字的 ADR 装不下它，你需要的是另一种武器——设计文档，和一场开好了的评审会。下一篇讲。
