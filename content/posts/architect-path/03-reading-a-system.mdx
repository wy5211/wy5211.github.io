任命后第一个周一，你踌躇满志，列了个清单：重构通知服务、把核心模块拆干净、升级那套老掉牙的构建工具。清单还没写完，老周把它按住了。

「先别动。你先看懂它。」

你嘴上说好，心里不服气：TeaDesk 我写了三年，还有我不懂的地方？打开仓库一看，还真有。工单核心的 18 万行代码，一半是两位创始人在 2022 年赶工写的，一半是三拨外包接力留下的；写消息推送那位两年前离职了；你在群里问「咱们的通知是怎么发出去的」，得到三个版本不同的答案，其中两个都对。

「看懂」听起来不像架构师的工作，更像入职培训。但接下来两周会让你改观：你后来做过的所有失败决策，回头看根子都在同一处——对现状的理解缺了一块。反过来，做得最顺的几次，靠的也是这两周攒下的底。

这两周怎么做，拆开是三件事：画图、追踪、考古。

## 第一件事：从语境图开始画，不要从代码开始读

画图用 C4 的分层法，从粗到细四层：语境、容器、组件、代码。多数人上手就错在从最细的那层开始——打开 IDE 读代码，两周读完一个模块，还剩十六个。

**先画语境图。**它不涉及一行代码，回答一个问题：TeaDesk 和谁打交道。

你花了半小时画出来：客户在网页工作台和微信小程序里用；工单满了给客服发邮件走的是 Mailgun，超时提醒发短信走的是阿里云通道；支付接的微信支付；客服转接要同步到客户的 CRM，有三家客户要求对接。这张图上每个角色都是你改不了的边界——Mailgun 的限流你得遵守，微信小程序的审核周期你得排进计划。

它的价值就是把这些「改不了的东西」摆在眼前。新手的方案经常死在这里：设计得很美，动到了自己根本动不了的地方。

**再画容器图。**容器指独立运行的东西：Next.js 前台、NestJS 的 API、MySQL、Redis、crontab 里跑的一个推送脚本、给大客户单独维护的小程序服务。这一层画完，你对「系统」的理解从「一个网站」变成「六个会各自出问题的东西」。

组件图和代码图这两周先不画。它们等具体决策需要时再下沉——那时候画，带着问题画，效率高得多。

## 第二件事：跟着一张工单走完全程

画图看的是静态结构，架构真正的麻烦都在动态里。方法很笨：挑一张真实工单，编号 #8841，从生到死跟一遍。

客户皓齿医疗的前台在网页表单提交「无法登录」，你从浏览器 DevTools 的第一个请求开始，记下每一跳：

```
网页表单 POST /api/tickets
  → NestJS API 校验、写 MySQL（tickets 表，状态 open）
  → 投递一条消息进 Redis 队列
  → crontab 脚本每 30 秒捞一次队列，调 Mailgun 给值班客服发邮件
  → 客服在工作台回复，API 写 replies 表，工单状态 pending
  → 脚本再发邮件通知客户，客户确认，状态 closed，进归档表
```

每一跳你问三个问题：数据存在哪、谁触发、失败了会怎样。

问到最后一跳你停住了。工单的当前状态同时存在于 MySQL 和 Redis 里——MySQL 是权威记录，Redis 是给工作台列表页加速的缓存，靠一个每五分钟跑全量比对的脚本保持一致。也就是说，状态变更之后最长有五分钟，客服看到的是旧数据。「工单明明关了列表还显示处理中」——上个月那次客诉，根因就在这。三个版本的「通知是怎么发的」，答案也在这条链路里：三个人说的是链路上三段不同的环节。

一张工单走完，你对系统的理解超过了过去三年。因为过去你只看自己负责的那一段，链路是第一次完整显形。

## 第三件事：git log 考古和三场访谈

代码仓库是最诚实的文档，因为没人记得美化它。

你按目录统计了最近两年的提交次数：工单核心模块 2100 次，平均每周 20 次，是第二名的三倍。提交热度就是变更热点，变更热点就是痛点区——改得多的模块，要么业务最赚钱，要么代码最烂，通常两样都占。这里就是 TeaDesk 的心脏，也是最该小心动刀的地方。

再顺藤摸瓜看提交信息。`git log --grep="临时"` 出来 47 条，最早一条在 2021 年 11 月，注释写着「临时方案，下个月重写」。它现在还在跑。还有成对出现的 `fix` 和 `fix 修复上个 fix 引入的问题`。这些提交信息就是系统的伤疤记录，每一道都对应一次当时的取舍——什么把人逼得抄了近路，近路又是在哪次救急里变成正路的。

最后一件事：访谈。找三位老员工各聊半小时，只问一个问题——「这个系统里，你最不敢动的部分是哪？」

创始工程师说通知脚本，两次线上事故都跟它有关；客服团队的主管说导出功能，每次大客户审计都要用，动坏了她担责；老周说数据库的 tickets 表，「四年前设计的，现在谁也不敢改字段」。三个答案没有重合，拼起来恰好是系统的三块雷区。这些雷区图上看不见，只有人知道。

## 两周的产出：三样东西

两周后你交出的不是一份报告，是三样能长期用的东西：

**一张容器图**，贴在 wiki 首页，新人入职第一天看的就是它。

**一页问题清单**，按「还会不会再咬人」排序：状态双写的一致性窗口排第一（每月都有客诉），构建工具的老化排第二（每周浪费合计半天），构想的「大重构」排在倒数——它暂时没咬过人。

**三条「当年为什么这么设计」**。比如为什么 tickets 表里有那么多驼峰命名的 JSON 字段——第一版是外包用 MongoDB 写的，后来迁到 MySQL，字段名没改。知道来龙去脉之后，你不会再犯「把这当成低级错误顺手清理」的错：那批字段里存着历史数据，清理等于动手术。

## 代价与边界

这套方法适合接手几万到几十万行的中型系统。几千行的小系统用不上两周，一下午够；几百万行的大系统得按业务域切块，你自己啃核心块，把外围块委托给各模块负责人再汇总。

也有更快的路：让 AI 读仓库生成架构说明。你后来试过，产出意外地好，尤其适合第一遍画图和「这个函数被谁调用」的追踪。但有两类信息它给不了：伤疤背后的人事与取舍（为什么 2021 年那版放弃了消息队列），和「没人敢动」的雷区（这活在老人脑子里）。AI 读的是代码，读不出哪些代码是同事的逆鳞。

最后是维护。这张认知地图从完成那天就开始过时。你后来的做法：涉及容器增减的改动，顺手更新那张图；每季度末花二十分钟对一遍。更系统的办法是让每个重要决策留下记录、跟图互相印证——那是一篇专门的话题（[第 7 篇：ADR](/posts/architect-path/07-adr)）。

现状摸清了，你觉得脚下的地实了。然后销售林姐签回一份合同，把这份踏实打断——皓齿医疗要续约扩容，合同附件里那页技术要求，每一行你都得翻译成架构语言，而它们互相打架。这是下一篇：需求背后是质量属性，全都要的时候，怎么排优先级。
