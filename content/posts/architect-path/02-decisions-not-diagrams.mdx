任命后第三天，你在还不知道自己该干什么的状态下，接到了第一个活。

产品经理凯文在群里丢了一条用户反馈：「工单状态变了还要手动刷新才看得到，能不能实时？」后面跟上一句：「技术上很难吗？」

群里两分钟内吵起来了。后端同学说上 WebSocket，功能一步到位；前端同学说轮询就行，三十秒一次，实现成本一天；有人半路插进来说你们该用 SSE。三条路各有名字，各有道理，谁也说服不了谁。凯文最后 @ 了你：「架构定一下？」

你硬着头皮去查资料，一个意外的发现：技术对比其实非常简单。

轮询：客户端定时拉取，实现最简单，代价是大量无效请求和最长三十秒的延迟。SSE：服务端单向推送，够用，断线重连要自己管。WebSocket：全双工，最灵活，代价是连接管理、心跳、网关配置全套复杂度。二十分钟，你把三条路的优劣列得清清楚楚。

但列完之后你盯着表格看，发现问题根本不在表里。真正的疑问有三个：**这个决策可逆吗？该谁拍板？拍错了多贵？**表格一行都没回答这些。

这三个问题才是架构决策的正文。这篇就讲它们。

## 架构是「那些后来很难改的决定」

有个流传很广的定义，来自 Ralph Johnson（设计模式四人帮之一）：

> 架构是那些重要的东西——而「重要」指的是，不管它是什么，它就是那个形成系统形状的东西。

后来 Mark Richards 和 Neal Ford 在《软件架构》里把它落得更直白：**架构就是一组决策，重点是那些「以后很难改」的。**

用这个定义看实时通知这件事，问题就变形了。三条技术路线都能实现功能，差别在「选错之后回头贵不贵」：轮询换成 SSE，改的是 API 层，一周的事；SSE 换成 WebSocket，要动网关、要处理长连接的状态、要给运维加监控，那是一个季度的事，中间还夹着线上事故的风险。

所以这个决策的实际问题不是「哪个好」，而是「我们对未来的判断有多确定」：如果明年产品要上「客服正在输入」这类双向交互，WebSocket 迟早要用；如果只是推送状态变更，SSE 够用到天荒地老。

你看，问题从技术对比变成了对业务未来的判断。这就是架构决策的样子。

## 单向门和双向门，快慢不一样

亚马逊的贝索斯有个出名的分法：决策分单向门和双向门。走进单向门就回不了头，双向门随时能退回来。他的规矩：双向门决策要快，错了退回来就是；单向门决策要慢，值得花大力气收集信息。

这个分法对架构师几乎是最实用的一件工具。回到实时通知：

- 「要不要支持实时」——单向门附近，一旦客户习惯养成，撤掉是事故。
- 「SSE 还是 WebSocket 起步」——双向门。SSE 起步，将来真需要双向再升级，中间的改造成本可预期。

于是你做了一个当时看起来没什么气势的决定：SSE 起步，把「是否升级 WebSocket」挂到产品路线图上，等产品把双向需求做实再说。二十分钟的会，散了。

省下来的精力留给单向门。那扇门后面是什么你当时还不知道——半年后它来了，叫「大客户数据隔离」，那才是让你失眠的决策（[第 4 篇](/posts/architect-path/04-quality-attributes)）。

## 不是每件事都值得开会：默认决策

另一件要紧的事：团队每周冒出的「选哪个」问题，绝大多数不值得进入决策流程。

因为业界已经替你做过实验了。日志用什么格式——JSON 结构化，这是无数团队踩坑后的默认答案；内部 API 风格——REST，生态最全；要不要自建用户系统——除非主营业务就是身份，否则买。这些默认答案不是最优解，是「生态位最优」：文档、工具、招来的人、AI 的训练语料，全都在默认答案这边。

偏离默认值需要明确的理由，而且理由要能写下来：「我们选自建而不是托管，因为核心场景要在内网跑」。写不出这句话的偏离，多半是手痒。

架构师在这里的作用不是替团队做这些小决定，而是守住一条线：**可以偏离默认，但偏离要留痕**。怎么留痕，[第 7 篇](/posts/architect-path/07-adr)专门讲。

## 好决策可能撞上坏运气

决策这门手艺里，最反直觉的一条：决策质量和结果质量是两回事。

想象两个平行世界。世界 A，你基于「产品两年内不会要双向功能」的判断选了 SSE，决策过程无可挑剔；半年后公司转型，产品全部押注在线客服对话，双向成了核心——SSE 成了瓶颈，迁移花了三个月。世界 B，你抛硬币选了 WebSocket，同样的转型来了，正好接住。

世界 B 的结果好，但你敢把系统押在 B 的决策方式上吗？

复盘要看过程：当时的输入是否完整、推理是否成立、备选是否被认真考虑。结果里混着运气，拿结果考核决策，团队很快会学成两种坏习惯——要么不敢决策（怕背锅），要么专挑讨好当下的决策（赌自己在任期内不出事）。

你给自己定了个规矩：每个决策记录写下「当时我们知道什么」。将来被结果打脸时，先看这一节，区分「运气问题」还是「过程问题」。前者复盘一句带过，后者才是要修的。

## 技术争吵的真相：三个人拿着不同的输入

那场 SSE 之争，你后来复盘，发现它根本不是技术分歧。

主张 WebSocket 的后端同学，心里装的是「技术事实」：WebSocket 性能好、功能全，这没错。主张轮询的前端同学，心里装的是「团队现状」：活多钱少，一天能上线的方案就是好方案，这也没错。而凯文没说出口的是「业务约束」：这个需求在季度 OKR 里排最后，本来就是个顺手做的活。

三个人都没错，三个人都在争一个自己没意识到的结论。技术事实、团队现状、业务约束——决策的三类输入，每个人手里只有一类。

所以你后来主持技术分歧时，议程从来不是「辩论哪个对」，而是把三类输入摆到同一张桌上：技术事实，做实验补齐（SSE 过公司的代理会不会被掐断，跑一把就知道）；团队现状，问负责人（谁维护、几周能上线）；业务约束，问产品（这个功能在商业上多重要、未来两年什么形态）。输入齐了，结论经常自己浮出来，根本吵不起来。

## 这套东西的边界

说清楚适用范围。这套「决策流程」适合有真实分歧、影响超过一个模块的技术选择。它不适合两种场景：一是答案明显唯一的问题（数据库连不上怎么办），走决策流程纯属浪费生命；二是纯审美之争（两个 lint 配置选哪个），掷骰子或者让最较真的人赢，都行——审美分歧不值得消耗信任余额。

还有一句要提前说的话：这套手艺的全部前提，是你对系统的现状有足够的认知。那场会你在「团队现状」一栏就卡了壳——TeaDesk 现在的通知是怎么发出去的？你答不准确。答不准确的人做的决策，是踩在想象的地面上。

所以下一篇做一件基础功：接手一个四年、十八万行、没文档的系统，怎么在两周内把它读明白。
