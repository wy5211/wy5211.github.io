搜索方案上线两周，P99 回到 1.4 秒，你在周会上受了表扬。热度还没散，陈舟抱着笔记本电脑坐到你旁边，屏幕上是一篇新框架的评测文章，他的状态你很熟悉——眼睛发亮。

「你看这个。Rust 写的，性能是咱们 Node 服务的三倍。工单核心模块正好越来越慢，我建议用这个重写，顺便把代码结构理干净。三倍啊。」

你看着他的眼睛，想起两年前的自己。那时候你也是这样端着一篇评测去找老周的，被他一句「先说清楚解决什么问题」顶了回来。当时你委屈了很久，后来才明白那句话救了你三个月的周末。

所以你没说不行。你说：「三倍这个数字很有意思，咱们把它拆开看看是真的吗。」接下来两周的选型评估，是这篇的全部内容。结论先剧透：重写被否了，但陈舟没沮丧，因为他自己在第三周就算出了答案。

## 第一步：把「性能好三倍」拆到具体

所有选型的第一步，是把宣传数字还原成具体场景。

「三倍」来自评测里的 HTTP hello-world 压测：框架本身的开销极小，并发吞吐自然漂亮。但 TeaDesk 的工单接口慢在哪？你打开上次[考古](/posts/architect-path/03-reading-a-system)记下的问题清单：慢查询、那个五分钟同步的缓存、序列化大 JSON。全是数据库和 IO 的账，没有一项是语言运行时的。

一个粗估就把问题摆平了：接口总耗时里，语言运行时占比不到 10%。运行时快三倍，接口整体快不到 3%——用户完全无感。**性能数字不是假的，但它是「那个场景」的三倍，不是「你的场景」的三倍。**评测文章永远测框架擅长的东西，你的系统慢在框架之外，这两件事隔着一条银河。

这不是 Rust 或任何具体技术的问题，是所有「换技术」提议的共同第一关：你优化的瓶颈，和新技术提升的能力，是同一个东西吗？

## 第二步：把真实权重排出来

假设性能差距是真的（比如某天瓶颈真的落在运行时上），该给「性能」多高的权重？

多数技术争论在这里跑偏：大家默认选型是技术问题，按技术优劣排序。实际选型是**工程问题**，排序是另一张表。你给陈舟列的权重表：

| 维度       | 权重 | 为什么                                                          |
| ---------- | ---- | --------------------------------------------------------------- |
| 团队熟悉度 | 最高 | 全组七个人，六个没写过 Rust。招人、review、排障速度全部打折     |
| 生态成熟度 | 高   | ORM、队列客户端、监控探针……Node 生态全都有现成的，Rust 要自己拼 |
| 文档质量   | 中   | 出事时救命的东西                                                |
| 社区活跃   | 中   | 决定三年后这技术还活着吗                                        |
| 性能差距   | 低   | 前提是差距不在你的瓶颈上——多数业务系统确实不在                  |

这张表的刺眼之处在于「团队熟悉度」压过一切。它看起来很不技术，但选型选的不只是技术，是**未来三年谁来维护它**。一个全员陌生的技术栈，意味着每一次线上排障都是新手作业。

对照之下，「性能好三倍」在权重表里只值第五位，而它连自己的位置都坐不稳——第一步已经拆穿了它不在瓶颈上。

## 简历驱动开发自查三问

权重表摆完，你缓和了一下语气，问了陈舟三个问题。这三个问题你给自己起名叫「简历驱动开发（CV-DD）自查」，因为你确信两年前那次的自己答不上来：

1. **这个技术解决的问题，我们真的有吗？**（性能瓶颈在数据库，不在运行时）
2. **如果明天要放弃它，退路是什么？**（重写过的核心模块，退路是 git 历史里那个旧版本——前提是这三个月业务没往前跑）
3. **如果这是别人的提议而不是你发现的，你会花两周推动它吗？**

第三个问题最诛心。陈舟沉默了一会儿，笑了：「可能不会。」

要说清楚：想用新技术的欲望本身不是罪。工程师的技术热情是团队最值钱的资产之一，掐灭它是最差的管理。CV-DD 自查的目的不是判罪，是把动机摆上桌面——为了解决业务问题，还是为了简历上的那一行？动机不同，后面的路径完全不同：前者走评估，后者走试点（这篇结尾会回来）。

## POC：做最难的路，不做最爽的路

选型流程里有个环节要单独讲：POC（概念验证）。多数 POC 死于同一个错误——**做给所有人看，不是做给自己看信息**。

常见的 POC 长这样：新框架搭个服务，实现一个最顺手的接口，压测跑个漂亮数字，汇报，通过。它验证不了任何风险，因为最顺手的接口本来就是最简单的路径。

有信息量的 POC 反着来：**专挑这个技术未来要面对的最难的路径做。**假如真要用 Rust 重写工单核心，最难的路径是什么？你和陈舟列出来：和现有 MySQL 的 schema 映射、那 300 多处工单-客户关联代码里最纠缠的三处、灰度期新旧服务双写一致性。POC 就做这三样，两周，并且**先写下放弃标准**：如果双写一致性方案超过 X 行胶水代码，或团队学习曲线超出预估一倍，POC 判负。

先定放弃标准再动手，这一步顺序不能反。事后再定标准，人会自动把标准定在结果之下——你会找到一万种理由解释意外，这是天性。

## 迁移成本计入总分

最后一记重锤，是陈舟自己砸下去的。

他认真估了重写的迁移成本：核心模块 4.7 万行，三人月起步；灰度双写期两个月，期间所有新功能冻结（业务方不会同意）；[第 1 篇](/posts/architect-path/01-what-architects-do)提过的那 300 多处工单-客户数据关联，每处都要人工确认。他把这些数字写进评估表的那天下午，自己得出了结论：

「性能收益 3%，成本三人月起。这买卖不划算。」

这句话由他说出来，和由你说出来，效果差十倍。选型流程的产出从来不只是结论，更是**结论的共识**——走过同样推理路径的人，才会真正执行和维护这个决定。

## 给热情一个出口

重写否了，但故事的结尾不是泼冷水。评估收尾时你提了个方案：下一个季度要起的报表导出服务——新的、独立的、没有历史包袱——允许陈舟用 Rust 写。条件照旧：POC 定放弃标准、三个月内可整体放弃、他自己当 owner。

这个安排不是安慰奖。新服务是试新技术的合法位置：失败半径小、不拖累核心、能真实产出「这个技术在我们团队手里是什么体验」的数据。三个月后报表服务跑得不错，慢是慢点，但内存占用只有 Node 版的三分之一；更重要的是，陈舟对 Rust 的评价从「三倍性能」变成了「编译慢但类型系统确实救过我两次」——热情没灭，但从信仰变成了手艺。

二手验证的方法也在这三个月里补上了：选型前看看**谁在生产环境用它、跑了多久、出过什么事故、出事时社区响应多快**。这些信息在 GitHub issues 和技术博客的故障复盘里都有，比评测文章可信一个量级——评测是 honeymoon，事故复盘才是婚后生活。

## 收尾

这套选型流程适合「引入会长期停留的技术」：语言、框架、数据库、基础设施。轻量的库级选择不用这么隆重，试错成本本来就低。判断标准还是那条：单向门走流程，双向门快进快出。

评估结束那天，陈舟主动把整个推理过程整理成了一份文档，模板是他自己找的。那份文档后来成了团队的标配——两百来个字，五个小节，专门记录「当时为什么这么选」。它就是下一篇的主角：ADR。
