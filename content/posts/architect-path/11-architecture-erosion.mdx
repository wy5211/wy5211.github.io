TickHelp 合并项目收官后的第一次 code review，你看见了那张熟悉的 diff。

新需求「工单满意度回访」，逻辑不复杂：工单关闭 24 小时后给客户发回访问卷。但实现方式是开发者直接在回访服务里查了工单表——绕过了租户过滤中间件（它只挂在 API 层），绕过了通知服务（自己 new 了一个邮件客户端），SQL 手写拼接。

你在评论区写：「为什么不走通知服务？」回复很快：「需求急，先这样，下个版本重构。」语气诚恳，你相信他是认真的。

这是这条边界被绕过的第四次。前三次分别是：一个内部脚本、一次数据修复、一个「临时」的导出功能——每个都诚挚，每个都活着。你盯着屏幕意识到：**不是人的问题。是架构在自然腐烂，而且速度比你以为的快。**

## 腐化的机制：近路如何成为路

架构腐化没有戏剧性的一刻，没有哪次会议决定「我们放弃模块化吧」。它的机制平淡到不起眼：

需求急 → 有人抄近路（理性选择，交付压力下近路甚至是对的）→ 近路代码上线，没人死 → 下一个人面对同样的压力，看到近路已经存在，抄起来更没有心理负担 → 近路逐渐成为路 → 一年后新人对着两套并存的路径问「我们到底该走哪套」，没有人答得上来。

注意第二步：**抄近路的每个人都是理性的。**说「要加强工程师的架构意识」是没用的，就像说「司机要礼让行人」解决不了路口设计问题。腐化不是道德事故，是激励事故：deadline 是硬的，架构是软的，压力之下软的总给硬的让路。

所以守护架构不能靠人的自觉，要靠**让近路变得难走**——走正路比抄近路更省事的时候，没人抄近路。这需要设防，你设了三道。

## 第一道：review 里的一个固定问题

人的防线，但不是靠说教，靠一个固定动作。

你给团队的 review 惯例里加了一条：「涉及跨模块访问的 PR，作者在描述里回答一句——为什么走（或不走）现有边界。」作者自己答，不是 reviewer 来抓。

这条规矩看着轻，机制很实：写 PR 描述时，人从「完成者」切换到「解释者」——「因为急所以直接查表」这句话写到描述里，自己看着都会心虚，多数人在写下来的那一刻就回去改了。真写出来的，reviewer 看到理由可以判断：放行（记入技术债清单）还是打回。

## 第二道：把边界变成机器执法

真正让近路难走的是这道防线：**边界检查工具化。**

权限改造时立的边界，多数可以用工具固化。你做了两件事，成本合计一天：

**一条自定义 lint 规则**：通知模块外不允许直接 import 邮件客户端——通知服务的边界直接编译不过。那位写回访功能的同事第二次提交时改走了通知服务，因为绕路的成本（跟 lint 斗争）高于正路（一个函数调用）。

**一个依赖方向检查脚本**，跑在 CI 里：模块依赖图上不许出现环，回访服务不许 import 工单模块的内部实现（只能走导出的接口类型）。用 madge 这类现成工具半小时就能搭起来。

这类东西有个正式名字，叫**架构适应度函数**（architectural fitness function）——把「边界不许被绕过」写成一条自动化检查，像测试一样在 CI 里跑。原则是：**能用机器守的规则，绝不浪费人的注意力。**人守规则会累、会松、会看关系，机器不会。

你补的第三样东西是那个最老的坑：工单状态的双写。依赖检查管不了运行时，你加了个每小时跑一次的对账任务，两边状态不一致超过五分钟就告警——[第 3 篇](/posts/architect-path/03-reading-a-system)考古发现的那个雷，三年后终于有了哨兵。

## 第三道：定期还债的固定节奏

前两道防新债，这一道还旧债。

[第 9 篇](/posts/architect-path/09-driving-change)推权限改造时你要来的那个制度——每迭代 20% 技术时间——在这里发挥了第二个作用：它是还债的固定现金流。腐化不可逆转（有历史包袱的系统不存在零债状态），能管理的只有**速度**：债的利率（每月拖慢交付多少）低于 20% 时间产生的偿还能力，系统就是可持续的。

你给团队立了个轻仪式，每季度半天，叫「还债日」：从技术债清单里挑利率最高的还。所谓利率最高，就是改起来最疼的那几个——开发者用脚投票的地方。「满意度回访绕过通知服务」那次，下个季度的还债日就被重构掉了，连同前三次的绕行一起。

仪式的意义不在半天本身，在于它让「还债」在团队的日历上有一个合法的位置——不用每次都临时论证「为什么花时间修这个」。论证成本归零，事情就会发生。

## 规则要少

三道防线听起来可以无限加：每条边界一条 lint、每个模块一份依赖白名单、每周一次架构巡检……停。

**三条规则会被执行，三十条规则会被无视。**工具守卫的规则越多，误报越多，开发者对红叉越麻木，最后连真正要命的那条红叉也被顺手 ignore 了。你的全部防线最后收敛成四条：lint 那一条、依赖检查那个脚本、对账那个告警、还债日那个仪式。够了。多守任何一条，都是在稀释前四条的严肃性。

判断哪条值得守的方法回到老问题：这条边界被踩穿，两年后改起来贵吗？贵，进防线；不贵，让它去——**腐化管理的目标不是纯洁，是可持续。**一支把全部精力用来防守的团队，和一支完全不管边界的团队，死得一样快。

## 收尾

把这套防线讲给老周听的时候，他问了个商人问的问题：「这些防的东西，值多少钱？」

你愣住了。你可以说它值「代码质量」，值「长期可维护性」，但这些词在预算会上没有汇率。老周见你卡住，补了一句：「下个月年度预算会，你有一个名额，讲十五分钟。把你要守的东西，换算成我能听懂的数。」

那个换算过程，成了整个系列里你被逼出来的最硬的一课。下一篇：和业务对话，把技术翻译成钱和时间。
