考古结束的那个周五，你觉得脚下的地终于实了。同一个下午，销售林姐敲开你的工位，把一份合同拍在你桌上。

皓齿医疗三年续约，门店从 40 家扩到 120 家，合同额翻了三倍。然后她翻到附件第三页：「他们 IT 部门要的，你看看。」

一页纸，四条技术要求：

1. 系统可用性 99.9%
2. 客户数据物理隔离
3. 工单列表查询响应不超过 3 秒
4. 审计日志保留三年

林姐说：「客户问能不能做到，我说没问题，我们工程师很厉害。周一给他们答复。」

你笑着送走她，回头逐条翻译这四行字，笑容慢慢没了。这四条在架构上互相打架，而老周给这个合同的工程预算是半个人年。

## 先翻译：每行字背后是一笔账

架构师看需求的方式，和看菜单不一样。菜单上的每道菜是独立的，需求清单里的每一条都在消耗同一份预算——系统的复杂度和团队的时间。逐条翻译：

**99.9% 可用**：一年停机不超过 8.8 小时。TeaDesk 现在是单实例部署，月均停机 2 小时，折算可用性 99.7%。要做到 99.9%，需要多实例、负载均衡、故障转移——这是一整套部署架构的改造。

**物理隔离**：皓齿的数据要存在单独的数据库实例里，和别的客户分开。现在 8000 家客户共用一套库。物理隔离意味着每接一个大客户就多一套库、多一份运维、多一笔成本——成本随大客户数量线性增长。

**查询 3 秒**：听起来宽松？现在工单列表 P99 是 1.2 秒，但那是 40 家门店的数据量。120 家门店意味着数据翻三倍，而列表查询走的那条链路，你在考古时刚看过——它还挂着那个五分钟同步的缓存脚本。3 秒不是躺着就能保住的，是个要主动防守的指标。

**日志三年**：存储问题好办，难的是「审计级」——什么样级别的操作要记、记了怎么防止被改、出了纠纷怎么取证明。这是一套合规工程。

翻译完你会发现：四条要求指向四个不同的方向，每个方向都要花钱，预算只有半个人年。**全都要，等于全都做不到。**

这时候需要的第一个认知升级是：这四条根本不是同类需求。

## 功能决定能不能用，质量属性决定能不能活

软件工程里把它们分成两类：功能需求（functional）和质量属性（non-functional requirements，业内叫 NFR）。

「客户可以在工作台回复工单」——功能需求，它决定系统**能不能用**。「回复要在 3 秒内显示」「系统全年不停机」「数据要隔离」——质量属性，它们决定系统**能不能活**。

区别残酷在哪：功能没做到，客户立刻发现，立刻投诉，所以没人敢漏；质量属性没做到，上线那天什么问题都没有，它是在系统长大的过程中慢慢显形的——数据涨了、用户多了、客户变大了，当初省掉的那条才浮出水面咬人。而且到那时候再补，通常已经晚了：物理隔离这种事，在共库架构上补，等于动一次大手术。

所以架构师的重要工作之一，是在没人喊疼的时候，替质量属性说话。

常见的质量属性就六类，翻译成人话：

| 属性   | 人话版       | 它的对头                 |
| ------ | ------------ | ------------------------ |
| 性能   | 多快         | 灵活性（快的东西常死板） |
| 可用性 | 多稳         | 成本（每个 9 都很贵）    |
| 可扩展 | 量涨了怎么办 | 简单性                   |
| 可维护 | 改起来多贵   | 上线速度                 |
| 安全   | 谁进不来     | 便利性                   |
| 成本   | 每月烧多少钱 | 以上全部                 |

注意右列：质量属性之间天然冲突。99.9% 和成本冲突，物理隔离和成本冲突，查询性能和数据量增长冲突。**「全都要」在物理上不成立，不是态度问题。**

## 把形容词翻译成可验证的句子

排优先级之前还有一步脏活：需求里的形容词必须变成可验证的句子，否则排了也没法执行。

「查询响应不超过 3 秒」——哪个接口？工单列表还是全部页面？平均 3 秒还是最慢也 3 秒？弱网算不算？你和林姐、皓齿的 IT 负责人对了两轮，落成一句可验证的话：

> 工作台工单列表接口，120 家门店满载运行时，P99 响应时间不超过 2.5 秒（预留 0.5 秒网络余量）。

P99 的意思是一百次请求里九十九次快于这个值，剩下一次可以慢——为什么不要求 100%，因为最慢的那次永远有意外（垃圾回收、网络抖动），为它买单性价比极低。这个概念[后端问题地图第 14 篇](/posts/backend-problem-map/14-observability)有展开。

同样的翻译做了四条。「物理隔离」翻译成「皓齿的数据库文件与其他客户物理分开，部署在独立实例」；「审计日志」翻译成「客服对工单的每次查看和修改均记录操作人、时间、原值新值，记录不可篡改，保留 36 个月」。

这一步琐碎，但它是后面所有取舍的地面。含糊的需求没法排优先级——你没法比较「比较快」和「比较稳」哪个重要。

## 一页需求里，真正塑造架构的只有三条

翻译完的下一个发现：四条要求对架构的影响力天差地别。

判断方法就一个问题：**这条做错了，两年后回头改，贵不贵？**

- 物理隔离——贵。它在共库的地基上补，要动数据层，迁移窗口、双写、对账全套上。它**塑造数据架构**。
- 99.9%——贵。部署形态（单实例还是多实例）定了，监控、发布流程、数据主从都跟着定。它**塑造部署架构**。
- 查询 2.5 秒——中等。索引、缓存策略要现在设计，但方向错了可以用加硬件顶一阵。它**塑造读写路径**。
- 审计日志——不贵。它是存储策略和流程，对整体架构几乎无塑形力。做到「合规」就行。

前三条有个正式名字，叫**架构驱动因素**（Architecturally Significant Requirements）。一页需求里通常就两三条，识别它们是架构师读需求的核心手艺：抓住这三条，架构的方向就定了；漏掉它们，细节做得再漂亮也是精致地跑偏。

## 排不下去的优先级，升级给能拍板的人

三条驱动因素，预算半个人年，做不完。你的第一反应是自己排个优先级：可用性第一、性能第二、隔离……

写了一半你停住了。物理隔离降到逻辑隔离（共用数据库但严格分租户加密），成本能降到四分之一——但这不是技术判断，这是**商务承诺**。皓齿的 IT 在合同里写了物理隔离，你单方面降级，等于替公司毁约。

架构师在这里的角色不是拍板，是把冲突翻译成成本，端给能拍板的人。你做了那张表：

| 方案             | 年增成本              | 风险                               | 客户感知                 |
| ---------------- | --------------------- | ---------------------------------- | ------------------------ |
| 物理隔离（全量） | 约 11 万 + 0.5 人运维 | 成本随大客户数线性涨               | 最强，销售话术最好听     |
| 逻辑隔离 + 审计  | 约 2.6 万             | 需向客户证明隔离强度；渗透测试要过 | 给到报告即可满足多数客户 |
| 维持现状         | 0                     | 大客户流失风险；出事故是公共事故   | 皓齿大概率拒签           |

表递给老周和林姐。他们和皓齿 IT 谈了一个下午，结果：99.9% 和 2.5 秒写进合同（这两条砸多少钱都要做到），物理隔离降级为逻辑隔离，代价是你们出一份第三方渗透测试报告和一年的免费审计日志。

你从这场谈判里学到这一篇最重要的一课：**优先级从来不是架构师一个人排的。**你负责把每条要求的价格标签算准、挂好，让老周和林姐在知情的状态下选。他们选完，你的战场才开始——把选中的三条做进架构里。

## 收尾：这件事的边界

质量属性分析适合用在「需求明显要挤压系统边界」的时刻：大客户合同、十倍增长预测、合规审计。日常小需求不需要这套流程，每条都做属性分析会把团队拖死——多数小需求就是功能，做完即可。

下一篇，三条驱动因素落地的第一个硬仗来了。皓齿上线三个月后，120 家门店的工单量把搜索接口拖到 8 秒——你面前摆着三个方案：给 Postgres 建全文索引、上 Elasticsearch、搞人工分类目录。团队各执一词。怎么把一场「信仰之争」变成一次能算账的取舍，是架构师真正的核心手艺。
