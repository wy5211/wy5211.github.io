ADR 跑了半年，TeaDesk 积了十一条决策记录，你以为最难的习惯已经养成。然后老周把一件事提上日程：多租户权限改造。

起因是那份合同。[第 4 篇](/posts/architect-path/04-quality-attributes)里物理隔离降级成了逻辑隔离，承诺给皓齿的是「严格分租户 + 加密 + 审计」。审计日志做了，加密做了，但「严格分租户」这个承诺，在代码层面是漏的：权限校验散落在各个接口里，有的查了租户归属，有的没查，全靠当年写代码的人的记性。安全渗透测试的下个季度就要来，老周的原话：「这次不能再靠记性。」

你评估了一下这个改造：动工单、客户、报表三个模块，跨你和陈舟两个小组，改完还要给全部存量接口补测试。ADR 记录单点决策，这件事装不下——它需要一份设计文档，和一场评审。

## 设计文档的骨架：六段式

你在 ADR 模板基础上扩了一版设计文档模板。骨架六段，先总览：

```
1. 背景与问题     为什么做这件事，现在哪里疼
2. 目标           做完之后什么变好，可验证地写
3. 非目标         这次明确不做什么
4. 方案与取舍     主方案 + 落选方案 + 为什么
5. 风险与缓解     最坏情况是什么，怎么兜底
6. 灰度与回滚     怎么分批上，每批怎么退回来
```

看起来平平无奇，对吗？每一段都有它要害的功能，逐个说其中三段——目标、非目标、灰度，是新手最容易写薄的三段。

**目标要可验证。**你的初稿写「统一权限体系」，老周批回来：「怎么算统一？」改成了两条可验证的：「全部涉及客户数据的接口经过租户过滤中间件（以代码扫描规则验证）；渗透测试中横向越权项为零」。目标的用途是结束争论——评审会上吵到收不住时，回到这两句话：这个方案能不能让它们成立？

**非目标是你最省力的武器，这一段单独讲。**

**灰度与回滚不能空着。**空着的理由通常是「还没想好」，但评审会上最贵的共识就是这句没想好——上线那周它会回来，以加班的形式。你写的灰度方案：按模块分三批，工单接口先上（用户量最大、暴露最充分），观察一周无越权告警再上下一批；回滚是配置开关，租户过滤可整体关闭降级运行，五分钟生效。

## 非目标：提前圈出「这次不改什么」

设计文档的所有段落里，非目标（Non-goals）是被低估最深的一段。它的功能是**提前埋葬跑题讨论**。

你的非目标清单有三条：

- 不改权限的数据模型（RBAC 表结构不动，只动执行层）
- 不处理历史遗留的明文客户备注字段（另立项）
- **不重构那个五分钟同步的缓存脚本**（你在[考古](/posts/architect-path/03-reading-a-system)时就立过翻案 Flag 的那个）

圈出来不是因为它们不重要，恰恰因为**重要且有人想顺路干**。评审会上一定会有人说「既然都动这里了，顺便把 X 也治了吧」——非目标就是给这句「顺便」准备的天花板。顺路改造是工程延期第一大来源：每件「顺便」都要重新评估、重新测试、重新灰度，「顺便」的成本从来不是顺便的。

注意非目标不是拒绝。那三条每条后面你都标了去向：缓存脚本的重构立了独立项目，排在下季度。「这次不做」和「永远不做」是两句话，写清楚前者，提议的人就不会觉得被拒绝。

## 写给人读：三件小事

结构对了，还有三件影响阅读体验的小事。

**TL;DR 置顶。**给只需要知道结论的人（老周、客服主管）一段话：「做什么、为什么、多大成本、什么时候上线」。他们没有义务读完七页，但他们的知情和支持是评审通过的必要条件。

**图先于字。**方案部分第一屏是一张现有的权限校验散点图（红叉标出漏查的接口），第二屏是改造后的中间件流程图。多数人对图的吸收速度是文字的十倍，而且图的歧义少——文字里「经过中间件」可以被脑补出四种实现，图上只有一种。

**细节进附录。**中间件的完整类型定义、迁移脚本的伪代码、接口清单一百二十行——全部放附录。正文里只留「见附录 C」。判断标准：这段内容评审会上会有人逐行读吗？不会的，都下去。

## 评审会：把挑战设计成流程

文档写完，评审会怎么开，决定它是体检还是刑场。

你踩过一次坑：第一次评审会，你提前十分钟才把文档发进群里，会上花了四十分钟给大家通读文档，讨论时间只剩二十分钟，最关键的租户过滤层设计没讨论到，会议在「下次再议」中结束——就是[第 5 篇](/posts/architect-path/05-tradeoff-analysis)那种会的翻版。

第二次你改了三条规矩，从此成为团队惯例：

**材料提前 24 小时发**，并且明说「没读文档的，会上先旁听十分钟再发言」。不是惩罚，是保护讨论质量——现场听人复述文档，是所有人时间的双重浪费。

**点名沉默者。**会上最危险的信号不是反对声，是安静。安静的人要么没读材料，要么有想法没开口，后者会在方案上线后用行动反对（写代码绕过你的中间件）。你的做法：直接点名问最相关的人。「陈舟，ORM 那层的租户过滤，你觉得会漏吗？」——那天这一问问出了整场评审最有价值的挑战，下一节讲。

**分歧降级为行动项，不在会上求全。**讨论卡住时，不逼当场达成一致，而是落成一条带责任人和截止时间的行动项：「周五前，陈舟验证 scoped session 方案对子查询的覆盖，结论补充进文档。」散会时方案是否完美不重要，重要的是每个人知道下一步是什么。

## 被挑战和被攻击的区别

那场评审里你收获了一次教科书级的挑战。陈舟盯着中间件流程图看了两分钟，问：「租户过滤加在 ORM 全局作用域上，那些绕过 ORM 直接写 SQL 的地方怎么办？」

会议室安静了几秒。你心里咯噔一下——因为确实有，报表模块有三处裸 SQL，你的扫描规则覆盖不到它们。

注意这一刻的两个走向。走向 A：你把问题理解为对我个人的攻击，开始辩解「那三处是历史遗留，当前不涉及越权……」；走向 B：你把问题理解为对方案的检验，当场在风险段新增一条：「裸 SQL 三处，迁移到参数化查询，第一批上线前完成。」

区别不在陈舟的措辞，在你的接收方式。**评审会的全部设计——提前读材料、点名、图先于字——都是为了把「对人」的张力降下来，把「对方案」的检验提上来。**架构师在评审会上最重要的自我管理，是分清这两者：别人挑的是方案的漏洞，不是你的漏洞；你感谢的方式不是全盘接受，而是把有效挑战吸收进文档、无效挑战记录进附录。

对反对意见的最后一个心法：**记录，而非说服。**有种反对说不服——它来自对风险的不同偏好，不是来自事实分歧。会上说服不了的人，硬压下去会变成执行期的暗礁。你的做法是给风险偏好留出口：灰度方案本身就是给反对者的台阶（「先上一个模块，出问题开关关掉」），实在相持不下的，反对意见原文记进文档附录，署名。一年后回看谁对谁错，比当场争赢有价值得多。

## 收尾

这场评审的产出：方案通过，三处裸 SQL 列入第一批整改，缓存脚本重构确认另立项，附录里躺着一条署名的保留意见（客服团队主管担心灰度期权限切换造成一线混乱，后来证明她对了一半，灰度时间因此从一周延到两周）。

设计文档和评审适合「一个决策牵动多个人多个模块」的改动。小改动别用这个阵仗——三千行的调整写设计文档是官僚，评审会是惰性的温床，一切流程的适用边界都是它的规模上限。

会后你以为最难的一关过了：方案通过、附署齐全、排期敲定。三个月后的一个周一，你打开进度看板，发现改造的第一个里程碑，状态还是「未开始」。通过的方案和发生的变化之间，隔着一整个组织——那是下一篇的事：架构师没有权力，只有影响力。
